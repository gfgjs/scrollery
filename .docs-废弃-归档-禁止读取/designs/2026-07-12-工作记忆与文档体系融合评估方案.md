## 0. TL;DR

**裁决:分清三层职责,偏好只保留一个 skill,并把收口缝做成 worklog 入库结构硬门。**

问题被业界判据重述后,坍缩成两个**正交**的子问题,答案彼此不冲突:

| 正交维 | 问题 | 业界判据 | 我们的答案 |
|---|---|---|---|
| **存储分层** | 三件套 与 docs/* 的**数据**该合还是分? | 认知架构/主流工具一致:易失工作记忆 与 永久知识库 **分两层,中间一道蒸馏缝**("two systems, one seam") | **分**(已是现状:planning/=工作/情景层,docs/*=语义/程序层) |
| **skill 粒度** | 操作这两层的**流程**该几个 skill? | Anthropic 无「单一职责」硬规,判据是 token 局部性 + 触发可辨识度;拆分代价**边际**(仅最少用 skill 描述被截、仍可调用),不否决拆分 | **偏好性裁决=一个 skill**(/planning):收口需**原子执行**、两层高共现、现 skill 约 148 行有余量(§4.3);docs/* 分类词表留 docs/ canon 不复刻 |

**三层职责**(采纳方案的骨架):

- **引用层(事实)**= **`docs/README.md` 是当前 taxonomy/schema 唯一真源**;2026-07-10 治理方案保存决策背景与迁移史;CLAUDE.md 只保留常驻入口指针。skill 按需读取 `docs/README.md`,不复刻分类词表/frontmatter schema(躲开治理方案 P7 转述传播风险)。
- **流程层(procedure)**= 唯一的 `/planning` skill。owns 两条流程:①三件套工作记忆生命周期(建/维护/接续),②**收口蒸馏缝**(把三件套的耐久价值提升进 docs/* 各层)。
- **强制层(enforcement,目标态)**= `check_docs.mjs`(已挂 CI,[ci.yml:170](../../.github/workflows/ci.yml)) + Phase 1 新增 closeout schema 校验。⚠️ 诚实边界:门禁只能阻止**已迁入 `worklogs/`**、却缺失/写坏 `closeout.md` 的任务入库;不能判断某任务何时完成、是否应从 `planning/` 迁出,也不能证明 agent 没漏选耐久候选(§5-#1)。

**载重点**:整个决定的价值不在「分层」本身(我们早已分层),而在**那道缝**——收口时把三件套的耐久价值路由进 docs/* 各层。这一步当前**缺失且无执行器**。目标态用 `closeout.md` 把它从纯 prompt 约定升级成**可静态审计的 worklog 入库契约**:CI 保证工件存在、schema 合法、已声明候选逐项处置;候选选择是否语义完备仍需人/agent 判断(见 §5-#1)。

## 1. 缘起与两系统现状

**缘起**:用户希望把「自研 planning skill」与「docs/* 模式」融合,或拆成多个 skill,并要业界调研 + 不完善之处。

**系统 A:`/planning` skill(易失工作记忆)** —— `.claude/skills/planning/SKILL.md`。为多阶段长任务在 `docs/planning/<日期>-<任务名>/` 建 `task_plan`/`findings`/`progress` 三件套;零 hook 零 token 税、中文名可用;收口 `git mv` 迁 `docs/worklogs/` 留档。承 Manus「文件即磁盘工作记忆」。

**系统 B:`docs/* 模式`(永久知识库)** —— 注意:**它今天并不是一个 skill**,而是「当前入口 + 历史背景 + 门禁」:
- **当前入口/事实真源**:`docs/README.md` 已登记 `refactor_2026/ designs/ reviews/ decisions/ runbooks/ planning/ worklogs/ archive/` 八目录 + 四根活文件(todo/completed/experience/README),并摘要当前维护规则。
- **背景/迁移史**:2026-07-10 治理方案仍保留当时六目录终态,尚未加「背景/迁移史」声明;Phase 2 只改其定位头,不再让它与 README 竞争当前 schema。
- **门禁**:`check_docs.mjs`(断链 + frontmatter + 归档横幅)+ `check_plan_canonical.mjs`,均已挂 CI。
- **摘要指针(待 Phase 2 修正)**:CLAUDE.md「Plan & Design Documents」节当前仍把 README 与治理方案并列为 canonical;目标态改成只指向 `docs/README.md`,治理方案作为历史背景链接。

**关键观察(地面真相,非推理)**:两系统**已经**在实际协作了。[todo.md:24](../todo.md) 记着:UIUX 重构线(S0–S7)**刻意不进 todo.md 立节**,全程活在 `docs/planning/` 三件套里,「待 S5–S7 收官后一次性正式回写」。也就是说——**planning/ 已在充当 todo.md 的减负阀**,正对着用户最初那句痛点「todo.md 太长太杂乱」。这不是巧合,是「易失工作层 vs 永久状态层」自发分化的证据。

## 2. 业界调研(2026-07-12 三路联网,来源随文附)

> 说明:`docs/*` 侧的业界调研(ADR/RFC/PEP/KEP/RFD/IETF + Google/Diátaxis/docs-as-code,20+ 来源)治理方案 §2–§3 已做过一轮。本次三路是去补它未覆盖的三块:Manus 文件记忆哲学、Anthropic 的 skill 粒度官方立场、易失↔永久记忆分层理论。

### 2.1 Manus 文件记忆 + 三件套源流

- **哲学(一手,Manus 博客 *Context Engineering for AI Agents*, 2025-07-18)**:文件系统是「终极上下文——大小无限、天然持久、agent 可直接操作」,当作**结构化外部记忆**而非仅存储。核心规则「压缩必须可还原」:网页正文可丢,只要留 **URL**;文档正文可略,只要留**路径**。这与朴素 summary/compaction 的**有损**截然相反。
- **复诵(recitation)**:为复杂任务建 todo.md 并逐步重写勾选,目的**不是给用户看进度,是操纵注意力**——把全局目标不断写到上下文末尾,利用 transformer 近因偏置对抗「lost-in-the-middle」。典型任务约 50 次工具调用,长到足以目标漂移。
- **保留错误轨迹**:失败的动作/报错/stack trace **不要清理、不要静默重试**。模型看到失败会隐式更新先验、降低重犯概率;「抹掉失败=抹掉证据,没证据就无法自适应」。→ 佐证我们三件套的**错误账**表设计合理,收口前不该删。
- **三件套是插件约定,非 Manus 原文**:`task_plan`(plan/控制态)+ `findings`(知识/结果)+ `progress`(情景日志)的三分,出自 `othmanadi/planning-with-files` 插件。
- **🔑 收口/归档是业界规范的空白**:调研原话——「收口→迁 worklog/archive 目录」这一步**不属于 Manus 原文,也不属于该插件**,只在少数自研变体里出现。**→ 我们的 planning/→worklogs/ + docs/* 蒸馏,本身是对业界规范的补强,不是抄来的**(这条把「收口缝」从补缺升级为「做实我们的独家优势」)。
- **代价(独立分析,Lance Martin 2025-10)**:复诵式**逐步重写** todo 会让约 **1/3 工具调用花在记账**(此数据是 Manus/Martin 的观察,**不是** planning-with-files 插件的实测)。planning-with-files 官方仓库**至今仍描述 PreToolUse/PostToolUse/Stop 等 hook**——逐工具注入正是那条税的来源。**我们零 hook 是主动设计选择**,不依赖「插件某版已砍 hook」这一(未逐版核实的)论断(此处 v1 曾用「因此」做因果拼接,已删)。

来源:manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus;github.com/othmanadi/planning-with-files;rlancemartin.github.io/2025/10/15/manus/。

### 2.2 Anthropic 官方:skill 粒度立场(直接改写了本题)

- **没有「单一职责=一 skill 一职」硬规**。那是第三方博客的说法。官方判据是 **token 局部性 + 触发可辨识度**,且**自家范例刻意把多能力放进一个 skill**:PDF skill = 抽取+填表+合并;BigQuery skill = 财务/销售/产品/营销四域,**一个 skill + 每域一个 `reference/` 文件**(官方称此为正确结构「Pattern 2」)。
- **「相关但有别」的官方解法 = 一个 skill + 渐进披露的 reference 文件**,不是拆多个 skill。SKILL.md 正文 ≤500 行,reference 文件**只准一层深**,>100 行的 reference 要带目录。
- **过度拆分有代价,但非「拖垮全体」**(v1 措辞已修):skill 清单约 **1% 上下文预算**,溢出后是**最少用的 skill 描述被截断、仅留 name(仍可调用)**,不是全体触发崩溃。所以「拆多个」的代价是**边际、可控**的——它压低触发裁决的信号权重,但不构成否决拆分的硬理由。
- **事实/流程是「去重启发式」,不是硬边界**(v1 措辞已修):官方真实区分是「**常驻 vs 按需**」——「CLAUDE.md 某节从**事实**长成**流程**就抽成 skill」。**skill 完全可同时装 reference + workflow**(PDF/BigQuery 即是)。我们让 docs/* 分类词表留 docs/ canon、不复刻进 skill,理由是**不制造第二份 canon(P7 转述风险)**,而非「事实禁止进 skill」。⚠️ **关键推论**:官方明言 **skill 指令不保证被执行**,所以「**必须执行**」的规则不能只靠 skill 散文——要么 hook、要么静态门。这正是 §5-#1 把收口硬门落到 **CI 工件校验**、而非 SKILL.md 文字的根据。
- **跨 skill 的「A 交接 B」不是官方原语**。组合要么 Claude 自己同时选中多个,要么走 subagent-fork 桥;「一个 SKILL.md 指向另一个 skill 的文件」**不是被支持的模式**。→ 若把 planning 与 docs 拆成两 skill,最关键的**收口→蒸馏交接会失去原语支撑**,变脆弱。
- **合并/拆分决策规则(官方判据合成)**:**合并**——若二者常一起用、单个 description 能无歧义覆盖两职、正文 ≤500 行;**拆分**——若语境互斥/罕见共用(省不共载的 token)、或触发会撞车、或**调用契约不同(自动 vs 手动)**。

### 2.3 易失↔永久记忆分层 + ADR + 蒸馏缝

- **认知架构统一模型(CoALA, arXiv:2309.02427)**:工作记忆(当前决策周期的活上下文)vs 长期记忆,后者再分**情景**(发生了什么)/**语义**(蒸馏出的事实政策)/**程序**(可复用技能)。→ **本文的工程映射**:三件套主要承担工作/情景记忆,docs/* 主要承担语义/程序记忆;这是借用论文 taxonomy 的项目建模,不是论文对本仓目录的实证结论。
- **MemGPT/Letta、Generative Agents(Stanford)**:main context(RAM)vs archival(disk);memory stream(原始日志)→ retrieval → reflection(把原始记忆合成高层洞见)。Generative Agents 的消融表明 reflection 是可信行为的重要贡献项之一——它支持「原始记录需要再综合」的方向,**不直接推出本仓应采用哪种 disposition taxonomy**。
- **ADR(Fowler/Nygard)= 我们 decisions/ 的对照先例**:一决策一文件、单调编号永不复用;**accepted 后正文不可重写,但状态元数据、取代横幅、双向链接允许受控更新**(改判=写新条 supersede 旧条 + 回填旧条状态链接;非严格整文件 append-only,v1 措辞已修);消极状态留档,「保留被取代记录=保留它统治了多久的历史」。→ 这与我们 archive/「正文冻结、仅文首横幅可追加」的归档不变量**逐字同构**;**且 decisions/ 的写纪律(正文冻结)与 todo.md(可变滚动)、三件套(可弃)都不同——这本身就证明 decisions/ 不能塞进易失暂存**。
- **蒸馏缝(refinery)是被反复理论化的核心**:LangMem 分「热路径」与「后台/潜意识」合并;Anthropic 结构化笔记 + subagent「烧几万 token、只回 1–2k 蒸馏摘要」;compaction「保留架构决策/未解 bug,丢冗余工具输出」。**普适规律:原始工作记忆不是耐久知识,需一步 consolidation 把信号提升进长期库,原始日志归档或丢弃——绝不原样当活知识索引**。
- **反面失败模式:知识库墓地化**。知识库失败不是因为空,而是因为**塞满陈旧料**;约 18 个月内平台沦为「装满过时信息的墓地」。→ 若把逐任务原始日志当一等 KB 条目,库会腐烂。所以要蒸馏而非倾倒。
- **多个典型工具采用类似分层**:Cursor(`.cursor/rules` 持久 vs `scratchpad.md` 含 Lessons 段的易失);**OpenAI Codex(最贴我们):`AGENTS.md` 常驻耐久 vs `PLANS.md`/ExecPlan 逐任务活文档,自带 `Decision Log`/`Retrospective`,「应能只凭 ExecPlan 重启」**;Aider `CONVENTIONS.md`(常驻规则);Copilot Spec Kit(spec≠instructions)。Devin 的会话记忆与账号级 Knowledge Base 则提示 promotion gap 风险。它们是类比证据,不是「所有工具无例外」的普遍定律。

## 3. 裁决:三层职责,一个 skill

三路调研合流后指向同一个结构(它既不是「合并」也不是「拆分」,而是把混在一起的三种职责拆清):

```
┌── 引用层(当前事实真源)───────────────────────────────────────┐
│  docs/README.md                                                │
│  = taxonomy / frontmatter schema / 状态语义 / 八目录职责       │
│  治理方案=背景/迁移史;CLAUDE.md=常驻入口指针                   │
│  【schema 只在 README 一份;skill 指向它,不复刻】               │
└───────────────────────────────────────────────────────────────┘
        ▲ 收口时读它,决定东西归哪个目录/怎么写 frontmatter
        │
┌── 流程层(procedure)= 唯一的 /planning skill ────────────────┐
│  ①三件套工作记忆生命周期(建/维护/接续)                       │
│     = 工作/情景记忆层,类比 Codex ExecPlan                     │
│  ②收口蒸馏缝(把耐久价值提升进 docs/* 各层)★载重★            │
└───────────────────────────────────────────────────────────────┘
        │ 出错也有网 ↓
┌── 强制层(enforcement,目标态)= check_docs.mjs + closeout 校验 ┐
│  既有:断链/frontmatter/归档横幅;新增:worklog 入库结构契约      │
│  不判断任务何时收口,不证明候选选择的语义完整性                 │
└───────────────────────────────────────────────────────────────┘
```

**为什么是这个形状**:Codex 是最贴我们的先例——它的 `AGENTS.md`(常驻耐久规则)+ ExecPlan(逐任务活文档,自带 Decision Log/Retrospective)可类比我们的 **CLAUDE.md 入口 + docs/README canon + 三件套工作记忆**。这个类比支持「常驻规则与逐任务活文档分层」;至于收口流程是否与 planning 放进同一 skill,是 §4.3 基于本项目高共现与原子性的**偏好性裁决**,不是类比推出的唯一答案。

## 4. 备选对比与裁决

### 4.1 备选 A:把 docs/* 整体合并进一个大 skill

**驳回**。Anthropic 允许 skill 同时承载 reference + workflow,所以「reference 不能进 skill」不是理由。本项目不把 docs/* 整体复制进去,理由是:①分类词表/frontmatter schema 已由 `docs/README.md` 持有,复刻会制造第二份 canon并触发 P7 转述漂移;②大段 reference 会增加按需加载成本,但 skill 实际只需要在收口时读取当前 README;③保持文档 schema 与操作流程解耦,未来 taxonomy 改动无需同步重写两份正文。采纳方案仅把**如何操作两层**的流程放进 skill,事实真源仍用链接读取。

### 4.2 备选 B:拆成两个 skill(/planning + /docs)

**暂不采纳,但保留可推翻性**。拆成两个 skill 的 listing 代价只是边际的:预算溢出时较少使用的 description 会退化为 name,并非拖垮全体。当前不拆的项目理由是:①planning 收口与 docs 路由高共现;②Claude 可同时选择多个 skill,但不存在保证 A 完成后必调用 B 的确定性交接,把原子收口拆开会增加漏步面;③当前 planning skill 体量足够小,不存在必须拆分的上下文压力。若未来出现与 planning 无关的高频 docs 操作,或两个流程触发语境明显分离,再独立 `/docs` skill。

### 4.3 采纳:第三选项(§3)——偏好性裁决,非「唯一解」

保留一个 `/planning` skill,docs/* 维持「引用 canon + 门禁」,把两者之间的收口缝做成 **worklog 入库结构硬门**(§5-#1)。

**这不是 Anthropic 判据「推出」的唯一解**(复审纠正:官方判据只是弱偏好,拆分代价边际、可控)。它是**基于本项目实况的偏好性工程裁决**,依据三条:

1. **收口需原子执行**:蒸馏缝是 planning 与 docs 的唯一强耦合点;跨 skill 没有「A 结束后保证调用 B」的确定性交接——放进同一个 skill 让它是**内部一步**,减少漏步面。
2. **两层高共现**:长任务几乎必然收口回写,二者常一起用(Anthropic「常一起用→倾向合并」)。
3. **skill 现约 148 行**,离 500 行上限尚远,纳入收口流程不触天花板。

**此裁决可推翻不冻结**(项目「契约不冻结」原则):若将来 docs 归档流程独立膨胀、或出现与 planning 无关的高频文档操作,再拆 skill 不迟。

**#1 详解(载重项):`closeout.md` = worklog 入库结构硬门**

问题的根:**没有任何 CI 能验证 SKILL.md 的散文指令被执行**,也无法仅凭自然语言判断「所有值得提升的发现是否都被 agent 识别」。因此 v1.2 把保证范围拆成两层:

- **语义层(人/agent 负责)**:判断哪些 findings/decisions 具有耐久价值,把它们登记为候选。
- **结构层(CI 负责)**:任务一旦迁入 `worklogs/`,保证每个**已声明候选**恰好处置一次、目标文件存在、工件无 pending。CI 不判断任务何时完成,也不证明候选选择本身完整。

### 候选来源与稳定 ID

- `findings.md` 模板新增「耐久提升候选」表,ID 为 `F-001`、`F-002`……。
- `task_plan.md` 的关键决策表增加候选 ID,需提升的决策用 `D-001`、`D-002`……;仅会话内决策可不编号。
- ID 在任务内唯一且一经分配不复用。validator 只能保证**已声明 ID**全覆盖,不能替代人对「是否该声明」的判断。
- 🆕 **声明源仅限两张表**:`findings.md`「耐久提升候选」表与 `task_plan.md` 关键决策表的 ID 列;三件套其余位置出现的 `F-*`/`D-*` 字样(如 progress.md 叙事「已处置 F-001」)一律视为**引用**,validator 不得计入声明集——否则叙事提及即凭空造出待处置候选。

### closeout schema

收口时生成 `docs/worklogs/<日期>-<任务名>/closeout.md`;它不在三件套豁免名单(`WORKLOG_ARTIFACTS`)内,须带合法 frontmatter,并包含:

| 候选 ID | disposition | target | locator | 去重证据 | N/A 理由 | verified |
|---|---|---|---|---|---|---|

- `disposition` 使用纯语义枚举:`experience | decision | design | runbook | completed | todo | code | test | no-promotion`。不再混用文件名、目录名与行为名。🆕 **`todo` = defer 去向**:候选具耐久价值但本任务不落地,登记 `docs/todo.md` 对应节改日做——这是本仓最高频的处置模式(defer 池/⏸ 项遍布全库),v1.2 枚举无法表达(`no-promotion` 声明「无需提升」语义不符,其余枚举要求提升物已存在);`todo` 行 target 固定 `repo:docs/todo.md`。
- 非 `no-promotion` 行的 `target` 必填,grammar 固定为 `repo:<仓根相对文件路径>`;validator 去掉 `repo:` 后检查文件存在——🆕 **验存仅限 docs 侧 disposition**(experience/decision/design/runbook/completed/todo)。`code`/`test` 行改用**冻结引用** `repo:<路径>@<引入 commit 短hash>`,validator 只验 grammar、**不验文件存在**:[check_docs.mjs:80-83](../../tools/check_docs.mjs) 当年刻意把代码路径排除出断链门(「代码改名即红」),若对历史 closeout 永续验存代码 target,未来每次源码改名都会红别人的归档件、维护税随归档数单调增长;冻结引用保住可追溯性(当时路径 + 当时 commit)而不产生活链税。**不接受行号**(会漂移)。
- `locator` 可选,用于写 Markdown heading 文本或代码 symbol;它是人类定位提示,本阶段不宣称 CI 能稳定验证各渲染器的 heading slug 或代码 symbol。
- `no-promotion` 行的 `target` 必须为 `—`,且「N/A 理由」必填;其他 disposition 的 N/A 理由必须为 `—`。
- `去重证据` 必填:`new` 表示新落点;复用已有知识时填 `repo:<路径>`。🆕 `no-promotion` 行填 `—`(与其 target 同规)。
- `verified` 只接受 `yes`;不设 `pending` 终态。

### 静态校验与冻结边界

`check_docs.mjs` 新增纯静态校验:

1. 任一含三件套的 `worklogs/*/` 目录必须有 `closeout.md`。
2. 从归档三件套读取所有 `F-*`/`D-*` 候选 ID;closeout 必须逐个覆盖且不得重复、不得出现未知 ID。
3. 校验 disposition、target grammar、目标文件存在、N/A/去重/verified 规则。
4. 正负 fixture 覆盖缺表、漏 ID、重复 ID、未知 ID、非法 enum、无理由 no-promotion、目标不存在,🆕 另补:叙事引用不入声明集、零候选空表(旧格式三件套归档,closeout 仅含表头,合法通过)、code/test 冻结引用 grammar。

🆕 **落地窗口(第三轮复审实证)**:`docs/worklogs/` 当前仅有 README(「已归档任务:暂无」)——本门**零追溯负担**,无需 grandfathering 条款;最佳落地时机是首个任务归档之前。

冻结纪律同步写入 `docs/worklogs/README.md`:

- 三件套是过程快照,收口后正文冻结。
- closeout 的「候选 ID/内容/disposition/理由」冻结;若目标文件迁移,只允许在同一移动 commit 更新 `target`/`locator`,不改变语义裁决。🆕 此活链义务**仅及 docs 侧 target**——docs 目标消失即门禁红,机械强迫同 commit 修链(自执行);`code`/`test` 冻结引用永不回改。
- 这是一道**worklog 入库结构门**,不是「所有完成任务必然收口」或「语义蒸馏绝不遗漏」的证明。

该方案不增加运行时 hook,不逐工具注入,仍保持零逐工具 token 税。
