## 1. 需求与范围

三条用户需求:

1. 文件树可选显示**所有格式**,并可选是否含**隐藏文件**;或只显示已注册格式。
2. 顶栏媒体大类筛选在图片/视频/LIVE/收藏基础上,**常显文档、音频**。
3. PNG/TXT/EPUB/PSD/RAW 等**细分格式**收进低频折叠区并可筛。

不在范围:三序统一(见 §9 遗留)、搜索谓词 localtime 修正(F-007,独立)、counts 显示(D-005 已裁不做)。

## 2. 术语(定形,全文与代码注释统一用词)

| 术语 | 定义 | 反例 |
|---|---|---|
| **已注册格式** | Host 能分类并允许入库的格式 = 内置 common 表 ∪ exotic Catalog。Catalog 已登记但插件未安装/未授权的 PSD **仍算已注册** | 不叫「支持格式」——会被误解为「一定能预览」 |
| **当前可用**(availability) | 能否在本机预览/派生。**独立维度**,不作为文件树显示范围判据,只作 badge | 不得与「已注册」揉成一个概念 |
| **所有文件** | 扫描根内所有普通文件,含无扩展名与未知扩展名。**不因此进入**媒体库/画廊/搜索/批量操作 | 不是「把未知文件入库」 |
| **树节点身份** | `nodeKey`/`parentKey`,路径派生,跨 DB/FS 模式稳定 | 不是 DB id |
| **实体身份** | `directoryId`/`mediaId`,仅当确有 DB 行时存在 | 禁止用路径 hash 伪造 |

## 3. 文件树三态(D-009)

区块标题右侧「显示内容」菜单,三种互斥状态,按本机持久化:

1. `已注册格式`(默认,走现有 DB 快路径,零回归)
2. `所有文件`(不含隐藏项)
3. `所有文件 + 隐藏项`

**为什么没有第四态**「已注册格式 + 隐藏项」:`fast_scan.rs:469` 的 `ensure_dir_chain` 只由已分类文件触发,`walker.rs:106` 又整棵剪掉隐藏目录 → **只含未知/隐藏文件的目录连目录行都不存在**。第四态在当前扫描契约下无法兑现,不是没做而是做不出。

隐藏项口径:

- Windows:点前缀 **或** `FILE_ATTRIBUTE_HIDDEN`
- macOS/iOS:点前缀 + 平台适配层可用的 hidden flag
- Linux/Android:点前缀
- 涵盖文件与目录;symlink 不跟随,越出扫描根的目标不可展开/打开

## 4. 数据架构:双数据源(D-010、D-013)

`已注册格式` 走现有 DB 目录树/媒体计数/文件分页。两种 `所有文件` 走新的受限 FS 惰性枚举 IPC。

### 4.1 统一节点模型(D-013)

```
TreeEntry {
  nodeKey: String        // 路径身份,必有,跨模式稳定
  parentKey: String?     // 路径身份
  rootId: i64
  relPath: String
  name: String
  kind: Dir | File
  hidden: bool
  registered: bool
  directoryId: i64?      // 仅 DB 确有目录行时
  mediaId: i64?          // 仅 DB 确有媒体行时
  mediaType: MediaType?
}
```

**铁律**:`directoryId`/`mediaId` 禁止伪造(路径 hash、临时序号皆不可)。理由是可复现的:`mediaRoute.ts:43-47` 对非 doc/audio **兜底到 `/view/{id}`** —— 伪造 id 不会报错,会把未知文件静默送进图片查看器。

**FS-only 目录的能力边界**(无 `directoryId` 时一律禁止):

| 禁止 | 依据 |
|---|---|
| 进入 `/folder/:id` | `FoldersSection.vue:594/673` `navigateToFolder(node.id)` |
| 画廊滚动锚点 | `FoldersSection.vue:665` `ui.pendingScrollDirId = node.id` |
| 拖拽源/目标 | `FoldersSection.vue:117-118` `dropId`/`dragId` === `node.id` |
| 移动/复制 IPC | 现有 IPC 签名收 DB id |
| active 高亮 | `FoldersSection.vue:115-116` `activeDirectoryId === node.id` |

允许:展开、键盘导航、刷新、复制路径。DB/FS adapter 必须**显式**区分两种身份,不能靠「碰巧有值」。

### 4.2 受限 FS 枚举 IPC

- 入参收 `rootId + relPath + displayMode + cursor`,外加可选 `kind: dirs|files` 过滤(2026-07-16 修复批回填,原文只列前四项):过滤发生在**快照之后**、不进缓存键、纯收窄无安全面;它把 FS 模式对齐 DB 模式的取数形状——「子目录一次给全 + 文件按页给」,前端因此只需一套树模型。
- 文件 IO 走 `spawn_blocking`。
- 展开时才读直接子项,分页 200。
- 超大单目录用有界 LRU 目录快照缓存支撑稳定分页,不让每页重跑 `read_dir + sort`。失效触发点(2026-07-16 修复批 R-05 回填,原清单漏了第 4 条——本应用自己改磁盘是最可预见的失真源):
  1. 切显示模式(`include_hidden` 进缓存键,天然分离);
  2. 显式刷新(`invalidate_tree_cache` IPC);
  3. 扫描完成(`scan_commands` 内接线);
  4. **应用内物理写**:file_ops 的 9 个写命令(move/copy/relocate/remove_hard 经 `InvalidateOnWrite` Drop 守卫,create_physical_folder/move_directory/copy_directory/delete_directory_to_trash/copy_media_items 显式清)与 remove_scan_root(_with_options)/clear_database(R-12)。统一**全清**而非逐根:批量项可跨多根,缓存双维度封顶(≤8 快照),重建 = 下次展开一次 `read_dir + sort`。
- 所有文件模式**不展示**「递归媒体数」角标(那是媒体数不是文件数);可显示已加载直接项数。
- **卷不可用**(移动盘拔出):结构化错误 + 空态,**不回落 DB 模式** —— 回落会让「所有文件」静默变成「已注册格式」,比报错更坏。

### 4.3 排序(D-002)

FS 枚举**沿用现有 DB comparator**:目录 `name ASC`(BINARY)在前,文件 `NOCASE ASC` 在后。

**不变量不是「逐字节相等」**:所有文件模式必然插入 FS-only 项,完整序列不可能与 DB 模式相等。可验证的契约是 **common-subsequence 稳定性**:

> 切模式前后,**共有目录之间**不重排、**共有文件之间**不重排;额外 FS 项按同一 comparator 插入。

对拍分两路(因 `list_directory_files` 只覆盖文件,目录来自 `get_directory_children`):共有目录对拍 DB 目录查询,共有文件对拍 `list_directory_files`。

### 4.4 文件行为(D-001)🔴 安全

| 情形 | 行为 |
|---|---|
| 有 `mediaId` | 现有应用内查看器路由 |
| 无 `mediaId`,Desktop | 单击只选中;双击经**自有 `reveal_tree_entry(rootId, relPath)` IPC** 在文件管理器中显示 |
| 无 `mediaId`,Android/iOS | UI 隐藏/禁用该动作;后端被直调返回稳定 `unsupported_platform` |

**不调用系统默认应用打开。** 威胁不是路径越界,是**根内文件本身可执行** —— 扫描根是照片目录,可能混有 `.exe/.lnk/.bat/.ps1`;`canonicalize` + 根边界会**放行**它们(它们本就在根内)。扩展名黑名单不可靠:`PATHEXT` 可改、`.lnk` 可转指、双扩展名、NTFS ADS。reveal 把最后确认交给系统文件管理器的信任链,功能损失只有一次点击,且日后要放宽随时可以,反向收窄则是行为回归。

**不向 WebView 授 `opener:allow-reveal-item-in-dir`**:该 capability 无预配置 scope,直接授予会绕过本文自己定义的扫描根边界(F-009)。移动端 `revealItemInDir` 官方不支持,**不得**用 `openPath` 降级 —— 那正好把刚挡掉的执行面放回来。

**落地形态比本节原定更紧(2026-07-16 P1-a 施工时核实上游后更正)**:原文写「Rust 侧**注册** `tauri-plugin-opener`,由自有 IPC 校验后内部调用 `OpenerExt`」。实测 `tauri_plugin_opener::reveal_item_in_dir` 是 crate 根导出的**自由函数**(不需 `AppHandle`),故插件**完全不注册**、capability 一条不授,JS 侧根本够不着 —— ACL 面为零,而非「注册了但不授权」。见 `ipc/reveal.rs`。

**有意行为**:隐藏目录内的已注册文件(如隐藏目录里的 PNG)`registered=true` 但**无 `mediaId`**(`walker.rs:106` 整棵剪掉,扫描器从未见过它)→ 走 reveal 而非应用内查看器。这是三态设计的必然推论,不是缺陷。
**2026-07-17 收窄(问题②方案 B v1 落地)**:纯文本白名单(txt/md/markdown)的无 `mediaId` 文件改走**应用内只读预览**(`get_tree_text_preview`,resolve_within_root + 后端白名单 + 1 MiB 截断,`<pre>` 纯文本渲染不解析 markdown)——不违上文 D-001:禁的是「交系统默认应用执行」,不是「本应用内只读查看」。白名单外(含全部可执行面)仍走 reveal,本段其余论证不变。详见 [树内文件行打开与拖拽设计件](../worklogs/2026-07-17-树内文件行打开与拖拽/设计-path预览与文件行拖拽.md)。

## 5. 顶栏一级筛选(D-008)

常显顺序:`图片 | 视频 | 文档 | 音频 | LIVE | 收藏 | 格式…`

- 文档/音频补进 `mediaTypes`。`MediaType`(`format.rs:15-20`)后端与前端本就有四大类,**无需新增 DB 枚举**。
- 实测支撑:文档 4,818 项(主体 txt 4,615)有实际价值;音频 32 项近乎空但无害。
- LIVE/收藏**不是**媒体类型,是与媒体类型相交的布尔 facet;仅 UI 同列,领域模型分离。
- `格式…` 是一级触发器,不把几十个格式 chip 铺在顶栏。
- chip 总数 **10/11**(现为 7/8)。

**描述符化 = 3 处,缺一不可**:

| # | 位置 | 现状 | 改法 |
|---|---|---|---|
| 1 | `AppToolbar.vue:341` | `chipCount = hasActiveFilters ? 8 : 7` | 由描述符数组推导 |
| 2 | `GalleryFilterChips.vue:11-101` | `inDom(0)…folded(7)` 模板字面量索引,映射只存在于 `:6` 注释 | 数组驱动 |
| 3 | `AppToolbar.vue:310-321` | `overflowRemeasureKey` 手工枚举筛选字段 | 由描述符派生 |

**第 3 处是最危险的**:漏加 `fileFormats` 则「格式」→「格式 3」文字变宽**不触发重测** = 顶栏闪展再收同类 bug,而且**无编译/SSR/测试信号**,只在真机抖动。顶栏已踩过一次同类(round7 docked 分支漏配对齐)。

顺手归一 i18n(零成本):`GalleryFilterChips.vue:45` Live chip 是裸字面量(两 locale 均无 key);视频 chip 借 `sidebar.videos`,图片 chip 用 `toolbar.filterImages` → 统一到 `toolbar.*`。

## 6. 格式注册表(D-007)

### 6.1 两层结构

**内部** `RegisteredFormatDef`(单一事实源,收敛五处):

```
ext: &'static str
media_type: MediaType
group: Option<&'static str>
phase1_image: bool
document_subtype: Option<DocumentSubtype>
```

**外部** IPC `FormatDescriptor`(UI 投影,不承载处理能力):

```
ext: String                          // 规范化小写,DB/API 存这个
media_type: MediaType
group: Option<String>
source: Builtin | Exotic { plugin_id }
```

只有 `ext/media_type/group/source` 的扁平 descriptor **派生不出** `is_phase1_image` 和 `doc_subtype` —— 故内部定义必须更丰富,IPC 只做投影。未来 exotic 若需新 `document_subtype` 或 Phase 1 能力,那是**处理能力 schema** 的独立扩展,不偷塞进 UI descriptor。

`group` 是必需的:`format.rs:47-48` 把 `heic/heif/avif` 与十个 RAW 塞在同一 match arm,`media_type` 分不出 RAW。

### 6.2 收敛范围 = 5 处

`classify_media_type`(`format.rs:35-70`)、`is_phase1_image`(`:74`)、`doc_subtype`(`:89`)、exotic `iter_formats()`(`catalog.rs:286`,**本就可枚举**)、前端 `src/constants/formats.ts`(零 importer 死镜像 → 删除或改由 IPC 灌;不处置则 P3 会被顺手 import 变成第三事实源)。

**有意不收 4 处**:`derive/kind.rs:128` `DOC_THUMB_FORMATS`、`thumbnail/cache.rs:416` `AUDIO_COVER_EXTS`、`video/media_foundation.rs:32` `MF_VIDEO_EXTS`、`ai/face_pipeline.rs:611` `WORKER_DECODABLE_FORMATS` —— 它们回答「能不能派生/解码」= availability 维度,与「是不是已注册」正交(§2 已切开)。强收会把两个概念揉死。

### 6.3 动态扩展协议(不写死总数)

当前 66 common + 1 PSD = **67 是数据快照,不是协议常量**。新增普通冷门格式只需在 Catalog 增 offering(`plugin_id/media_kind/formats`),合并 registry / facet / URL·SQL 筛选 / parity 测试**自动覆盖**,不改中央计数或白名单。

**Catalog loader 校验已全部存在,P0 复用不新建**:

| 校验 | 位置 | 测试 |
|---|---|---|
| 不得覆盖 common | `catalog.rs:223-224` `CommonFormatConflict` | `:426` |
| 跨 offering 重复扩展名 | `:245-247` `DuplicateFormat` | `:384` |
| 扩展名合规 `[a-z0-9]{1,16}` | `:217-218` `InvalidFormat`(`is_valid_format` `:323-328`) | `:396` |
| plugin_id / 重复 plugin / override_common / 空 capabilities | `:201-211` | — |

注:`is_valid_format` 是**拒绝**非小写而非转换(`:226` 原样克隆);`norm_formats` 变量名与 `:214` 注释「归一化」是误称。失败响 = `InvalidFormat`,行为本身优于静默转换,**不改**。

**一个 offering 的多个 `formats` ≠ 一个 UI alias group** —— 那只表示同一插件能处理它们。未来需要别名合组,给 Catalog schema 增**显式可选 group 元数据**,禁止从 offering 边界猜测。

### 6.4 parity 测试(不硬编码 67)

1. 枚举全部 builtin 定义,双向对拍 `builtin registry ≡ classify_media_type`。
2. 对当前 Catalog snapshot 每个扩展名验证 common 返回 `None`、Catalog 返回声明大类。(装载期 `CommonFormatConflict` 已结构性保证违反者载不进 snapshot,故本项是 characterization,保留以锁定 common-first 语义。)
3. 动态合并集对拍 common-first combined classifier(`walker.rs:18-19`),集合基数**由实际数据推导**。
4. `is_phase1_image` / `doc_subtype` 从 builtin registry 派生后逐值等价。
5. **新增第二个 exotic fixture**,证明无需改中央白名单或期望总数即可自动进入合并集与 facet。

⚠️ 「67 项合并 registry ≡ `classify_media_type`」**不可成立**:`format.rs:122-127` 明确锁定 `classify_media_type("psd") == None`,PSD 只经 `walker.rs:18-19` 的 common-first 回退被 Catalog 识别。内置表只能对拍 **common** classifier,完整并集必须对拍 **combined** classifier。

## 7. 细分格式弹层(D-003、D-004、D-005、D-012)

### 7.1 呈现

按图片/视频/文档/音频四组展示**库内实际存在**的已注册扩展名,标签统一大写。支持搜索、全选当前组、清除;触发器显示 `格式` 或 `格式 N`,已选项在弹层回显。exotic 格式按注册表出现,availability 只作 badge(不影响能否筛出 PSD)。

首版只启用库内实际存在的格式。当前快照:registry 67 vs 库内 29 → 砍掉 38 个为 0 的选项。Catalog 扩展后自动跟随。扫描完成或 Catalog snapshot 更新后刷新 facet。

### 7.2 facet 取数(D-005)

```sql
SELECT DISTINCT file_format FROM media_items
WHERE is_deleted=0 AND companion_of IS NULL
```

**分组在 registry 侧做**。媒体大类归属是 registry 的知识(`png → Image`),不是 DB 的知识。实测(生产库 543,449 项):

| 查法 | 耗时 | 计划 |
|---|---|---|
| `DISTINCT file_format`(裸) | 0.0 ms | `COVERING INDEX idx_media_format` |
| `DISTINCT file_format` + 基础谓词 | 0.0 ms | `USING INDEX idx_media_format` |
| `DISTINCT (media_type, file_format)` + 基础谓词 | 114.3 ms | 全扫 |
| `GROUP BY (media_type,file_format) + COUNT(*)` | 216.0 ms | `TEMP B-TREE` |

推论:

- **不显示 per-format counts**(唯一用途是预判结果数,点下去就知道;不值 216ms + 缓存 + 失效)。
- **不建缓存层、不做失效逻辑** —— 0ms 不值得。每次开弹层现查。
- **基础谓词是契约不是装饰**:与正常媒体视图(`queries.rs:1291-1295`)一致,阻止只存在于回收站/companion 的格式污染全局 facet。当前生产库 raw distinct == base distinct == 29 **是数据巧合**(实测:被基础谓词滤掉的仅 4 行,全是 `is_deleted=1` 的 jpg,而 jpg 在 base 中也存在),不能用巧合替代契约。
- facet 是**全局口径**(库能筛什么),不随视图收窄。文件夹视图里可能出现选中后 0 结果的格式 —— **有意行为**,与评分/颜色 chip 既有语义一致(评分 chip 在空文件夹里也不消失)。

### 7.3 别名归一(D-003)

`group` 把「一个 UI 概念对应多个物理扩展名」统一成**一套**机制:

- `JPEG` = `{jpg, jpeg}` —— **实测必需**:库内 jpg 515,728 与 jpeg 2,530 **并存**,不归一则 JPEG chip 是个 2,530 项的心智陷阱。
- `TIFF` = `{tif, tiff}`(同在 `format.rs:39` 一行)
- `RAW` = `{cr2, cr3, nef, arw, dng, raf, orf, rw2, pef, srw}`

核心状态存**规范化的具体扩展名**,`group` 只是 UI 概念,**不写进 DB/API**。不入库归一:`file_format` 是文件的客观属性,改写会让 DB 与磁盘失真且不可逆,且 `queries.rs:1817` 等既有格式谓词都要复核。

RAW 列表**必须由后端 descriptor 下发**,不得前端硬编码(那是 `format.rs:47-48` 的复制)。

### 7.4 RAW(D-004)

**首版支持,零数据时不常显**。实测生产库 RAW 与 heic/heif/avif 全部为 0 → 按「只列库内实际存在的格式」本机不显示 RAW。走 §7.3 的 group 机制后,**RAW 是注册数据而非条件代码**:库里出现任一 RAW 扩展名时自动显示 RAW 组,核心状态展开为**当前存在且被选中**的具体扩展名。用 CR2+NEF fixture 锁定该能力。

### 7.5 组合语义(D-011)

- 维度内 **OR**:`PNG + JPEG`
- 维度间 **AND**:`图片 AND (PNG OR JPEG) AND 收藏 AND 评分≥3`
- 选了媒体大类时,弹层只展示兼容组;取消某大类时同步移除该类已选细分格式,杜绝不可见的冲突筛选
- `mediaTypes=[]` / `fileFormats=[]` 各表示该维度不限;清除筛选同时清空二者

## 8. 筛选契约贯通(D-006)
