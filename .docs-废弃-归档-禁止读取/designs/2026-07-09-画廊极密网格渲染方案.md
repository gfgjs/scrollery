## 0. 背景与目标

### 0.1 用户诉求(2026-07-09 原始需求)
1. 顶栏缩略图行高滑块调至 **60px** 且**全屏**时,同屏 + 前后屏缓冲会渲染**数千张缩略图 = 数千 DOM 节点**。
2. 此时**快速滚动**或**进入选择态**出现明显卡顿。
3. 设想:行高小于某阈值时**转 canvas 绘制**,求可行性与取舍分析。
4. 联网调研业界优秀开源 / 闭源项目与同类竞品的处理方案。

### 0.2 一句话目标
在**不牺牲跨平台一致性**(尤其 iOS / WKWebView)与无障碍的前提下,把 60px 全屏下「单屏数千个**重响应式组件**」的渲染 / 交互成本压到 60fps 可承受区间;canvas 作为**按需的、Windows 门控的混合增强**,而非一刀切默认路径。

## 1. 现状取证 = 分析报告(并入存档)

> 本节即用户所需「分析报告」,所有结论均带代码实证锚点。**先纠一个前提**:画廊**已经在虚拟化**([MediaGrid.vue:598](../../src/components/media/MediaGrid.vue#L598) 的 `useVirtualScroll`,只渲染 `visibleRows`),布局几何在 **Rust 后端**算([galleryLayoutSource](../../src/composables/galleryLayoutSource.ts) 的 `fetchRowsByY`)。所以这不是「虚拟化缺失」,而是「虚拟化已到位、但极小行高下单屏密度爆炸」的临界区。

### 1.1 三个根因(定位到行)

| # | 根因 | 证据锚点 | 量级 |
|---|---|---|---|
| **1** | **可见窗口本身巨大**。缓冲 = `clamp(rowHeight × 8, 400, 1200)`px/侧 | [useVirtualScroll.ts:330-334](../../src/composables/useVirtualScroll.ts#L330-L334) + [defaults.ts:20](../../src/constants/defaults.ts#L20) | 4K 全屏 60px ≈ 48 行 × ~48 列 ≈ **2000–3000 格** |
| **2** | **每格是一个「重」组件**。~10 个 computed + 2 watcher + `useHoverPreview` + `onMounted` 解码 | [MediaThumb.vue](../../src/components/media/MediaThumb.vue) 全文 | ×2000–3000 实例 = **快滚时挂载 / 卸载 churn 主源** |
| **3** | **进入选择态 = 全窗口同步重渲染**。全局单例 `isSelectionMode` 一翻转,广播到每格 | [useSelection.ts:41](../../src/composables/useSelection.ts#L41) → [MediaGridRow.vue:88](../../src/components/media/MediaGridRow.vue#L88) → [MediaThumb.vue:95](../../src/components/media/MediaThumb.vue#L95)/[:225](../../src/components/media/MediaThumb.vue#L225) | 每格新增 overlays+checkbox ≈ 3 节点,数千格**在一次 Vue flush 内**建节点 + 布局 + 绘制 + 全文档 style recalc |

### 1.2 单屏格数(真机实测,非估算)
- **v2 报告 §9.5 已实测**(用户 devtools,全屏 + 极小缩略图):**3556 cell × 2.1 节点/cell = 网格 7294 节点**。compact culling 已到地板——每 cell 仅「根 div + img」,故 2.1 节点/cell(比一般卡片精简)。
- 该报告对此节点数的裁定:**合法地板**(每节点 = 一张可见照片),节点层「削不动除非整网格 canvas 化」。**本文承认这一裁定,并指出它只覆盖「静态节点数」维度**(§1.3 三维度拆分)。
- 缓冲 = `clamp(rowHeight×8, 400, 1200)`px/侧([useVirtualScroll.ts:330-334](../../src/composables/useVirtualScroll.ts#L330-L334));60px 下 480px/侧 = 8 行/侧,与 3556 cell 量级自洽。

### 1.3 三个成本维度(v2 报告「削不动」只覆盖第一个)
把「单屏数千格」的成本拆成三个正交维度,才能看清哪些能不靠 canvas 就降:

| 维度 | 是否已到地板 | 能否不靠 canvas 降 | 对应根因 |
|---|---|---|---|
| **A. 静态 DOM 节点数** | ✅ 已到地板(7294,v2 §9.5)| ❌ 削不动(除非整网格 canvas)| 根因 1 |
| **B. 每格 Vue 组件响应式重量** | ❌ 未到地板(~3556 个 MediaThumb,各带 ~10 computed + composable)| ✅ 能(轻量卡片,T1)| 根因 2 |
| **C. 状态变更的响应式级联** | ❌ 未到地板(仅进选择态才爆发)| ✅ 能(容器单类 + 伪元素,T0)| 根因 3 |

- **v2 报告「削不动」= 维度 A**:节点数确是合法地板。但**用户报告的两个症状(快滚 churn / 进入选择态卡顿)主要落在 B / C**,而 B/C 未到地板、且有结构性(非 canvas)解——这是本文相对 v2 的增量。
- **`content-visibility` 为何救不了**:[MediaGrid.vue:378-385](../../src/components/media/MediaGrid.vue#L378-L385) 已在 compact 对每格开 `content-visibility:auto`,但它只跳过**离屏**元素;那 ~3556 格**真真切切在视口里**,浏览器必须全画,故只省缓冲行、省不掉维度 A 主体。而 A 已是地板——所以**主攻方向应是 B/C(T0/T1),而非再抠 A**。
- **canvas(T4)的独特价值**:它是唯一能同时压掉 A+B+C 的手段(节点→1、无逐格组件、选中=Set+重绘),但代价与 iOS 风险最高,故列末档(§9)。

### 1.4 「进入选择态卡顿」的机制细节(根因 3 展开)
- `isSelectionMode` 是**全局单例 `ref`**([useSelection.ts:41](../../src/composables/useSelection.ts#L41)),经 prop 链 MediaGrid → MediaGridRow(`selection-mode`)→ MediaThumb(`is-selection-mode`)下发。
- 它 false→true 时:(a) 每个 MediaGridRow / MediaThumb 因 prop 变化**失效重渲染**;(b) [MediaThumb.vue:95](../../src/components/media/MediaThumb.vue#L95) 的 overlays 容器 `v-if="!compact || isSelected || isSelectionMode"` 与 [:225](../../src/components/media/MediaThumb.vue#L225) 的 checkbox 从「不存在」变「存在」,**每格新建 ~3 节点**;(c) `.media-card--selection-mode`([MediaGridRow.vue:51](../../src/components/media/MediaGridRow.vue#L51))类在数千元素上翻转 → 触发**接近全文档的 style recalc**。
- **结论:这不是绘制(paint)瓶颈,是响应式 + 样式失效爆炸(reactivity / style-recalc blowup)。** 这决定了它有**不依赖 canvas 的结构性解**(§5 T0)。

## 2. 业界调研(联网,2026-07-09)

### 2.1 开源 web 照片管理器:无一用 canvas 画网格
| 项目 | 渲染 | 关键事实 | 源 |
|---|---|---|---|
| **Immich** | DOM(Svelte)+ thumbhash 占位 | 虚拟化到位后,瓶颈转为**同步布局几何计算**:54 个 DOM 节点却冻结 **~18s**(7 万同日资产一次算完才让出主线程);硬限「同日 >1 万资产基本不可用」 | [#28861](https://github.com/immich-app/immich/issues/28861) / [#21284](https://github.com/immich-app/immich/issues/21284) |
| **PhotoPrism** | DOM(Vue)| 多选 / 密集卡顿的解法是**结构性、非 canvas**:裸 `<button>` 替框架组件、`v-if` 而非 `display:none`、`memoize-one` 缓存每卡 getter、overscan ±4 | [infinite-scrolling docs](https://docs.photoprism.app/developer-guide/ui/infinite-scrolling/) |
| **digiKam**(原生 Qt)| **QPainter 立即模式 + 视口裁剪** | 唯一「canvas 类比」实践:只画可见格 + 预生成 wavelet 缩略图(原子入库)→ 密集网格「秒开」 | [Image View](https://docs.digikam.org/en/main_window/image_view.html) |

**要点**:你已把布局几何下沉 Rust,**天然避开 Immich 最致命的瓶颈**;你的瓶颈是纯前端渲染层,比 Immich 单纯。

### 2.2 闭源 / 商业竞品:web 系全用 DOM,原生系瓶颈在缩略图管线
| 产品 | 栈 | 做法 / 证据 | 源 |
|---|---|---|---|
| **Google Photos**(web)| DOM | 拆 `_computeLayout`(罕跑)vs `_doLayout`(滚动跑);分段,单次只 layout 几百格;方向性缓冲 | [teardown](https://medium.com/@danrschlosser/building-the-image-grid-from-google-photos-6a09e193c74a) |
| **Eagle**(与你同栈 Electron/Chromium)| DOM 窗口化 + **只渲缓存缩略图** | 官方称流畅到 **~25 万**资产,10 万+ 实测「丝滑」——**同栈 DOM 能赢的直接证据** | [Eagle KB](https://en.eagle.cool/article/205-does-the-size-of-library-affect-software-performance) |
| **Lightroom / Bridge / Apple Photos** | 原生(GPU/Metal)| 真瓶颈是**缩略图 / 预览缓存管线**,非网格节点数;且原生**仍会卡**(Apple Photos 大库启动数分钟) | [Lightroom GPU](https://helpx.adobe.com/lightroom-classic/kb/gpu-preview-generation.html) |
| **AG Grid 等数据表格** | canvas / 100 万+ 单元 | 「canvas 网格」模式出现在**百万级单元数据表**,不是照片 DAM | [AG Grid](https://www.ag-grid.com/javascript-data-grid/dom-virtualisation/) |

### 2.3 webview 约束(跨端关键)
- **节点数为何卡**:style recalc / layout 随节点数近线性且常跑全文档;5000→1000 节点可把一次交互从 **420ms → 50ms**;Lighthouse 警告 >800、报错 >1400 body 节点。你「数千节点 + 选择态类翻转」正是全文档 recalc 的典型征兆。[Lighthouse DOM size](https://developer.chrome.com/docs/lighthouse/performance/dom-size)
- **`content-visibility: auto` + `contain-intrinsic-size`**:近免费的「虚拟化 lite」,现 **WebView2 与 WKWebView 18 / iOS 18、Firefox 125 均支持**;**必须**配 `contain-intrinsic-size`,否则离屏项塌 0 高、滚动条乱跳。[web.dev](https://web.dev/articles/content-visibility)
- **图层提升需克制**:`will-change`/`translateZ` 过度提升 → layer explosion,GPU VRAM 膨胀,「越用越卡」。仅对正在动画的元素提升。[Smashing](https://www.smashingmagazine.com/2016/12/gpu-animation-doing-it-right/)
- **canvas 在 WKWebView/iOS 可能反向劣化**⚠️:iOS 单页 GPU 内存 ~1.4–1.5GB 上限,WKWebView 更早触顶;iOS 15「GPU Process: Canvas Rendering」曾把 WebGL **60→30fps**;大 canvas backing-store 加速内存触顶崩溃。故**切 canvas 可能帮 Windows、拖垮 iOS**。[cordova-ios#1246](https://github.com/apache/cordova-ios/issues/1246) / [WKWebView 内存](https://developer.apple.com/forums/thread/133449)

## 3. 判据扩展(承接 v2 复核报告 §9.2)

v2 报告 §9.2 立的判据是「总览类可视化(滚动条/缩略轴/热力条/minimap)用 canvas/降采样;列表类可视化(树/网格/长列表)用虚拟滚动」。本专项给它补一条**极密退化规则**:

> **当网格密到「单屏上千格」,这一屏本身就退化成一块「同时可见但画不下」的总览面**——scrubber 的 canvas / 降采样教训在网格上**重新适用**。但退化临界不在「行高」单一维度,而在 **「单屏活动节点数 × 每节点响应式重量」**;所以先降「每节点重量」(T0/T1)往往比直接换渲染器(T4)更划算,且全端安全。

## 5. 【T0】拆除选择态级联(最高 ROI,近免费,直击报告症状)

### 5.1 目标
让「进入选择态」从「数千组件同步重渲染 + 建节点 + 全文档 recalc」降为「**1 个容器元素 1 次 class 变更**」,收益立竿见影且全端安全。

### 5.2 现状机制(根因 3,见 §1.4)
`isSelectionMode` 翻转 → 每格 overlays/checkbox 的 `v-if` 由假变真 → 逐格重渲染建节点 + `.media-card--selection-mode` 全文档 style recalc。

### 5.3 改法方向(结构性,非 canvas)

> 🟡 **交付回写(caf9dd2)**:本次实际交付的是 §5.6 的**最小变体**(compact 覆盖层整体不渲染 + 两个选择态 class 对 compact gate + 点击切选),**未采**本节 1/2 的「容器单类 + `:deep()` + 伪元素 checkbox」路线——因实际代码耦合高于「极低」(见 §5.6 原因),且残余廉价 re-render 本就由 T1 独立组件根除更干净。本节 1/2/3 作为「彻底消除残余 re-render」的备选保留,不作本次施工依据。
1. **选择态开关只作容器单类**:在 `.media-grid`(或 `.media-grid__content`)挂一个 `is-select-mode` 类,用**后代选择器** `.is-select-mode .media-card { … }` 让 CSS 承担外观变化。进入选择态 = 1 元素 1 次 class 变更,不再让数千节点 prop 失效。
2. **compact 的 checkbox 用 CSS 伪元素**:`.is-select-mode .media-thumb--compact::after` 画圈,`.media-thumb--selected::after` 画对勾——**伪元素不新增 DOM 节点、不触发逐组件响应式**。选中态视觉你其实已有([.media-thumb--selected](../../src/components/media/MediaThumb.vue#L911) 的 scale + box-shadow,纯 CSS 由 `isSelected` 类驱动)。
3. **去掉 MediaThumb 对 `isSelectionMode` prop 的模板依赖**(compact 分支):compact 下不再因 `isSelectionMode` 变化重渲染;`isSelected` 仍走 class(单格粒度,廉价)。

### 5.4 必须保全的 UX(施工红线)
- 60px 下若去可点 checkbox,须让 **compact 选择态下的普通点击 = 切换选中**(当前普通点击是开图,[MediaGrid.vue:1075](../../src/components/media/MediaGrid.vue#L1075) `handleCardClick`);否则丢了「点一下加选」主交互。改 `handleCardClick`:`if (compact && isSelectionMode) → toggleSelect` 分支先于 router.push。
- 非 compact(大图)行为**零改动**:大图下 checkbox / hover 富交互保留,只有 compact 走精简路径。

### 5.5 验收
- **量化**:进入选择态耗时(§10 探针 `selectEnterMs`)与「新增节点数」应 **≈ 归零**;真机 60px 全屏进选择态无可感卡顿。
- **回归(真机)**:compact 点击加选 / Ctrl+Click / Shift 范围选 / Esc 清空 / 大图下 checkbox+hover 富交互全部正常。
- **测试**:`handleCardClick` 的 compact 选择态分支纯逻辑可单测(input:compact+selectionMode+event → 期望 toggle vs open)。

### 5.6 交付回写(caf9dd2,2026-07-09 本会话)
实际交付 = §5.3 的**最小变体**,门禁全绿(仅本地)vitest 432/vue-tsc 0/eslint 0,⏸GUI 真机验收:
- **MediaThumb**:覆盖层 `v-if` 由 `!compact || isSelected || isSelectionMode` 收为 `!compact`(compact 进选择态**零建节点**);`media-thumb--selection-mode` 类加 `&& !compact`(compact 不翻转此类 → 无 style recalc)。
- **MediaGridRow**:`media-card--selection-mode` 类加 `&& !compactCells`(该类唯一用途=选择态抑制 hover 缩放,compact 本无 hover-pop,零影响)。

## 9. 【T4】canvas 混合网格(用户设想:可行性、取舍、架构)

> **定位**:收益上限最高、成本最高、且有 iOS 反向风险。**应由 §10 测量数据触发**(T0–T2 后若极密快滚 / 内存仍不达标),而非现在就承诺。若上,形态 = **混合(canvas 画 + 薄 DOM 覆盖层)+ Windows/WebView2 门控 + DOM 回退**。

### 9.1 可行性:高(三点降险)
1. **均匀网格是 canvas 的「特例」**:格子位置 = 索引的纯函数,点击命中 / 框选 / Shift 范围选都是 **O(1) 算术**(`col=floor(x/cellW)`,marquee = 相交索引区间),不是 Figma 那种要空间索引的自由画布难题。后端还有 `GET_ITEM_Y_BY_ID` 等坐标能力([MediaGrid.vue:698](../../src/components/media/MediaGrid.vue#L698))。
2. **你已有完整 canvas playbook**:[TimelineScrubberCanvas.vue](../../src/components/media/TimelineScrubberCanvas.vue) 已实现 DPR 幂等适配(`fitCanvas`)、从 CSS 变量读调色板 + 主题重绘(`readPalette`)、rAF 节流绘制 / pointermove、`canvas pointer-events:none` + 外层 div 做 `role`/键盘 a11y、甚至「放大镜」区域放大。网格版几乎是它的二维推广。
3. **你已有「DOM ↔ Canvas 一键切换」UI 模式**([MediaGrid.vue:214](../../src/components/media/MediaGrid.vue#L214) 的 `timelineRenderMode`),正好复用为 webview 门控 + A/B 对比脚手架。

### 9.2 取舍:canvas 换 DOM 白给的东西,要逐件补
| 丢失项 | 补法 | 成本 |
|---|---|---|
| **无障碍**(现 `role="button"`/`aria-pressed`/`tabindex`,[MediaGridRow.vue:56-59](../../src/components/media/MediaGridRow.vue#L56-L59))| **镜像 DOM**:仅为可见窗口每格渲一个轻量 `role="gridcell"` 焦点元素,canvas 选中 ↔ DOM 焦点双向同步(Figma 模式)| **最大隐藏成本,多数团队低估** |
| 逐格命中 / 框选 | O(1) 算术,**canvas 反而更简单** | 低(利好项)|
| hover 视频预览([useHoverPreview](../../src/composables/useHoverPreview.ts))| 薄 DOM 覆盖层定位到 hover 格,复用现有 composable | 中 |
| 右键 / 拖拽 / tooltip | 挂覆盖层节点,复用浏览器原生 | 中 |
| 图像解码 / 上传 | 自建 `createImageBitmap` + worker(可选 `OffscreenCanvas`)+ **每帧限量 LRU 驱逐**(GPU 内存预算 + `MAX_TEXTURE_SIZE` 运行时钳制)| 中高(现在 `<img>` 让浏览器代劳)|

### 9.3 渲染器选型(若上,先轻后重)
1. **先 Canvas 2D `drawImage` 窗口化**:无批处理,但只画可见 2000–3000 格,很可能已远胜 DOM,**零新依赖**——契合「<10MB 核心 + 控依赖」。Canvas 2D 舒适区 ~1000–3000 draws/帧。
2. **仅当 2D draw-call 成瓶颈 / 冲「百万级 60px」时**再上 **WebGL 精灵批处理 + 纹理图集**(须运行时 `gl.getParameter(gl.MAX_TEXTURE_SIZE)` 钳制,保证 ≥4096 兼容)。
3. **库参考**(若不自研):PixiJS ~120KB gz(电池全带、v8 tree-shakeable)、Konva ~55KB(自带命中)、OGL ~8KB / regl ~30–71KB(自建批处理)、three.js ~150KB(2D 网格过重)。**倾向先自研 Canvas 2D 不引库。**

### 9.4 跨端门控(硬约束)
- **默认路径仍是 DOM**(T0–T3 优化后);canvas 作为 **`ui.galleryRenderMode` 开关 + Windows/WebView2 门控**的增强。
- iOS/WKWebView **强制 DOM**(§2.3 的内存 / 降帧风险);Android WebView 视真机实测再定。
- 复用现有 `timelineRenderMode` 的 localStorage 持久化 + 一键切换范式,内测期可 A/B 对拍。

### 9.5 结论
canvas 可行且被 digiKam 的原生实践背书,是「极密档」的**正确终局备选**;但因(a)T0–T2 更可能直接消除已报症状、(b)iOS 反向风险、(c)a11y / 富交互重建成本,**它是最后一步而非第一步**。

- **内联评分/收藏编辑**(canvas hover 交互):经右键菜单 / 详情页 / 选择工具栏仍可达。
- **`showThumbInfo` 的 info-overlay + ORIG/THUMB/size 徽章**(power-user 开关默认关;文本布局 + backdrop-blur 不易在 canvas 复刻)。

> **defer 的判据(关键)**:以上三项均是**非 compact 的显示/编辑增强**,**不影响被对比的滚动 + 进选择态性能**(即非「perf-公平」缺口,是「feature」缺口),且均有替代入口;加之本轮 GUI 不可自测,宜留独立、可真机验收的 pass。**补齐 hover 预览的低风险路径已想定**:host 持单例 `useHoverPreview` + 定位到 hover 镜像格的 `<video>`/sprite 覆盖层(复用现有 composable,~40 行,靠持久镜像格的 mouseenter 触发,无「挂载即在光标下 mouseenter 不触发」问题)——留待用户指示。

**裁决(§9.4/§9.5 不变)**:canvas 转正定位仍是**按需增强 + iOS/坐标门控 + DOM 回退**;默认路径仍 DOM。是否长期投入(补齐 defer 项 + 商店化)由本轮真机对比数据触发。

### 9.8 转正 v2 修正:推翻 DOM 镜像层 → 零逐格 DOM(mirror-removal,2026-07-09 本会话)
**用户实测**:§9.7 v1 的 canvas 反比 MVP **更卡**;devtools 实证镜像层 `.mgc-mirror` 有 **2658 个 `.mgc-cell` 节点**——每可见格一个 `<div>` 恰好把 canvas 意在消除的**维度 A(节点数)重新引入**,与「用 canvas 减 DOM 节点」的立项目标背道而驰。**教训**:a11y 镜像不是「交互的必要条件」;我把 §9.2 自己写过的「最大隐藏成本」误当免费午餐,是本方案最大的一次误判。

**v2 现行方案(零逐格 DOM)**:
- **删除镜像层**。canvas 恢复为**唯一交互元素**:点击 / 右键 / pointerdown 全在 canvas 上,经 `hitTestCell` **算术命中**(O(1),利用 `item.x`;该纯函数本就有 7 测)→ 回吐宿主 `handleCardClick` / `onContextMenu` / `onCardPointerDown`。
- **框选(唯一真需 `elementFromPoint` 的交互)**:给 `useSelection` 加 `setPointerIdResolver(fn)` 注入点;`MediaGridCanvas` 挂载时注入纯算术解析器 `idAtClient`,其 `onPointerMoveGlobal` 用它替代 `elementFromPoint→closest('[data-item-id]')`。→ **框选 / Ctrl+A / Shift 范围 / 拖到文件夹**全部工作(拖拽的**文件夹落点**仍用侧栏真实 DOM 的 `elementFromPoint`,不受影响),**零逐格 DOM**。卸载时 `setPointerIdResolver(null)` 复位,DOM 模式回到 `elementFromPoint` 路径。
- **节点数回到 MVP 级**(1 canvas + 0 逐格),快滚 / 选择不再被 2658 节点拖累。

**审计表(§9.7)对应修正**:第 1/3 行(框选 / 点击 / 右键)由「镜像层」改为「resolver 注入 + canvas 单元素算术命中」;**第 2 行(逐格键盘 / 读屏 a11y)诚实降级为 DOM 模式专属**——canvas 仅 grid-level `role=grid` + `aria-label` + 可聚焦。第 4–13 行(availability / pending-delete / 真 LRU / 自愈 / 主题 / 门控 / 平滑)**v2 全保留**,视觉与资源正确性不受此次回退影响。

**a11y 诚实降级**:canvas 模式(实验性、opt-in、Windows 门控)以「逐格键盘 / 读屏焦点」换「零 DOM 节点」——这正是用户在「优先节点数 / 速度」时选择的权衡;**DOM 模式仍是 a11y 完备的默认路径**。补齐 canvas 逐格 a11y 的正道 = **单个 roving focus proxy**(仅 1 节点,随方向键在网格内移动 + 焦点环由 canvas 画),非本轮范围,留待需要时单列一 pass。

**v2 补记(inflight cap 回退)**:v2 初版给图像加载设了 `MAX_INFLIGHT=12` per-frame 并发上限(§9.7 审计表第 8 行的「转正处理」),用户实测出现**肉眼可见的从上到下逐波出图**、体感变慢。根因:`draw` 自上而下遍历,前 12 格起载后其余 `return null`,下一批须等 `onload → scheduleDraw → draw` 的 rAF 往返才起——把加载序列化成「每波 12 张、波间隔一帧」的爬行。MVP 无此上限(一次把可见格 `src` 全排入浏览器连接池,池自身限并发)故「一屏直出」。**已移除该上限**:`getImage` 只对可见格调用(离屏行 `draw` 里已 `continue`),在途数天然被可视窗口界定,无需人为 per-frame 上限。**审计表第 8 行「限并发 12」随之撤销**,改为「可见格边界天然限量」。(**思路记录 + 已回退**:60px 单屏 >2000 格时 `MAX_CACHE=2000` 会驱逐仍可见的图 → 闪一下再重载(用户 2026-07-09 真机确认)。曾尝试「驱逐跳过当前可见格」修复(每帧 `draw` 重建 `visibleIds`,`cacheSet` 驱逐时 skip 其中 id;commit `8b42c92`),但用户实测该改动**疑似引入两个新症状**:① 惯性/无极滚轮**飞掠卡顿**、② **快滚到位后短暂白屏**——推测因驱逐循环由「删定量即止(≤N 次)」变为「每次 `cacheSet` 全表扫描跳过可见集」,快滚时多 `cacheSet` 叠加 O(n) 拖帧。**已回退**该修复以隔离观察;「闪一下」thrash 暂重新暴露,待 ①② 根因定位后再以**不拖帧**的方式重解——候选:仅滚动停稳时驱逐 / 驱逐预算化(每帧删上限)/ 可见集用 O(1) 标记而非全表扫描。**这一路真机三连(镜像层 2658 节点→逐波出图→闪一下)提示:canvas 图像缓存/加载调度需按「滚动相位」设计,不能只按「单帧正确」设计**。)

门禁全绿(仅本地)vitest 451/vue-tsc 0/eslint 0/build。⏸GUI:canvas vs DOM 快滚 / 进选择态对比;框选 / Ctrl+A / Shift / 拖到文件夹 / 右键 / 点击开图在 canvas 下与 DOM 一致;canvas「一屏直出」不再逐波。

## 10. 测量基线协议(本次交付,让 T0–T4 收益可证伪)

> 承接「触碰命门路径前先补 characterization」+「Done = 有可观察证据」。改渲染层前先立可复现的数字基线,否则任何「变快了」都是体感臆测。
>
> **与 v2 报告实测的分工**:维度 A(节点数)v2 §9.5 已测(7294,静态地板);探针的**新增量是量化维度 B/C**——`selectEnterMs` + 新增节点数直接量化根因 3(选择态级联),滚动 FPS 量化根因 1/2(快滚 churn)。这两个数 v2 的节点普查看不见,恰是 T0/T1 收益的证伪标尺。

### 10.1 探针 `useGalleryPerfProbe`(dev 门控,零生产成本)
- **门控**:仅当 `localStorage['scrollery.debug.perfProbe']` 为真时激活(镜像 [useVirtualScroll.ts:59](../../src/composables/useVirtualScroll.ts#L59) 的 `scrollery.debug.safeMax` dev-flag 惯例);关闭时**立即 return,不挂任何监听**,生产零开销。
- **接线**:[MediaGrid.vue](../../src/components/media/MediaGrid.vue) setup 内一行调用,以 getter 注入 `gridEl / isScrolling / isSelectionMode`,**不改模板、不碰热路径 render**。
- **三项指标**:
  1. **DOM 节点普查** `census()`:`.media-grid` 下 `.media-card` 数、总 `childNodes` 数、当前可见格数——对应根因 1,复刻你 devtools `temp1.childElementCount` 取证习惯,挂 `window.__scrolleryPerf.census()` 供手动调。
  2. **滚动 FPS** :`isScrolling` 为真时启 rAF 采样,停稳时打印本段 min/avg FPS + 掉帧数——对应根因 1/2(快滚 churn)。
  3. **进入选择态耗时** `selectEnterMs`:`isSelectionMode` false→true 时 `performance.now()` 打点,double-rAF 后测「同步重渲染 + 布局 + 首帧」耗时 + 前后节点数增量——对应根因 3。
- **纯函数抽出 + 单测**:帧时间戳 → `{avgFps,minFps,dropped}` 的聚合抽为 `summarizeFrames(timestamps)` 纯函数入 helper,单测锁定(承接「纯映射进 helpers + spec」惯例)。

### 10.2 基线采集流程(真机,你执行)
1. dev 跑起,`localStorage.setItem('scrollery.debug.perfProbe','1')` 刷新。
2. 全屏 + 行高滑到 60px,进入一个 ≥6 万项视图(或全部照片)。
3. 依次记录:`__scrolleryPerf.census()`(节点 / 格数)、快速甩滚 3 次(读 FPS 段)、进选择态 1 次(读 `selectEnterMs`)。
4. 存为「T0 前基线」;每落一档(T0/T1/T2)后同流程复采,对拍收益。

### 10.3 目标阈值(候选,真机校准前不定死)
- 单屏元素节点数:目标压向 Lighthouse <1400 区(或明确记录为「canvas 触发线」)。
- 进入选择态:`selectEnterMs` < 1 帧(~16ms)、新增节点 ≈ 0(T0 应达成)。
- 快滚 min FPS:≥ 45(可感流畅下限,真机校准)。
