# 玻璃模式内容底面修复:新增 `--glass-content-fill` 半透明画布

> 方案日期:2026-09-06
> 上游关系:[窗口材质毛玻璃方案](C:/workspace/scrollery/docs/designs/2026-08-24-窗口材质毛玻璃方案.md)的修订案。该文决策记录第 7 条「内容布局容器透出,具体媒体/卡片表面承重」在设置页被实测证伪——设置行按自身设计语言「融入页面、无卡片面」,可读性实际完全押在页面画布上,而玻璃模式恰好把画布抽空。本方案不改其层级纪律与画廊边界,只把「内容画布」从 100% 不透明修订为玻璃模式下 90% 半透明;施工收口时须同次修订该文决策记录正文(AGENTS:推翻规范性文本同次编辑改正文)。
> 需求来源:用户真机反馈——Acrylic 模式下设置页整页发灰、观感割裂(2026-09-06 截图实测,见 §2)。

## 1. 摘要

真机实测确认前端玻璃管线( `data-glass='acrylic'`、webview 透明、chrome 填充)全部工作正常,症状的直接原因是 **DWM Acrylic 背板在用户机器上渲染为一块均匀纯灰 #D2D2D2**(材质回退态或纯色壁纸),而玻璃模式把 `.app-shell` 唯一画布抽空后,除 DocumentViewer 外所有视图根都没有自身背景,整页直接坐在背板上。文字密集页面(设置页为最)的可读性因此完全取决于背板质量——背板一旦是死灰或花桌面,页面即失效。

修复:玻璃模式新增内容底面角色 token **`--glass-content-fill`**(`color-mix(bg-primary 90%, transparent)`,mica/acrylic 共用),落在**文字密集视图的根元素**(opt-in 枚举,不铺在 `.app-content` 上以免截断画廊的「完全透出」设计);同步把 `.settings-header` 等残留不透明子面改为消费该 fill;新增 `glass_content_opacity` 配置键(scale,20–120,默认 100)对齐既有 4 组透明度先例。

修复后背板无论处于实时模糊、回退死灰还是任何壁纸,文字页底色都被钳制在 ≈90% 主题色附近,对比度不随背板漂移;玻璃表达由 chrome 四表面 + 画廊(保持现状)承载。

## 2. 症状与像素实测(2026-09-06 截图,Fresh·浅色 × Acrylic)

| 区域 | 实测 RGB | 解释 |
|---|---|---|
| 内容区/导航列 8 处远距离采样 | 全部 (211,211,211) | 整窗底下是一块**逐像素均匀的中性纯灰 #D2D2D2**,不是任何主题色(全主题绿调),也非启动底色(`--startup-bg`=#f2f7f4) |
| 标题栏 | (241,244,242) | 精确 = 82% × `--color-bg-secondary`(#f7fbf9) + 18% × #D2D2D2 → `data-glass='acrylic'` chrome 填充**正常工作**,且反证背板 = (211,211,211) |
| 设置页头部条 | (242,247,244) | 精确 = `--color-bg-primary`(#f2f7f4) → `.settings-header` 在玻璃模式下**仍不透明**,与下方透明区形成割裂 |

结论:CSS 层无故障;故障 = DWM 背板失去实时内容(均匀纯灰)+ 应用侧文字页无底面承重。

## 3. 根因

1. **背板层**:DWM 对材质合成的静默回退——系统「透明效果」关闭 / 省电模式 / 远程桌面会话 / GPU 不支持时,Mica/Acrylic 不报错地画成纯色([Microsoft Learn: System backdrops](https://learn.microsoft.com/en-us/windows/apps/develop/ui/system-backdrops));另有 Win11 acrylic 失焦退化(window-vibrancy#139,上游方案 §6 已登记)。也可能是窗口背后恰好为均匀纯色。应用无法可靠探测该状态(无公开 API),也不应试图探测。
2. **应用层**(根因修复落点):上游方案把「内容布局容器透出」与「具体表面承重」绑在一起,但——
   - 设置页设计语言是「accordion 展开后融入页面,行分隔线承担层级」(`SettingsView.styles.css` 对 `.settings-card` 强制 `background: transparent`),**页面本身才是唯一承重面**,玻璃模式抽掉画布后没有任何表面兜底;
   - CollectionsView / PersonsView / PluginStoreView 等视图根本就不自带背景(非玻璃模式坐在 `.app-shell` 画布上),玻璃模式同样裸背板,只是此前未被反馈;
   - 少数子面(`.settings-header`、`.doc-viewer`)仍自铺不透明 `--color-bg-primary`,形成透明/不透明拼布。

## 4. 方案

### 4.1 核心 token:内容底面

```css
/* glass.css,html[data-glass] 共享块 */
--glass-content-scale: 1;
--glass-content-fill: color-mix(
  in srgb,
  var(--color-bg-primary) calc(90% * var(--glass-content-scale)),
  transparent
);
```

- **源 token 用 `--color-bg-primary`**(非玻璃模式的画布色),保证玻璃/非玻璃两态下页面底色同源,仅透明度不同。
- **mica/acrylic 共用 90%**:两态背板内容都不可控,基准取同值减少自由度;真机验收若需分材质,再拆入各自材质块(文件既有惯例)。
- **不叠加 backdrop-filter**:模糊由 DWM 完成,遵守父方案 blur 纪律。
- **90% 的层级语义**:内容面(90%)比 chrome(72/82%)更实——文字承重面高于装饰性 chrome,与非玻璃模式「canvas 画布 / chrome 更亮」的明度阶梯同向。

### 4.2 落点:视图根 opt-in,不铺 `.app-content`

fill 落在各视图根元素,`.app-content` 维持纯布局容器。若铺在 `.app-content`,画廊 route 的 `media-grid-layout`(设计上 `glass_gallery_opacity` 默认 0% 完全透出 DWM)会被底下 90% 画布垫实,推翻已交付的画廊决策且无法用 CSS「减掉」。glass.css 本就是逐表面配方文件,枚举 opt-in 与其模式一致。

视图现状盘点与处理:

| 视图 | 根类名 | 玻璃模式现状 | 处理 |
|---|---|---|---|
| 设置 | `.settings-view` | 根被显式置 transparent(本次症状页) | 改为 `var(--glass-content-fill)`;`.settings-header` 置 transparent 由根面承托 |
| 收藏 | `.collections-view` | 无自身背景 → 裸背板 | 新增 fill 规则 |
| 人物 | `.persons-view` | 同上 | 新增 fill 规则 |
| 插件商店 | `.plugin-store` | 同上 | 新增 fill 规则 |
| 文档阅读器 | `.doc-viewer` | 自铺不透明 bg-primary(拼布) | 玻璃模式下改 `var(--glass-content-fill)` |
| 音频播放器 / 日志窗 / 画廊Lab | `.audio-player` / `.log-window` / `.hlab` | 面板内部多处自铺 bg-primary,根面情况待核 | 施工时逐个核查,判据:根面裸则加 fill,内部语义面板不动 |
| 媒体画廊 | `.media-grid-layout` | `--glass-gallery-fill`(默认 0% 完全透出) | **不动** |
| 设置横幅 | `.settings-config-banner` | 语义色(error/info) | **不动**(状态横幅自身语义承重) |

glass.css 文件头注释补一条约定:**新增视图根若承载文字,必须在 opt-in 清单加 fill 规则**——这是后续视图的接入手册。

### 4.3 配置键:`glass_content_opacity`

与既有 4 组 scale 完全同构(UInt,默认 100,hot,收敛 20–120):20%→18% 极透,100%→90% 基准,120%→color-mix 钳到 100%(内容面不透明,等价 none 的内容区)。设置页在既有 5 个透明度项旁自动获得第 6 项;非玻璃模式不消费该键。

### 4.4 对比度验算(基准 90%,fill = bg-primary@0.90 叠背板)

fresh-light 文字 token 对填充后底色的对比度,背板取两个极端(纯黑 / 纯白):

| 文字 | 纯黑背板(fill≈#DA…(218,222,220)) | 纯白背板(fill≈(245,248,246)) | 阈值 |
|---|---|---|---|
| primary #20352d | ≈9.6:1 ✓ | ≈12:1 ✓ | 正文 4.5:1 |
| secondary #52675e | ≈4.4:1 ✓(辅助) | ≈5.6:1 ✓ | 辅助 3:1 |
| tertiary #71827a | ≈3.0:1 边缘 | ≈3.7:1 ✓ | 辅助 3:1 |

最坏情况(近黑背板)下正文/辅助全达标;tertiary(eyebrow 等装饰小字)在纯黑背板边缘——验收矩阵含暗壁纸抽查,不达则调 `glass_content_opacity` 至 110–120。其余五主题同法验算,列入验收清单。

## 6. 风险与缓解

| 风险 | 表现 | 缓解 |
|---|---|---|
| 内容面 90% 后玻璃感变弱 | 设置页与 none 模式肉眼差异小 | 预期权衡:文字页可读性优先,玻璃表达由 chrome + 画廊承载;用户可调 `glass_content_opacity` 20–120 |
| 视图根 opt-in 漏接 | 新视图在玻璃模式裸背板(本 bug 复发) | glass.css 头注释接入手册;验收清单含「新视图检查项」 |
| 极端暗壁纸下 tertiary 文字 <3:1 | eyebrow/提示字发虚 | 验收矩阵专项;调 `glass_content_opacity` ≥110 即可达标 |
| color-mix 钳制语义 | scale 120 时 fill 变全不透明 | 预期行为(调大=更实),注释言明 |
| 旧决策文档失同步 | 2026-08-24 文决策记录与实现相悖 | 施工收口 commit 同次修订该文 §3/§9 正文(AGENTS 规则) |

## 8. 明确不做(出界)

- 探测系统透明效果/省电/RDP 状态并自动切换材质——无可靠公开 API,CSS 底面已使观感与背板状态解耦
- 给设置行/卡片逐个加玻璃表面(改页面设计语言、选择器爆炸,且不解决 collections 等页)
- DWM tint 按主题调色(SWCA 路径才消费,Win11 22H2+ 忽略,收益面窄)
- 画廊默认透明度语义变更(已交付决策,不动)

## 9. 决策记录

| 决策 | 取舍 | 理由 |
|---|---|---|
| 内容画布 = 90% 半透明 fill,而非恢复不透明 | 玻璃感 ↓ | 上游「推翻整块不透明」的依据是实色 canvas 截断 DWM;半透明 fill 不截断(仍透 10%),是同一主流程内的修订而非回退 |
| fill 落视图根 opt-in,不铺 `.app-content` | 多 4-8 条选择器 | 铺容器会把画廊默认 0% 透出垫实,推翻已交付画廊决策;glass.css 本就逐表面配方 |
| mica/acrylic 共用 90% 基准 | 少一个自由度 | 两态背板内容均不可控;真机验收需分再拆 |
| 源 token = `--color-bg-primary` | — | 与非玻璃模式页面底色同源,两态观感连续 |
| 新增 `glass_content_opacity` scale 键 | +1 配置键 | 与既有 4 scale 先例同构,链路零新机制;「文字页更实/更透」是用户偏好 |
| `.settings-header` 一并改透明 | +1 条规则 | 不改则拼布残留,症状只消一半 |
| 不做背板状态探测 | — | 无公开 API;CSS 底面使观感与背板解耦,探测失去意义 |
