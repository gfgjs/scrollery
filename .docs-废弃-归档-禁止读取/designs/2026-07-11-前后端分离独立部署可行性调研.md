# 前后端分离独立部署可行性调研(Q 线)

> **性质**:可行性调研 + 路线建议,**未立施工项**。业界事实来自 2026-07-11 联网调研(带引用);本仓事实来自同日代码盘点(带文件路径,关键计数已独立抽验)。
> **目标场景**:服务端部署在 NAS 或私人服务器(Docker 或裸二进制),PC / Mobile 通过浏览器或 App 访问;照片库存放在服务器侧,多设备浏览、管理、备份。

## 1. 需求场景与问题定义

Scrollery 当前是桌面优先的 Tauri 2 单机应用:Vue 3 前端与 Rust 后端同进程(webview + 宿主),媒体库、缩略图缓存、SQLite 数据库全部在本机。本调研回答三个问题:

1. **技术可行性**——现有代码距离「可拆」有多远:哪些是传输层机械替换,哪些是「前后端同机」的语义假设,哪些是平台绑定的硬工作量。
2. **业界怎么做**——Immich / PhotoPrism / Ente 等成熟自托管相册项目的服务端形态、客户端策略、部署与分发渠道;以及 Spacedrive / Jellyfin / VS Code Remote 这类「一核多壳」架构的分层方式。
3. **路线**——若做,如何分阶段推进,风险和开放决策有哪些。

约束前提(承接现有产品事实):桌面单机形态是首发主线,不能因拆分而回退;拆分后的服务端形态应与桌面形态**共享同一 Rust core 与同一 Vue 前端**,不做第二套产品。

## 2. Scrollery 现状:前后端耦合面盘点(本仓实证)

> 盘点方法:全库结构扫描 + 关键计数独立复核(2026-07-11,工作树 = `bcf0934` 后含 UI 线未提交改动)。

### 2.1 已具备的解耦资产(利好面)

- **invoke 单一入口**:全库唯一 `invoke` 导入点是 `src/utils/ipc.ts`(`invokeIpc` / `invokeIpcRaw` 两个函数);业务代码 0 处直连。命令名由 `src/constants/ipc.ts` 的 `IPC` 常量对象 + `IpcCommand` 类型约束,裸字符串在类型层被拒。→ 前端换传输层的改造面收敛在一个文件。
- **结构化错误契约已跨界**:后端 `src-tauri/src/error.rs` 的 `AppError` 派生 `Serialize`,以 `{ code, message }` 过界;前端 `IpcError` / `AppErrorCode` 联合(~17 个稳定码:`Io`/`Db`/`ViewStale`/`VolumeOffline`/`Cancelled`/`Ai`…)。→ HTTP 化时错误语义可原样平移(HTTP status + code 字段)。
- **S0 browser harness = transport 抽象原型**:UI 重构线 S0 已建成 `?ui-harness=` 分流——`utils/ipc.ts`(invoke→fixture)、`utils/appEvents.ts`(listen→no-op)、`utils/appWindow.ts`(window→DOM stub)三个边界适配,真实 `App`/stores/`MediaGrid` 已证明可在纯浏览器挂载渲染。→ 「同一前端、多种宿主」的缝已经开好,web 客户端沿同一缝换成 HTTP 实现即可。
- **后端已是进程外 worker 形态**:`psd-worker` / `psd-probe` / `ai-worker` 三个独立二进制(`crates/exotic-workers/`),与主进程走长度成帧 stdin/stdout 协议(`exotic-protocol` crate:Hello→Ready 握手、Request/Success/Failure、Progress 帧兼心跳,静默限时 + 3600s 总帽);ORT/onnxruntime 只在 `ai-worker` 内加载。→ 重活已经不在「桌面壳」里,服务器宿主可原样复用 supervisor/worker 结构。
- **workspace 已分层**:10 成员(`exotic-protocol`、`scrollery-plugin-api`、`scrollery-ai-core`、`scrollery-exotic-trust`、`scrollery-free-stub`、`scrollery-pro`、三 worker、主 crate);核心逻辑在 `scrollery_lib`(staticlib+cdylib+rlib)。→ 新增一个 server 宿主 crate 不需要动既有分层。
- **DB 形态天然适配单机服务器**:rusqlite 单文件(`app_data_dir/scrollery.db`)+ WAL + 读连接池 8 + 单写连接(`Mutex<Connection>`),busy_timeout/mmap 等 PRAGMA 已齐(`src-tauri/src/db/connection.rs`)。→ 与 PhotoPrism 的 SQLite 单机形态同型;多浏览器标签的并发读已有池化基础。
- **reader 纯文本链路已是「命令返回内容」模式**:`get_document_text` / `get_text_chapter` / diff 等 26 个 doc 命令以字符串/结构体过界,编码探测、分章、简繁转换全在 Rust 侧(`src-tauri/src/ipc/doc_commands.rs`)。→ 这条链路天然可远程,零资产协议依赖。

### 2.3 「前后端同一台机器」的语义假设清单(比传输更深一层)

传输替换解决不了这些——它们假设**服务进程所在机器就是用户面前那台机器**:

1. **桌面动作命令**(`system_commands.rs`,8 个):`open_directory` / `show_in_explorer` / `set_as_wallpaper` / `copy_image_to_clipboard` 等,在服务器上执行会打开**服务器的** explorer/壁纸/剪贴板。远程模式需按命令降级:禁用、或语义转换(如「在资源管理器中显示」→「下载原图」)。
2. **原生文件夹选择器**(`plugin-dialog`,5 处调用):加扫描根(`FoldersSection.vue:242`)、首跑向导、缓存/日志目录设置。远程模式需**服务端目录浏览 UI**(业界通行做法,见 §3)。
3. **文件操作语义**(`file_ops_commands.rs`,9 个):移动/复制/删除操作的是服务器盘——语义仍成立,但确认文案与失败恢复 UX 需按远程场景重审。
4. **DocThumbRenderer 客户端渲染回传环**:webview 渲 pdf/svg → PNG 经 `invokeIpcRaw` 回传入缓存。浏览器客户端仍可行,但意味着**部分派生管线依赖「恰好有个客户端在线」**——服务器形态宜将此类渲染迁到服务端(headless)或接受「首个访问的客户端补渲」。
5. **移动卷模型**:`volume_watch.rs` 15s 轮询、`VolumeOffline` 错误码——NAS 场景语义变化(服务器的外接盘,而非用户面前的 U 盘),UI 文案与操作引导需适配。
6. **插件/许可体系假设端侧验证**:license token 存 OS keyring(每机器);信任根 keyset 经 `scrollery-pro`/`scrollery-exotic-trust` 的 build.rs `include_str!` 编译进二进制;Ed25519 离线验签。server 部署下「谁持有授权」(服务器持有 vs 每客户端持有)必须重新设计——这是商业模型问题,不只是技术问题。
7. **单用户单实例假设**:一个 `scrollery.db`、单写连接、无账号/会话/租户概念、tray + 单主窗。浏览器可多标签并发(读池可服务),但**没有任何鉴权**——服务器形态必须新增认证层(见 §3 业界做法)。
8. **Windows-only 核心路径**(~27 文件 `cfg(windows)`):WIC 图像解码引擎(`engine/gpu/wic_engine.rs`,非 Windows 返回 None 走 CPU image crate fallback)、Media Foundation 视频封面/关键帧(`video/media_foundation.rs`;FFmpeg 仅 Perf feature 占位「glue not implemented」)、DXGI 适配器枚举、volume GUID 探测。**NAS/服务器几乎必然是 Linux**——服务器形态的解码/视频/AI 执行后端需要 Linux 路径补齐,这是最大的确定性硬工作量(CPU 解码兜底已有,视频派生与 DirectML→CPU/CUDA 切换需做)。
9. **更新与分发**:`tauri-plugin-updater` 面向桌面;服务器形态的升级走 Docker 镜像 tag / 二进制替换,是另一套发布管线。

### 2.4 小结:拆分成本的结构画像

- **薄的地方**(1-2 文件级收口点,机械替换):命令调用、错误契约、事件包装、资产 URL 构造、DTO 镜像。
- **中等**(逐命令排查,少量重设计):~10 个返回绝对路径的命令、8 个桌面动作命令、5 处 `Channel` 流、dialog 选路径流程、file-ops UX。
- **厚的地方**(真正的工程量):Linux 解码/视频后端、认证与多客户端会话、插件许可的部署模型、服务器形态的发布管线、移动端 App(见 §5)。

## 3. 业界方案调研(2026-07-11 联网)

> **方法与证据等级**:§3.1–§3.2 出自 deep-research 管线——5 角度并行搜索 → 26 来源 → 125 条候选事实 → 25 条送验 → **每条 3 票对抗核实**(19 确认 / 6 否决),下文标注票数;被否决的表述在文中列为「表述红线」,引用本报告时不得复活。§3.3–§3.6 为同日定向补证(抓取官方一手文档,逐条带来源,未经三票程序,证据等级低一档)。

### 3.1 移动端「相机胶卷后台自动备份」是客户端形态的分水岭(已核实)

1. **生态分化,竞品官方自认**(3-0×2):LibrePhotos 官方功能对比表自认「Android App ✔️ / iOS App ❌ / Auto backup ❌」,同表 Immich 三项全 ✔️、PhotoPrism 三项全 ❌——**在该三方对比内**只有 Immich 交付了「双端可安装 App + 自动备份」组合。旁证:LibrePhotos 官方 mobile 仓(react-native,自述 proof-of-concept)2026-04-23 已 archived 且从未实现 backup;第三方 UhuruPhotos 原生 Android App 反而补位实现——恰证自动备份要靠专门的原生投入。
   **范围修正(勿外推)**:放宽到全阵营(§3.3 档案),交付「双端官方 App + 自动备份」的仍是极少数——Immich 与 **Ente**(均官方 Flutter 双端;Ente 后台一致性官方自认有缺,见第 4/6 条);Piwigo 有官方原生双端 App、Nextcloud Memories 有官方 Android(自动上传由 Nextcloud 官方 App 承担),此二者证据等级低一档;其余(PhotoPrism/LibrePhotos/Photoview/Lychee/Damselfly/HomeGallery)均无官方 App。deep-research 合成层「阵营中只有 Immich」的原始表述过宽,本报告已按档案修正。
   来源:docs.librephotos.com/docs/user-guide/features/、docs.immich.app/features/mobile-backup/
2. **PhotoPrism 的 PWA 路线官方自证不承担自动上传**(3-0×2):官方明确不提供应用商店原生 App,移动端 = 可装主屏的 PWA(「almost native app-like experience」)+ 第三方 App 补位;PWA 文档通篇无相机胶卷自动/后台备份能力描述,需传原件的场景官方导流第三方 PhotoSync(经 WebDAV)。
   来源:docs.photoprism.app/user-guide/pwa/、developer-guide/native-apps/、user-guide/sync/mobile-devices/
3. **iOS 浏览器/PWA 上传还有「原格式不可程序化保全」问题**(2-1,中置信):经 Safari/PWA 上传时 iOS 可能先把照片/视频转码为「更兼容格式」,服务器收到的已非原件;应用侧不可控不可检(用户可手动在 iOS Photos picker 设 Format=Current 规避,不可绝对化表述)。跨生态佐证:Nextcloud forum #91672、nextcloud/server#30375、Apple Dev Forums #743049。
   来源:docs.photoprism.app/user-guide/pwa/(Preserve Original Format When Uploading on iOS 小节)
4. **可安装 App 在 iOS 上也受不可绕过的平台硬约束**(3-0×3):Immich App(Flutter)是「前台 + 后台周期性」双机制,但 iOS 侧必须用户开启系统级 Background App Refresh,后台调度完全归 OS(机会式,App 无法控制何时运行);Ente 实证 force-kill 后 iOS 不再投递 silent push,后台链路断,只能手动重开。Apple 一手文档印证:BGTaskScheduler「app refresh tasks are not a way to get regular execution time」。
   来源:docs.immich.app/features/mobile-backup/、ente.io/faq/features/background/、developer.apple.com/documentation/backgroundtasks/bgtaskscheduler
5. **Android 自主度更高但非「装上即稳」**(3-0×2):Immich 在 Android 可暴露调度约束配置(仅充电时运行、拍摄→上传最小延迟,经 WorkManager;iOS 完全不可配);但 OEM 激进电池优化破坏后台 worker 是官方承认的「well-known problem」,需用户手动豁免(官方导流 dontkillmyapp.com;issue #26115 显示部分机型豁免后仍失败)。
   来源:docs.immich.app/features/mobile-backup/
6. **「可安装 App 是必要条件而非充分条件」**(3-0):即便有服务端 silent push 唤醒,Ente 官方也承认后台同步「isn't currently consistent on iOS and on certain Android devices」;而 PWA 在 iOS 连机制入场券都没有(无 silent push、无 Background Sync / Periodic Background Sync / Background Fetch;iOS 16.4+ Web Push 必须伴随用户可见通知)。
   来源:ente.io/faq/features/background/
   表述红线:「silent push 每次仅 30 秒窗口 + 服务端必须参与唤醒」1-2 被否决,不得作强结论引用。

**对 Scrollery 的直接推论**:纯 Web/浏览器客户端可完整覆盖**浏览/管理/搜索**场景;若要对标 Immich 级「相机胶卷自动备份」,必须投入可安装移动 App(Tauri 2 移动壳在本项目路线图内,方向吻合),且要按 iOS 机会式调度、Android OEM 豁免引导做预期管理——这是全行业共同天花板,不是实现质量问题。

### 3.2 架构先例:Spacedrive 与 rspc(已核实,附引用边界)

1. **Spacedrive 是 Tauri 生态「单一 Rust core + 多端客户端」最直接的结构先例**(3-0×4):v2 采用 daemon–client 分层(headless daemon 承载 core:library 数据库、索引/同步/分析后台任务、RPC 接口);核心为单一 Rust crate(CQRS/DDD),每个操作注册为类型安全 action/query 并**自动生成 TypeScript 类型**;同一引擎在 monorepo 支撑五形态——apps/tauri(桌面三平台)、apps/mobile(React Native)、apps/cli、**apps/server(headless,实体工程:Dockerfile + docker-compose + TRUENAS_SETUP.md + SD_AUTH 多用户认证,GHCR 有容器包)**、apps/web(浏览器);README 把 desktop / headless server / hosted file service / embedded API 并列为同一产品的部署形态;v2.0.0-alpha.2(2026-02)实发桌面三平台安装包 + sd-server tarball + web tarball。
   来源:v2.spacedrive.com/core/architecture、overview/self-hosting、github.com/spacedriveapp/spacedrive
   **引用边界(必须随附)**:此为「架构结构可行性」证据,**不是**「生产级成功」证据——原 12 人/$2M 团队解散后单人 clean-room 重写(2025-06 起),alpha.2 自述 "many features are NOT working",移动端从未上架应用商店,最后 push 2026-04-19(距今约 3 个月静默)。
   表述红线(0-3 否决):不得宣称其客户端是「无业务逻辑薄 UI」;不得宣称其「无开箱远程访问形态」(apps/server 有 Docker+SD_AUTH+TrueNAS 指引);不得引用「38.6k stars / release 停在 0.4.3」旧数据(v2 alpha 系列 2025-12 起已发布)。
2. **Spacedrive 移动路线揭示「拆分」存在两条正交路线**(3-0):它不做「瘦客户端连远程服务器」,而是**把整个 Rust core 嵌进移动 App**(FFI),手机自行索引、自建 SQLite(SeaORM)、与其他设备 leaderless P2P 对等同步(可无桌面独立运行);相机胶卷备份是「备到网内任意对等设备」而非上传中心服务器;cloud 只是无特权普通节点。与 Immich 式 server-first 瘦客户端相反。→ Scrollery 拆分设计的第一个路线抉择(见 §4/§5)。
   来源:v2.spacedrive.com/core/architecture("iOS and Android apps embed the entire Rust core directly in the application binary"、"Every device functions as an equal peer")
3. **rspc 验证了 client 侧「类型化 API + 可插拔 transport」模式,但其本身不可选型**(3-0×3):前端 `createClient<Procedures>({ transport })` 把 transport 作为构造参数注入,`@rspc/tauri` 的 TauriTransport 与 `@rspc/client` 的 FetchTransport(HTTP)/ WebsocketTransport(subscriptions)共用同一类型面——「桌面走 Tauri IPC、Web 换 HTTP/WS」在客户端 API 层可无缝切换。但 rspc 处弃用/停摆:全站弃用横幅导流 specta.dev(新文档 1.0.0-rc alpha)、最新稳定 tag v0.4.0(2025-01)、维护者 2025-03-12 公告无限期退出并自述「the Tauri integration is broken, the documentation is a mess」。→ **模式可借鉴,依赖不可接**;Scrollery 宜自研薄 transport 抽象(本仓已有 `invokeIpc` 单入口 + harness 分流先例,见 §2.1)。
   来源:rspc.dev/client、rspc.dev/integrations/tauri、github.com/specta-rs/rspc/discussions/351
   表述红线:rspc server 侧「request context 抽象 transport」1-2 否决;「官方 Tauri 集成当前可用」0-3 否决。

### 3.4 部署形态与运维口碑:单二进制+SQLite vs compose 重栈(定向补证,2026-07-11)

**两方官方立场**:

- **Immich(重栈)**:官方唯一安装方式 = Docker(含 Compose plugin),非 Linux 系统 "strongly discouraged";RAM 最低 6GB / 推荐 8GB(4GB 须关 machine learning),CPU 2–4 核;Postgres 数据文件(典型 1–3GB)必须 "local SSD storage, **never a network share**"——对 NAS 用户是显性约束。官方 compose 由 **4 个容器**组成:`immich-server`、`immich-machine-learning`、`redis`(镜像实为 valkey:9)、`database`(Postgres 14 + VectorChord 向量扩展)。人气佐证:107,267 stars(2026-07-11 GitHub API 取数)——重栈并未妨碍其成为品类第一。(docs.immich.app/install/requirements、官方 docker-compose.yml)
- **PhotoPrism(轻栈)**:数据库 SQLite 3(默认)+ MariaDB 10.5.12+(生产推荐;官方只按「是否需要 scalability」划分,**无数字阈值**);安装面广——compose、单容器、Linux 裸机包、FreeBSD ports、树莓派镜像、多家 NAS 渠道;最低 2 核 / 3GB RAM。(docs.photoprism.app/getting-started/)

**用户口碑(抱怨面,一手帖)**:
- 「I wanted to like Photoprism because unlike Ente and Immich, it supports SQLite databases and doesn't require postgres (**I want to keep home lab maintenance to a minimum**)」(Ask HN 2025 自托管照片栈帖,230 分;news.ycombinator.com/item?id=44428119)
- 「**I just wish it didn't need Postgres and SQLite was an option.**」;同串点出技术根源:Immich 用 pgvector 向量扩展做搜索,「so it's not as easy as changing the db engine」(Immich HN 主题帖 565 分/205 评;news.ycombinator.com/item?id=45165684)
- **server/mobile 版本锁步**:「we don't have to update our server version every couple of days/weeks because otherwise **the mobile app stops working**」+「dependency bumps needed every few days」(同上)
- 「I don't want to have to deal with keeping up with patch notes and potential breaking changes」(lemmy.world/post/2435666)
- Postgres 运维负担实例:《Latest update breaks Postgres》讨论——升 v2.5.0 后库报 "invalid page in block" 损坏,维护者答复「restore from backup」,且向量扩展另有强制迁移链(公平性注:维护者判定损坏源于硬件/环境而非该次升级)(github.com/immich-app/immich/discussions/25824)

**反方 counterpoint(同样一手)**:
- 「**Why is docker compose a red flag? That feels like a benefit to me.**」;「My personal experience is zero maintenance (other than updating docker container) since deployment several years ago」;「I run it in a container on my synology NAS which has no GPU at all」(HN 45165684)
- 「Immich is now with 32k assets for me, working flawlessly and only using 300MB when active」;同帖反向抱怨 PhotoPrism「still occupies about 50% CPU routinely」——**轻栈 ≠ 轻负载**(lemmy.world/post/2435666)
- 双跑评测(empty.coffee,现址 mike.lapidak.is):PhotoPrism「a challenge to set up, with a plethora of settings that must be tweaked」,整体倾向 Immich,但点名其「the mobile app and server must run on the same version」

**小结**:抱怨聚焦三点——① Postgres+向量扩展不可替换,想要 SQLite 的用户无门;② server/mobile 版本锁步 + breaking changes 追更压力;③ NAS 上 6GB RAM、DB 必须本地 SSD 的资源脚印。反方证明 compose 本身不是普遍障碍、维护可以近零。→ 对 Scrollery 的空档判断与「版本锁步是前车之鉴」见 §5。

**远程访问与认证(生态实际做法)**:

1. **Immich(功能最全的参照)**:reverse proxy 给出 Nginx/Caddy/Apache/Traefik 四例,要求转发 Host/X-Real-IP/X-Forwarded-*、必须域名根部署(不支持子路径)、`client_max_body_size 50000M` + 关请求缓冲、websocket upgrade、Traefik 读/空闲超时 600s(否则上传 1 分钟即断)——大文件上传与实时通道是反代配置的两大雷区。OAuth 支持 OIDC(Authentik/Authelia/Okta/Google/Keycloak 五家示例),含 auto register、claim 映射角色/配额、backchannel logout,以及**移动端 redirect URI `app.immich:///oauth-callback`**(移动 App 接 SSO 需自定义 URL scheme,先例已备)。官方暴露立场:Remote Access 指南三选项 VPN(OpenVPN/WireGuard)/ **Tailscale** / reverse proxy,明确警告 "Never forward port 2283 directly to the internet",且自陈活跃开发期「不能排除严重安全漏洞的存在」——**官方倾向 VPN 优先,公网反代是便利换风险**。(docs.immich.app/administration/reverse-proxy/、/administration/oauth/、/guides/remote-access/)
2. **PhotoPrism**:内建 auth(`PHOTOPRISM_AUTH_MODE`=password 默认/public 不建议外网)+ 多用户角色;OIDC SSO 有配置项但部分能力(domain 校验、自定义 role、Entra ID 组)标注 pro/team 层级,且前提是 HTTPS;TLS 官方推荐 Traefik 反代(此时 `PHOTOPRISM_DISABLE_TLS=true`)或内建 TLS(自签/自备证书)。(docs.photoprism.app/getting-started/config-options/、/getting-started/using-https/、photoprism.app/pro/kb/openid-connect/)
3. **Ente self-hosted**:museum server + Photos/Albums/Auth 三 web 服务,compose 一键(1 GB RAM / 1 CPU 起步);认证走 E2EE 语义下的 **SRP(4096-bit)**——Argon2id 派生 loginKey,服务器全程不见密码;未见官方 OIDC/外部 SSO 文档(未查证)。(ente.com/help/self-hosting/、ente.io/blog/ente-adopts-secure-remote-passwords/)
4. **Tailscale「什么都不暴露」模式**:双端装 agent 即可 NAT 后直连 p2p WireGuard;**Serve** 仅 tailnet 内共享,**Funnel** 经 relay 发布公网(relay 不解密流量);Immich 官方文档本身即推荐此路线。(docs.immich.app/guides/remote-access/、tailscale.com/kb/1223/funnel)
5. **社区基线两条路径**:①reverse proxy + TLS(+ 可选 Authelia/Authentik 这类 SSO/2FA 前置层);②VPN-only(Immich 定位为「即使应用自身有漏洞仍有保护层」的最稳选项)。(authelia.com/overview/prologue/introduction/、docs.immich.app/guides/remote-access/)

**对 Scrollery 的直接推论**:(a) 服务端打包策略以「官方 Docker 镜像 + compose 文档」为轴心即可通吃四大 homelab 目录与 Synology/QNAP 容器路线,原生 SPK/qpkg 商店可后置甚至不做;(b) 单二进制形态的价值在裸机/低配 NAS 与「无 Docker 心智负担」,不在渠道准入;(c) 认证最小集 = 内建账号体系 + 反代兼容(Forwarded 头/websocket/大上传),OIDC 是进阶生态标配可分期;(d) 官方姿态可效仿 Immich:默认推荐 VPN/Tailscale,公网暴露给出反代硬要求清单并如实提示风险——与本项目「诚实叙事」原则一致。

### 3.6 架构参照补充:Jellyfin 与 VS Code Server(定向补证,2026-07-11)

- **Jellyfin——「单 server 自带 Web UI + 文档化 API 养活客户端生态」的成熟形态**:server 基于 .NET(全平台);**web 客户端默认内嵌于 server**——单进程同时托管 API 与 Web UI 静态文件,浏览器直连 8096 一个端口即用(7359/udp 仅发现),对 NAS 反代极友好;同一 jellyfin-web 前端复用为桌面浏览器/Android/iOS 多端外壳;客户端生态 = first-party + third-party,后者基于文档化 OpenAPI REST(api.jellyfin.org)构建;auth 为内建本地账户(首启向导建管理员,无强制云账号)+ Quick Connect 短码授权(适配 TV 等弱输入设备);NAS 分发以「官方容器 + 社区打包」为主,FreeBSD 因 .NET 不兼容明确不支持。(jellyfin.org/docs/general/about、github.com/jellyfin/jellyfin、github.com/jellyfin/jellyfin-web、api.jellyfin.org、jellyfin.org/docs/general/server/quick-connect/)
- **VS Code Server/Remote——「桌面应用内建 client-server 分离」的最大规模先例**:同一 UI 在本地/远端后端间透明切换(官方 FAQ:「moving the execution of certain commands to a 'remote server'」);扩展体系被切分为 UI extensions(本地跑)与 Workspace extensions(远端跑)——即**能力按归属分层,而不是整体二选一**;vscode.dev 纯浏览器零安装,但 terminal/debugger 须经 Remote Tunnels 接远端 compute;`code serve-web` 可起浏览器可访问的 web 版(2026-07-11 本地 CLI 实证;该命令在官方文档站的专述页未查证)。(code.visualstudio.com/docs/remote/vscode-server、/docs/remote/faq、/docs/setup/vscode-web)
- **类比锚点**:Jellyfin 证明 server 形态的产品结构(内嵌 Web UI、单端口、API 契约),VS Code 证明「同一 UI、后端可换位」的交互契约与能力分层法——两者相加,恰是「Tauri 桌面壳与 NAS server 共用同一套 Vue UI」的先例支撑。

## 4. 业界共性模式与路线分叉

### 4.1 反复出现的共性模式

1. **「server 持库 + 内嵌 Web UI + 文档化 API」的单服务形态**:Jellyfin 单进程单端口默认同时托管 API 与 Web UI(§3.6);Spacedrive apps/server 为一等部署形态(§3.2);浏览器客户端零安装即用,移动/桌面客户端走同一 API。
2. **移动端 = 专门的可安装 App,PWA 不承担备份**(§3.1,三票核实);且 App 与 server 的版本兼容是长期运维面——Immich 的 server/mobile 版本锁步是被反复点名的痛(§3.4)。
3. **重活与请求路径分离**:Immich 把 machine-learning 独立成容器(§3.4 官方 compose);ML 放置存在「进程内 / 独立容器 / 端侧」三型谱系,派生资产则以「预生成为主、按需为辅」为通例(§3.3 小结 ③④)。Scrollery 的进程外 worker 结构(§2.1)与「独立容器」型零结构阻力,现有缩略图/封面预生成缓存链(§2.1)与业界通例同型。
4. **认证分层**:内建账号体系打底(Jellyfin 首启向导、PhotoPrism AUTH_MODE、Ente SRP),OIDC 对接自托管身份生态(Authentik/Authelia/Keycloak)是进阶标配;官方姿态普遍「VPN/Tailscale 优先,公网反代自担风险」(§3.5)。
5. **分发以 Docker 镜像为轴心**:四大 homelab 目录准入 = 镜像 + 一层元数据;Synology/QNAP 实践路线同为容器(§3.5)。单二进制/裸机是加分项而非门票——但 HN 口碑证明「想要 SQLite、把 homelab 维护降到最低」的用户群真实存在且现无人服务好(§3.4)。

### 4.2 路线分叉:拆分设计必须先答的两道题

**分叉一:server-first 瘦客户端 vs local-first core 下沉 + P2P 同步**

- Immich/Jellyfin 路线:库在 server,客户端不持库、只做缓存;成熟、简单,与「NAS 持库、多端访问」的目标场景一一对应。
- Spacedrive 路线:整个 core + 库嵌进每个端,leaderless P2P 对等同步(§3.2,三票核实);适配「多设备各有本地库」的文件管理语义,但同步引擎是全新的大工程,且该项目自身未达生产级(引用边界见 §3.2)。
- **本报告判断**:Scrollery 的目标场景是 server-first 语义;桌面单机版继续是 local-first 单节点。两者共享同一 Rust core,是**同一 core 的两种宿主**,而非两种产品。「跨设备库同步」(桌面库 ↔ NAS 库双向同步)是第三种语义,不应与本次拆分捆绑立项——列入 §7 开放问题。

**分叉二:client transport 双实现 vs 全端归一 HTTP**

- 方案 A——前端 transport 抽象双实现:桌面继续走 Tauri invoke + asset protocol(零回归),web/remote 走 HTTP/WS。client 侧「类型化 API + 可插拔 transport」模式已被 rspc 验证成立(§3.2);本仓 `invokeIpc` 单入口 + S0 harness 分流就是现成的缝(§2.1)。
- 方案 B——桌面壳也改走 localhost HTTP(Jellyfin/VS Code serve-web 的彻底形态):协议单一、测试面单一、桌面天然「自带 server」;代价是 179 命令一次性大手术,且 asset protocol 的本地流式性能、Channel 低延迟等桌面路径需重新评估。
- **本报告判断**:分阶段——先 A 后评估 B。A 让 web 形态以增量方式落地、桌面零风险;若维护双 transport 的成本随时间上升,再在数据支撑下评估归一(§6 阶段划分)。

## 5. Scrollery 可行性评估

### 5.1 总体判断

**结构上可行,且起点显著好于业界通常情形**:

- 前端改造面天然收敛:全库 179 命令调用走 `invokeIpc` 单入口、错误已是稳定 code 契约、事件/窗口各有中央包装,S0 harness 已实证「真实 App/stores/MediaGrid 在非 Tauri 宿主挂载」(§2.1)。
- 后端纠缠呈漏斗形:`AppState` 传输无关,`AppHandle` 只线程化到 13 个文件(emit/dialog/path),重活已在进程外 worker(§2.1/§2.3)——加 axum 宿主是「加壳」不是「动骨」。
- **部署形态空档真实存在**:rusqlite 单文件 + workspace 分层 → 「单容器/单二进制 + SQLite」形态,Immich 做不到(pgvector/VectorChord 锁死 Postgres,官方明言 SQLite 无门),PhotoPrism 有形态但能力面与体验被口碑诟病(§3.4 三痛点)。公平陈述:轻量位并非无人——Photoview/Damselfly/HomeGallery 均为 SQLite/无外部 DB 的轻形态(§3.3),但能力面与移动端都远薄(无官方 App、ML 能力有限)。空档的准确表述是「**轻部署形态 × 完整能力面 × 桌面级体验**的组合」无人占据;这是部署形态判断,不等于能力面对标——Immich 的多用户/分享/ML 搜索成熟度是多年积累,宣称口径按「持续约束 E」的诚实叙事执行。

**但可行 ≠ 便宜**。确定性工作量(§2.4「厚」档):Linux 媒体后端(WIC/Media Foundation 均 Windows-only,FFmpeg feature 仅占位)、认证与多客户端会话、资产 HTTP 化、插件许可部署模型、服务器发布管线、移动 App(若要自动备份)。

### 5.2 推荐架构形态

1. **新增 `scrollery-server` 宿主 crate**(workspace 平级成员):axum(HTTP + WebSocket)+ 复用同一 `scrollery_lib`。命令层函数体已是「编排 + `Arc<AppState>`」形态(§2 抽样),axum handler 与 tauri command 可同源(手写镜像/宏/build 脚本代码生成——机制在阶段 1 spike 中定,不预设)。
2. **事件抽象**:域模块的 `AppHandle.emit` 改为注入 `EventSink` trait——桌面实现 = Tauri emit,server 实现 = WS broadcast;13 个文件机械替换(§2.3)。5 处 `Channel` 流改为 WS 消息按请求 id 关联。
3. **资产端点**:`/assets/…` 系列(缩略图/原图/视频/音频/文档),视频音频支持 Range;替代 asset protocol。前端 `resolveAssetUrl` 宿主感知;~10 个返回绝对路径的命令改返回不透明 id/相对 URL(§2.2)。
4. **前端 transport**:`invokeIpc` 增加 http 分支(沿 S0 harness 同一缝);`useTauriListen` 底层可切 WS 订阅;桌面动作命令(open_directory 等 8 个)按 capability 声明在 web 端降级/替换(「在资源管理器显示」→「下载」)。
5. **单二进制故事**:前端 dist 经 rust-embed 内嵌 → 一个可执行文件 + 一个 SQLite 文件 + 一个缓存目录;官方 Docker 镜像打包同一二进制,compose 文档即分发面(§3.5)。
6. **typegen 随拆分引入**(ts-rs 或 specta):双传输面下手工镜像的漂移风险翻倍,治理时机正确(§2.2)。
7. **认证**:内建账号(argon2 派生 + session token)起步,反代兼容(Forwarded 头/WS upgrade/大上传)按 Immich 雷区清单自检;OIDC 分期;文档姿态 = Tailscale/VPN 优先(§3.5)。
8. **版本锁步前车之鉴**:API 版本协商 + 兼容窗口从第一天进设计(§3.4 口碑)。

### 5.3 桌面语义命令的处置原则

- `system_commands` 8 个(打开目录/资源管理器/壁纸/剪贴板):按「服务器是谁的桌面」逐一裁决——web 端禁用或语义转换,桌面端不变(§2.3)。
- `plugin-dialog` 选目录 5 处:web 端换服务端目录浏览 UI(业界通行,§2.3)。
- DocThumbRenderer 客户端渲染回传环:浏览器客户端天然兼容(pdfjs 在 web 更自然),保留;服务器 headless 渲染列为后备优化。
- 移动卷/VolumeOffline:语义在 NAS 场景仍成立(服务器外接盘),文案适配即可。

### 5.4 移动端策略(按 §3.1 硬约束)

1. 第一步:响应式 web(手机浏览器)覆盖浏览/搜索/管理——零额外工程面,PWA 可安装到主屏。
2. 第二步:Tauri 2 移动壳复用同一 Vue 前端 + remote transport——「可安装 App」达成,浏览管理体验原生化。
3. 第三步(若要对标 Immich 自动备份):iOS BGTaskScheduler / Android WorkManager 的原生后台任务集成(Tauri 移动插件或伴生轻 App),并按业界共同天花板做预期管理:iOS 机会式调度 + force-kill 断链、Android OEM 豁免引导(§3.1)。**此步成本最高、且上限被平台锁死,立项前单独评估。**

## 6. 路线建议(阶段划分,每阶段独立有价值、可停)

- **阶段 0——收口纪律(零成本先行,随日常开发)**:新代码不得绕过 `invokeIpc`/`resolveAssetUrl`/`useTauriListen`;既有 5 处 `convertFileSrc` 直连、`scanStore` 2 处 `listen` 直连收口进包装;新命令避免返回绝对路径。不引入任何新形态,纯降低未来拆分成本——与 UI 重构线的 S0 harness 资产天然协同。
- **阶段 1——验证性 spike**:axum 宿主 + 只读子集(布局/缩略图/原图查看)+ 局域网浏览器访问。目标:实测资产 HTTP 化与 `compute_layout` 等重命令在真实库上的表现;验证「同一前端双宿主」端到端;定下命令镜像的代码生成机制。产出物即扔亦可,结论进设计。
- **阶段 2——可用的局域网 server**:全命令面镜像(桌面语义命令按 §5.3 处置)+ WS 事件/流 + 内建认证 + Linux 媒体后端(CPU 解码兜底先行、FFmpeg 视频派生落地)+ Docker 镜像与 compose 文档 + 单二进制发布。
- **阶段 3——生态与移动**:homelab 目录上架(Unraid/Umbrel/CasaOS/TrueNAS,按 §3.5 准入清单)+ Tauri 移动壳 remote 模式 + OIDC + 备份能力(先「App 内前台手动/Wi-Fi 下上传」,后台自动备份按 §5.4 第三步单独立项)。

## 7. 风险与开放问题(待拍板)

1. **多用户边界**:server 形态是否永远「单户家庭」?多账号/分享是 Immich 需求大头,但会把 auth/DB/隐私面全部复杂化——建议 v1 明确单用户多设备,多用户列路线图。
2. **插件/许可部署模型**(与 Part6/Part8 商业线联动):license token 现存 OS keyring、信任根编译进二进制、entitlement 假设端侧验证(§2.3)——server 部署下「谁持有授权」(server 持照供全家 vs 每客户端持照)是商业条款问题;headless/容器内 keyring 不可用,需 file-based secret 方案。
3. **SQLite 并发上限**:读已池化(8 连接),写单连接串行——单户多设备的写频率(收藏/评分/相册)大概率够用,但需在阶段 1 spike 实测;不预设换库。
4. **Linux 媒体性能**:服务器上无 WIC/Media Foundation/DirectML,缩略图与视频派生回退 CPU 路径的吞吐需实测(NAS 低功耗 CPU 是最差情形);ORT 的 EP 策略(CPU/CUDA/ROCm)另评。
5. **跨设备库同步**(Spacedrive 语义)明确不在本次范围;若未来立项,是独立的同步引擎工程。
6. **安全面**:资产端点的路径界定(现有 `normalize_db_path`/UNC 规约是基础,§2.3)、上传链路的防御、纯 web 下 CSP 重新收紧、更新器与 server 升级的分轨。
7. **Windows server 形态**:少数用户会想在 Windows 主机跑 server(现有 WIC/MF 后端反而是优势)——单二进制 Windows 版成本低,可顺带,但支持矩阵扩一格是长期承诺,需拍板。
8. **API 兼容承诺**:一旦有独立客户端,命令契约从「仓库内私有」变「跨版本公共」——版本协商、废弃周期、契约测试都要建制度(Immich 锁步之痛,§3.4)。

## 8. 结论

- **可行性:成立**。本仓的传输耦合面收敛、核心纠缠浅、worker 已进程外、SQLite 形态匹配 NAS 场景;业界有完整先例链(Spacedrive 证结构、Jellyfin 证产品形态、VS Code 证交互契约、rspc 证 client 模式)。
- **分水岭清单**:①移动自动备份必须可安装 App 且受平台硬约束(全行业天花板);②Linux 媒体后端是最大确定性工程;③插件许可的部署模型是商业问题先于技术问题;④「跨设备库同步」不要与本次拆分混为一谈。
- **建议**:按 §6 阶段推进,阶段 0(收口纪律)可立即生效,阶段 1 spike 作为立项决策的实证输入。本报告未立施工项,待用户拍板。
