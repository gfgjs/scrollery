# Canvas 密集缩略图性能分析与优化方案

> 同日后续实施：A调度/回退/指标、B窗口对齐、C1稀疏选档已分批落地；本文保留实施前分析快照，现状与真实库结果见[实施与真机验证](../reviews/2026-09-12-Canvas密集缩略图优化实施与真机验证.md)。§8.1关于多档GC保活的顾虑已按现行代码修正。

分析阶段仅产出方案，未修改产品代码或运行真实库写入/缩略图重生成。证据基于 2026-09-12 分析时工作区，包含当时其他会话尚未提交的后端变更。当时没有新增目标机实测，本文的收益与参数均须按验收方案裁决。

分析结论：可以优化，优先对象是加载调度和提前准备，而不是先重写 Canvas。实施前代码确认三类问题：快滚可能取消仍有效的预取、正常滚动缺少跨帧可见优先保证、行数据窗口不保证覆盖位图预取窗口；稀疏多档选档还可能继续使用过大的源。当时尚不能给出各自对用户症状的贡献比例。单纯减小缩略图、扩并发或加内存都不是完整解法。

## 1. 问题与结论边界

用户场景：4K 全屏、64px 格子、同时可见 1500+ 缩略图，滚动明显经历占位符到真图的替换；即使生成 64px 图仍可见，256/512px 源更慢。目标是降低图片入屏后的等待，并保持滚动帧健康。

必须分别记录三个尺寸：格子的 CSS 尺寸、DPR 换算后的显示像素尺寸、服务实际返回的缩略图尺寸。不能用 4K 面板分辨率直接代替 CSS 视口面积，也不能只凭设置中的生成尺寸断言每个请求的实际选档。

“磁盘文件存在”“浏览器响应/系统文件缓存热”“Canvas 位图 LRU 热”是三种不同状态。完整热缓存滚动、已生成文件的位图冷滚动、未生成项首览必须分开测。正常滚动只需要提前补齐新进入的条带，不应等价于每帧重新加载 1500 张；若回滚同一区域也重复冷加载，应另查淘汰、规格变化、失活/重挂载与取消。

## 2. 成本模型

以下是数量级估算，不是本机实测，方形图片按 RGBA 4 字节/像素计算。

| 方形源边长 | 单图像素 | 1500 张的累计像素 | 对应累计原始像素字节 |
|---|---:|---:|---:|
| 64 | 4,096 | 6.14 MP | 23.4 MiB |
| 256 | 65,536 | 98.30 MP | 375 MiB |
| 512 | 262,144 | 393.22 MP | 1500 MiB |

这里是处理一屏图片所涉及的累计像素量，既不是压缩文件大小，也不是同时驻留内存、实际显存占用或耗时倍数。源图变大增加读入/解码/转换成本的可能性；64px 图仍保留逐图请求、调度、对象与回调开销。

以 1500 个冷格、64 个在途槽为简化模型，完整覆盖需要约 24 轮等效槽位服务量（真实完成过程连续，不是同步批次）。若测得饱和状态每槽平均服务时间为 10/30/60ms，则 N×L/C 的理想持续吞吐估算约为 0.23/0.70/1.41 秒。真实浏览器可能受更低的内部并发、主线程与呈现约束影响，不能把 64 槽当成 64 个并行解码核心，也不能用这个公式预言扩槽收益。

稳定滚动的补图需求可近似为 λ = 可见图片数 N × 速度 v / 视口高度 H。例如 N=1500、v=一屏/秒时，需要约 1500 张/秒的持续就绪吞吐。预取只有在长期就绪吞吐能覆盖需求、且提前量覆盖排队与服务时延时，才能让新图入屏即显示；盲目扩大窗口不能解决吞吐不足。

## 3. 绘制路径核实

- `MediaGridCanvas.vue::draw` 已用 `visibleRowRange` 二分定位可见行，非每帧遍历全库；单 Canvas 与单例 DOM 悬停卡已经落地。
- 每次 draw 会清整屏、同步可见项选中快照、逐格绘制，并在尾部推进预取。`scheduleDraw` 已按 rAF 合并，因此多个位图完成不等于每张各执行一整次绘制。
- `mediaGridCanvas.cellRenderer.ts::drawCell` 普通格也有三层 save/restore、占位底色、图片与内描边；compact 已跳过多种信息覆盖层，基础非选中态也已跳过圆角 clip。
- `SelectionAnimTracker.sync` 每次 draw 创建可见项 Map，且每格 getImage 会参与加载与缓存访问。这些是可定位的热点候选，尚无本轮证据说明它们主导换图时延。
- `gallery.draw` 是 JS 调用区间，不能代替浏览器光栅化、合成与实际帧健康。旧实验出现过 JS draw 更快但帧率更差，应同时看两者。

## 4. 加载、缓存与预取：当前证据

### 4.1 实际链路和既有机制

已生成文件的链路为：行 item 携带 thumbPath → `buildThumbUrl` → scoped asset protocol → fetch/blob → 源 ImageBitmap → 裁剪/可选缩小 ImageBitmap → 提交 LRU → rAF 绘制。

Canvas 复用 `useThumbLoader.ts` 的 URL 构造函数，但不使用该 composable 的逐图 `img.decode()` 加载状态机。`useRequestQueue` 的 50ms/24 项批处理用于未生成项/无路径直显项的生成或路径解析，不是健康已生成缩略图的字节加载队列。单例 DOM 悬停卡另有 DOM 加载路径，不能归因为 1500 格都走该路径。

| 机制 | 当前值/行为 | 源码定位 |
|---|---|---|
| 位图在途总量 | 每个 pipeline 实例 64；可见和预取共享；包括 fetch、blob、bitmap 准备 | `useCanvasThumbPipeline.ts:51,122,142` |
| 已提交位图缓存 | 12,000 条 / 512MiB 双约束，Map LRU | `useCanvasThumbPipeline.ts:43,47`；`canvasThumbState.ts:113,141` |
| 位图输出尺寸 | 格高×DPR 选 64/96/128/192/256/384/480 高度桶，再按格纵横比裁剪；只缩不放 | `mediaGridCanvas.helpers.ts::bitmapBucketH/bitmapPrepParams` |
| 开闸位图预取 | 前 1.25 屏、后 0.5 屏；1500 可见格对应预算 1875/750 项 | `useCanvasThumbPipeline.ts:325`；`mediaGridCanvas.helpers.ts:121` |
| 关闸位图预取 | 前 1.25 屏、后 0；已存在 URL 的可见项仍可加载 | `useCanvasThumbPipeline.ts:122–134,327,493` |
| 预取推进 | draw 尾最多 16 个新启动/1ms；idle 最多 64/2ms，timeout 80ms；仍受 64 在途约束 | `useCanvasThumbPipeline.ts:328–332,417,454` |
| 重绘与计划 | 完成后 scheduleDraw；currentY 变化取消旧迭代计划并按新位置重建，非直接清空 LRU | `useCanvasThumbPipeline.ts:222–226`；`MediaGridCanvas.vue:525` |
| 规格更新 | 数据签名变则硬失效；只变尺寸/纵横比规格时旧位图续画并更新 | `useCanvasThumbPipeline.ts:106–120` |

缓存按输出图尺寸计费，不能把 1500 张 512px 源的累计解码字节直接算成 LRU 占用。以方形格、足够大的源、DPR=1/1.5/2 为例，输出 64/96/128px 每屏约 23.4/52.7/93.8MiB；64px 源不被强制放大。12,000 项最多约 8 个 1500 格视口，较高 DPR/宽图会先碰字节限制；还要扣除前后预取和其他访问。此量级不足以断言“同一屏因缓存太小反复淘汰”，也不能保证任意距离回滚仍热。Blob、在途 full/out 位图、浏览器原生对象与 GPU 资源不在该字节账本中。

### 4.2 优先修正的调度语义

**S1：快滚时取消量按全部可见格数计算，可能取消仍有价值的前向预取。代码确定，发生频率与耗时贡献待测。**

`prioritizeVisibleThumbLoads` 只检查闸门关闭且槽满；随后统计 `visibleCount`（所有可见格），只保护正在加载且已可见的 ID，并要求为 `min(64, visibleCount)` 腾槽。它没有先判断可见项有多少真正缺图。

可成立的执行轨迹：1500 个可见格全部命中缓存；64 个在途任务全在前方、尚能取消；闸门关闭；一次 draw 到来。此时仍会尝试取消这 64 个前向任务。随后新的滚动计划又可以选择这些前方 ID，形成重复取消/读取机会；同一未重建计划也可能已越过被取消项，延后其重试。这是调度逻辑允许的结果，不是本轮已观测到的重复次数。源码：`useCanvasThumbPipeline.ts:233–267`。

**S2：开闸时缺少跨帧可见优先保证。代码确定，实际阻塞量待测。**

同一次 draw 内可见循环先于尾部预取，已有正确局部顺序；但 idle 可在两帧之间填满共享槽，新可见项只能等空槽。当前优先级函数在开闸态直接返回。只有完成回调安排重绘后才重试可见项，队列等待没有单独记录。

建议把 S1/S2 合为一套有界的需求调度：先识别真正没有可画位图且有可加载源的可见项，再安排近期会入屏的预取；已有 stale 可续画的规格升级靠后。开闸/关闸均用相同优先级原则。先利用空槽、保留即将入屏的有效请求；只有确需腾槽且任务已无近期价值时取消 fetch，不因“槽满”本身取消。进入 bitmap 准备后的不可取消任务继续占槽直到落定，不伪释放。

实现应沿现有 pipeline 收敛；候选集合有界并按 ID/数据签名去重即可，不必引入通用调度框架。不要只删除开闸条件，否则会把 S1 的过度取消扩散到正常滚动；不要一遇冷格就停掉全部预取，否则会持续消耗提前量。

### 4.3 数据窗口与位图预取窗口不共享边界

**S3：位图想预取 1.25 屏，不保证对应行数据已提供。代码确定，目标机影响待测。**

bucket 的请求边距为 `min(6000, 1000 + EMA速度(px/ms)×300)`，再按段取整；64px 行高的段高为 1280px。位图预取只能枚举已就绪的 mounted rows。理论上，若相关段都 ready 且不受库头尾裁剪，前向数据覆盖约为边距加 0 到不足一段的余量（实际行首归段还有边缘行影响），不能把整段取整余量当成稳定保证。

对 CSS 视口 H=2160、EMA≈0 的示例，位图目标 2700px，bucket 边距基线只有 1000px，连最大约 1280px 的额外段余量也不足以保证 2700px。慢速也可能不足；忽略取整时，需要 EMA 至少约 `(2700−1000)/300=5.67px/ms` 才由边距本身保证。H=1440 时需约 2.67px/ms。这里的 H 是 CSS 高度，4K 面板 DPR 不同会改变 H，不直接代入固定 2160。

速度 EMA 不会因时间经过自动归零，因此不能说每次停稳边距都回到 1000px；冷启动/速度尚低/程序化重置是需关注的条件。关闸前后图像窗口仍前向 1.25 屏；64px 行高的加载闸门速度阈值约 3.2/1.6px/ms，与数据窗口边距的尺度也不同。行级备用引擎 compact 缓冲约 256px、请求放大后约 307px/侧，同样不能支撑高视口的 1.25 屏预取。

段尚未 ready 时，`mountedRows` 不返回该段；可能出现没有布局项的空洞。这个症状与“有占位格但没有图片”必须分别计数，否则只看冷格数会把整段没行误当成无冷格。

建议先让数据窗口至少包含图像预取所需的几何范围，并为取行延迟留量，再统一根据滚动方向、速度与实测加载 P95 调整前向提前距离。第一步可只修两层窗口的最小覆盖契约，保留现有速度边距作为上限内补偿；不急于一次引入全套自适应控制。数据就绪距离、已启动图片距离与已可绘图片距离各自可观测。

### 4.4 缓存与绘制的后续顺序

优先验证当前窗口与短距离回滚是否命中，记录淘汰是条目数、字节数还是签名/生命周期失效，再决定可见/近前向保护范围及低端设备预算。以屏数和在途工作量控制预取，不先将 512MiB 全局翻倍。

若位图全热时仍掉帧，再做紧凑普通格快路径：减少无状态格的 save/restore 与重复状态设置，选区快照在选区版本或可见集合变化时更新。图片带透明通道时仍需正确底色，不可普遍删除占位底色；选中、离线、待删除与玻璃效果保持一致。

只在浏览器 trace 显示光栅/提交主导时，再考虑停稳补图的局部更新或行/块缓存。滚动时视口内所有内容都发生位移，普通 dirty rect 不会自动减少到“只有新入屏条带”；需额外的内容平移复用与失效模型。联合大路径 clip、全量 OffscreenCanvas/Worker 或 WebGL 重写均不作为首轮方案。

## 5. 已核实外部语义

`createImageBitmap(Blob)` 与 `createImageBitmap(ImageBitmap, crop, resize)` 的输入类型和处理含义不同，后者不能直接称为第二次源文件解码。标准定义裁剪/缩放及任务完成语义，但不能由此推断目标 WebView2 的具体线程数或 GPU 路径。[WHATWG HTML：ImageBitmap](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#the-imagebitmap-interface)

离屏缓存可减少重复绘制，但是否适用于本项目的滚动、选择动画、透明玻璃与缓存生命周期，需要独立评估。[MDN：Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)

## 6. 旧线索的适用范围

| 旧线索 | 本轮判断 |
|---|---|
| B1：DOM 深响应与逐格组件 | 不作为本轮 Canvas 主因；Canvas 已单画布、浅 watch、显式 patchTick。公共行源仍可能有代理成本，交由当前窗口证据判定。 |
| B2：增强事件触发布局重算 | 当前 `useGalleryTauriSync` 仍是 2000ms 尾随防抖，再走统一 requestCompute；不是严格每 2 秒周期重算。只在扫描/增强并行或布局事件确实发生时纳入归因。 |
| B3：404 懒自愈与布局失效 | 属于文件不存在/加载失败场景；不能解释健康的已生成文件普遍加载慢。先记录 404/失败率再决定是否单独修。 |
| B4：Canvas 全窗绘制 | 已二分定位可见行，仍整屏清除与逐格重绘；是帧健康候选，须看浏览器 trace，不能仅用 draw span 裁决。 |
| B5：超长滚动映射模式的 wheel | 应作为超长库和特定输入方式的对照场景，不与普通大小库的逐图供给混为一项。 |
| B6：computeLayout 的语义键与元数据 | 发生在布局计算路径，非每张已生成缩略图加载或每次 draw 必经；没有布局重算证据时靠后。 |

现有 2026-08-16 审查报告包含历史实测，但有三个边界：当时窗口尺寸/DPR/资源分布并非统一的本轮 4K 条件；热缓存单件与并发冷装载的耗时差不能唯一定位到应用的 64 槽限制；64→128 的扩槽实验未证明冷格改善，属于不采纳而非证明扩槽永远无效。新一轮应记录完整条件并配对比较。

## 7. 后续验收原则

### 7.1 基线条件

固定相同媒体 ID、排序、分组、视口 CSS 宽高、DPR、显示刷新率、WebView2 版本及构建类型。以本机 4K 目标条件为主，另在较弱机器复测；CPU 限速只能模拟部分计算压力，不能代表低端 SSD 和 GPU。

第一轮聚焦已有缩略图且无后台扫描/增强的图片集合，保持实际 1500+ 可见；控制变量测试源图 64/256/512，并记录服务实际返回尺寸和压缩字节。不能把设置写成 64 当成返回 64 的证据。

### 7.2 最小场景矩阵

| 场景 | 目的 | 必须记录的条件 |
|---|---|---|
| 目标路径已全部预热进位图缓存，原路往返 | 隔离绘制与是否重复淘汰 | 整条测试轨迹能否放进缓存、规格是否稳定 |
| 文件存在、位图缓存冷，连续慢滚/中速滚动 | 裁决预取和持续供给 | 建议 0.25/1/2 屏每秒，分别统计 |
| 同样位图冷，快速拖动至固定陌生区域后停止 | 测不可预测冷进入的恢复尾延迟 | 落点一致、首帧时间、50%/95% 出图时间 |
| 方向突然反转，滚出后立即回滚 | 识别错向预取与无效取消 | 命中、淘汰、重复读取和取消后已完成工作量 |
| 行数据段边界附近同速滚动 | 区分没拿到布局项与有项但没图 | 行覆盖、行请求延迟、实际位图就绪边界 |
| 最后补扫描并行、404、全选、玻璃、超长库映射 | 排除状态回归和条件性瓶颈 | 每种单独对照，不混入首轮主因实验 |

### 7.3 指标与裁决

- 主指标：图片进入视口到首次真图呈现的 P50/P95/P99；首次入屏即有位图的比例；冷跳转后视口达到 50%/95% 真图的时间。区分位图 ready 与实际呈现，精确呈现时刻需要浏览器 trace/画面采样，不能只把 Promise resolve 当成显示完成。
- 换图暴露：采样冷格数随时间的变化，计算 Σ(冷格数 × 持续毫秒)，并除以相应可见格数时间积分得到平均冷格比例。`coldCellFrames` 实际按 draw 调用累计，帧率/重绘频率变化会改变口径，不能单独跨方案裁决。
- 拆段：候选进入调度→启动、请求→响应头/字节完成、源解码、裁剪缩放、缓存提交→下一次 draw；另记后端排队、选档/文件检查、读文件。端到端计时覆盖所有分段，不用跨进程绝对时钟直接相减。
- 辅助：可见/预取在途与等待队列时间序列、源档位分布、有效提前量、缓存命中/淘汰原因、无效取消量；renderer/GPU/应用相关进程内存与浏览器 trace，不只 JS heap 或已提交位图字节。
- 护栏：按显示刷新率校准帧预算，同时对比 P95/P99 帧间隔、long task、draw 与原生内存峰值；检查图像裁剪、透明图、选中/离线/删除状态、缩放与 KeepAlive 回包所有权。
- A/B：同一区域、同实例可切换参数，明确每轮各层冷热状态；无法同实例切换时采用重启交错重复并控制页缓存，建议每臂至少 5 次。改动后的热身与冷测分开，不把 HMR 或重挂载后的 LRU 冷当成暖场景。
- 建议立项目标（并非已承诺收益）：普通连续冷滚的时间归一化冷格暴露量下降至少 50%，热路径保持接近零冷格；呈现时延尾部改善且帧健康、峰值内存没有超过测量噪声的明显回退。绝对毫秒目标等本机基线确定后再冻结；冷跳转不以绝对零占位作为验收要求。

### 7.4 现有工具的使用限制

`gallery.bitmapLoad` 在占到槽后才开始计时，记录于 finally；可包含成功、失败或中止，回退 Image 时该 span 也不等于回退完成时间。它不含候选等待启动的时间。此前“并发 37–101ms 相比串行 2–3ms，证明前端 64 槽排队主导”的推断不足，不能据此选择扩槽方案。

`gallery.prefetchedCells` 是当前计划的新增启动计数，不是完成数量，更不是预取距离或命中率；`cacheBytes`/`inFlightThumbs` 等摘要 gauge 主要提供最后状态，不能充当峰值或持续时间证据。应保留时间序列或累计分布。

`galleryPerfProbe.helpers.ts::summarizeFrames` 默认用 60Hz 的 25ms 掉帧阈值，当前调用未传刷新率；120Hz 下会漏记一部分 missed-vsync。应以按刷新率校准的 recorder 为主，并输出原始帧间隔。`scripts/bench/canvas-realapp-bench.mjs` 直接写 scrollTop，适合重复轨迹，但不能替代真实 wheel/触摸板/滚动条的手势链测试。脚本已被其他会话修改，本轮不改动或执行它。

## 8. 后端供给与源尺寸

### 8.1 选档不是自动生成多档

当前生成档位为 64/128/256/512/1024，生成任务写选中的一档；已生成项不会因显示成小格而自动补齐所有档。行载荷的选档需求为 `ceil(max(格宽,格高)×DPR)`；方形 64px 格在 DPR=1.5 时需求为 96，通常目标是 128 档。横图若格宽更大还会选更大的档。没有满足档时保留数据库记录的路径，因此也不能断言 DPR>1 时 64 档绝不会被读到。

**S4：稀疏多档集合下，现有选档没有逐项尝试下一个较大档。代码确定。**

`pick_serving_tier` 先按全局非空档目录选一个最小满足档，`prepare_with` 只检查该项的这一候选，`rewrite_path` 未命中即保留 DB 路径。例如需求 96，128 目录因其他图片而非空，本项缺 128、存在 256、DB 指向 512，实际仍回退到 512。源码：`thumbnail/serve.rs:137–155,184–195,206–219`。这与“没有小档文件”是两个问题，已有中间档也可能未被利用。

建议先把语义落实为“对该图片，选择实际存在的最小满足档”，在现有阻塞 prepare 阶段中进行有界的升序候选探测、同批去重与结果复用；保留无可用候选时的 DB 路径回退。权衡是稀疏目录下可能增加 stat，必须统计额外探测数与节省的源字节，不能把查档本身变成更重的滚动热路径。

第二步才是按需求补小档：在用户实际浏览/近期即将浏览且只有大档的项目中，低优先级生成合适小档，当前请求立即使用已有源，不等补档完成。初版复用现有按档编码与缓存写入，只增加有限的补档请求；保持图像质量、旋转、透明与缓存键语义，派生文件仍 tmp→同卷 rename。低性能设备在前台积压/帧健康恶化时暂停补档，不以一次重置全库生成状态作为方案。

如果选择从现有大缩略图降采样生成小档，可避免再次访问原始大图，但需要验证二次有损编码质量。2026-09-12 实施复核修正：现有 `reconcile_orphan_gc` 已按 `cache_key` 判活，删除路径也已枚举五档，有用的小档不会仅因不在 DB 的单一 `thumb_path` 中而成为孤儿；无需为多档保活额外迁移数据库或重做 GC。补档仍须处理前台积压时让路、换缓存根与清理/删除期间的落盘竞态。是否长期保留双档、额外磁盘预算及生成成本，应另行量化；当前不建议直接做全库存量回填。

### 8.2 小文件仍有逐请求固定开销

当前行数据从内存布局/条目缓存批量取得，健康已生成图片的每次字节加载不做逐图 IPC 或逐图 DB 查询。工作区版本 `serve.rs::prepare_offloaded` 已将选档目录探测与候选文件检查移到阻塞线程，并有 1000ms 档目录探测缓存；这是其他会话的现有修改，本轮不重复提出“把这部分挪出 async”的已完成方案。

图片字节则经 Tauri 内置 asset 协议，Windows 的 asset.localhost 是协议映射，不是独立 HTTP 服务进程，不能直接套用普通 HTTP/1.1 的六连接限制。

根 `Cargo.lock` 锁定 Tauri 2.11.4 / wry 0.55.1；本机对应 registry 源码显示：

- `tauri/src/protocol/asset.rs::get/get_response` 在 handler 内同步完成路径/作用域校验、open、metadata、MIME 探测和响应体准备。
- MIME 最多先读 8192 字节；小于 8192 字节的非 Range 请求复用已读缓冲，并非再整文件读一遍；较大文件先探测、rewind，再读取响应体。
- `wry/src/webview2/mod.rs` 的 WebResourceRequested 回调直接调用该 handler，响应通过 `SHCreateMemStream` 交给 WebView2。源代码可确认同步工作；其在真实滚动中对宿主事件循环的占用及与 renderer 帧延迟的相关性，仍需 trace。
- 该 asset handler 未显式声明 Cache-Control/ETag/Last-Modified；浏览器是否复用响应、系统页缓存是否热，需要实际记录，不能由缺少这些头推导“完全无缓存”。

这提供了“64px 仍可能慢”的具体供给链候选：图再小也要逐张经过授权、文件操作、协议回调、响应对象及位图准备。高性能 SSD 和显卡不能消除这些操作。尚无本轮数据判定它们与调度问题的耗时占比。

若 trace 证明该路径主导，下一步研究保持 scoped assetProtocol、convertFileSrc 和现有权限语义的有界异步供给/依赖层优化；先明确数据拷贝、事件回调和 IO 的分段成本。不要直接把健康图片改成逐张 IPC/base64，也不取消路径边界校验换速度。当前方案不改变项目硬约束。

## 9. 推荐执行批次与备选门槛

| 批次 | 工作 | 验证与交付 | 预计改动规模 |
|---|---|---|---|
| A：测量与调度 | 补等待/完成/呈现代理与冷格时间积分；修 S1/S2，按真实可见缺图和近期价值分配槽，不盲扩并发 | 增补调度表征测试；目标区段 A/B，报告重复取消量、入屏命中和帧健康 | 中：pipeline、helper、perf、聚焦测试 |
| B：对齐两层窗口 | 修 S3，布局行覆盖图像预取区间，优先验证固定覆盖契约，再按时延调提前量 | 段边界/高视口/慢滚/快滚/反向；区分行空洞和图片冷格；限制挂载量 | 中：两虚拟引擎与共享窗口输入 |
| C：利用合适源档 | 先修 S4 的稀疏选档；再以需要时补小档为独立实验，保留当前大档可立即显示 | 比较实际源尺寸、额外 stat、字节、生成与磁盘成本；禁止假设改设置就补齐现存图 | 选档较小；补档为中等跨层改动，已有 GC 支持多档保活 |
| D：实测命中后的降本 | 按 trace 选择 bitmap 转换、asset 同步供给、compact 绘制中的一项做隔离 A/B | 同区域、同缓存层冷热条件重复比较；不将几个变更混成一臂 | 随命中热点而定 |

批次 A 优先级最高，是因为存在具体错误取消条件、可见优先缺口和测量盲点，且能复用现有结构；不是声称其收益已被实测证实。A/B/C 每批交付独立完整行为并集中验证，避免并行改多个变量后无法归因。

针对复杂方案的裁定：

| 备选 | 可能改善什么 | 暂不作为首选的理由 / 重访条件 |
|---|---|---|
| 64→128/256 并发 | 减少应用侧等槽（只有内部供给仍有余量时） | 旧实验未证明收益；先看等待时间、实际服务并发和原生内存。可用 32/64/96/128 隔离 A/B，弱机可能需要更低并发。 |
| 跳过无必要的第二次 bitmap 转换 | 源已吻合时减少裁剪/复制/转换与中间对象 | 第二次不是再解压源文件；需保裁剪和颜色/透明语义。旧单段实验未改善冷区，按新分段指标命中后再试。 |
| 降低 resize/smoothing 质量 | 缩放成本 | 改变画质，且缓存预缩小后未必是热点；仅在匹配源尺寸后仍需大量缩放时对照，不设为默认降质策略。 |
| Worker / OffscreenCanvas | 主线程提交或计算 | Blob bitmap 本就有异步 API；搬 Worker 不自动解决文件请求和吞吐。需证明主线程占用而非等待主导，并处理交互与资源所有权。 |
| 打包文件 / atlas | 若单文件操作或逐图解码任务固定成本主导，可能减少请求/对象数量 | 包式存储不等于 atlas：前者可减少文件操作但未必减少逐图解码；后者合并纹理/解码单位但提高过取、局部更新和淘汰成本。动态排序不适合按当前可见行永久拼包。还涉及缓存引用、删除、自愈、版本与跨平台，留到轻量方案后的结构性实验。 |
| 脏矩形 / 行块复用 | 已加载画面的重复绘制 | 不解决图片未 ready；滚动需要内容平移和额外失效逻辑。位图全热仍掉帧且 trace 命中才做。 |

### 9.1 下一轮必须补的行为测试

调度：快滚+槽满+可见全热时不取消有效前向预取；真实可见缺图只腾必要槽；开闸时新可见优先；方向改变/远跳清理过期候选；不可取消解码保持实际在途账本，旧代回包不串图。

窗口：64px 行高、高 CSS 视口、不同段边界相位均满足最小前向覆盖；未 ready 段单独计空洞；边距和候选数有上限；两虚拟化引擎均覆盖。

选档：单档/稀疏多档/缺失候选但中间档存在/候选文件稍后消失/DPR 与宽图，检查读文件次数和正确回退；保留当前阻塞线程与锁纪律。

### 9.2 独立发现：Image 回退存在资源所有权缺口

源码审查额外确认：`loadBitmapImpl` 在 fetch 异常或 bitmap reject 时调用 `loadViaImage` 后返回；外层 `loadBitmap` 的 finally 随即删除 `thumbLoads` 身份。但 Image 的 onload/onerror 随后要通过 `isCurrentLoad` 检查，因此正常异步事件到达时会被拒绝，既不提交位图也不释放 thumbState 的 loadingSet。这可使回退项长期占位并占住加载槽，直到签名更新或清理状态。

定位：`useCanvasThumbPipeline.ts:94–96,154–165,185–187,227–231,285–303`。它只解释确实触发 Image 回退的样本，不应被拿来解释所有正常 64px WebP。现有 FakeImage 不触发 load/error 事件，测试未覆盖此路径；下一轮应先补正常回退成功/失败及失活晚回包的表征测试，再将任务身份保留到实际回退完成。该正确性修复可与批次 A 相邻独立交付。
