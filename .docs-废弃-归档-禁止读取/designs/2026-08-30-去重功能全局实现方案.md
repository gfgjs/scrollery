# 去重功能全局实现方案

> **演进说明（2026-09-02）**：本文继续描述已经落地的精确摘要、重复组查询与应用内软删除能力基线。当前目标体验见[主画廊重复项浏览方案](2026-09-02-主画廊重复项浏览方案.md)：重复项进入主画廊，提供按重复组与按关联文件夹两种排列，首版不接入清理。此前已经实现的候选树—范围画廊—清理草案保留为[文件夹优先复核方案快照](2026-09-02-内容去重文件夹优先复核方案.md)，不再是目标主入口。

## 1. 当前结论

Scrollery 当前只提供**字节级精确重复分析 + 人工复核 + 应用内软删除**：

> 文件大小候选 → quick digest 筛选 → exact digest 确证 → 逻辑单元分组 → 人工选择 keeper 与副本 → 执行时重新验证 → Scrollery 回收站

不提供系统回收站、磁盘文件删除、cleanup journal、quarantine 或物理空间回收。此前为物理清理建立的整条实验链已经从当前代码和新库 schema 删除，不保留旧 IPC 或开发库兼容层。已经存在的旧数据库若含历史 `dedup_cleanup_journal`，V31 不读取也不删除，避免迁移抹去旧审计/恢复证据；它不属于当前能力。历史论证归档于 [物理清理旧案](../archive/2026-08-30-去重功能全局实现方案-物理清理旧案.md)。

当前硬边界：

1. media_items 继续表示库内位置项，不引入 content/asset/location 三层模型。
2. content_hash 是扫描变化指纹，不是重复证据；重复证据只来自版本化 exact digest。
3. 去重分析是独立、低优先级、可停止和可续跑的后台任务，不进入常规扫描热路径。
4. Live Photo 以主文件与 companion 的组合摘要作为逻辑单元，companion 不独立成组。
5. 只允许用户确认后的应用内软删除；磁盘文件不移动，逻辑字节不等于真实释放空间。

## 2. 数据契约

### 2.1 源新鲜度

media_items.file_mtime_ns 保存扫描取得的纳秒 mtime；source_revision 是源代次。扫描确认源变化、同大小可疑变化、missing 后重现或 companion 变化时，必须推进相关源代次并删除旧 dedup_index 行。

快速扫描的 unchanged 判定同时比较秒级 mtime、纳秒 mtime 与文件大小。任一可疑变化进入指纹定案；即使可信完整 change fingerprint 相同，也会推进 source_revision 并清除 exact sidecar。抽样 fingerprint 相同不能证明未采样区域未变，按源变化处理。

### 2.2 dedup_index

当前 V26 sidecar 为：

~~~sql
CREATE TABLE dedup_index (
    item_id          INTEGER PRIMARY KEY REFERENCES media_items(id) ON DELETE CASCADE,
    source_revision  INTEGER NOT NULL,
    hash_version     INTEGER NOT NULL,
    quick_digest     BLOB,
    exact_digest     BLOB,
    unit_digest      BLOB,
    unit_size        INTEGER,
    physical_key     BLOB,
    status           TEXT NOT NULL,
    error_code       TEXT,
    checked_at       INTEGER NOT NULL
);
~~~

- 摘要使用 BLOB；hash_version 覆盖算法、域分隔和组合编码。
- 缺行代表 pending，不为全库预建空行。
- physical_key 用于在 hash 写回时识别物理对象漂移，必须保留；它不授权物理删除。
- 不存在 link_count、永久 duplicate group、cleanup journal 或 quarantine 字段。
- V27–V29 是退役实验的空迁移槽；V30 只修正历史卷类型；V31 幂等补建 quick 候选索引，修复已经执行过 V26 的旧库访问路径。

## 3. 分析与写回

1. SQL 先按 file_size 找候选桶，候选使用稳定 keyset 分页。
2. quick 阶段计算版本化头/中/尾采样摘要，只用于缩小 exact 输入。
3. exact 阶段流式计算完整 BLAKE3-256，并生成普通文件或 Live Photo 的 unit_digest。
4. 所有文件 IO 在数据库 writer 临界区外完成。
5. 每批写回必须同时满足当前 run generation、source_revision、文件大小、纳秒 mtime、companion 关系和既有 physical_key；不满足即丢弃结果。
6. 只有 status=ready、hash version 当前、sidecar revision 与媒体行 revision 相同的主项能进入重复组。

停止任务会先推进数据库 generation，旧 worker 即使迟到也不能写入新轮结果。有效 sidecar 可跨任务续跑；reset 分批清理当前代次，避免长 writer 事务。

## 4. 查询与 IPC

当前业务命令面：

- start_dedup_analysis(reset)
- stop_dedup_analysis()
- dedup_status()
- list_duplicate_groups(cursor, limit, filters)
- list_duplicate_members(group_key, cursor, limit, filters)
- apply_dedup_soft_delete(selection)

组和成员都使用后端生成的不透明 keyset cursor；不向前端下发全库 ID 数组。分析当前固定为可见资料库范围，不保留伪装成可配置 scope 的参数。

软删除不使用 preflight token。用户先在前端确认，随后一次提交：

~~~text
selection = group_key + keeper_id + selected_item_ids + expected_member_count
~~~

后端在 dedup lifecycle 读锁与数据库 writer 临界区内重新查询当前 exact-ready 整组，并验证：

- group key 的 digest/size 合法；
- 当前成员数与用户看到的数量一致且至少为 2；
- keeper 仍在当前组且不在删除集合；
- selected IDs 唯一、均属于当前组；
- 每个成员仍满足当前 hash version、source revision、未删除、主项、可见根条件。

验证通过后调用通用 soft_delete_items，由其对称扩展 Live Photo companion、推进 source revision 并清除 sidecar。任一条件不满足返回稳定错误码，不执行部分删除。

## 5. 前端状态

去重选择只属于当前打开组：

- 打开或重开组时恢复建议 keeper，并清空选择；
- 切组不会保存隐藏的跨组选择；
- keeper 不能同时被选择删除；
- 软删除成功后清空选择并刷新组；
- 迟到成员响应由 request generation 丢弃，不能把 A 组成员写入 B 组；初始化期间若分析完成事件到达，退出初始化时会补做一次组刷新。

页面只展示一个“移入 Scrollery 回收站”动作，明确说明磁盘文件不会移动、不会释放空间。组列表继续虚拟化，大数组使用 shallowRef。

## 6. 非目标与验收

非目标：相似图、裁剪/转码关系、自动 keeper、用户元数据合并、系统回收站、永久删除和真实可释放字节估算。

改动必须至少验证：

- 扫描源变化推进 revision 并清 sidecar；
- quick 碰撞不直接形成重复组；
- hash 期间替换/截断/删除不发布摘要；
- 旧 generation 和旧 source revision 写回被拒绝；
- Live Photo 组合摘要与 companion 失效；
- 执行软删除时组漂移、keeper 冲突或成员变化被拒绝；
- 分组和成员接口默认排除离线/缺失及零字节项，显式筛选时两者保持相同结果；
- 已执行 V26 的旧库可由 V31 补齐 quick 候选索引；
- 前端切组迟到响应隔离、重开清选择、成功 mutation 清选择；
- migration、Rust 去重聚焦测试、TypeScript 类型检查和受影响 lint 通过。
