## 0. 一句话结论 (TL;DR)

两处 DOM 膨胀都是**「渲染节点数随数据量线性增长、无任何窗口化/降采样」**,而非某个虚拟化机制「失效」:

1. **左侧文件树** (`temp1` = 4194 元素 / 20972 节点):**从未接入虚拟化**。所谓「最初设计是虚拟树」的意图在当前 `FoldersSection.vue` 里**没有落地**——它是一条朴素 `v-for`,把「所有已展开目录 + 各目录自身全部文件」拍平后**全量渲染**。这不是「虚拟树失效」,是「压根没做虚拟树」。
2. **右侧时间轴** (`temp2` = 2042 元素 / 2050 节点):在 **folder/none 分组模式**下,**一个数据分组 = 一个 DOM 节点** (`.tl-sep-node`)。分组数随文件夹数线性增长,却全部塞进一条约 600-900px 高的 scrubber 里——绝大多数节点在渲染那一刻就画不下、不可见,是纯浪费。

治理方向 (业界唯一成熟答案,详见 §4):
- 文件树 → **虚拟滚动 (windowing)**:只渲染视口内的几十行,DOM 与库容量解耦。
- 时间轴 → **降采样到像素分辨率** (必要且低成本) → 可选再上 **canvas 绘制** (归一两种模式、DOM 降到 1)。

百万级 ×20 目标下,二者改造后 DOM 节点数**恒定有界**。

## 1. 现场取证的独立复核 (归属比旧案更确定)

### 1.1 原始采样
```
temp1.childElementCount = 4194 ; temp1.childNodes = NodeList(20972)   → 左侧文件树
temp2.childElementCount = 2042 ; temp2.childNodes = NodeList(2050)    → 右侧时间轴 (folder/none 分组)
```
- 当前库容量:约 6 万项;目标场景:百万级 (再 ×20)。

### 1.2 归属判定 (排除法坐实,非推断)

右侧其实有**两个**绝对定位的竖轴组件,必须区分,否则会误判 temp2:

| 组件 | 文件 | 渲染节点数 | 是否 temp2 |
|---|---|---|---|
| **MediaScrollbar** (自研逻辑滚动条) | [MediaScrollbar.vue:24-30](../../src/components/media/MediaScrollbar.vue#L24-L30) | **恒定 1** (`v-if="geom"` 单个 thumb div) | ❌ **排除** (已是 O(1)) |
| **TimelineScrubber** date 分组 | [TimelineScrubber.vue:16-31](../../src/components/media/TimelineScrubber.vue#L16-L31) | `monthBuckets` 逐月,月数有界 (~100-200) | ❌ 量级不符 |
| **TimelineScrubber** folder/none 分组 | [TimelineScrubber.vue:35-44](../../src/components/media/TimelineScrubber.vue#L35-L44) | `separators` 逐分组,**一组一 `.tl-sep-node`** | ✅ **就是它** |

**判据**:`temp2` 的 childNodes/childElementCount = 2050/2042 ≈ 1.0,即「几乎全部子节点都是叶子元素、无内层子 div」——与 `.tl-sep-node` (空 div、无子节点) 的结构精确吻合。而 `separators` 的类型 ([layout.ts:84](../../src/types/layout.ts#L84)) 是 `{ label; y; groupId? }[]`,后端**每个分组产一条**。故 `temp2 = 2042 = 采样时的文件夹分组数`。

> **比旧案强在哪**:旧案把 temp1/temp2 归属标为「推断,非确证」。本文通过排除 MediaScrollbar (源码确认恒 1 节点) + separators 类型确认 (一组一条),把 temp2 **坐实**到 TimelineScrubber 的 folder 分支,不再是推断。

**temp1 = 文件树**:剩下的受检竖向长列表只有文件树。它是 `.tree` 容器内一条 `v-for`,ratio ≈ 5 (20972/4194) 来自 Vue `<template v-for>` + `v-if/v-else` 为每行插入的注释锚点节点 (`<!--v-if-->` 之类)——这也解释了「膨胀不只贵在 button 本身,更贵在 Vue diff 要遍历这 2 万个节点」。

**30 秒自证** (可选,给用户复核用):devtools 控制台跑 `temp1.className` / `temp2.className`,或 `temp1.closest('[class]').className`,即可当场确认归属。

## 2. 根因分析:文件树 (代码实证)

### 2.1 结论:确系「从未虚拟化」,不是「别的原因」

**事实**:[FoldersSection.vue:49-101](../../src/components/sidebar/sections/FoldersSection.vue#L49-L101) 是一条朴素 `v-for over displayRows`,每行一个 `<button>`,**无窗口化**:
```
<template v-for="row in displayRows" :key="...">
  <button v-if="row.kind === 'dir'" ...>   <!-- 目录行 -->
  <button v-else ...>                       <!-- 文件行 -->
</template>
```
`displayRows` ([:211-231](../../src/components/sidebar/sections/FoldersSection.vue#L211-L231)) 把**所有已展开目录 + 各自全部文件**拍平成一个线性数组,`v-for` 有多长就渲染多少 button。

数据层 `useFolderTree` ([useFolderTree.ts](../../src/composables/useFolderTree.ts)) 只做**懒加载** (`loadChildren`/`loadFiles` 按需拉数据),**完全不做任何窗口化**:`nodes.value` 里有多少已展开节点,模板就渲染多少行。项目里**存在**虚拟滚动 composable:`useVirtualScroll.ts` 被 [MediaGrid.vue](../../src/components/media/MediaGrid.vue)(画廊)消费,`useHVirtualScroll.ts` 被横向画廊 Lab(HGalleryLabView)消费——**二者均从未接入文件树**(评审事实订正,承接 §9.6)。

> **对用户提问的直接回答**:「最初设计是虚拟树」的意图,在当前实现里从未落地。这是 **「未用虚拟树」**,不是「虚拟树失效」,也不是「别的原因」。

### 2.2 为什么 temp1 高达 20972:文件被拍进了同一列表

关键放大器:`displayRows` 把**文件行也拍进同一线性列表** ([:219](../../src/components/sidebar/sections/FoldersSection.vue#L219) 的 `for (const f of dir.files!)`)。展开一个含 3000 张照片的目录,瞬间产生 3000 个文件 `<button>`。6 万库展开几个大目录,4000+ 行轻易达到;百万级 ×20 展开**单个**大目录即可达数万行。

> **量纲提示**:文件树的膨胀由**用户展开行为**驱动 (展开的目录越大越多,DOM 越大),上限极高;而时间轴的膨胀是**只要处于 folder 分组就恒定存在**(见 §3)。两者机制不同,但根因同为「无窗口化/降采样」。

### 2.3 为什么当初没做成虚拟树:两个后加特性与朴素虚拟化冲突

治理方案必须正面处理这两点,否则会破坏现有观感:

1. **粘性目录头** ([:635-646](../../src/components/sidebar/sections/FoldersSection.vue#L635-L646) `position: sticky`):目录行靠 CSS sticky 钉住,滚长文件列表时文件夹名始终可见。**窗口化会移除滚出视口的行 → CSS sticky 的粘附基准断裂** (详见 §4.1 为何二者不能直接组合)。
2. **交错的两种行高** (目录 28px / 文件 26px,[:617](../../src/components/sidebar/sections/FoldersSection.vue#L617) / [:672](../../src/components/sidebar/sections/FoldersSection.vue#L672)):定高虚拟化最简单,但此处两种高度交错,严格做需可变高度虚拟化 (前缀和/高度映射)。**注**:两者仅差 2px,统一到 28px 后可退化为最简单的定高虚拟化 (文件行 +2px 纯观感,可忽略),这是低风险的 MVP 路径。

### 2.4 二次成本:computed 全量重算

`displayRows` 是 `computed`,任何展开/折叠/计数刷新都会**重算整个数组并 diff 全部节点**;每次扫描后 `folder-stats-changed` 事件触发的 `reloadTreePreserveExpansion` ([:322-338](../../src/components/sidebar/sections/FoldersSection.vue#L322-L338)) 全程被这 2 万节点的 diff 拖累,非仅首屏。虚拟化只解决「DOM 渲染」,若单目录文件数极大,`displayRows` 这个**纯 JS 数组**本身的重算也需在源头限制 (见 §5 的 T2)。

## 3. 根因分析:时间轴 (代码实证)

### 3.1 结论:folder 模式「一分组一节点」的量纲错配

[TimelineScrubber.vue](../../src/components/media/TimelineScrubber.vue) 两种模式:
- **date 分组** → `v-for over monthBuckets`,每月一个 `.tl-month` ([:16-31](../../src/components/media/TimelineScrubber.vue#L16-L31))。**月数天然有界** (6 万库约 100-200 月),`monthBuckets` 是后端**按月聚合**的产物——**本质已是降采样**,基本不是问题。
- **folder/none 分组** → `v-for over separators`,每分组一个 `.tl-sep-node` ([:35-44](../../src/components/media/TimelineScrubber.vue#L35-L44))。**分组数即 DOM 数**,`temp2 = 2042` 就是采样时的文件夹分组数,随文件夹数线性增长,百万级 ×20 可达数万。

### 3.2 为什么这是比文件树更纯粹的浪费

scrubber 是 `position: absolute; top:10px; bottom:10px` ([TimelineScrubber.vue:155-164](../../src/components/media/TimelineScrubber.vue#L155-L164)),高度 ≈ 视口高 (约 600-900px)。600px 里画 2042 个点 = 平均每 0.3px 一个点,**必然重叠、亚像素堆叠**,人眼根本区分不出 2042 个分组。

> 这 2042 个 DOM 节点里**绝大多数在渲染那一刻就是不可见的冗余**。付了 2042 节点的布局/合成/diff 成本,只换来约 600 像素行的信息量。且不像文件树 (需用户展开才膨胀),**只要处于 folder 分组模式这 2042 节点就恒定在 DOM 里**。

### 3.3 既有优势:交互已是纯数学映射,改造风险低

[TimelineScrubber.vue:107-119](../../src/components/media/TimelineScrubber.vue#L107-L119) 的 `jumpToPointer` **已是纯数学映射** (`clientY → 比例 frac → 月索引 / y`),**不依赖逐点 DOM 命中**。这意味着无论改降采样还是改 canvas,**点击/拖拽跳转的交互契约几乎不用动**——这是 canvas 化成本低的关键前提 (见 §4.2 / §5)。

## 4. 业界成熟方案 (联网调研,带一手来源)

### 4.1 超大文件树 → 虚拟滚动,这是行业唯一答案

**VSCode Explorer** (正是管理数万项 node_modules 的场景) 用自研 `List` + `IndexTree`。官方 Wiki ([microsoft/vscode Wiki: Lists And Trees](https://github.com/microsoft/vscode/wiki/Lists-And-Trees)) 明确:
- **只渲染视口内节点**:"render a collection of elements in a scrollable view, while making sure **only the visible elements actually end up in the DOM**"。官方称可轻松加 **10 万元素** 不卡。
- **每元素高度的内存映射表**:"keep an **in-memory map of each element's height** and track the viewport's position to know which elements should be rendered in and out of the DOM"——正好覆盖我们「目录 28 / 文件 26 交错」的可变高度难点。
- **IndexTree = List + 缩进 + twistie**:"A rendered tree can always be **rendered as a list**; it is each row's indentation level and twistie which give the perception of tree structure"——树在内部被**拍平成线性 list**,层级只靠缩进 + 三角表达;子树增删走 splice。

**通用模式:先拍平再窗口化,而非递归渲染树** (来源:上引 Wiki + [flattree](https://github.com/cheton/flattree))。原因:
1. 虚拟化的数学前提是「线性可索引 + 给定 scrollTop 用累加/二分求可见区间」,线性数组天然满足;递归树要算「第 N 个可见节点在哪」需每帧 DFS,O(n) 不可接受。
2. 折叠一个目录 = 把它的子区间从 flat 数组 splice 掉;层级用每行的 `depth` 字段表达。
3. flat rows 全是 sibling,DOM 行可干净地回收复用 (row recycling);递归嵌套 DOM 无法池化。

> **对我们的意义**:`displayRows` **已经完成了「拍平成线性行」这一半**,只差「对线性行窗口化」这一半。

**sticky 目录头:必须用独立浮层,不能用 CSS sticky + 虚拟化直接组合** (来源:VSCode 树 sticky scroll 官方 issue [#161207](https://github.com/microsoft/vscode/issues/161207)、编辑器 [Sticky Scroll 博客](https://devblogs.microsoft.com/visualstudio/sticky-scroll-now-in-preview/))。为什么不能直接组合:
1. `position: sticky` 的粘附相对于**滚动流内该元素的真实 DOM 祖先/上下文**生效;虚拟化后滚出视口的父目录行**根本不在 DOM 里**,sticky 无从粘附。
2. flat rows 里父子是 **sibling** 而非 ancestor 包裹,sticky「粘到容器顶直到父块滚完」的语义不成立。
3. DOM 行被回收复用,节点身份不稳定,无法承载持久 sticky 状态。

VSCode 的做法:**一个独立的 sticky overlay widget 浮在列表之上**,每次滚动时根据「视口顶部 item 索引 → 在 flat 模型里回溯祖先链」重算应显示的粘性行,单独渲染 (数量有上限,如不超过树高 40%)。这是「**数学重算 + 独立浮层**」,而非复用被虚拟化掉的 DOM。

**Web 生态可选库** (版本经 npm registry 实测 2026-07-09):

| 库 | 最新稳定版 | 可变行高 | 回收池化 | scrollToItem | 备注 |
|---|---|---|---|---|---|
| **vue-virtual-scroller** (Akryum) | **3.0.4** (2026-05-20) | ✅ `DynamicScroller` | ✅ `RecycleScroller` | ✅ | Vue 3 生态首选;`next` 标签仍停在旧 beta,**装 `latest` 非 `@next`** |
| **@tanstack/vue-virtual** | **3.13.31** | ✅ `measureElement` | ✅ (overscan) | ✅ | headless,先估后测 |
| **virtua** | **0.49.2** | ✅ 自动测量 | ✅ | ✅ | 多框架,变高开箱即用 |

> 文件树每行基本等高 (icon + 单行文本),属 fixed-height 最简单一档,**自研等高虚拟化甚至优于引库** (无变高测量开销、零依赖、贴合 `<10MB 核心` 约束);现成库都**不直接提供树 sticky**,sticky 浮层无论如何都要自研。

### 4.2 时间轴 scrubber → 降采样到像素 / canvas 绘制

**Google Photos** 的 Web scrubber (一手来源:[Google Design — Building the Google Photos Web UI](https://medium.com/google-design/google-photos-45b714dfbed1)):
- 初始只传 **sections + counts** (每段 + 该段照片数),不传百万条元数据;客户端按「照片数 × 平均纵横比」**估高撑出占位**,实测后回填校正、整体位移下方段落。
- date scrubber 本质是「**把 sections/counts 映射到滚动条比例位置**」的**数学映射**,而非给每个分组画一个 DOM 节点。

**降采样 (downsampling/bucketing) 到像素分辨率** —— 数千点堆在几百像素的正解,通用原则:**目标容器多少像素高,就最多聚合出多少个可绘制槽位**。做法:scrubber 高 `H` px → 把 N 个数据点按「位置 → 桶索引」聚合进约 `H` 个桶,桶内做密度/计数聚合 → 只绘制这约 `H` 个桶。我们的 `monthBuckets` (date 模式) **已天然是这种按月聚合的降采样**,所以 date 模式没问题;**folder 模式缺的正是同一层聚合**。

**canvas 绘制 minimap/scrubber** (一手来源:[VSCode minimap.ts 源码](https://github.com/microsoft/vscode/blob/main/src/vs/editor/browser/viewParts/minimap/minimap.ts)):VSCode editor minimap 用 **canvas** 绘制,按 devicePixelRatio 把整行代码压成 4×2 / 2×1 像素块 (本质降采样),帧间增量复用像素。CodeMirror minimap 同理用 canvas。

**三方案权衡** (针对我们的 scrubber):

| 方案 | 节点数 | 大量数据点 | 交互命中 | 适用 |
|---|---|---|---|---|
| **DOM (现状)** | O(N) 数万 | ❌ 布局/合成/diff 炸裂 | ✅ 原生事件 | 仅 N 很小 |
| **降采样 + DOM** | O(像素) ≈ 数百 | ✅ 有界 | ✅ 原生事件 | **必要的第一步,低风险** |
| **canvas** | **1** | ✅ 最优,可画连续密度 | 需数学映射 (见下) | **终局/归一,可选** |
| 单个 SVG `<path>` | 1 | ✅ (一条轮廓线) | 整条 path 一个命中区 | 只画单一密度曲线时 |

**canvas 的交互命中**:用**数学逆映射**而非 DOM 命中 (来源:[Canvas Hit Detection Methods](https://joshuatz.com/posts/2022/canvas-hit-detection-methods/))。scrubber 是一维线性布局,最简单:`const rect = canvas.getBoundingClientRect(); const frac = (e.clientY - rect.top) / rect.height` → 反解到时间轴/桶 → 跳转;hover 同理反解出桶的日期/计数,定位一个 DOM tooltip 浮层。**我们 `jumpToPointer` 已经是这套纯数学映射,canvas 化交互几乎零改**。

### 4.3 可复用的通用判据

> **总览类可视化 (滚动条/缩略轴/热力条/minimap):用 canvas 或降采样——「全量同时可见但画不下」→ 降维到像素。**
> **列表类可视化 (树/网格/长列表):用虚拟滚动——「同时只看一小段」→ 只渲染那一段。**

我们两处恰好一类一个:时间轴属前者 (降采样/canvas),文件树属后者 (虚拟滚动)。

### 4.4 诚实边界

- **Apple Photos / Lightroom / Mylio / Peakto 的 scrubber 具体渲染选型** (DOM vs canvas vs 聚合) **无公开一手来源** (闭源应用无实现级文档),本文未臆断,仅按原生 UI 惯例做范式类比 (原生应用多走绘制而非 DOM 节点,与 canvas 同范式)。
- VSCode List 的 **DOM 行池化/回收** 属源码级机制,官方 Wiki 只逐字承诺「插入/移除 DOM + 高度内存映射」,池化为源码级推断。
- 「CSS sticky 不能与虚拟化直接组合」是基于三条已确证事实 (虚拟化移除滚出视口 DOM + flat rows 是 sibling + DOM 回收) 的架构推理,非某文逐字断言。

### 5.2 推荐顺序:S (canvas) + S3 (loupe) 一并 → T1 → (T2 按实测)

**S + S3 (时间轴 canvas + loupe) 建议一并做**:
- canvas 化把 folder 模式 temp2 从 2042 → 空闲 ≈1 节点,直接命中用户「极致压低常驻 DOM」诉求;且**全量 separator 数据仍留在 JS**,只有像素被聚合 (§5.3),故不丢任何可交互能力。
- loupe 与 canvas **强耦合、宜同批**:正因主轴退成 canvas (保留全量数据 + 近零节点),loupe 才能"按需、局部、有界"地叠加 (§5.6);反之若主轴仍是全量 DOM,loupe 就是雪上加霜。二者一起才是完整可用的交互。
- `jumpToPointer` 已是纯数学映射,canvas 化交互几乎零改;canvas 的整轨命中 + 吸附最近 separator,已先改善「不好点」一半,loupe 补齐「密集区精确挑选」。

**T1 (文件树虚拟化) 是收益最大也最硬的一项**:temp1 20972 → 约数百,最贴「百万级」目标,但涉及 sticky 覆盖层重构、可变高度、拖拽命中、`expandToNode` 定位改造。建议**分两步降风险** (§5.4)。

> **一个必须点明的取舍**:若「百万级 ×20」是硬目标,**T1 是不可省的那一项**——文件树膨胀上限最高 (单个大目录即数万行)。时间轴 canvas 消除的是"恒定存在的浪费",文件树虚拟化消除的是"上限最高的浪费";二者独立无依赖,可并行,T1 优先级不因其难而下降。

**T2 (单目录文件分页)** 是 T1 的补充非替代:虚拟化只解决 DOM,`displayRows` 这个纯 JS 数组在展开数万文件目录时仍会变长、拖累每次 computed 重算。**建议 T1 落地后按实测决定是否做**。

### 5.3 【S】时间轴改 canvas 绘制 (转正主方案)

**核心架构:数据驻留与 DOM 节点解耦。** 全部 separator/monthBucket 作为**纯 JS 数字数组**留在内存 (几十 KB,可忽略),只画进 **1 个 `<canvas>`**——空闲 DOM ≈1 节点,而数据**全分辨率保留**,供命中检测与 loupe 精确访问。屏幕像素被"降采样"是物理必然 (600px 画不下 2042 点),但**数据不丢** (承接 §5 用户对"降采样丢节点"的质疑:canvas 下连数据都不需砍,只砍像素)。

- **绘制** (两种画法,均无需砍数据,可结合):
  1. **累积密度**:每个 separator 画一条半透明 1px 线 (canvas 里 2000 次 `lineTo` 无布局/合成成本);重叠区 alpha 自然累加 → 免费得到密度热力带,越密越亮。
  2. **桶聚合密度条**:先聚合到约「条像素高」个桶,每桶一根密度条 (便于峰值保留/地标提亮)。
  - 地标保留:年份边界 (date 模式复刻 `isYearStart`)、top-N 大文件夹单独提亮,防被密度冲淡 (承接 §5.6 前对"防冲淡"的三手法)。
- **命中检测**:整条轨道为命中区,点任意 y → `frac = (clientY-rect.top)/rect.height` → 二分查**最近 separator** → 跳其真实 y。纯数学 O(log n),无 DOM 命中。**比现状"点 4px 小圆点"更好点**。
- **工程细节** (承接 MediaScrollbar 已有 ResizeObserver 模式):DPR 适配 (retina 清晰,绘制坐标系与命中坐标系须一致,勿混用 CSS px / raw px);`ResizeObserver` 重算尺寸并重绘;主题 `watch resolvedThemeId` 读 CSS 变量 (`--color-accent`/`--color-border`/`--color-text-secondary`) 重绘;`currentY` 变化仅重绘高亮层。
- **年份标签** (date 模式):每年 1 个稀疏 DOM (≤ ~20,有界),或一并画进 canvas。folder 模式无。
- **重绘触发源**:①数据 (separators/monthBuckets) 变 ②`currentY` 变 (高亮) ③尺寸变 (ResizeObserver) ④主题变 (watch)。均 rAF 节流。
- **不碰后端/layout 缓存契约** (承接「布局缓存四契约」):纯前端消费既有 props。

### 5.4 【T1】文件树虚拟滚动 (方案细化)

**技术选型**:**先自研定高 MVP,`vue-virtual-scroller` (stable 3.0.4) 留后备**。
- 不复用 `useVirtualScroll`:它的核心接口是 `fetchRowsByY(topY, bottomY) => Promise<LayoutRow[]>`——**不持有行数组、按 Y 区间向后端异步拉行** (为百万图「行不驻留 JS」而生),与文件树 `displayRows` 全量 in-memory 数组的前提**相反**;且其座标压缩 (>16.7M px)、wheel 惯性补偿、fetchId 竞态守卫对树 (最多约 2M px) 全是**冗余负担**,却都是经多轮真机硬化的**验证过热路径**。让它伺候结构不同的第二消费者,风险 >> 收益。正确的 DRY 是**复用模式** (prefix-sum 绝对 y + 绝对定位行 + rAF 节流) **而非代码**。
- 行高统一 `ROW_H = 28` (文件行 26 → 28,+2px 纯观感),退化为最简单的 `startIndex = floor(scrollTop / ROW_H)`,约 40 行、零依赖、无 prefix-sum/二分。触发切库/升级变高的条件:真机发现快滚 DOM churn 明显掉帧,或行高需求变复杂 (变高 + 字号缩放联动)。

**DOM 五层结构** (窗格 + 视口 + 撑高占位 + 渲染层 + 覆盖头):
```
.tree-pane            position: relative        ← 定位锚 (覆盖头相对它绝对定位)
├─ .tree-sticky-head  position: absolute; top:0 ← sticky 覆盖头 (1 个 DOM,恒在窗格顶)
└─ .tree-viewport     overflow-y:auto; @scroll  ← 真正滚动容器,自有 scrollTop
   └─ .tree-spacer    height = rowCount*ROW_H    ← 撑起总高,产生真实滚动条
      └─ .tree-layer  transform: translateY(offsetY) ← 只含可视窗口行,整体平移到起始行
         └─ <button>… 仅 visibleRows
```
- 覆盖头**必须在视口外层** (`.tree-pane` 的绝对定位子);放视口内会随内容滚走。
- 渲染层用 `translateY` 平移 (非改 `paddingTop`),避免每帧 reflow。
- 现状的逐行 `position: sticky` **全部移除**,由覆盖头取代。

**sticky 覆盖头「当前目录」反查** (VSCode Sticky Scroll 思路,MVP 只钉一级):
- `FileRow` 已自带 `dirId` ([FoldersSection.vue:207/220](../../src/components/sidebar/sections/FoldersSection.vue#L207)),反查是 O(1):`row = displayRows[floor(scrollTop/ROW_H)]; return row.kind==='dir' ? row.node.id : row.dirId`。
- **关键正确性陷阱 (必测)**:`displayRows` 里目录的**自身文件排在其整个子树之后** ([:216-228](../../src/components/sidebar/sections/FoldersSection.vue#L216-L228))。例如 `A(dir)·B(dir)·fb1·fa1(A的文件)`,滚到 `fa1` 时「最近的前一个 dir 行」是 B (**错**),但 `fa1.dirId === A` (**对**)。**故必须用 `FileRow.dirId`,不能「向上扫描最近 dir 行」**。

**分两步施工降风险**:
- **T1-a**:`v-for` → 虚拟列表 (定高 28px,**暂去 sticky**,目录行普通流) + characterization/新增测试 + 独立滚动窗格布局。先验性能与展开/折叠/点击/reload 正确性,隔离虚拟化本身 bug。
- **T1-b**:补 sticky 覆盖头 + `resolveCurrentDirId` 接线。
- **T1-c**:关联点改造 (见下)。

**必须一并改造的关联点** (逐项对账现状功能,防回归):
1. **`expandToNode` 的 `scrollIntoView` + `setTimeout(50)`** ([useFolderTree.ts:135-146](../../src/composables/useFolderTree.ts#L135-L146)) 依赖目标 DOM 存在——虚拟化后目标行可能不在 DOM。改为:算目标在 `displayRows` 的 index → 设 `viewport.scrollTop`;删掉 `setTimeout` DOM 等待 hack,改数据驱动。滚动职责宜从 `useFolderTree` 移交给独占 viewport 的 `FoldersSection`。
2. **拖拽命中 `data-dir-id`** ([FoldersSection.vue:438-442](../../src/components/sidebar/sections/FoldersSection.vue#L438-L442)) 经 `elementFromPoint(...).closest('[data-dir-id]')`——虚拟化后只有可视目录行有 DOM。风险:拖到滚出视口的目录无法命中。缓解=**拖拽近视口边缘时自动滚动** `.tree-viewport`;覆盖头带 `data-dir-id` 亦为合法投放点。
3. **右键菜单/新建对话框/drag ghost** ([:107-138](../../src/components/sidebar/sections/FoldersSection.vue#L107-L138)):均 Teleport 到 body 或独立状态,**不受窗口化影响**。
4. **`active`/hover 高亮**:纯 class 绑定,自动只作用于可视行,**无需改**。

### 5.6 【S3】时间轴 loupe 放大镜浮层 (2026-07-09 用户新增诉求)

**动机 (用户原话)**:「现在轴上的节点很小不好点也不好分辨,很难用」。canvas 密度带解决了"看总览",loupe 解决"密集区精确挑选"。**形态已定:侧向 loupe 浮层** (2026-07-09 用户拍板,备选 fisheye 原地鱼眼 / 原地展开局部窗均否决)。

**机制**:
- 鼠标移入轴 → 取光标 `frac` → 从**保留的全量 JS 数据**里取光标邻域**最近的 K 个 separator** (K≈15-25,常数,与库容量无关)。
- 轴旁弹出一条**高约 400px 的放大浮层**,把这 K 个节点**均匀铺开** (每个约 20px 一格,带日期/文件夹名 + 张数标签) → 个个可分辨、可舒服点击。
- 光标沿主轴移动 → 浮层内容平滑跟随邻域滚动 (一个"放大的二级 scrubber");光标行在浮层内居中高亮。
- 点浮层某项 → 精确跳到该 separator 真实 y (复用 `emit('jump', y)`)。
- 移出轴 → 浮层消失 (`v-if`,空闲零节点)。

**为什么它不重新引入 O(N) 节点**:loupe 只渲染"光标邻域 K 个"而非全部,**K 是常数**。所以放大镜是"按需、局部、有界"的细节层;空闲 0 节点、悬停 +~20。这也是**必须先 canvas 再叠 loupe** 的原因:canvas 保留全量数据 + 近零常驻节点,loupe 才能优雅叠加。

**取舍说明**:loupe 的 K 个格子用 **DOM** (而非 canvas) 渲染——文字标签 + 逐项命中在 DOM 上最省事,且 ~20 个瞬态节点 (仅悬停) 对"极致压低常驻 DOM"的目标可忽略。若追求纯粹零 DOM,loupe 也可做成第二块小 canvas + 数学命中,但文字/主题成本上升,不建议。

**触屏/无 hover 设备**:loupe 依赖 hover,触屏无 hover。降级=触屏下长按或拖拽轴时以"拖拽点邻域"驱动同一 loupe (承接 scrubber 已有的 pointer capture 拖拽),保证移动端也可精确挑选。

**命中/映射纯函数** (入 helpers + 单测,承接 timelineScrubber.helpers 惯例):`frac → 邻域 K 个 separator 索引`、`loupe 内 slot index → separator`、`separator → loupe 内 y 位置`。

**测试**:邻域取 K 的边界 (轴首/轴尾不足 K 个时的截断)、光标移动时邻域窗口滑动、点击 slot → 目标 y 映射。

## 6. 直接回答用户四问

1. **「左侧文件树最初设计是虚拟树,为何还有这么多 DOM?是未用虚拟树还是别的原因?」**
   → **就是未用虚拟树**。当前 `FoldersSection.vue` 是朴素 `v-for` 全量渲染,数据层 `useFolderTree` 只懒加载、不窗口化,项目里的虚拟滚动 composable 从未接入文件树。不是「虚拟树失效」,是「压根没做」。此外**文件被拍进同一列表**放大了膨胀 (展开一个大目录即数千文件 button)。

2. **「右侧轴组件可否用 canvas 绘制?」**
   → **可以,且业界成熟** (VSCode editor minimap 正是 canvas)。canvas 把 DOM 降到 1、可画连续密度;交互用数学逆映射,而我们 `jumpToPointer` 已是纯数学映射,改造成本低。**但**:更低成本的**必要第一步是降采样** (folder 模式补上 date 模式已有的桶聚合),仅此就把 temp2 从 2042 降到数百、消除性能病根;canvas 是「归一两种模式 + DOM 降到 1」的**终局/可选增强**,非必需。(**§9 终审确认此判断**:经竞争式评审,canvas 采实测驱动二期,并新增 T0 廉价先手先验证——这也闭合了本段与 §5 早前「canvas 转正」横幅的红线冲突。)

3. **「业界怎么处理 (VSCode 管理超大 node_modules / 竞品)?」**
   → 见 §4。**树 → 虚拟滚动** (VSCode 自研 List/IndexTree,只渲染视口节点、高度内存映射、先拍平再窗口化、sticky 用独立浮层);**时间轴 → 降采样到像素 + canvas** (Google Photos 用 sections+counts 数学映射;VSCode minimap 用 canvas + 按 DPR 降采样)。通用判据:总览类用 canvas/降采样,列表类用虚拟滚动。

4. **「给出分析报告和方案 (不改代码)」**
   → 本文即报告 + 方案,已落盘 `docs/2026-07-09-文件树与时间轴DOM膨胀-独立复核报告v2.md`,本轮不动代码。

## 9. 竞争式评审裁决与终审决议 (2026-07-09)

> 本节为**当前权威**:与前文任何早前横幅/顺序冲突处一律以本节为准(承接「分片为线现状源」「修订史移入附录」纪律)。产出方式:6 路对立立场子代理竞争式评审 + 每路配独立核验员对真实源码对抗性验真 + orchestrator 独立复核关键项(含亲核 cache.rs 后端桶化机制)。41 条发现,验真后 23 valid + 18 partially-valid,**零 invalid**。

### 9.1 整体裁决
**根因分析与代码实证主体扎实**(事实核对员逐条确认 8 大类实证无误:朴素 v-for 无虚拟化、文件拍入同列表、useFolderTree 无窗口化、expandToNode 的 querySelector+setTimeout、MediaScrollbar 恒 1 节点、jumpToPointer 纯映射、fa1 陷阱须用 dirId 等)。**施工方案需先补 §9.4 must-fix**,尤以 canvas/loupe/T1 三处存在「按现码直接会坏」或「未登记的架构冲突」。

### 9.2 用户终审决议(三分叉)
1. **数据侧 O(folders)** → 采 **(A) 全量 separator 留 JS**:数 MB 相对现代 16GB 内存可忽略,换 loupe 邻域本地二分**零延迟**;不走后端 folder_buckets(避免 hover 加 IPC 延迟)。**须修正 §5.3 措辞**:separators 是「带 label 字符串的**对象**数组」非「数字数组」,当前 2042 条约数百 KB、百万级数 MB(非「几十 KB」);§0/§5.1「DOM 恒定有界」补注「separators 数据仍 O(folders),内存可接受」。
2. **canvas 必要性** → 采纳评审:**canvas 降为「实测驱动的二期可选」**。先量化「全屏 + 极小缩略图」下 MediaGrid 常驻节点(devtools 数一次)——它(约 5k-10k:视口约 1000-1900 cell × 多节点 MediaThumb)才是「全屏数千节点」主因;scrubber 降采样后仅数百、占比小,canvas 数百→1 属边际收益。canvas 不再冒充百万级 DOM 目标的关键项。更省的杠杆可能是极小尺寸下调小 `SCROLL_BUFFER_ROWS` / 精简 compact 态 MediaThumb 层数。
3. **loupe 定位** → 采纳评审:**loupe 降为二期**。先交付 **T0**(整轨吸附 + flyout)真机验证是否已足够缓解「不好点/不好分辨」,再决定 loupe 必要性。

### 9.5 应采纳(非阻塞增强)
- **键盘 slider**:scrubber 加 `role="slider"` + tabindex,↑↓ 逐 separator / Enter 跳 / Home-End 首尾。天然规避「小目标命中」,是「不好点」的**直接主解之一**,应作 T0 伴随项(补当前零键盘 a11y 缺口——组件根 div 现无任何 role/tabindex)。
- **canvas 范围收窄到 folder/none**(若二期做):date 模式 ~100-200 节点、富交互(年份 label / flyout / 高亮)、天然可主题,无膨胀不必重写;canvas 设 `aria-hidden` 装饰化,跳转 a11y 交已有 `role="scrollbar"` 的 MediaScrollbar;为 S/S3 单列真机回归清单(§7.4 现只覆盖 T1)。
- **accordion 折叠 v-show 高度动画** → `.tree-viewport` 必挂 **ResizeObserver**(容器高 0→N 重算窗口,否则展开后空白行;被否决复用的 useVirtualScroll 恰在此处挂了 RO);单测覆盖 height 0→N 窗口恢复。
- **拖拽边缘自动滚动**用**独立 rAF 循环**(指针静止在边缘不产生 pointermove→朴素在 move 回调里滚不会触发);单测/真机覆盖「按住不动在边缘」。
- **ROW_H 单一 CSS 变量同源**(如 `--tree-row-h`,CSS 与 JS 读同一值),防未来密度/缩放 token 改动致 scrollTop→index 坐标数学静默漂移。
- **fa1 陷阱是行为改善非平移**:现状 CSS sticky 对目录尾随文件其实钉的是最后一个子文件夹(陈旧),新覆盖头 dirId 反查会「正确」钉父级;characterization 测试须对「现状 sticky」与「新覆盖头」**分别取证**,勿要求逐帧一致(否则把改善编码成回归)。
- **sticky 覆盖头去重/过渡**:顶行本身为 dir 时,覆盖头与在流真实行须去重(隐藏在流行)或做 VSCode 式像素上推过渡;characterization 须含「dir 行位于视口顶」态。
