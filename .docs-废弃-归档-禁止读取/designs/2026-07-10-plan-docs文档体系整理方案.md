## 0. TL;DR

**病**:plan-docs 累积 77 个文件,三代命名混杂、六类文档混居一室、无任何索引、文档状态(现行/过时)不可见、todo.md 膨胀至 103KB 且分节编号已撞车、代码注释指向文档的引用已出现断链。

**业界共识**(§2–§3,六大体系 + 企业实践调研):文本入库 + 按类型分区 + 机器可读元数据头 + 「不可变快照 + 取代链」的改判机制 + 由元数据生成的索引 + 消极状态(已废弃/已拒绝)一等公民。

**方案**(§4–§5,分阶段迁移见 §6):
1. **目录按「文档类型」分区**(全部仍在 `plan-docs/` 内,不触碰 copybara 排除面与 rename-gate 豁免面):`refactor_2026/`(架构正典,原地不动)+ `designs/`(单点设计)+ `reviews/`(审查快照)+ `decisions/`(决策存证)+ `runbooks/`(活手册)+ `archive/`(吸收 `_deprecated/`、exotic v3 目录与已完成使命的文档——exotic 整目录归档是 Part0 §0.3 降级裁决的物理兑现);根目录只留 `README.md`(总索引)+ `todo.md` + `completed.md` + `experience.md` 四个活文件。
2. **每份非归档文档带 frontmatter 状态头**;归档文档一律文首加「已归档/已废弃 + 取代链」横幅,正文不改(存证不变量)。
3. **README.md 总索引**:按主题线 × 类型双导航,标注状态;后续可由脚本从 frontmatter 自动重生成。
4. **todo.md 瘦身**:整节收官的段落成建制剪切至 completed.md;修复分节撞号;目标从 103KB 降到 ≤40KB。
5. **生命周期规则回写 CLAUDE.md**,并给 `tools/` 增加轻量文档门禁(断链检查 + frontmatter 校验),与既有 `check_plan_canonical.mjs` 同族。

**刻意不做**(§7):不把文档移出 `plan-docs/`(2026-07-11 目录更名 `docs/` 后规则本体不变:一切文档不出 `docs/`);不重命名 `refactor_2026/` 及 Part 文件;不改写任何历史快照的正文;不引入外部文档平台/静态站生成器。

### 1.2 病灶清单

**P1 无索引,入口即迷宫。** plan-docs 根目录没有 README;唯一的导航是 CLAUDE.md 里两行命名约定和仓库 README 一句「refactor_2026 系列是现行架构」。要找「画廊性能的现行设计」,读者必须自己知道去翻 `2026-07-09-画廊极密网格渲染方案.md` 而不是 `2026-07-10-画廊滚动飞掠卡顿分析.md`——文件名不含类型与状态信息。

**P2 三代命名混杂。** 同目录共存三种世代的命名:裸主题名(`architecture_notes.md`、`experience.md`)、版本号名(`implementation_plan_v1.2.md`、`exotic_format_plugin_plan_v3.1_addendum.md`)、日期名(`2026-07-06-*.md` 现行约定);refactor_2026 内又有 `PartN_` 与 `T16_/T18_/T20_` 两套编号体系。按名检索无规律可循。

**P3 类型混居。** 根目录 22 个日期散件里混着六种性质完全不同的文档:normative 设计方案(阅读器完善方案)、审查快照(Fable5 全面审查报告)、决策 brief(渠道·开源边界)、施工计划(改名施工,已执行完)、运维手册(CI runner 手册,活文档)、实验报告(horizontal-gallery-lab)。读者无法从位置判断「这份文档现在还作数吗、是拿来执行的还是拿来存证的」。

**P4 状态不可见。** 典型标本:`implementation_plan_v1.2.md`(52KB)是 refactor_2026 之前的初代总纲,早已被 Part0–8 整体取代,但文首无任何「已被取代」标注,读起来与现行文档无异。`_deprecated/` 目录是唯一的状态信号,但它只表达「废弃」一档——「已完成使命的施工计划/快照」与「被推翻的方案」语义不同,现在要么滞留根目录冒充现行文档,要么挤进 _deprecated 丢失差别。

**P5 todo.md 膨胀 + 编号撞车。** 滚动现状源 todo.md 已达 103KB:分节按工作线以字母递增(A–M),2026-07-06 与 2026-07-09 两次立项都取了 `## I.`,现在存在两个 I 节;文末「已完成(本会话,存档参考)」段持续增长。虽有 2026-07-05 的「详注剪切至 completed.md」轻量化,但整节收官后的状态板仍全量滞留。对每个新会话都要加载 todo.md 的 AI 协作模式,这是直接的 context 成本。

**P6 断链已发生。** `src-tauri/Cargo.toml:193`、`src-tauri/src/db/schema.rs:264`、`src-tauri/src/db/queries.rs:4472` 三处注释引用 `plan-docs/feature_expansion_plan_v1.md`,而该文件已被移入 `_deprecated/`——移动时无人更新引用,也没有任何机制能发现。这证明:**没有引用检查的目录整理,本身就是断链制造机**(本方案 §6 的每一步移动都必须带同 commit 引用更新 + 机械验证,§5.5 的门禁脚本让它以后不再靠自觉)。

**P7 快照转述传播风险。** CLAUDE.md 已记录教训(完成度审查给 Part3 T11 错标「HDR」,正文回写照抄传播):多份审查快照互相转述结论,而快照之间没有「取代链」标注,后来者无法判断哪份是最新权威。review_fable_5_2026-07-10/ 以「一轮审查一目录 + README 索引」的形态出现,是正确方向,但只此一例。

### 1.3 既有的正确实践(整理时必须保留/放大)

诊断不全是坏消息,以下四点是项目已经自发长出的、与业界共识(§3)吻合的机制,方案将把它们制度化而非推倒:

1. **todo.md 单一滚动现状源 + completed.md 详注归档**——等价于业界「live board 与 append-only log 分离」,红线地位不变。
2. **正文回写红线 + 推翻横幅**——等价于 ADR/IETF 的「取代链」机制,已写入 CLAUDE.md。
3. **`tools/check_plan_canonical.mjs`**——自制 docs-as-code 门禁,用可执行断言防止被推翻表述残留,思路与 PEP 0 自动索引同源(机器啃元数据,不靠人工纪律)。注:该脚本目前未挂 CI,纯手跑。
4. **`review_fable_5_2026-07-10/` 目录制审查包**——与 KEP「一提案一目录」同构,将推广为审查快照的标准形态。

### 1.4 硬约束(整理动作的边界)

| 约束 | 出处 | 对方案的含义 |

## 2. 业界调研(2026-07-10 联网实证,来源随文附)

> 调研方式:两路独立检索,全部结论抓取一手来源核验(官方仓库 README / 模板文件 / 流程原文 / 作者博文),共 20+ 来源。本节是压缩转述,细节以链接原文为准。

### 2.1 开源世界的提案/决策文档体系(六家)

| 体系 | 目录与命名 | 元数据与状态机 | 改判机制 | 索引 |
|---|---|---|---|---|
| **ADR**(Nygard/MADR) | `docs/decisions/NNNN-短横线标题.md`,顺序编号永不复用 | 五段式(Context/Decision/Status/Consequences);状态 proposed→accepted→deprecated/superseded;MADR 用 YAML front-matter | **接受后不可变**(AWS:immutable;Azure:append-only log);推翻=新写一条+旧条标 superseded+双向互链(adr-tools `adr new -s N` 自动做) | `adr generate toc` / log4brains 从 front-matter+git log 自动生成 |
| **Rust RFC** | 单仓 `text/NNNN-feature.md`;编号=PR 号(零成本防抢号) | 文件内无状态头,**状态由仓库位置表达**(merged=active / closed / postponed);定案走 FCP 公示 10 天 | 已合并原则上不大改;实质修改须新 RFC+旧文加注 | 自动渲染成 RFC Book |
| **Python PEP** | `pep-NNNN.rst`,编号由 editors 分配后永不变 | RFC 2822 文首头:Status/Type/Created/**Replaces/Superseded-By**/Resolution;状态机 Draft→Accepted/Rejected/Withdrawn→Final | 取代靠 Replaces/Superseded-By 头互链;已随版本发布的功能不能改判,只能走 deprecation | **PEP 0 索引由各 PEP 元数据头全自动生成** |
| **K8s KEP** | `keps/sig-xxx/NNNN-短名/`,**一提案一目录**(README.md 正文+`kep.yaml` 元数据);编号=tracking issue 号 | kep.yaml 结构化字段:owning-sig、status(provisional/implementable/implemented/**replaced**…)、**stage(alpha/beta/stable)与 status 双轴分离** | 被取代标 replaced | 发布工具读 kep.yaml 自动汇总,无手工总表 |
| **Oxide RFD** | `rfd/{四位号}/README.adoc`,一号一目录;以编号命名的 git 分支占号 | 文首元数据 authors/state/discussion;六态 prediscussion/ideation/discussion/published/committed/abandoned | 定位是「**请求讨论而非请求批准**」,发布不设批准门;修改走新分支 | rfd.shared.oxide.computer 自动渲染检索 |
| **IETF RFC** | 编号文档 | Obsoletes/Updates 头 | **发布后永不修改**,演化全靠新 RFC 部分更新(Updates)或整体作废(Obsoletes)旧文 | 官方索引 |

跨体系共性(两路调研独立提炼后合并,8 条):

1. **纯文本入 git,评审即 PR**——决策史=版本史,六家无一例外。
2. **稳定编号、一号一物、永不复用**;编号尽量挂在既有基础设施上自动防冲突(PR 号/issue 号/分支占号)。
3. **「不可变 + 取代链」是通行的改主意机制**:已定稿文档只追加不重写;推翻=新增一条+双向回链。历史因此永远可考。
4. **消极状态是一等公民**:Rejected/Postponed/Abandoned 全部入库并写明理由——防止同题反复重议。
5. **元数据机器可读、置于文件头**;**索引由元数据自动生成**,手工目录只是小规模退化方案。
6. **模板钉死「记 why」骨架**(Context/Decision/Consequences/alternatives considered)。
7. **「达成共识」与「已落地」严格分离**(Rust active ≠ 实现;KEP status ≠ stage)。
8. **规模驱动形态演进**:单文件 → 一提案一目录(KEP/RFD),动因是提案要携带多文件资产;目录同时成为稳定引用锚点。

### 2.2 企业内部工程文档治理

**Google·设计文档生命周期观**(Malte Ubl《Design Docs at Google》,industrialempathy.com/posts/design-docs-at-google/):设计文档「像所有文档一样,随时间与现实脱节」,其价值从施工蓝图退化为**了解系统当初思路的最易达历史入口**;实现与设计冲突时强烈建议回写,但坦承「人类不擅长更新文档」,常见终态是「带一堆修正案的美国宪法」。(校勘:流传的「代码才是真相」并非原文字面,是该观点的自然推论。)另一反向提醒:**方案无歧义时写设计文档是纯开销**。

**Google·g3doc 与 docs-as-code**(《Software Engineering at Google》ch.10,abseil.io/resources/swe-book/html/ch10.html):文档入版本库、有 owner、变更走 review;**freshness date(最近核验日期)元数据 + 超期(如 3 个月)自动提醒**;文档五分法(reference/design/tutorial/conceptual/landing page),「每类服务不同目的,不应混在一份文档里」;死文档「要么删除,要么显式标 obsolete 并指路新去处——哪怕只加一句『这已经不管用了』也比什么都不说强」。理念源自 GooWiki 因无 owner 而大面积过时的失败教训。

**Diátaxis**(diataxis.fr,Cloudflare/Gatsby/Vonage 等采用):tutorial/how-to/reference/explanation 四象限;核心论点——**文档应围绕用户需求的结构组织,把不同目的混进同一份/同一处文档正是文档混乱失效的根源**。

**docs-as-code**(writethedocs.org/guide/docs-as-code/):文档与代码同库、走 PR、CI 自动检查(链接检查/lint);Google/Microsoft/AWS/GDS 等均实践。

**公司级 RFC 文化**:Squarespace(engineering.squarespace.com/blog/2019/the-power-of-yes-if)——意见鲜明的模板(status 头/approvers/alternatives considered/运维工作量)+「Yes, if」评审哲学(不设是否门,只给带条件的同意);Uber(blog.pragmaticengineer.com/scaling-engineering-teams-via-writing-things-down-rfcs/)——写下来→指定 approver 批准→**广播全工程**,模板从评审者反复追问的问题中有机长出;HashiCorp(hashicorp.com/en/how-hashicorp-works/…)——**PRD(定义问题)与 RFC(提出解法)分离成两份文档**,RFC 状态机 WIP→In-Review→Approved→**Obsolete**,角色字段单一 owner。

**防腐化(doc rot)**:SWE at Google 的「owner + 核验日期 + 超期提醒 + 死文档标注指路」闭环;GOV.UK(gov.uk/guidance/how-to-publish-on-gov-uk/reviewing-and-approving-content)**发布时即设 review date**,到期找 owner/领域专家确认「仍需要吗、仍正确吗」,生命周期终点内容下线。

**大仓库 docs 组织实例**:kubernetes/community 按组织单元(sig-*/wg-*)分目录,而**决策提案(KEP)独立分离**在 enhancements 仓;etcd 仓内 `Documentation/` 只放贡献者/开发者文档并按类型分层(contributor-guide/dev-guide/etcd-internals/**postmortems**),用户文档另去 etcd.io——按受众分家、按类型分层。

## 3. 从业界共识到本项目:设计原则

本项目的特殊性:**单人 + AI 协作**(读者主要是用户本人与每次冷启动的 AI 会话)、私有仓(plan-docs 整体不入公开镜像)、中文文档、已有三条自发长出的正确机制(§1.3)。业界实践须过这层滤网:

| # | 原则 | 来自 | 落点 |

## 5. 治理规则

### 5.1 命名与开新文档的门槛

- **快照类**(designs/reviews/decisions 下):`YYYY-MM-DD-主题.md`,日期=创建日,永不改名(名即引用锚点,对应业界「编号一经分配不变」)。
- **living 类**(runbooks/ 与根目录四件):不带日期,名即主题;时效靠 frontmatter `last-verified`。
- **开新文档的门槛**(D10):同时满足「方案有歧义/有备选需要对比」且「预计正文 > 50 行」才开新文档;否则 todo.md 对应节记一行,或在既有文档追加小节。审查修复批、琐碎裁决,写 todo.md 行内备注即可。
- 新多部头工作线:`designs/<主题线>/` 子目录 + 线内自编 PartN/TN;**先在 README.md 工作线登记表登记字母/线名**(根治 todo.md 分节撞号,§1.2-P5)。

### 5.2 元数据头(frontmatter)规范

非归档的每份 `.md` 文首带标准 YAML frontmatter(键英文、值中文,与 CLAUDE.md「structural tags 保持英文」一致):

```yaml
---
status: 现行 | 施工中 | 快照 | 已归档 | 已废弃
type: 架构正典 | 设计方案 | 审查快照 | 决策记录 | 运维手册 | 施工计划 | 实验报告 | 经验沉淀 | 治理方案 | 索引
line: 主题线名(与 todo.md 分节、README 登记表对齐)
created: YYYY-MM-DD
last-verified: YYYY-MM-DD      # 最近核验日期(freshness date,g3doc 同款)
supersedes: 相对路径            # 可选:本文取代了谁
superseded-by: 相对路径         # status=已废弃/已归档 且有后继时必填
---
```

状态语义:
- **现行**:normative,可照着施工;承担「正文回写红线」义务。
- **施工中**:正在写/正在按其施工,尚未收口。
- **快照**:一轮审查/评估的定格产出,出生即带「内容=截稿日事实」的免责;仍有现行参考价值(最新一轮)。
- **已归档**:完成历史使命(施工计划已执行完、快照被更新一轮取代),内容对当时仍真实;正文冻结。
- **已废弃**:方案被推翻,**勿按其施工**;正文冻结,文首横幅指向后继。

存量文件的补头策略:活区(designs/reviews/decisions/runbooks/refactor_2026 现行件)在迁移阶段 3 补齐;archive/ 存量**不补 frontmatter,只加文首横幅**(横幅比 YAML 对人类读者更醒目,且避免大面积触碰冻结正文)。

### 5.3 生命周期(状态机与横幅)

```
                    ┌─→ 已归档(完成使命)──┐
施工中 ──收口──→ 现行 ─┤                      ├─→ (正文冻结,永居 archive/)
   │                └─→ 已废弃(被推翻)──┘
   └─(审查/评估类直接出生为)→ 快照 ──下一轮取代──→ 已归档
```

- **收口即处置**:施工计划执行完毕的收口 commit,必须同时完成「移入 archive/ + 加横幅 + 更新 README 索引 + 修活区指向它的链接」。不允许「先收口、改日再归档」——那就是 P3/P4 病灶的来源。
- **推翻即横幅**(沿用现行红线格式):文首第一行加

  > 🔴 **本文已被推翻/取代(YYYY-MM-DD)**:一句话原因。现行方案见 [<后继>](路径)。

  「已归档」用 📦 前缀同格式。整篇推翻走本条;**单节推翻仍走既有「正文回写红线」**(改写该段或段顶横幅),两者不冲突——节级纠偏在活文档内,篇级处置进 archive/。
- **归档不变量**:进 archive/ 后正文只读(仅允许追加/修订文首横幅)。归档文档内部的旧相对链接**不修**(存证原样,README 声明此规则);活区指向被归档文档的链接必须在归档 commit 中改指新路径。
- **消极状态留档**(D5):被推翻的方案不删除;横幅必须写明「为什么被推翻、被什么取代」,防同题重议(AWS ADR 同款要求)。
- **核验节奏**(D8):`status: 现行` 且 `last-verified` 超过 2 个月的文档,列入下一次全库审查的附带任务——AI 对照代码现状逐份确认「仍正确?」,更新 last-verified 或改判状态。runbooks 每次实际使用后顺手更新 last-verified。

### 7.1 刻意不做(及理由)

1. **不把任何文档移出本目录。**(🔄 2026-07-11 修订:目录已由 `plan-docs/` 更名 `docs/`,规则本体不变——copybara 排除面与 rename-gate 豁免面已同 commit 改键 `docs/` 前缀,私密性与目录叫什么名字无关;原文下述「新建顶层 docs/ = 暴露面」与「要公开的技术文档另起 docs/ 单独放行」两条推理随更名**作废**,公开技术文档改归官网仓 scrollery-site,主仓不设放行通道。)原文(2026-07-10):copybara 的公开镜像排除与 rename-gate 的旧名豁免都键在 `plan-docs/` 前缀上(§1.4);新建顶层 `docs/` 意味着文档进入同步管线的暴露面,变现与红线策略文档的泄漏风险不可接受。要公开的技术文档,按 2026-07-02 既有裁决另起 `docs/` 单独放行——那是「发布对外文档」动作,不是本次「整理内部文档」动作。
2. **不重命名 `refactor_2026/` 目录与 PartN 文件。** check_plan_canonical.mjs 硬编码其路径与文件名模式;代码注释、completed.md、AI 记忆大量引用;重命名是纯美观收益、全额断链成本。
3. **不改写任何快照/归档文档的正文。** CLAUDE.md 已有教训(转述在文档间复制传播,越传越像多方印证):大规模改写合并历史文档=制造新的转述层。用户授权的「重新整理组合」用在:**移动、分组、加横幅、建索引、todo/completed 间的整节机械搬运**(零改写移位);不用在重写历史正文上。R2-7 改名四件套之类的同题多文档,靠 `decisions/` 同日期前缀 + README 索引成组,不物理合并。
4. **不引入外部文档平台/静态站生成器**(log4brains/MkDocs/Docusaurus)。读者只有本人 + AI,都直接读 markdown;渲染站解决的是多人分发问题(D9),反而引入依赖(违背控依赖红线)。
5. **不给 archive/ 存量补 frontmatter。** 文首横幅对人类读者更醒目,且避免大面积触碰冻结正文;frontmatter 只强制于活区。
6. **不拆分跨类型的单份文档**(如 D1 签发机 = 设计+手册):拆分制造双源,按最高频用途归类即可(§4.2)。

### 7.2 风险与缓解

| 风险 | 缓解 |
