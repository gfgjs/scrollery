## 一、确定的事实（不夸大、不甩锅）

落地 Part1-T1 时，AI 多次**编造工具返回结果**：发出工具调用后没有停止生成，自己续写了"预期的结果"（假装 Edit 落盘成功、假装测试通过、编造 git diff / grep 输出），并据此继续操作。结果 working tree 被改成不一致状态，AI 反复"修复"并不存在的问题，最终回滚到事故前的 commit 重来。

**唯一确定的根因 = AI 会编造工具结果。** 至于"工具本身是否也不稳定"，AI 无法可靠区分"工具真失败了"和"AI 幻觉了调用/结果"，故**不把责任归给工具**——那只会给幻觉找台阶、稀释真正的教训。**不是上下文长度问题。**

## 二、施工铁律（逐条守）

1. **发出工具调用 = 立即停止输出。** 等真实结果回来再写下一个字。绝不在同一段里写"结果"或其后的分析/推断。
2. **任何 "success" 返回都不算数。** Write / Edit / cp 之后，必须用独立的 Read / Glob / `git diff` **看到真实内容**，才能确认落盘。（本次事故中，连"已 Write 成功"的文件，事后 Read + Glob 发现根本不存在。）
3. **一次一个关键操作**，验证通过再下一步。不要一条消息里并行多个写操作后就假设全部成功。
4. **真实与预期不符时，第一反应是 Read 真实文件、以工具输出为准**，绝不脑补解释矛盾。
5. **破坏性操作（reset --hard / cp 覆盖 / checkout --）前确认、后验证**，用 `git status` / `git reflog` 兜底。

## 三、本仓已知环境约束（客观事实，与幻觉无关，但施工须知）

- **编译/测试用 Bash 工具跑 `cargo`**，不用 PowerShell（PS 5.1 把 native 命令 stderr 包装成 NativeCommandError，退出码 0 也显示成错误，输出易误读）。只认 `test result:` / `error[` 等结构化行。
- **本机无外网 cargo**：一律 `--offline`，禁新增未缓存 crate（详见 memory `gotcha-offline-cargo`）。
- **CRLF**：`git checkout HEAD -- <file>` 在 autocrlf 下可能因换行规范化产生意外；强制恢复优先用 `git reset --hard <commit>`，并编译验证是否真生效。

## 四、适用范围

所有"动真实代码"的施工会话（依赖序 Part1→Part6→Part7→Part4→Part8 全程）。纯文档/规划会话第三节工具约束不适用，但第二节铁律 1-4 始终适用。
