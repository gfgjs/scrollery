## 1. 症状(用户真机 A/B 确认)

T4 canvas 转正后,用户报两个**滚动**症状:

1. **无极滚轮快速飞掠时滑块跳动/卡顿**(按住滑块快速拖动则正常)。
2. **快滚到位后短暂白屏再绘图**。

关键观测:**两症状在 DOM 与 Canvas 双渲染模式都复现、与节点数无关、大行高(120px)也复现只是不明显**。这条排除性证据把根因从「渲染层」逼到了两种模式**共享的 bucket 虚拟滚动引擎**([useBucketVirtualScroll.ts](../src/composables/useBucketVirtualScroll.ts),默认引擎:按需取数 + 惯性中渲染),而非 canvas、非某个渲染实现。

## 2. 诊断(已定性)

| 症状 | 根因 | 机制 |
|---|---|---|
| 快滚白屏 | 取数延迟 | `fetchBucketRows` → IPC `GET_BUCKET_ROWS` 的**载荷往返**:每段 ~600 项,每项曾携带 `thumbhash: number[]`(~28 字节,JSON 化 ~100 字节)。后端 `get_bucket_rows`([cache.rs](../src-tauri/src/layout/cache.rs))是二分查找 + 克隆的快查询,不是重算——瓶颈在载荷序列化/反序列化与传输,不在查询。 |
| 滑块卡顿 | 段落地爆发抢主线程 | 快滚中每段落地触发「反序列化 + 挂载/重绘」爆发;挂载/取数速率 ∝ velocity × 列数/行高。滑块由 `currentLogicalY` 驱动、rAF 同在主线程,爆发期无法解耦 → 滑块跳。 |

两者本质是**同一「按需取数 + 惯性中渲染」架构的两个投影**:载荷往返造成延迟(白屏),反序列化 + 挂载爆发抢主线程(rAF 驱动的滑块跳)。故先前调段大小(a5a126d 段高按行高自适应 `clampSegmentPx`)只改「爆发形态」不改「速率」,体感改善有限。

## 3. A/B/C 决策(2026-07-10 用户拍板)

诊断后给出三条路线:
- **B(针对滑块卡顿)**:快滚甩滚低保真——飞掠期推迟图片加载启动、降速/停稳再载(业界 fling 标准做法)。
- **A(攻白屏)**:方向性预取 或 瘦身取数载荷(thumbhash 不以 JSON 数组过桥)。
- **C(收尾归档)**:把残留当按需架构已知边界。

用户拍板:**先做 B 看效果,再做 A**。B 真机达标后用户要求「继续优化」,遂追加**续优化甲 + 乙**。

## 4. 交付明细

### 4.1 B · 快滚甩滚低保真加载闸门(commit `0a39e31`)

- **机制**:新建模块级单例闸门 [useThumbLoadGate.ts](../src/composables/useThumbLoadGate.ts),由 `MediaGrid.onGridScroll` 按**物理滚动速度**置位。飞掠中(velocity > 阈值)抑制**新**缩略图 decode/生成请求的启动,降速或停稳后放行补起。已缓存/已解码的图照常绘制;闸门只抑制加载**启动**、不丢加载(放行时各 loader/canvas 的 `watch` 补起);停稳 settle 兜底保证最终必放行。
- **为何模块单例而非 prop 穿透**:DOM 模式信号需穿 MediaGrid→MediaGridRow→卡片→useThumbLoader 四层,给数千张 compact 卡传响应式 prop、每次翻转触发全量 re-render 本身就是一次 hitch。单例让「真正发起加载的 loader」各自 watch,零 prop 穿透、零卡片 re-render(镜像 `useSelection.setPointerIdResolver` 惯例)。
- **闸门变量是速度而非 `isScrolling`**:代码里 `isScrolling` 对慢滚也为 true,直接用它 gate 会令慢滚全程不出图;症状只在快速飞掠出现(爆发速率 ∝ velocity)。故抽纯函数 `scrollVelocity` + `shouldDeferThumbLoad`(阈值 3px/ms,[mediaGrid.helpers.ts](../src/components/media/mediaGrid.helpers.ts),+10 测)——慢滚照常出图、快滚才抑制。
- **接线**:`useThumbLoader.loadThumb` 顶部 gate 判定→挂待载标,watch 闸门放行补起(覆盖 MediaThumb + MediaThumbCompact 两种 DOM 卡);`MediaGridCanvas.getImage` 命中缓存后、发起加载前 gate 拦截,watch 闸门放行触发重绘;canvas 的「一屏 N 张 Image() 齐发」爆发受益最大。
- **真机验收**:dropped 从飞掠期 5–11/burst 降到 **0–1**,白屏几乎不可见。

### 4.2 甲 · 削「停稳后略微延迟」(commit `da43dfa`)

- 无极滚轮**急停**时最后一帧速度高、闸门仍关,若只靠 150ms settle 兜底放行则出图偏慢。新增 `GATE_RELEASE_MS`(64ms ≈ 4 帧)专用短去抖:滚动停顿即放行闸门,比 settle 早 ~86ms 出图。取值 > 飞掠帧间隔(~16ms)故动量途中不误放;慢滚时闸门本已 false,此路径幂等 no-op。

### 4.3 乙 · 载荷瘦身:占位色后端 hydrate 算好(commit `8078d7c`)

- **核实**:画廊三消费点(`MediaGridCanvas` / `MediaThumb` / `MediaThumbCompact`)对 thumbhash **全部只调 `thumbhashToAverageColor` 取一个平均色**;完整 blur data-URL 只在实验视图 HGalleryLabView 用。即「为了一个占位色,每项过桥一个 ~28 字节 thumbhash 数组 × 600 项/段」——既是白屏(取数载荷)源,又是段落地反序列化爆发源,还附带 canvas `draw` 每帧逐格现算均色。
- **做法**:后端 `hydrate_item`(仅可视区 ~10² 项)由 thumbhash 算好占位平均色 `#rrggbb` 过桥,`LayoutRowItem.thumbhash` 字段整体替换为 `placeholder_color`;前端直接用、消灭渲染热路径逐格逐帧均色计算。**保住彩色占位质感**(非退化为固定灰——用户曾提议固定灰,经权衡:前端改灰不动后端 = 零性能收益,而既然要动后端,紧凑色的载荷收益与丢弃几乎一样大却保质感,故选紧凑色)。
- **跨语言一致性**:`thumbnail/thumbhash.rs::average_color_hex` 复用 `thumbhash` crate 的 `thumb_hash_to_average_rgba`(golden 生成器同一函数),与前端 TS 移植版在 ±2/通道内一致(前端 `thumbhash.spec.ts` 已锁此容差);Rust 单测断言金标 `landscape_gradient` hash → `#7a7e80`,锁死跨语言一致。`MediaGrid.onRequestThumb` 生成结果回填改算 `placeholderColor`(单项、罕发,±2 不可辨)。
- **共享文件写冲突处置**:`justified.rs` / `layout.ts` 为与并行会话(时间轴 epochDay 重构)共编且对方未提交。本提交经 **hunk 级 `git apply --cached`**(按 `placeholder_color`/`average_color_hex` vs `epoch_day` 代码标记自动分拣)仅纳入本变更 4+1 处,并行会话未提交工作原样留在工作树、分毫无损——已逐项核验(暂存区 0 行对方内容、工作树保留对方 55 行)。

## 6. 残留与已知边界(收口)

飞掠卡顿的**可解结构性开销已全部处理**(B 加载爆发 + 甲 释放延迟 + 乙 载荷/均色计算)。剩余属**按需架构固有开销**,性价比低,收口不再攻:

1. **DOM 模式逐格挂载**:段落地时创建/卸载逐格 DOM 节点是按需虚拟滚动的固有成本,B 只砍其中的 decode 部分、挂载本身不可消(canvas 模式无此项,故 canvas 飞掠体感更平)。
2. **真图 decode**:停稳后占位色 → 真缩略图的 decode/paint 是不可消的真实工作;甲已把「闸门释放延迟」这段人为延迟削掉,剩下的是浏览器解码本身。
3. **方向性预取(原 A 的另一半)**:白屏已基本消失,方向性预取收益不确定、高速下未必兑现,**不做**;若将来真需百万级库再评估。
4. **canvas 是否长期投入 / G-T3(decoding=async)**:属「画廊极密网格专项」母线的独立待决项,与本滚动飞掠线正交,见 todo.md §G 专项行。
