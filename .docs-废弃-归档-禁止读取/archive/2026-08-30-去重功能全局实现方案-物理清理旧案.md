# 去重功能全局实现方案

## 1. 结论先行

Scrollery 的首个去重版本只解决**字节级精确重复**，采用独立后台分析、持久内容索引、重复组人工复核和分级清理的闭环：

> 文件大小候选 → 快速摘要筛选 → 完整内容摘要确证 → 逻辑资产分组 → 人工选保留项 → 应用回收站 → 可选物理清理

核心裁定如下：

1. `media_items` 继续表示“一个库内位置/文件项”，不把全仓重构为 content/asset/location 三层模型。
2. 现有 `content_hash` 是抽样变更指纹，不是精确内容身份；两种语义必须拆开。
3. 精确去重不进入常规扫描热路径，而是低优先级、可暂停、可续跑的独立任务。
4. 新增按 `item_id + source_revision` 失效的 sidecar 索引；摘要存 32 字节 BLOB，算法带版本。
5. Live Photo 是由主文件和 companion 共同构成的逻辑单元，必须按组合摘要分组。
6. 首版只提供“建议”，不自动删除；独特用户元数据冲突时强制人工选择。
7. “移到 Scrollery 回收站”和“移到系统回收站”是两个产品动作：前者可撤销但不释放磁盘空间，后者才可能释放空间。
8. 物理清理必须另建事务式作业，不能复用当前 `remove_media_items_hard`。

近似图、裁剪图、转码图和语义相似内容不属于本方案。它们未来可以复用审查界面，但不能复用精确重复的证据与删除规则。

## 2. 当前事实与必须推翻的假设

### 2.1 施工前事实与已落地模型

- `media_items` 是一条路径一行，`(directory_id, file_name)` 唯一；大量相册、标签、人脸、AI、编辑版本和书签数据直接以 `item_id` 关联。
- `content_hash` 继续保留为可空的扫描变更指纹，不是精确内容身份；新文件也不依赖它作为入库前置条件。
- 施工后的 schema 为 V30：`file_mtime_ns`、`source_revision`、版本化 `dedup_index`、
  `dedup_cleanup_journal.quarantine_path` 及清理授权快照已落地；V30 同时把历史路径派生卷
  降为 `unknown`，避免未确认卷类型的旧行开放物理清理。
- 常规扫描仍使用轻量 change fingerprint；精确分析单独流式计算版本化 BLAKE3-256。大文件的头/中/尾抽样只用于候选筛选，不参与重复或删除证据。
- 同秒同大小改写由纳秒 mtime 进入可疑变更路径；即使 change fingerprint 恰好相同，也会推进 `source_revision` 并清除旧 exact digest，避免抽样漏检重新污染重复组。
- 文件复制/编辑输出通过普通扫描或 ingest 建立自己的 mtime/source revision；精确摘要必须在目标文件上重新确证，不能继承源项摘要。

因此，直接 `GROUP BY content_hash` 会同时产生漏报、旧值误用和大文件假阳性，不能成为删除依据。

### 2.2 删除语义与已落地安全闸门

- 软删除只更新 `is_deleted`，会扩展 Live Photo companion，应用内可恢复，但物理文件仍在，释放空间为零。
- 历史 `remove_media_items_hard` 已补上系统回收站失败即返回的安全闸门；去重清理仍使用独立 journal 路径，不复用该通用命令的编排。
- 去重物理清理先完整预检和复核，再按 journal 记录移动、成功持久化、数据库收尾；系统回收站失败或 DB 收尾失败均保留媒体行。
- 删除 `media_items` 会级联大量关联数据，并可能要求重新汇总人物聚类等派生状态。

因此，已有软删除可以作为首版安全动作；已有硬删除不能作为去重清理实现。

### 2.3 P0 扫描并发前置缺陷（已修复）

当前扫描状态存在两个去重任务也不能继承的代次问题：

1. 同一根目录重启扫描时，旧任务结束会按 root 无条件移除 token，可能移除新任务 token。
2. missing 标记使用按 root 命名的 seen 临时表；不同 root 已隔离，但同一 root 的旧、新任务仍可能清空或复用同一张表。

施工中已改为 generation-aware compare-and-clear，seen/online 临时表带 run generation；旧任务不能清理新任务 token、seen 或新状态。

## 3. 方案比较

| 方案 | 正确性 | 扫描性能 | 改造面 | 裁定 |
|---|---:|---:|---:|---|
| 直接复用 `content_hash` 分组 | 不足 | 好 | 小 | 否决：它不是精确身份 |
| 每次扫描内联完整 hash | 高 | 差 | 中 | 否决：污染高频热路径并耦合失败 |
| 即点即算、不持久化 | 高 | 一般 | 小 | 否决：大库重复工作，无法可靠续跑 |
| 全仓 content/asset/location 范式重构 | 高 | 可控 | 极大 | 延后：首版收益不足以覆盖波及面 |
| 独立任务 + sidecar 精确索引 | 高 | 好 | 中 | **采用** |

即使当前不要求兼容旧实现，全仓规范化也不是更优首版：现有用户状态和派生数据以位置项为中心，强行迁移只扩大状态合并、编辑归属和离线卷语义的决策面，并不提高精确去重的核心正确性。

## 4. 数据契约

### 4.1 `media_items` 的源代次

新增或等价实现：

```sql
ALTER TABLE media_items ADD COLUMN file_mtime_ns INTEGER;
ALTER TABLE media_items ADD COLUMN source_revision INTEGER NOT NULL DEFAULT 1;
```

- 扫描确认内容可能变化、文件被替换或 companion 关系变化时，递增 `source_revision`。
- mtime 变化且 change fingerprint 相同时：若为抽样 `sha256s:`，仍递增 `source_revision`、清除 exact sidecar，并让普通派生/缓存换代；只有可信完整 `sha256:` 才可保留普通派生元数据和缓存键。两者均不复用 exact sidecar，因为抽样指纹无法覆盖大文件全部字节。
- 仅路径移动且物理内容身份已被可靠保持时，可以保留代次。
- 任何摘要结果写回都必须带 `WHERE item_id = ? AND source_revision = ?`；影响行数为零即丢弃旧结果。
- 现有 `content_hash` 应重命名为 `change_fingerprint`，或新增字段迁移其语义；它仅用于扫描变化侦测。

### 4.2 `dedup_index`

首版不物化永久 duplicate group。组由版本化 `unit_digest` 动态查询，避免维护第二套易漂移成员关系。

```sql
CREATE TABLE dedup_index (
    item_id          INTEGER PRIMARY KEY
                     REFERENCES media_items(id) ON DELETE CASCADE,
    source_revision  INTEGER NOT NULL,
    hash_version     INTEGER NOT NULL,
    quick_digest     BLOB,
    exact_digest     BLOB,
    unit_digest      BLOB,
    unit_size        INTEGER,
    physical_key     BLOB,
    link_count       INTEGER,
    status           TEXT NOT NULL,
    error_code       TEXT,
    checked_at       INTEGER NOT NULL
);

CREATE INDEX idx_dedup_exact_candidate
ON dedup_index(exact_digest, item_id)
WHERE exact_digest IS NOT NULL;

CREATE INDEX idx_dedup_unit_group
ON dedup_index(unit_digest, unit_size, item_id)
WHERE unit_digest IS NOT NULL;
```

约束：

- 摘要用 BLOB，不存十六进制文本。
- `hash_version` 同时覆盖算法、域分隔和组合摘要编码；升级时旧行自然失效。
- 缺行代表 pending，不用为全库预建空行。
- `physical_key` 仅用于硬链接识别和空间估算，不是跨挂载永久身份。
- 查询结果只返回分页游标和当前页，不通过 IPC 传递全库 ID 数组。

### 4.3 逻辑单元摘要

普通文件：

```text
unit_digest = H("scrollery/single/v1" || size || exact_digest)
```

Live Photo 主项：

```text
unit_digest = H(
  "scrollery/live-photo/v1" ||
  main.size || main.exact_digest ||
  companion.size || companion.exact_digest
)
```

companion 自身保存 `exact_digest`，但不作为独立重复组成员。主文件相同、伴生视频不同的两个 Live Photo 不是精确重复。

## 5. 分析流水线

### 5.1 范围

- 默认分析数据库中可见、未删除、在线扫描根内的已索引主项。
- 不重新遍历未知目录；用户应先扫描资料库。
- 离线卷保留既有有效索引，但默认不参与“可立即清理”候选。
- 零字节文件默认不显示，避免噪声；可通过高级筛选查看。
- 网络卷沿用扫描根状态和系统能力检查；物理清理是否可用由预检返回，不把网络卷当作天然安全。
- 当前 IPC 版本先实现库级分析；非空 `rootIds` 会返回稳定的 `DEDUP_INVALID_SCOPE`，不会假装提供根范围分析。

### 5.2 候选与摘要

1. SQL 先按精确 `file_size` 找数量大于 1 的候选桶。
2. 所有候选先计算带域分隔的头/中/尾快速摘要；小文件的窗口可能覆盖全部内容，但仍统一走候选筛选阶段。
3. 仅对快速摘要碰撞桶流式计算完整 BLAKE3-256；完整摘要才是重复证据。
4. 快速摘要使用固定头/中/尾 256 KiB 窗口；完整摘要使用固定 2 MiB 缓冲顺序读取，不 mmap。
5. 当前分析器采用低优先级单后台线程和受控批量写回；吞吐以同设备顺序读取基线校准，不把统一 MB/s 作为产品承诺。

BLAKE3 适合当前以吞吐量优先的本地完整性识别。若依赖落地受阻，SHA-256 仍是正确但较慢的替代；无论哪种算法都必须版本化，且不能沿用抽样 hash。

### 5.3 文件漂移防护

每个文件在打开后和读完前后核对：

- 文件大小；
- 纳秒修改时间；
- 平台文件身份；
- `source_revision`。

任一变化即标记 stale/unstable，不发布摘要，稍后重试。文件 IO 绝不在 SQLite writer mutex 内执行；只把结果分批短事务写回。

扫描侧的 change fingerprint 只用于判断是否需要进入可疑变更路径，不能替代 exact digest。mtime 变化且指纹相同时，抽样 `sha256s:` 仍必须推进 `source_revision`、切换普通派生/缓存代次并清除 dedup sidecar；可信完整 `sha256:` 才可以保留普通 EXIF/派生缓存。两者都不复用 exact sidecar；这同时覆盖大文件未抽样区域改写和 Live Photo companion 触发主项组合摘要过期。

### 5.4 调度与可恢复状态

- 使用与 `RunTokenSlot` 相同的 generation-safe token 模式，旧任务只能 compare-and-clear 自己的代次。
- 摘要结果持久化，因此停止后下次从有效行续跑，不需要保留庞大内存快照。
- 分析是低优先级只读任务：扫描、缩略图、派生和文件操作活跃时主动让步。
- 进度沿用后端快照 + Tauri 事件：刷新页面后通过 `dedup_status` 恢复，不依赖 WebView 内存状态。

推荐进度字段：`runId`、`status`、`phase`、`itemsDone/Total`、`bytesDone/Total`、`groupsFound`、`potentialLogicalBytes`、`errors`、`waitingOn`。

## 6. IPC 与模块边界

推荐最小命令面：

- `start_dedup_analysis(scope, reset)`
- `stop_dedup_analysis()`
- `dedup_status()`
- `list_duplicate_groups(cursor, limit, filters)`
- `list_duplicate_members(group_key, cursor, limit)`
- `preflight_dedup_cleanup(selection)`
- `apply_dedup_soft_delete(preflight_token)`
- `purge_dedup_to_system_trash(preflight_token)`（当前 Live Photo 物理清理会由预检明确禁用）

错误必须是可序列化稳定码，例如 `DEDUP_BUSY`、`SOURCE_CHANGED`、`KEEPER_REQUIRED`、`PATH_OUTSIDE_ROOT`、`TRASH_UNAVAILABLE`；不把原始内部错误字符串暴露到前端。

建议文件边界：

```text
src-tauri/src/dedup/{hash,index,cleanup}.rs
src-tauri/src/db/queries/dedup.rs
src-tauri/src/ipc/dedup_commands.rs
src/stores/dedupStore.ts
src/views/DuplicatesView.vue
```

命令须在 `src-tauri/src/ipc/registry.rs` 显式登记；本项目的 `capabilities/default.json` 只声明 Tauri 原生插件权限，业务 command 由 `generate_handler!` 注册，不另造无效的插件 ACL。

## 7. 重复组产品与交互

新增懒加载路由 `/duplicates`，作为 Library 下的独立 lens，不套现有 GalleryRouteLayer：重复组是聚合行，不是一张媒体卡。

页面采用高密度、可访问、虚拟化列表：

- 顶部显示重复组数、额外副本数、覆盖率、错误数和“潜在逻辑大小”。
- 每组展示路径/扫描根、大小、修改时间、在线状态、硬链接、Live Photo、收藏/评分/相册/标签/书签等保护标记。
- 每组恰好一个 keeper（单选）；其他成员用复选框表示待处理。
- 可提供 keeper 建议，但只由“选择建议”按钮应用，不自动执行清理。
- 多个成员各有独特用户元数据时标为冲突，首版不静默合并，必须人工决定。
- 长列表使用现有 `@tanstack/vue-virtual`；大数组用 `shallowRef`，稳定 key，语义化按钮和键盘焦点。

建议 keeper 评分只用于排序：在线且当前可验证 > 用户状态更丰富 > 路径更像原始库 > 更早入库。评分不能替代最终确证。

文案必须明确区分：

- **移到 Scrollery 回收站**：应用内可恢复，释放空间 0。
- **移到系统回收站**：应用内不可撤销，可尝试从系统回收站恢复；真正释放空间通常还需清空系统回收站。

`file_size` 是逻辑长度。硬链接、稀疏文件、压缩文件、APFS/NTFS clone/reflink 会让实际可回收空间更小，所以只能展示“潜在逻辑大小”，不能承诺可释放字节数。

## 8. 清理安全模型

### 8.1 首版：应用回收站

在执行软删除前重新校验 group key、成员 `source_revision`、keeper 仍存在且未被选择删除，并按逻辑单元扩展 companion。任一成员变动则整个组返回 `SOURCE_CHANGED`，要求刷新复核。

### 8.2 已落地基础与安全边界：物理清理

物理清理是独立阶段，使用持久 `dedup_cleanup_journal`，逐项记录 planned/moving/moved/succeeded/failed/recovery_required。预检与执行必须：

1. 保证删除集合之外至少有一个重新验证的 keeper。
2. 展开全部 companion。
3. canonicalize 路径并确认仍位于已注册扫描根内。
4. no-follow 打开普通文件，核对 physical identity、大小、mtime_ns、source revision。
5. 对待删项与 keeper 重新做完整摘要，或组件级逐字节比较。
6. 先写入 `moving` journal，再在同一父目录创建独占隔离目录并原子 rename；隔离路径写入
   `quarantine_path` 后才允许文件动作，系统回收站只接收隔离路径。V30 同时保存 size、纳秒
   mtime 等删除授权快照，供重启后的 DB 收尾复核。
7. rename 后再次完整核对摘要和 physical identity；成功移动到系统回收站后持久化
   `moved/succeeded`，最后删除 DB 行。系统回收站失败、状态不确定或 DB 收尾失败均保留媒体行。
8. 启动时利用 journal 对“文件动作或 DB 收尾中断”等状态做对账：隔离文件仍存在且原路径
   为空时，在释放 DB writer 锁后以 no-replace 方式恢复；恢复失败或隔离文件已消失则标记
   `recovery_required`，不猜测系统回收站状态。只有逐项 journal 明确为 `succeeded` 且媒体行
   仍存在时才允许重试 DB 收尾，混合成功/失败批次也按 item 独立收敛。
9. 所有文件 stat、摘要、rename、恢复和系统回收站调用都不持有 SQLite writer mutex；
   journal 更新只使用短事务。

清理阶段持有 `file_job_owner`，分析阶段不长时间持有它。

Live Photo 的物理清理需要逻辑单元原子性。当前版本明确排除包含 companion 的物理清理，只允许软删除；普通文件虽有同卷 quarantine staging，仍未为多组件操作建立全组件成功保证，不能交付可能只删除一半组件的实现。

当前能力矩阵由预检和稳定原因码共同约束。Windows 桌面固定本地卷的句柄绑定 quarantine、journal 和恢复基础已实现，但当前版本不启用系统回收站交接：公开 Shell 删除 API 只能按路径接收 `IShellItem`，无法证明它仍绑定到预检句柄的物理对象；因此 `physical_cleanup_supported()` fail closed，物理 purge 返回 `PHYSICAL_CLEANUP_UNSUPPORTED`，正常 IPC 不会删除 DB 行。Windows 可移动卷、网络卷、未知卷、UNC 根，以及非 Windows 桌面平台同样只保留应用回收站。Live Photo（含任一 companion）在所有平台均禁用物理清理。重新启用系统回收站前必须实现句柄绑定的原语，并用真实 Windows 卷和替换竞态矩阵验收；不能仅凭 Linux/内存测试宣称跨平台已验证。

## 9. 硬链接与重复扫描根

walker 跳过符号链接，但不能阻止硬链接或同一物理文件被不同扫描根覆盖。分析时应以平台稳定文件 handle 提取 physical key：Unix 使用 device/inode，Windows 使用 volume serial + 128-bit `FILE_ID_INFO.FileId`。

- 多条记录指向同一 physical key 时，可作为“同一物理文件的多条位置记录”显示。
- 它们不应计入可回收物理空间；删掉非最后一个硬链接通常释放 0 字节。
- physical key 只在当前挂载和本次复核中使用，路径可能被替换，清理前必须重取。
- 符号链接继续不跟随，路径边界检查不能只依赖字符串前缀。

## 10. 分阶段施工

### P0：先修正确性地基

- 扫描 token generation-aware compare-and-clear。
- 同 root seen 状态 run-specific，或串行化到旧任务真正退出。
- 明确拆分 change fingerprint 与 exact digest。
- 禁止去重复用当前硬删除路径；去重物理清理使用独立 journal，历史通用硬删也不再在系统回收站失败后删除 DB 行。

### P1：精确内容索引

- `file_mtime_ns`、`source_revision`、`dedup_index` migration。
- 流式 BLAKE3、快速筛选、前后状态复核、分批写回。
- 普通文件与 Live Photo 组合摘要。

### P2：任务与查询

- generation-safe run state、停止/续跑、进度事件与状态快照。
- duplicate group/member keyset pagination。
- 大库查询和 writer lock 基准。

### P3：复核与软删除

## 11. 验证门槛

### 11.1 必测行为

- 同大小不同内容不能合组；抽样窗口相同但中间不同的大文件不能合组。
- 同秒、同大小改写能使旧摘要失效。
- hash 期间替换、截断、删除文件时不发布旧结果。
- 旧 run 结束不能清理新 run token 或覆盖新状态。
- 硬链接、重复扫描根、离线卷、missing、应用回收站均有确定语义。
- Live Photo 主文件相同但 companion 不同不能合组。
- 全选删除、keeper 漂移、路径越界、symlink、stale group 必须拒绝。
- 系统回收站失败时 DB 行和用户元数据保持。
- cleanup journal 能恢复各崩溃切点。
- 百万行合成库采用 keyset 分页，内存不随全库成员线性增长。
- 前端保证每组一个 keeper、建议不自动执行、确认文案区分两种回收站、进度刷新可恢复。

### 11.2 性能验收目标

- 分析器额外常驻内存保持 `O(batch + workers × buffer)`，初始目标小于约 64 MiB（不含 OS page cache）。
- SQLite writer lock 持有 p95 初始目标小于 20 ms。
- 取消延迟由一个读块限制，目标小于 500 ms。
- hash 吞吐以同设备顺序读取基线为准，目标不低于其 70%，不设跨设备统一 MB/s。
- 常规扫描不计算完整摘要，扫描性能回归目标小于 3%。

这些数值是首轮验收预算，应由 Windows/macOS 本地 SSD、网络卷和移动设备实测校准，不是公开产品承诺。

### 11.3 CI 与手工验证

按改动面执行 rustfmt、cargo check/clippy/test、前端 lint/typecheck/vitest/build，并接入 `.github/workflows/ci.yml`。CI 覆盖代码、内存夹具和测试临时目录；Windows 系统回收站成功/失败、固定盘与可移动盘识别、硬链接/重挂载、网络卷及 iOS/Android scoped storage 仍需手工验证。首版不在真实用户媒体上做破坏性自动化测试。

## 12. 非目标与暂缓项

- 不自动删除，不后台静默应用 keeper 建议。
- 首版不合并相册、标签、评分、编辑版本等冲突元数据。
- 不承诺实际释放空间等于逻辑大小。
- 不在常规扫描中为所有文件计算完整 hash。
- 不把 sampled fingerprint 当安全证据。
- 不为首版引入永久 duplicate-group 物化表或全仓内容范式迁移。
- 不把近似重复与精确重复混成同一删除等级。

## 13. 参考调查的处理

两条参考会话实际是一次主任务及其只读侦察分支，不是两份独立证据。其“独立精确分析 → 重复组审查 → 可撤销清理”方向被保留；“现有 hash/软删除链足以直接承担去重闭环”则被当前代码事实否决。本文以 2026-08-31 当前工作树、测试输出和主代理终审为准。

## 14. 施工后裁定（2026-08-31）

- P0–P3 已落地；P4 的 cleanup journal、预检、同卷 quarantine、恢复和应用回收站已接入现有入口，但系统回收站交接当前 fail closed，不能把 P4 物理释放宣称为可用。
- `content_hash` 仍只承担 change fingerprint。可疑 mtime 变化即使指纹相同，也推进 `source_revision` 并清除精确 sidecar；companion 变化同时使主项组合摘要失效。
- 若未来启用物理清理，执行顺序固定为预检/复核 → `moving` journal → 同卷 quarantine 原子 rename →
  隔离路径复核 → 系统回收站 → 持久化成功 → DB 删除 → 对账。当前系统回收站步骤因无法证明句柄绑定而
  fail closed；回收站失败或 DB 失败不删除媒体行；Live Photo 物理清理首版明确禁用。启动对账的文件动作在 writer 锁外执行。
- 当前 `DedupScope::Roots` 的非空范围返回 `DEDUP_INVALID_SCOPE`，首版只分析整个可见资料库；离线/零字节默认隐藏但可由查询筛选显式包含。
- Windows 当前仅实现固定本地卷的身份读取、句柄绑定 quarantine 基础和 fail-closed 能力检查；系统回收站交接尚未开放。Windows 可移动/网络/未知/UNC、非 Windows、Live Photo 均明确禁用物理清理；重新开放前的系统回收站、真实硬链接/重挂载和移动端 scoped storage 仍需平台手工验收。自动化测试只使用临时目录，不触碰用户真实媒体。
