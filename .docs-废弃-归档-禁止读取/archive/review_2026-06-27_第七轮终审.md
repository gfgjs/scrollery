### 1.2 verify_token/Ed25519「留开源不 gate」vs「channel-direct 物理排除」三处口径打架

- **status**：new（canonical 未机械收敛的残留矛盾）
- **锚点**：
  - [Part6:263](Part6_插件平台与exotic收尾.md) / [Part6:485](Part6_插件平台与exotic收尾.md) §8.7：「verify_token + VerifyingKeyset + verify_strict **留开源、不下沉**」
  - [Part6:462](Part6_插件平台与exotic收尾.md) §8.4：「ring::aead/ring::hkdf/**verify_token**/fetch_package HTTPS 加 `#[cfg(feature=channel-direct)]`」

  - [Part7](Part7_发布工程.md) RK3/§6/T11 + [Part0:361](Part0_总纲与产品定稿.md) §9.3：「msstore build `strings`/`cargo tree` 扫无 Ed25519 符号，零命中才过」
- **亲验**：[license.rs:131](../../src-tauri/src/exotic/license.rs) `verify_token`、[crypto.rs:170](../../src-tauri/src/exotic/crypto.rs) `VerifyingKeyset::verify` 当前在开源核心、**无任何 cfg gate**；evaluate_token / KeyringLicenseStore 均直接调 verify_token。三者不可同真：留开源不 gate → msstore 二进制必含 Ed25519 符号 → Part7「零 Ed25519」验收注定 fail；给 verify_token 加 cfg → 所有引用处连锁编译失败。
- **终审校正**：原 finding 将「下沉(open-core 轴)」与「cfg 门控(channel 轴)」略混谈（二者正交：verify_token 可既留开源仓、又在 msstore build 被 cfg 编译排除）。但**核心机械结论成立**——§8.7「留开源」与 Part7「零 Ed25519 符号」验收不可同真。
- **修法（推荐 A）**：承认 Ed25519 验签符号留 msstore 二进制可接受（公开算法、无密钥材料、不违 Store 合规——Store 禁的是「下载-执行代码」非「签名验证」）；把 Part7 RK3/§6/T11 验收从「无 Ed25519 符号」**收窄为「无 AES/keyring/updater/下载-执行路径符号」**（对齐 Part6:462 实际口径）；删 Part0 §9.3:361「Ed25519 加 channel-direct」；消除 Part6:263/485 与 :462 自相矛盾。
- **票型**：evidence + blocker **双 lens 双 P1 双 refuted=false**。注：§3 正文(§3.11)自身就与 §8.7 相左 → 该矛盾**未被「§3 正文为唯一权威」机械消解**。

### 1.3 层2 在线激活无 PoP/nonce，subject_hash 客户端自报 + HMAC key 公开 → 设备绑定/激活计数可绕过

- **status**：new（= 第 6 轮 P0-8「needs-human、挑战机制确未见」的落实）
- **锚点**：[Part8:238-242](Part8_商业化与分发.md) §3.3.1「`subject_hash=HMAC-SHA256(license_id, cpu||disk)` → `POST{license_id, subject_hash}`（仅两项，无 PII/无签名/无 nonce）→ 服务端查激活次数 ≤N」；[Part8:249](Part8_商业化与分发.md) §3.3.3a 只补 activation-* 签发密钥治理、未补 PoP/nonce。
- **亲验**：[license.rs:42](../../src-tauri/src/exotic/license.rs) `pub license_id: String` 是 LicensePayload **明文字段**，token = `base64url(payload_json).base64url(sig)`（[license.rs:4](../../src-tauri/src/exotic/license.rs)）→ payload 明文可解 → license_id 公开 → 以其为 HMAC key 时 **HMAC 退化为公开-key 哈希**（仅「不传硬件原值」的混淆价值，无认证价值）；激活端无签名/nonce → 持泄漏 token 者可对任意硬件自算合法 subject_hash、重放激活。
- **后果**：层2 宣称「挡退款滥用 + 无限设备激活」（§3.3 定位）+ Part0 §8.2 层1b「挡 token 共享/VM 直拷」**被自身设计部分击穿**：陌生人持泄漏 token 的 license_id 可在 ≤N 台设备自助激活、消耗正版激活槽、新机重激活即获新设备绑定 token。**与 RK13 是不同攻击面**（RK13=解密权重；本条=冒名激活），§5 RK 表未单列。
- **修法**：§3.3.1 激活请求改回传**完整签名 token**，服务端先 `verify_strict` 验签确认持有合法 token 再计数（PoP）；或加服务端 nonce 挑战-响应防重放。§5 RK 表新增独立「冒名设备激活」条目（勿与 RK13 混）。**或**显式把层2 强度下调为「仅退款 CRL、不宣称设备绑定防绕过」对齐 §8.3 诚实评级。
- **定级说明**：层2 为可选、默认离线不依赖（一 blocker lens 倾向 P2/P3）；但「挡无限设备激活/防直拷」的**肯定表述未被 §8.3 收回，宣称-实际不符是实质接缝** → 终审采 **P1**（求真务实：安全宣称不得强于实际）。
