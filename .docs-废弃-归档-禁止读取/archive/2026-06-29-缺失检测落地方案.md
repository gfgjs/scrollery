# 缺失检测（Missing Detection）落地方案

> 📦 **已归档(2026-07-10 文档治理)**:缺失检测四道闸核心闭环已落地(Part2 §3.3 有账);本档为当时的分阶段施工计划存证。

> 范围：Part2 §3.2「离线守门 + 删除检测」的**可执行落地序**。这是全 plan 标注的**最高危数据安全子系统**（§5「缺失误标·最高危」）。本文档把 Part2 的设计落到**当前真实代码**上，给出分阶段、每阶段独立可验证可提交、删除能力**最后才上线**且先经 dry-run 的执行蓝图。
>
> 基准：Part2_扫描与画廊流水线.md §3.1/§3.2/§4（权威设计）。本文档只做**执行序 + 代码落点 + 守门矩阵 + 测试 + 灰度**，不重述设计动机。

## 0. 核心不变量（任何阶段都不得违反）

1. **离线 ≠ 删除**：卷离线绝不触发差集。
2. **不完整扫描 ≠ 删除**（比 1 更广，terminal review 补）：遍历有任何错误（权限/IO/网络盘半断）→ seen 集不完整 → **绝不差集删除**。
3. **扫描缺失 ≠ 用户删除**：缺失写 `availability='missing'`（可自动复原），**绝不写 `is_deleted`**（仅用户回收站）。
4. **识别失败的卷视为始终在线**（宁可不删、不可误删）。

## 2. 分阶段实施序（删除能力最后上线）

> 原则：**先把"采集完整性 + 状态机"做扎实（零删除、零数据风险），再做平台探测，最后才接入会写 `missing` 的差集——且先 dry-run。** 每阶段一个中文 commit，独立 `cargo test` 绿。

### 阶段 A — WalkReport 完整扫描门闩（平台无关，零删除）

**落点**：`scanner/walker.rs` + 唯一调用方 `fast_scan.rs:290`。

- `walk_media_files` 返回类型 `Result<Vec<WalkedFile>>` → `Result<WalkReport>`：
  ```rust
  pub struct WalkReport {
      pub files: Vec<WalkedFile>,
      pub errors: Vec<WalkError>,   // 遍历/metadata 失败明细（path + 原因 code）
      pub complete: bool,           // errors.is_empty()（即「seen 集完整、允许差集」）
  }
  ```
- 把 `.filter_map(|e| e.ok())` 改为显式 `match`：`Err` 推入 `errors`（记 path + 错误类型），不再静默丢。
- `metadata()` 失败：推入 `errors` 而非裸 `continue`。
- `cancel` → 仍 `Err(Cancelled)`（取消不是「完整扫描」，天然 `complete=false` 语义由调用方按 Err 处理）。

**验收**：单测——临时目录含一个无权限/不可读项时 `complete==false` 且 `errors` 非空；全部可读时 `complete==true`。**本阶段不接差集，纯采集信号**。

### 阶段 B — seen_ids 累积（含 Unchanged）+ missing→online 自动恢复（零删除）

**落点**：`fast_scan.rs` 批量循环 + `db/queries.rs` upsert。

- 批量循环前声明 `let mut seen: HashSet<i64> = HashSet::with_capacity(total)`；每个文件 upsert 后**立即** `seen.insert(outcome.id())`——**放在 [:397](../src-tauri/src/scanner/fast_scan.rs#L397) 的 exotic `if`/`continue` 之前**（这是 T5 的硬要点：Unchanged 也必须进 seen）。
- `upsert_fast_scan_item` 的 UPDATE 分支加 `availability = CASE WHEN availability='missing' THEN 'online' ELSE availability END`（重现自动恢复 missing→online；**不碰 is_deleted/offline**，§3.2.4）。

**验收**：单测——upsert 一个 `availability='missing'` 的既有项 → 自动复位 `online`，且 `is_deleted` 不变；构造 Unchanged 项验证其 id 进入 seen（可经一个收集回调或导出 seen 供断言）。**仍不删除**。

### 阶段 C — VolumeProber 卷探测（T1，平台相关，零删除）

**落点**：新增 `scanner/volume_probe.rs`。

- `trait VolumeProber { enumerate() -> Vec<ProbedVolume>; resolve_path(path) -> Option<stable_id>; }`（§3.1.1）。
- **先落路径兜底实现**（`stable_id = "path:" + 规范化绝对根`）——平台无关、可立即单测、保证 mark_missing 有「在线卷集」可用。
- 再落 Win（`GetVolumePathName`→`GetVolumeNameForVolumeMountPoint`→GUID）/ mac（DiskArbitration `DAVolumeUUID`）真实实现，`#[cfg(target_os)]` 门控；取不到 GUID/UUID → 退化路径兜底。
- 启动期对账（§3.1.3）：`enumerate` → 刷新 `volumes.is_online` + 在线卷下项 `availability` 归位。**此步只读卷 + 写卷在线态，不扫描、不删除。**

**验收**：路径兜底 `resolve_path` 单测；Win/mac 真实实现以手动验证 + `cargo check` 双平台（按项目 DoD：未自动覆盖的标注清楚）。

> ⚠️ 平台门控会触发 macOS runner 编译（Part7 硬前置）——本阶段只在 Windows 实测，mac 路径用 `#[cfg]` 占位 + 编译通过，真机验证记为待办。

### 阶段 D — mark_missing 三重守门 DAO + **dry-run**（删除逻辑就位但不接线）

**落点**：`db/queries.rs` 新增 `mark_missing`。

```rust
/// 三重守门差集：仅在线卷(守门1) + 仅本 scan_root 子树(守门2) + 本次未出现(守门3)。
/// dry_run=true 时只 SELECT count(*)（返回「将标记数」），绝不 UPDATE。
pub fn mark_missing(
    conn: &Connection,
    root_id: i64,
    online_volume_ids: &[i64],   // 运行时已复查在线的卷集（守门1）
    seen_ids: &HashSet<i64>,     // 完整 seen（守门3）；大集合走 temp 表 LEFT JOIN
    dry_run: bool,
) -> Result<usize>;
```
- SQL（§3.2.2）：`UPDATE media_items SET availability='missing' WHERE directory_id IN (SELECT id FROM directories WHERE root_id=?root) AND volume_id IN (在线集) AND is_deleted=0 AND availability!='missing' AND id NOT IN (seen)`。
- **大集合**：seen 百万级 → `temp.seen_ids(id INTEGER PRIMARY KEY)` 批插 + `LEFT JOIN … WHERE seen.id IS NULL`（避免巨型 `NOT IN`）。
- `dry_run` 把 `UPDATE` 换成 `SELECT count(*)` 同条件——这是 §5 灰度的落点。

**验收**：单测矩阵（FK 可控）——
- 在线卷 + 完整 seen + 某项不在 seen → 标 missing；`is_deleted` 不变。
- 离线卷下的缺失项 → **不标**（守门1）。
- 别的 scan_root 子树的缺失项 → **不标**（守门2）。
- seen 里的项 → 不标（守门3）。
- dry_run=true → 返回将标数但 DB 不变。

### 阶段 E — 接入 run_fast_scan 收尾（删除能力**上线**，先 dry-run 一轮）

**落点**：`fast_scan.rs` Step 4 + `run_fast_scan` 签名/上下文。

- `run_fast_scan` 取得本 scan_root 的 `volume_id`（查 `scan_roots`）+ 卷在线判定。
- **入口守门**（§3.1.3）：`resolve_path(root)` → 卷离线 → `return Ok(Skipped)`（不动 DB）。
- Step 4 写删前的**四道闸**：
  1. `WalkReport.complete == true`（阶段 A）——否则只上报错误、**不差集**。
  2. 卷在线**复查**（TOCTOU，写删瞬间再查一次 `is_online`）。
  3. `online_volume_ids` 传入（守门1）+ root 子树（守门2）+ seen（守门3）。
- **上线方式（已定 2026-06-29：直接实写）**：四道闸 + 软标记兜底足够安全，生产路径直接 `dry_run=false` 实写 `missing`；`mark_missing` 仍**保留 `dry_run` 参数**供单测断言「将标记数」与日志可观测（写删前 `info!` 打印将标记 N 项 + 样本 id），但不设「先 dry-run 再切 on」的灰度门。

**验收**：端到端——构造「真实删一个文件 + 完整扫描 + 卷在线」→ 标 missing；「扫描中途模拟卷离线」→ 不标；「walk 注入一个错误」→ `complete=false` → 不标。

## 3. 守门矩阵（四道闸，缺一不可）

| 闸 | 防的误删场景 | 落点 |
|---|---|---|
| 入口守门（卷离线即 return） | 拔盘后扫描 | 阶段 E / §3.1.3 |
| 完整扫描门闩（complete） | 权限/IO 错漏文件 | 阶段 A / WalkReport |
| TOCTOU 复查（写删前再查在线） | 扫描中途拔盘 | 阶段 E |
| 三重守门 SQL（在线集∩子树∩¬seen） | 跨卷/跨根/未变更误删 | 阶段 D |
| **软标记 + 自动恢复**（兜底） | 万一误标，重现即复原、且永不碰 is_deleted | 阶段 B+D |

## 4. 依赖与排期

```
A (WalkReport)  ─┐
B (seen+恢复)   ─┼─→ D (mark_missing+dry_run) ─→ E (接线, dry_run→on)
C (VolumeProber)─┘
```
- A、B、C **互相独立**，可任意序先落（都零删除、低风险）。
- D 依赖 B（seen）+ C（在线集）。
- E 依赖 A+C+D，是**唯一让删除上线**的阶段，且先 dry-run。
- **本方案范围**：A–E（缺失检测最小闭环）。Part2 的 T2（插拔监听线程）、T4（SourceChanged 全失效）**不在本方案**——T2 是体验增强（启动对账已够安全）、T4 是独立 bug，均可后续单独做。

## 5. 风险与回滚（§5 对齐）

- **最高危「缺失误标」**：靠「软标记 + 自动恢复 + dry-run 灰度」三层兜底——即便逻辑有错，最坏是把在场文件误标 missing（前端灰显「可能已移动」），重现/重扫即自动复原，**永不进回收站、永不碰 is_deleted、永不物理删**。
- **卷识别失败**：路径兜底 + 「识别失败视为始终在线」（宁可不删）。
- **回滚**：E 的灰度开关一键切回 `off`/`dry_run`；A–D 都不改变线上删除行为，可独立保留。
