### Top 建议(完整清单见 §7)

- **P0-1 收缩叙事,不收缩代码**:营销与 v0.1 只打"照片(+视频)",阅读器/音频降为"隐藏能力"(模块化/设置开关),停止阅读器线新增投资直至照片主线变现。

## 2. 产品设计 Review

### 2.1 定位与市场:白地真实,且刚被第三方验证

Part0 的定位句——"本地优先·隐私第一·完全离线的跨平台四媒体智能管理器,Picasa 文件夹树哲学继承者"——放到 2026-07 的市场里检验,**核心判断成立**:

- **桌面-本地优先细分确认欠供给**(E 路)。开源阵营 15+ 项目几乎全是 server/Docker 形态(Immich 107k★、PhotoPrism 40k★ 都要自建服务器);真正桌面本地只有 digiKam(功能王者但被普遍评"复杂、UI 陈旧、Win 上 DB 易损")、Tropy(仅档案照片)、TagSpaces(打标器)。"把 Immich 级端上 AI 送到不装 Docker 的普通桌面用户手里"这个空隙确实无人占据。
- **需求信号仍旺盛**(F 路)。DPReview/HN 2024-2026 持续有人找 Picasa 替代;digiKam 被公认"能做一切但远不如 Picasa 简单";Windows 自带 Photos 因慢/云依赖被主动逃离。HN 2025 自建相册热帖暴露的未满足点依次是:连拍/重复"该留哪张"的智能选优、人脸跨年龄关联、语义搜索质量、10 万+规模性能——与本项目能力面高度重合。
- **反订阅情绪是真实购买力**(F 路)。Mylio 订阅涨价引发老用户反弹、Lightroom 仅订阅被长期诟病、Eagle($34.95 买断,官方 store 核实)与 ACDSee 永久授权受赞。本项目"买断+付费大版本"的定价设计($9.9-24.9 插件带)与 Eagle/Tonfotos($39/$99)同带,**定价直觉经对标验证合理**。
- **中文角度是真护城河**(F 路)。Immich/Lap 均用英文中心 CLIP;寻隐/Queryable(iOS,本地中文搜图)证明了中文端侧语义检索的付费意愿;知乎"照片管理"长期热议=国内桌面市场被低服务。Chinese-CLIP 头等支持是西方竞品结构性给不了的差异点。

**但市场窗口出现了计时器——Lap 警报**(E/F 路交叉证实):julyx10/lap,Rust+Tauri+Vue+SQLite+ONNX,端侧 CLIP+InsightFace 人脸,桌面本地优先,宣称"10 万+ 文件流畅、大库为默认",免费,1.3k stars,2026 年 v0.2,Show HN 与 Windows 社区已有关注。**这是与 Scrollery 技术栈、定位、性能主张几乎逐项重合的直接竞品。**

| 对比轴 | Lap(已发布) | Scrollery(未发布) |
|---|---|---|
| 平台 | 仅 Windows | Windows(mac 计划中) |
| 分发信任 | 未签名(SmartScreen 警告) | 签名/公证在 Part7 计划内 |
| 人脸合规 | InsightFace(权重非商用,商业化即雷) | YuNet+SFace 商用轨(已规避) |
| 中文语义 | 多语言 CLIP 变体 | Chinese-CLIP 头等(双档) |
| 媒体面 | 照片为主 | 图/视/音/文四媒体 |
| 商业模式 | 无(免费,单人) | open-core+插件店+三渠道(已建成未变现) |
| 成熟度 | **已发布**,有真实用户反馈循环 | 未发布,无用户 |

判断:Lap 的存在同时是**需求验证**(有人用同样的判断下注并获得初步关注)与**时间压力**(先发者在积累口碑与迭代反馈)。Scrollery 的每一项纸面优势都以"发布"为前提——**这把 §2.5 的变现/发布滞后从"商业问题"升格为"竞争问题"**。

### 2.2 头号产品风险:范围 vs 聚焦

从代码实证看(A/C 路),这不是一个照片管理器,而是"全媒体资产库 + 电子书阅读器 + 文档校对工作台 + 音频播放器"的复合体:30 张表中 6 张属阅读器(书签/进度/替换规则/版本树/章节索引/每书偏好),180 个 IPC 命令中 26 个属文档域(全域最多),DocumentViewer 1354 行携 AI 校对(OpenAI 兼容 API+keyring)、类 git 版本管理、正则替换规则引擎;另有同步歌词的音频播放器、WebDAV 网络盘、PSD worker、壁纸/剪贴板集成。

设计文档的自辩(D 路:文本文件本就是资产/竖排竹简=品牌签名/校对+版本=护城河)在"资产管理器"叙事内自洽,**但新立项视角下有三个反驳**:

1. **购买动机不叠加**。竞调显示用户为"照片之痛"付费(百万张卡顿、找不到人、怕丢整理成果);没有证据显示同一批人为"阅读器+校对"付费——那是另一个市场(Calibre/legado/校对工具)的 MVP。四媒体让"卖点清单"变长,但让"一句话定位"变糊。
2. **每一面都有独立的 table-stakes 债**。阅读器面对的是 Calibre/legado 级期待,音频面对的是 foobar2000 级期待——多一个媒体面就多一条"永远补不完"的期待曲线,而照片主线自己的 table-stakes 还有大缺口(§2.3)。
3. **机会成本已经可测**。阅读器 K 线(R1-R5)与多主题、UIUX 重构消耗的是同一个单人开发者的窗口期,而 Part8=0%(§2.5)。

**建议(P0-1):收缩叙事,不收缩代码。** 已建成的能力是沉没成本且质量不低,删除是浪费;要收的是**新增投资与对外叙事**:
- v0.1 与全部营销面只说"照片与视频"(README 头句、官网、store 文案);
- 阅读器/音频降级为"隐藏能力":默认不在主导航露出(设置开关或按扫描内容自动显现),定位为"顺手打开你库里的 epub/mp3"而非产品支柱;
- 阅读器线冻结新增(竖排收尾可完成,R6 仿真翻页等后置),直至照片主线变现闭环跑通;
- 长期若校对/版本工作台确有独立价值,考虑拆分为第二产品(共享 Rust core),而非在同一产品里摊薄。

### 2.3 Table-stakes 缺口(对照竞品用户抱怨的分级)

A 路以 grep+IPC 双验证确认缺席,结合 F 路"用户抱怨最多项"分级:

**v1 发布前必须有**(缺了会直接出现在差评里):
- **基础编辑三件套**:裁剪/旋转(写回或 sidecar)/曝光微调。当前连旋转都是瞬态的(不落盘)。Picasa 的"简单编辑"是其被爱要素之一;完全零编辑的"管理器"在消费者预期里不成立。
- **导出/另存**(含批量缩放导出):零导出意味着用户在应用里做的一切都出不去,与"非破坏"哲学并不冲突(导出=复制变换,不动原件)。
- **幻灯片放映**:家庭用户核心场景,实现成本低(查看器+定时器+转场)。
- **签名安装包**:Lap 的 SmartScreen 摩擦被评测反复点名,是"精致可信"最便宜的证明(Part7 已计划,优先级应前移)。

**v1.x 快速跟进**(差异化前的补课):
- **去重 UI**(先精确 hash 后感知 pHash/dHash;§5.2 数据层先决)——HN 头号诉求"该留哪张"的前半件;
- **地图视图**:GPS 数据已入库(image_meta.exif_gps_*)且 thumb-info 已读 location,只差一个 UI 面——当前是"数据在、面没建"的最低成本空白;
- **设备导入**(相机/手机 DCIM 拷贝导入,含按日期归档),Picasa 用户的肌肉记忆;
- 批量重命名、外部编辑器 handoff("用 XX 打开")。

**可以慢**(有替代或非核心):打印、云备份(明示非目标)、RAW 冲洗(§3.5 另议)。

**已达标且优于均值**:评分/颜色标签/收藏/回收站+undo(双机制含 redo)/视频播放(关键帧 sprite)/Live Photo/简繁转换/a11y(204 处 aria,竞品几乎无人做)。

### 2.4 可移植性与信任经济学:零写回哲学的代价

现状(C 路):所有用户策展(persons 命名、收藏夹、评分、颜色、标签、书签)只存 `scrollery.db`;XMP 只读(仅 Live Photo 检测);无任何导出;faces/persons 向量绑 model_name。

这与 Picasa 的核心遗产**正好相反**:`.picasa.ini` 让用户整理成果与照片同放同走,digiKam 至今支持导入它——这正是"被 Google 弃 10 年仍被怀念"的物质基础。F 路竞调将"绝不碰我的文件+我的整理成果不被锁定"列为第一信任诉求;LibrePhotos 写回 XMP-MWG-RS 人脸区域被列为可移植性范本;而"怕再投资一个注定被弃的 app"是 Picasa 难民的普遍心理(F 路多来源)。

**判断**:"默认零写回"作为安全哲学是对的(绝不改用户文件),但"零出口"是另一回事——前者保护用户文件,后者困住用户劳动。对单人维护的新产品,"你的整理成果随时可带走"恰恰是化解"弃坑焦虑"的最强营销词,与开源核战略同构。

**建议(P0-2 的两件 + P1)**:
1. **策展导出**(JSON/CSV:人物命名、相册、评分、标签、颜色):纯读 DB 拼文件,成本极低,信任回报极高;
2. **`.picasa.ini` 导入桥**:读取 Picasa 人脸命名/星标/相册——对"Picasa 遗产用户"这一首要画像是迁移楔子(digiKam 已证需求),且与 Chinese-CLIP 并列构成对 Lap 的差异化;
3. **可选 XMP sidecar 写回**(faces→MWG-RS、rating→xmp:Rating、label/tags→dc:subject):默认关、显式开;与 digiKam/Lightroom 互操作,补全"半专业摄影师"画像的工作流。quick-xml 已在依赖树,增量成本可控。

### 2.5 商业化设计审视

open-core 机械本身(D/B 路)——单函数 swap 点、Copybara 物理剥离、三渠道 cfg 互斥、Ed25519 层0、D1 签发彩排——工程完成度高且设计克制(诚实边界:自认卖"集成+体验"而非"秘密权重";拒绝 kill-switch/指纹上报)。**结构上没有要改的。要改的是执行顺序:**

- v0.1 切割线(Part0 §11.4:仅 Win+核心免费+exotic-formats 单插件闭环+CI/签名/updater)本身是**优秀的决策**——问题只在它没有被当作队列的排序键。

**建议(P0-3)**:把"Part8 最小闭环"(Paddle/FastSpring 接入+签发端+官网一页+下载/购买/激活全链一次真实走通)排在一切新特性前;以 v0.1 切割线为唯一队列排序键,特色线(阅读器/主题商店/H-Lab 毕业)一律排后。

## 3. 技术选型 Review

> 新立项假设下重新问一遍:"2026 年 7 月,这个产品该用什么建?"结论:**桌面栈几乎每一项现有选择都会被重选一次**——这在 greenfield review 里是罕见的高分;需要动的只有三处(CLIP 引擎、FTS、以及"移动=Tauri"的默认假设)。

### 3.1 应用壳:Tauri 2 桌面=验证为强解;移动=建议改道

**桌面裁决(G 路,23 检索):Tauri 2 成立且是强解。** 依据:v2 stable 已 21 个月(2024-10→2026-07,2.9.x);对本产品的三大已知坑,项目全部已经绕开——
1. **IPC 大二进制惩罚**(社区基准:10MB 载荷 macOS ~5ms vs Windows ~200ms)→ 项目缩略图走 asset protocol 直供,元数据走 IPC,进度走 Channel(B 路证实),正确;
2. **web 网格高度上限**(Chrome 16,777,200px)→ 项目 bucket 虚拟化+自研逻辑滚动条已绕(README/T16);
3. **webview WebGPU 不可用**(caniwebview:三大 webview 默认全不 ship;Hopp 实测 Tauri 前端 WebGPU 不可用)→ 项目 GPU 路径在 Rust 侧(WIC/D3D11),未押注 webview WebGPU,正确。

**Immich 用 Rust→WASM justified-layout 支撑 2M 资产**(10M boxes <50ms)从旁证明:web 技术栈的百万级网格是可达的,且本项目"布局在 Rust 进程内"的形态比 WASM 更强(无 JS 边界序列化)。真正的天花板只剩 **WebView2 内存**(解码位图驻留;Tauri 官方承认对 webview 进程内存掌控有限)——建议建立"内存预算基准"(固定库规模下滚动 10 分钟的 WebView2 进程峰值)纳入 O 线真机验收。

**唯一的诚实风险信号**:检索不到任何重媒体旗舰跑在 Tauri 上(Eagle=Electron、digiKam=Qt、Immich 桌面=浏览器)。本项目在此品类是拓荒者——这不构成否决(架构对策已齐),但意味着**没有前人的坑图**,WebView2 内存/合成行为的边界要靠自己的基准测出来。

**移动裁决:不要 all-in Tauri mobile。** 官方自述 mobile DX 未达标;无一等 photo-library(PHPhotoLibrary/MediaStore)插件——对照片应用是要害缺口;后台任务靠第三方插件;Android webview 长列表滚动是已知痛(Immich 移动端因此用 Flutter)。2026 的诚实答案(Firefox/Immich 同形状):**共享 Rust core(UniFFI)+ 桌面 Tauri + 移动 Flutter/原生壳**。

**建议(T-1,零成本高保值)**:现在不动工移动端,但把"core 不依赖 tauri 运行时"立为依赖方向守则(scanner/db/thumbnail/ai/layout 均不 import tauri,IPC 层保持薄壳)——Q 线调研已证实传输耦合收敛于 invokeIpc 单入口,说明这条守则当前基本成立,守住即可。未来移动转正时,core 经 UniFFI 抽出,壳另起,不赌 Tauri mobile 成熟。

### 3.2 前端框架与 UI 体系

- **Vue 3 + Pinia + vanilla CSS variables + 自研 Ui\* 原语**:对 solo 开发者是克制而正确的组合——依赖面极小(15 个运行时依赖,无 UI 框架),主题系统(6 套+亮暗双槽+token 三层)因此可控。竞品课(digiKam"Frankenstein UI")反证了这条路的价值。
- vue-i18n 双语+完整性门禁、a11y 204 处 aria:同类桌面工具几乎无人做到,是"精致可信"叙事的实证。
- 唯一提醒:自研原语库(UiButton/Dialog/Popover…)+双渲染路径(§4.3)+多主题的组合让**前端自有平台代码**持续膨胀(56,921 行已与后端等量)。原语库本身质量高(全带 spec),但每新增一个原语都是永久维护面——UiToolbar 之后建议原语面冻结,新需求优先组合既有原语。

### 3.3 数据库:rusqlite-only 正确;两处补强

- **rusqlite(bundled)+WAL+单写 Mutex+r2d2 读池**:对桌面单机是 2026 正确解,竞品课反面(Immich 强绑 Postgres+专用向量扩展=部署重量)与正面(纯 SQLite 单文件=用户可自救)都支持它。Q 线"SQLite 匹配 NAS 轻部署"的判断亦然。
- **补强一:FTS5**。文件名搜索现为 `LIKE '%q%'`(全表扫,ipc/search_commands.rs:16 自注"Phase 3 迁移")。新立项视角:这不该是 Phase 3,而是搜索体验的地基——**CJK 需 trigram tokenizer**(unicode61 对中文逐字退化;trigram 无 ICU 依赖,H 路检索证实为实用解),建议西文 unicode61+CJK trigram 双列并存,覆盖文件名/相册名/人名/EXIF 机型。
- **补强二:向量落库形态**。现状 f32 LE BLOB 自管+内存 f16 暴力检索,经算式验证可行(§3.4);sqlite-vec 的价值不在速度(v0.1.x 也是线性扫)而在"向量进 SQL 联合过滤"(如"2023 年+这个人+语义'海边'"单查询)。**无一主流开源项目在用 sqlite-vec——差异化空位**(E 路)。评估性引入(vec0 虚表存 int8 量化副本),不替换现有内存引擎。

### 3.4 AI 栈:一处警报、一处盯梢、两处被验证正确

- **🟠 警报:Chinese-CLIP 上游半弃养**(H 路:OFA-Sys issue 积压无响应、无新 release)。它仍是中文效果最好的选择之一,且是本产品护城河,不必换掉;但作为**唯一**默认引擎的风险=无 bug 修复、无新架构跟进、社区工具链逐渐脱钩。**建议(T-4)双引擎**:cn-clip 保中文头等 + **SigLIP2**(Apache-2.0,109 语,Immich 官方多语推荐之一)作商用/多语主线;`ai_embeddings.(item_id, model_name)` 复合主键与 profile 注册表**已经为多引擎设计好了**,增量成本主要是模型分发与重嵌入管理。同时把两个权重的再分发许可逐一核清(Jina-CLIP-v2 CC-BY-NC、MobileCLIP2 Apple 研究许可均有商用陷阱,勿引入)。
- **🟡 盯梢:DirectML 维护冻结**(sustained engineering,维护者离开;未正式 deprecate)。微软新方向=Windows ML(2025-09 GA,动态 EP catalog:TensorRT-RTX/OpenVINO/QNN,含 NPU);ort crate(2.0.0-rc.12,活跃)尚未封装 EP catalog。**近期安全**(现路径继续用),但"NPU/Copilot+ PC 最优路径"将只在 Windows ML 侧——建议在 defer 台账立一条"ort×Windows ML EP 封装成熟度季检"。macOS 侧注意 CoreML EP 的切图回退陷阱(ViT-B 级常 CPU 更快,逐模型 benchmark,勿无脑开)。
- **🟢 被验证正确之一:YuNet+SFace 商用轨**。InsightFace 权重(buffalo/SCRFD/ArcFace)仅限非商用是行业级地雷(竞品 Lap 正踩着);本项目商用轨+`face-noncommercial` cfg 物理隔离+商业流水线符号扫描兜底,是稀缺的合规工程。保持。
- **🟢 被验证正确之二:暴力 f16 余弦+ANN dormant**。算式与公开基准(H 路):1M×512-d f16≈1.02GB,瓶颈=内存带宽,~25-50ms/查询下限,rayon+SIMD 实测量级 5-30ms——交互完全够用。扩容顺序:**先 int8 量化**(内存减半再减半、带宽同步受益)**后 ANN**(usearch int8 HNSW);faces 表(一图多脸,行数远超 items)会更早到阈值,聚类侧到 1M 脸时改 Chinese Whispers(边数线性)。
- **🟢 架构位正确**:host 零 ort、推理在子进程、与 exotic worker 共用监督/协议基建——与 Ente(全端侧 ONNX)、PhotoPrism(SCRFD+FaceNet)的行业收敛一致,且进程隔离比两者都激进(GPU 驱动崩溃不拖垮主程序)。行业水位对照(Apple=MobileCLIP2 端侧、Google=EmbeddingGemma 端侧):"照片不离设备"的营销主线已被巨头确立,本项目方向顺风。

### 3.5 媒体解码与格式路线

- **🟢 HEIC/HEVC 专利路线被验证为 indie 正道**:不自带 HEVC 解码器,Windows 走 WIC(+用户侧 HEVC 扩展)、macOS 走 ImageIO,把专利责任留给 OS——现架构(WIC 引擎+engine arena 注册序)正是这个形态。**红线:永远不要为"开箱即用 HEIC"引入 libheif 静态分发**,那会把 Access Advance/Via LA 专利面拉到自己身上。
- **视频缩略图**:Media Foundation(Windows)=同款正道;ffmpeg 仅作 perf 变体的 LGPL 动态链接后备(feature 边界已建未实装)——保持,且未来实装时避开 `--enable-gpl/nonfree`。
- **JXL 机会(T-6)**:2026 转折点已到(Chrome 145 以纯 Rust jxl-rs 重新引入、Safari 17+ 原生、三星相机试水)。`jxl-oxide`(纯 Rust)成熟可用——低成本支持 JXL 解码,并可把"JPEG→JXL 无损重压省 ~20% 空间"做成工具型卖点。
- **RAW 缺口需要一个显式决策(T-7)**:目标画像第二位是"隐私敏感半专业摄影师",但当前 RAW 完全缺席(引擎只有 image-rs+WIC)。两条路:A. 明确"v1 不做 RAW,画像收窄为消费者/收藏家"(诚实定位);B. `rawler`(纯 Rust,许可干净)打底做"RAW 浏览/缩略图"(不做冲洗),缺机型回退 LibRaw。**判断:选 A 先发,B 进 v1.x**——RAW 浏览是半专业画像的入场券,但不该挡 v0.1。
- 去重/质量补件(P1-6 的技术侧):`image_hasher`(dHash 粗筛+pHash 精筛)+BK-tree;质量选优 Laplacian 方差快筛+NIMA/MUSIQ(ONNX,复用 ort 与 GPU 调度)——全部落在既有基建上,无新依赖类别。

## 4. 架构方案 Review

### 4.1 总评:值得原样保留的部分(greenfield 重来也这么建)

以下机制在同类项目中罕见,是本仓库的真实资产,新立项视角下**逐项复议后全部保留**:

1. **纪律固化为可执行门禁**:async 内 rusqlite 必须 spawn_blocking——不是注释约定,而是**源码扫描回归单测**(ipc/blocking.rs,扫全部命令文件,违例即红);错误 code 契约、引擎注册序、渠道依赖树(updater 不泄入 store 变体)同样有测试锁定。这把"架构师在场才守得住的规矩"变成了"CI 在场就守得住"。
2. **推理子进程化 + 统一 worker 基建**:ort/DirectML/驱动崩溃/VRAM 泄漏全部隔离在 ai-worker;host 编译期零 ort。更优雅的是 AI worker 与冷门格式 worker **共用一套** 帧协议/Supervisor/validate("AI=会推理的插件 worker"),一份监督逻辑服务两类负载。
3. **开闭源 seam 收敛到单函数**:`default_entitlement_provider()` 是唯一 swap 点,pro 不依赖 src-tauri(破环),Copybara 标记剥离;keyset 解析失败一律降级 FreeStub(绝不越权放行)。open-core 的物理隔离做到了"结构上无法泄漏"。
4. **写边界防御自愈**:派生物 tmp→rename 原子写、LRU 驱逐同事务复位状态、对账 GC 双护栏、迁移逐块事务化——"崩溃/驱逐/竞写是常态"的设计假设贯穿。
5. **调度分层**:让步阶梯(scan>thumb>derive>AI)+交互节流窗+CPU/GPU 双闸+CLIP↔face 会话互斥——"扫描/浏览/AI 同时跑仍流畅"的工程量远超一般相册,是"百万级流畅"卖点的真实支撑面之一。

### 4.2 布局引擎在 Rust:方向正确,天花板要说清

"justified/grid 布局在 Rust 计算+行级虚拟化拉取"偏离了"Tauri 只做桥,逻辑在前端"的常规,但被生态独立佐证为正确方向(Immich 把同样的计算下沉 Rust→WASM 才撑起 2M 资产;本项目进程内形态更优)。分组 rayon 并行+前缀和缝合 bit-exact、常驻 ~32B/项、items_cache 把取数与几何解耦——设计质量高。

**天花板在"全集物化"本身**:默认视图故意压制索引走顺序全表扫+全量 LayoutItem 载入+内存排序(queries.rs:1073-1084,EXPLAIN 实证索引随机回表 1M 需 6.6s,压制后 ~100ms,本人复核)。这个取舍在 1M 内是**对的**(实测数据支持),但要诚实承认其含义:
- 首屏冷启动与内存随行数**线性增长**,数百万级没有 keyset 兜底;
- 头号卖点"百万级流畅"当前受 >~25 万项坐标平移 bug(SAFE_MAX 休眠)与 O 线真机验证未完的双重钳制。

**建议(A-1)**:百万级合成库真机基准(冷启动/滚动帧率/内存三线)先于任何"百万级"对外措辞恢复——这与 CLAUDE.md"公开 claims 追实现"红线一致;基准未过前,公开文案维持"十万级实测流畅、百万级设计目标"的诚实分档。**不建议**现在改 keyset 混合架构:物化模型的简单性(布局/选择/时间轴全建立在"全集在手"上)是真实资产,推翻它的成本远大于把物化打磨到 1M 达标。

### 4.3 DOM+Canvas 双渲染路径:最大的长期维护负债

MediaGrid(2374 行 DOM)+MediaGridCanvas(1373 行)、TimelineScrubber(631)+TimelineScrubberCanvas(1030)——同一交互语义两套实现(A 路)。每一个新交互(选中动画、悬停卡、拖拽、a11y)都要写两遍且行为逐像素对齐(近期 git 历史里"canvas 对齐 DOM"系列提交即其税单)。

新立项视角:这是**过渡态而非终态**,应设定裁决时间表——O 线真机验收(canvas 性能倍数)出结论后,胜者转正、败者降级为兼容 fallback 并冻结特性追加(只修不加)。注意张力:项目 a11y 投入很重(204 处 aria),而 canvas 网格的 a11y 需要平行可达性树——若 canvas 胜出,a11y 层的对齐成本要一并计入,不能只比帧率。**建议(A-2)**:把"双渲染裁决"列为显式决策项挂 O 线,裁决前两条路径特性冻结(Boy Scout 修缮除外)。

### 4.4 跨平台就绪度:抽象已建 ≠ 实现已建

B 路诚实结论:Windows 是唯一一等公民(WIC/MF/DXGI/卷探测/DWM);ImageEngine/VideoBackend/StorageBackend 三 trait 抽象齐备但非 Windows 实现全缺;Linux 仅编译+单测(自托管 WSL);**macOS 无 CI,iOS/Android 无构建**。而 README/定位句写的是"跨平台(Windows/macOS/iOS/Android)"。

- 抽象先行本身是对的(接缝在正确的位置,mac 补 Image I/O/AVFoundation 是"填接缝"不是"改架构");
- 风险在**承诺面与实现面的时间差**:双平台首发是对 Lap 的核心差异化(§2.1),但 mac 侧连 CI 都没有,"fast-follow"没有工程节拍支撑。
- **建议(A-3)**:v0.1(Win)发布前,建立 macOS 编译面 CI(cargo check + 前端构建,GitHub-hosted macos runner 或自托管),把"mac fast-follow"从口头承诺变成每日守护的绿灯;mac 实功能(Image I/O/AVFoundation/签名公证)按 Part 计划维持变现后启动。

### 4.5 Q 线(前后端分离/服务端部署):建议显式 defer

Q 线调研结论"结构可行且起点优于业界"成立(invokeIpc 单入口/错误 code 契约/worker 已进程外都是真实优势),但其自列的四大分水岭——Linux 媒体后端(WIC/MF/DirectML 全 Windows-only,=把 §4.4 的缺口再乘一遍)、移动自动备份平台天花板、插件许可部署模型——每一条的成本都不低于"把桌面端打磨到可变现"。**新立项视角判断:这是诱人的第二产品,不是当前产品的下一步。** 建议:显式 defer 至桌面变现闭环后再议;仅执行其"阶段0 收口纪律"(零成本的传输层整洁保持,与 T-1 的 UniFFI-ready 守则同一件事)。

### 4.6 插件/授权架构:冻结复杂度

四层防护(Ed25519 已建/AES 后置/设备绑定/在线激活可选)+三渠道+三真相模型+签名 registry+原子安装——对一个未变现产品,这套机械的**绝对完成度已超出首发所需**(层0 足以支撑 v0.1,Part0 自认层1 只挡懒人)。它已经建成且质量高,不是问题;**问题只会出现在继续加层**。建议(A-4):把插件平台复杂度冻结在现状,层1 AES/设备绑定维持 defer(现行裁决正确),新增防护的触发条件改为"盗版实证发生"而非"变现启动"。

### 4.7 阅读器/校对子系统的架构位

## 5. 数据结构 Review

> 基准:30 表/34 索引/迁移 V18(A 级证据,本人 grep 直验;全表清单见工作记忆 findings)。

### 5.1 值得保留的部分

- **四类 meta 1:1 分表列存**(image/video/audio/document_meta):比"一张宽表塞 NULL"或"JSON blob"都干净,EXIF 列存使色彩/GPS 可索引可查询。
- **partial index 用得讲究**:media_items 15 个索引多为带谓词的部分索引(fav/del/rating/trash…),匹配各选择性视图;回收站 keyset 翻页(V11)是教科书式修复。
- **迁移机制**:STEPS 顺序块、每块 DDL+版本号同事务原子提交、失败回滚可安全重跑——半迁移死循环被结构性杜绝。
- **人脸域的用户意图保护**:is_confirmed/is_unassigned/face_rejections 三重钉扎+face_coverage 独立记账(零脸图不误重扫)+model_name 轨隔离——这是踩过"重聚类打散用户命名"坑的团队才会有的 schema,竞品(digiKam 人脸慢/PhotoPrism 漏检)对照下属第一梯队设计。
- **卷感知**(volumes.stable_id=卷 GUID,availability 与 is_deleted 正交):可移动介质"离线≠删除"的语义正确,多数桌面竞品做不到。
- **凭据不落库**(storage_backends.cred_ref→keyring)、设置全走 app_config KV(单一事实源)。

### 5.2 最深的结构性债:路径身份模型

**现状**:文件身份=`(directory_id, file_name)` UNIQUE;`cache_key=xxh3(rel_path/name|mtime)` 驱动全部派生工件命名;content_hash 存在但仅作"可疑变更"检测基线(size 相同时才比对),**不参与身份/去重**。

**后果链**(C 路+本人验证):
1. **无内容去重**:同图两目录=两行+两套缩略图/嵌入/人脸(盘占与算力翻倍),去重 UI(P1-6)无地基;
2. **移动/改名/touch 即全量重派生**:cache_key 变→四档缩略图+ai_thumbs+face_thumbs 全部作废重算。"用户整理照片库"(移动/重命名恰是资产管理器鼓励的行为)会触发自家缓存雪崩;
3. **策展随行困难**:persons/albums 锚定 item_id,item 锚定路径——文件在应用外被移动后,策展与文件的关联断裂(尽管有"可疑变更"检测缓冲)。

**新立项对照**:Apple Photos/Immich/PhotoPrism 均为"资产(内容)身份+路径是属性";Picasa 用 .ini 把策展锚到目录但人脸簇全局。内容身份是这类产品的行业收敛。

**建议(D-1,分三步渐进,不动 UNIQUE 约束不做大手术)**:
1. **第一步(低成本高回报)**:派生缓存键与路径解耦——cache_key 改锚 content_hash 前缀(或 blake3 短哈希),移动/改名后派生工件全部免重算(只 UPDATE 路径列);扫描端"同 size+同 hash"即识别为移动而非删除+新增,策展自然随行;
2. **第二步**:content_hash 升为一等公民(全量回填+索引已有 idx_media_hash),`sha256s` 抽样对 >64MB 保留但对图片类(通常 <64MB)走全量;以此为地基做精确去重 UI;
3. **第三步(可选,伴随去重 UI)**:感知哈希列(pHash/dHash,BLOB+BK-tree 内存索引)支撑"近似重复/连拍选优"。
*注:blake3 曾在设计中被定为 content_hash 算法后离线降级 sha2(C 路);第二步时值得重议——blake3 对全量哈希的吞吐优势在回填场景是数量级的。*

### 5.3 检索结构

- **FTS5(T-3)落在数据层**:新虚表 `media_fts(file_name, album_names, person_names, camera_model…)`,CJK trigram+西文 unicode61 双 tokenizer 列;触发器或扫描端同步维护。替换 `LIKE '%q%'` 全表扫。
- **ai_search_results 的单会话假设**(每搜 DELETE 全表+重插,file_id 为 PK):多视图/并发搜索互踩,且把"瞬态查询结果"持久化进主库(WAL 写放大)。**建议(D-2)**:改内存态(host 侧 HashMap/临时表 `temp.`),或加 session_id 列——倾向前者,查询结果本就不该落主库。
- **向量存储**:f32 LE BLOB 存储+f16 内存检索的双精度设计合理;若引入 T-8(sqlite-vec int8 副本)则形成"主存 f32(真值)/内存 f16(检索)/落库 int8(过滤)"三层,注意声明真值层唯一(BLOB f32),其余皆派生可重建。
- **tags 树无消费者**(C 路:tags/item_tags 建表齐全含树形 parent_id,未见查询消费者;A 路:前端无标签 UI)。**建议(D-3)**:要么接 UI(与 P2-7 XMP dc:subject 写回联动),要么在 schema 注释里标注 dormant——避免后来者误以为已有标签功能而在其上叠设计。

### 5.4 出口结构(承接 §2.4)

为 P0-2/P2-7 预铺的数据层工作:
- **导出 schema(D-4)**:定义稳定的 JSON 导出契约(persons{name,cover,face 锚点}/albums{name,成员相对路径}/ratings/labels/tags…以**相对路径+content_hash 双锚**标识条目,使导入方可在文件移动后仍能匹配);
- **XMP 写回映射表**:faces→XMP-MWG-RS RegionList、rating→xmp:Rating、color_label→xmp:Label、tags→dc:subject——LibrePhotos/digiKam 同款,互操作即验证;
- `.picasa.ini` 导入桥的解析目标:`[.album:]`/star/faces 节(Contacts2 格式)→persons/albums/favorites 映射。
