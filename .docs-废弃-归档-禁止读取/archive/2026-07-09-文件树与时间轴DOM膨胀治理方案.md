### 1.2 左侧文件树:不是「别的原因」,就是**未用虚拟树**

**事实(代码实证)**:[FoldersSection.vue:49-101](../src/components/sidebar/sections/FoldersSection.vue#L49-L101) 是一条朴素 `v-for`:
```
<template v-for="row in displayRows" :key="...">
  <button v-if="row.kind === 'dir'" ...>   <!-- 目录行 -->
  <button v-else ...>                        <!-- 文件行 -->
</template>
```
`displayRows`([:211-231](../src/components/sidebar/sections/FoldersSection.vue#L211-L231))把**所有已展开目录 + 各自全部文件**拍平成线性数组。`useFolderTree`([useFolderTree.ts](../src/composables/useFolderTree.ts))只负责**懒加载数据**,**不做任何窗口化**——`nodes` 里多少已展开节点,模板就渲染多少 `<button>`。

项目里**存在**虚拟滚动 composable(`useVirtualScroll.ts` / `useHVirtualScroll.ts`),但只被 [MediaGrid.vue](../src/components/media/MediaGrid.vue) 消费,**从未接入文件树**。

> **判定:「最初设计是虚拟树」的意图,在当前 FoldersSection 实现里没有落地。这是「未用虚拟树」,不是虚拟树失效。**

**为什么 4194 这么大?关键是文件行,不只是文件夹**:`displayRows` 把**文件也拍进同一列表**([:219](../src/components/sidebar/sections/FoldersSection.vue#L219) 的 `for (const f of dir.files!)`)。展开一个含 3000 张照片的目录,瞬间产生 3000 个文件 `<button>`。60k 库展开几个大目录,4000+ 行轻易达到;百万级 ×20 展开一个大目录即达数万行。

**为什么当初没做成虚拟树?两个后加特性与朴素虚拟化冲突**(须在方案里正面处理):
1. **粘性目录头**([:640-641](../src/components/sidebar/sections/FoldersSection.vue#L640-L641) `position: sticky`):目录行靠 sticky 钉住,滚长文件列表时始终可见文件夹名。**窗口化会移除滚出视口的行 → sticky「钉住栈」断裂**。sticky + 虚拟滚动共存出了名难做。
2. **交错的变高行**(目录 28px / 文件 26px,[:624](../src/components/sidebar/sections/FoldersSection.vue#L624) / [:677](../src/components/sidebar/sections/FoldersSection.vue#L677)):定高虚拟滚动最简单,但此处「目录/文件交错、两种高度」,需**可变高度虚拟化**(前缀和/高度映射表)。

**二次成本**:`displayRows` 是 `computed`,任何展开/折叠/计数刷新都会重算整个数组并 diff 全部 4000+ 节点;每次 reload(如扫描后 `folder-stats-changed` 事件,[:335-351](../src/components/sidebar/sections/FoldersSection.vue#L335-L351))全程被拖累,非仅首屏。

### 1.3 右侧时间轴/文件夹轴:**一数据点一节点**的量纲错配

**事实**:[TimelineScrubber.vue](../src/components/media/TimelineScrubber.vue) 两种模式都逐点渲染 DOM:
- **date 分组** → `v-for` over `monthBuckets`,每月一个 `.tl-month`([:16-31](../src/components/media/TimelineScrubber.vue#L16-L31))。月数有界(60k 库约 100-200 月),**基本不是问题**。
- **folder / none 分组** → `v-for` over `separators`,每分组一个 `.tl-sep-node`([:35-44](../src/components/media/TimelineScrubber.vue#L35-L44))。`separators` 长度 = **分组数量**([layout.ts:84](../src/types/layout.ts#L84),后端每 group 一条)。**temp2 = 2042 = 当前文件夹分组数**,随文件夹数线性增长,百万级 ×20 可达数万。

**根本问题:scrubber 高度像素级有界,节点数却数据级无界**。时间轴是约 600-1000px 高的总览条。600px 里画 2042 点 = 平均每 0.3px 一个点,**必然重叠、亚像素堆叠**,视觉根本区分不出 2042 个。

> **这 2042 个 DOM 节点里绝大多数在渲染那一刻就是不可见的冗余。** 付了 2042 节点的布局/合成成本,只换来 ~600 像素行的信息量。比文件树更纯粹的浪费:scrubber 的点**永远同时在视口且永远画不下**。

**既有优势(降低改造风险)**:[TimelineScrubber.vue:109-121](../src/components/media/TimelineScrubber.vue#L109-L121) 的 `jumpToPointer` **已是纯数学映射**(`clientY → 比例 → 月索引/y`),**不依赖逐点 DOM 命中**。故改 canvas / 降采样时,**交互契约几乎不用动**。

## 2. 业界成熟方案(联网调研)

### 2.1 文件树 / 超大目录 → 虚拟滚动(windowing),行业唯一答案
VSCode Explorer(正是管理 node_modules 这类数万项目录的场景)用自研 `List` + `IndexTree`:
> *"the list will ask the height to a provided virtual rendering controller, keep an in-memory map of each element's height and track the viewport's position in order to know which elements should be rendered in and out of the DOM… only the visible elements in the viewport are rendered as DOM nodes."* —— [microsoft/vscode Wiki: Lists And Trees](https://github.com/microsoft/vscode/wiki/Lists-And-Trees)

要点与我们的差距一一对应:
- **只渲染视口内节点**(树多大,DOM 恒定几十行);
- **可变高度**靠「每元素高度的内存映射表」(正好覆盖目录 28 / 文件 26 交错难点);
- **IndexTree** 把树 splice 映射成扁平 list splice——即「先拍平成线性行(我们的 `displayRows` 已做),再对线性行窗口化」。**我们已完成拍平这一半,只差窗口化这一半。**
- **sticky 目录头** VSCode 用独立的 **Sticky Scroll** 机制(单独渲染钉住行),而非依赖列表内 sticky——这正是我们 T1 需借鉴的关键。

Web 生态等价件:`vue-virtual-scroller`(`DynamicScroller` 支持可变高度)、TanStack Virtual(框架无关、Vue 适配良好)。

### 2.2 时间轴 scrubber → 降采样到像素分辨率 或 canvas 绘制
竞品([Mylio](https://mylio.com/)、[Peakto](https://cyme.io/en/products/peakto/)、Google/Apple Photos)的时间轴滚动条遵循同一原则:**scrubber 绘制成本由「条像素高度」决定,而非数据点数量**。两条主流路径:
- **路径 A(仍用 DOM,降采样)**:把 N 个数据点桶合并到 ~条像素高度个槽位(如 600 槽),每槽聚合密度。DOM 节点数钉在 O(像素) 而非 O(数据)。我们的 `monthBuckets`(date 模式)**已天然是这种按月聚合的降采样**,所以 date 模式没问题;**folder 模式缺的正是同一层聚合**。
- **路径 B(canvas / 单 SVG path)**:整条热力/密度用一次 `<canvas>` 或一个 `<path>` 画完,DOM 节点数 = 1。交互用数学映射而非逐 DOM 命中——我们 `jumpToPointer` 已是纯数学映射,canvas 化交互改造成本很低。

### 2.3 判据(可复用的通用准则)
> **总览类可视化(滚动条/缩略轴/热力条)用 canvas 或降采样;列表类可视化(树/网格)用虚拟滚动。** 前者「全量同时可见但画不下」→ 降维到像素;后者「同时只看一小段」→ 只渲染那一段。

## 4. 【T1】文件树接入可变高度虚拟滚动 + sticky 覆盖层

### 4.1 目标
`displayRows`(已拍平)之上套一层**可变高度窗口化**,DOM 从 O(展开项) 降到 O(视口)。恒定几十行,与展开规模、库容量解耦。

### 4.2 技术选型(2026-07-09 勘查已定案)

**勘查结论:不扩展 `useVirtualScroll`,新写树专用小虚拟化器。**

`useVirtualScroll` 核心接口是 `fetchRowsByY(topY, bottomY) => Promise<LayoutRow[]>`——**不持有行数组,按逻辑 Y 区间向后端异步拉行**(为百万图库「行数据不驻留 JS」而生),与文件树 `displayRows` 全量 in-memory 数组的前提**根本相反**;且其 `SAFE_MAX` 座标压缩(>16.7M px)、wheel 惯性补偿、fetchId 竞态守卫对树(最多 ~2M px)全是**冗余负担**,而这些是经 T16/F1/F2/P1-12 多轮真机硬化的**验证过热路径**。让树复用须同时给它泛型化行类型 + 加同步 in-memory 数据源分支 = **改动验证过的百万图热路径去伺候结构完全不同的第二消费者,风险 >> 收益**。

> 注:`useVirtualScroll` 的「可变高度」其实天生支持(每行自带绝对 y/height 绝对定位,`rowHeight()` 仅算预取缓冲不参与定位)——但该优点被埋在画廊专用异步机器里,不值得为复用而扭曲核心。正确的 DRY 层级是**复用模式(prefix-sum 绝对 y + 绝对定位行 + rAF 节流)而非代码**。

| 选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **T1-MVP:统一行高定高虚拟化** | 目录 28/文件 26 仅差 2px→统一 28px 后退化为 `startIndex=floor(scrollTop/H)`,约 40 行、零依赖、零 prefix-sum/二分 | 文件行 +2px(纯观感,可忽略) | ✅ **首选,先做** |
| **T1-Full:变高 in-memory 虚拟化器** | prefix-sum + 二分,像素精确 | 复杂度略高 | 🔶 **按需升级**(若字号缩放拉开行高差距) |
| 扩展 `useVirtualScroll` | 零新依赖、同栈 | 需泛型化 + 加同步数据源分支,污染验证过的百万图热路径 | ❌ **否决**(风险 >> 收益) |
| `vue-virtual-scroller`(`RecycleScroller`/`DynamicScroller`) | 节点池化回收(快滚 GC churn 更少)、`scrollToItem` 内建、久经实战;stable **3.0.4**(npm 实证见下) | 多一个 dep + CSS(触「控依赖膨胀」「<10MB 核心」);库存两套虚拟化;仍不解决 sticky | 🔶 **后备**(可行、低风险,非否决) |

> **npm 实证(2026-07-09,`registry.npmjs.org` 直查)**:`dist-tags.latest = 3.0.4`,发行时间 **2026-05-20**;repo = **github.com/Akryum/vue-virtual-scroller**(公式,非同名 fork);`peerDependencies.vue = ^3.3.0`。注:`next` 标签仍停在旧 `2.0.0-beta.8`,**稳定 Vue 3 线走 `latest`(3.x)**,勿误装 `@next`。此前「Vue 3 支持万年 beta」的顾虑已彻底作废。
>
> **决策(2026-07-09,用户拍板):先自研 MVP,`vue-virtual-scroller` 留作后备。**
> 理由:树在统一 28px 后是虚拟化最简单一档,节点池化的边际收益在侧栏树上不显著,而本项目重视 `<10MB 核心` + 控依赖;故先自研快速验证性能与 sticky 覆盖层这一硬骨头。**触发切库的条件**:若 T1-a 真机发现①快速滚动 DOM 增删 churn 明显掉帧,或②行高需求变复杂(变高 + 字号缩放联动)使自研成本失控——则切 `vue-virtual-scroller`(接口相近,迁移成本可控;装 `latest` 非 `next`)。
> **修订史**:本表初版曾把 `vue-virtual-scroller` 标「❌ 否决(先渲染再测量多此一举)」,该表述基于「Vue 3 支持万年 beta + 只有 DynamicScroller 测量」的过时认知;经 2026-07-09 联网复核 + npm registry 直查(stable 3.0.4 官方版 + RecycleScroller 定高无测量)修正为「🔶 后备」。

### 4.3 可变高度处理
- 行高来源:目录行 28px、文件行 26px(§1.2)。构造**高度映射函数** `rowHeight(row) => row.kind === 'dir' ? 28 : 26`。
- 维护**前缀和数组**(或委托 `DynamicScroller` 内建):`offsetY(index)` = 前 index 行高度和,用于 ①总高度 ②`scrollTop → 起始可视 index`(二分)③目标 index → scrollTop。
- 行高一旦后续做主题缩放(字号变),须让映射函数读取当前 token,避免写死。

### 4.4 sticky 目录头 → 独立覆盖层(本方案唯一硬骨头)
朴素 sticky 在窗口化后失效(§1.2)。**采用 VSCode Sticky Scroll 思路**:
- **不再依赖列表内 `position: sticky`**;窗口列表里的目录行恢复普通流。
- 在虚拟列表容器**顶部叠一层绝对定位的「当前目录头」覆盖行**(1 个 DOM 节点),内容 = 当前 `scrollTop` 所在文件夹(由前缀和反查:找到「包含当前视口顶部的目录节点」)。
- 覆盖头随滚动更新文本;进入下一目录时切换(可选:临界处做「上推」过渡,即下一个目录头顶到覆盖头时把它推走,复刻现有 [:629-639](../src/components/sidebar/sections/FoldersSection.vue#L629-L639) 的观感)。
- **嵌套目录**:若要复刻多级钉住,覆盖层可叠 N 级(N=当前深度),或先只钉最近一级(MVP)。建议 MVP 先钉一级,真机看是否够用再加。

### 4.5 分两步施工(降风险)
- **步骤 T1-a(无 sticky 的虚拟树)**:先把 `v-for` 换成虚拟列表,**暂时去掉 sticky**(目录行普通流)。目的:先验证性能与滚动/展开/折叠/拖拽正确性,隔离虚拟化本身的 bug。
- **步骤 T1-b(补 sticky 覆盖层)**:再加 §4.4 的覆盖头,复刻钉住观感。

### 4.6 必须一并改造的关联点
1. **`expandToNode` 的 `scrollIntoView`**([useFolderTree.ts:141-146](../src/composables/useFolderTree.ts#L141-L146))依赖目标 DOM 存在——窗口化后目标行可能不在 DOM。改为:**先算目标 `displayRows` index → `scroller.scrollToItem(index)`**(或算 offsetY 后设 scrollTop)。`setTimeout(...50)`([:135](../src/composables/useFolderTree.ts#L135))的 DOM 等待 hack 应一并去掉,改为数据驱动定位。
2. **拖拽命中 `data-dir-id`**([FoldersSection.vue:438-442](../src/components/sidebar/sections/FoldersSection.vue#L438-L442))经 `document.elementFromPoint(...).closest('[data-dir-id]')`——虚拟化后**只有可视目录行有 DOM**,拖拽到「滚出视口的目录」无法命中。评估:拖拽是即时交互,目标通常在视口内,风险低;若需拖到远处目录,靠**自动滚动(拖到边缘触发 scroll)**补齐,不破坏命中模型。
3. **`active`/`scrolledDirectoryId` 高亮**:纯 class 绑定,窗口化后自动只作用于可视行,无需改。
4. **右键菜单/新建对话框/drag ghost**:均 Teleport 到 body 或独立状态,不受窗口化影响。

### 4.7 验收
- **性能**:temp1 childNodes 从 20972 → 数百(视口行数 × ~5);展开万级文件目录后 DOM 恒定。
- **功能回归清单(真机)**:展开/折叠、懒加载文件、点击目录跳转、点击文件打开、拖拽移动/复制、右键新建子文件夹、`expandToNode` 自动展开+滚动到、sticky 头随滚动正确切换、扫描后 `folder-stats-changed` reload 保持展开态。
- **测试(characterization + 新增)**:`displayRows` 拍平结果、`offsetY`/index↔scrollTop 二分映射、覆盖头「当前目录」反查。

## 11. 【T1-MVP】可施工详细设计(基于方案 A:独立滚动窗格,2026-07-09 用户拍板)

> 本节是 T1-a/b/c 的施工蓝图。**不含代码**,只定 DOM 结构、坐标数学(纯函数)、覆盖头反查算法、交互保全、涉及文件与测试清单。行高统一 **`ROW_H = 28`**(文件行由 26 升 28,+2px 纯观感)。

### 11.1 关键前提(现状取证补充)
- **滚动容器是共享的**:[AppSidebar.vue:75-84](../src/components/sidebar/AppSidebar.vue#L75-L84) 的 `.sidebar__scroll-area` 被四个 section 共享;文件树无独立滚动。
- **accordion 两根片段是承重设计**:[AccordionSection.vue:1-18](../src/components/sidebar/AccordionSection.vue#L1-L18) 靠「header 是 `.sidebar__scroll-area` 直接子元素」实现跨区块 sticky 堆叠,注释明确「do not tidy / 普通块级流(非 flex)让 sticky 更稳健」。
- **方案 A 的取舍**:把 Folders 本体改为独立滚动窗格 → 树获得自己的 `scrollTop`,虚拟化最干净;代价是 Folders 本体内部滚动、需调 accordion 布局(见 §11.7)。

### 11.2 DOM 结构与滚动模型
把现状「`.tree` 内一条 `v-for` 全量 button」改为「窗格 + 视口 + 撑高占位 + 渲染层 + 覆盖头」五层:
```
.tree-pane            position: relative        ← 不滚动的定位锚(覆盖头相对它绝对定位)
├─ .tree-sticky-head  position: absolute; top:0 ← sticky 覆盖头(1 个 DOM 节点,恒在窗格顶,不随内容滚)
└─ .tree-viewport     overflow-y:auto; @scroll  ← 真正的滚动容器,自有 scrollTop(方案 A 核心)
   └─ .tree-spacer    height = rowCount*ROW_H    ← 撑起总高,产生真实滚动条
      └─ .tree-layer  transform: translateY(offsetY) ← 只含可视窗口的行,整体平移到起始行
         └─ <button>… 仅 visibleRows,每行 ROW_H 高,自然流(不再逐行 sticky/absolute)
```
要点:
- **覆盖头必须在视口外层**(`.tree-pane` 的绝对定位子),不能放视口内——滚动容器内的绝对定位子会随内容滚走,无法钉在可视顶。
- **渲染层用 `translateY` 平移**(命令式或响应式绑定),而非改 `paddingTop`,避免每帧 reflow(复用生产 `useVirtualScroll` 已验证的「spacer + layer transform」思路,但**不移植座标压缩**——树最多 ~2M px,远低于 SAFE_MAX)。
- 现状的逐行 `position: sticky` + `--tree-dir-sticky-top`([FoldersSection.vue:640-641](../src/components/sidebar/sections/FoldersSection.vue#L640-L641) / [:240-243](../src/components/sidebar/sections/FoldersSection.vue#L240-L243))**全部移除**,由 §11.4 覆盖头取代。

### 11.3 scrollTop ↔ index 坐标数学(纯函数,定高)
抽到 `folderTreeVirtual.helpers.ts`(承接 timelineScrubber/mediaScrollbar helpers 的「纯映射进 helpers + 单测」惯例)。三个纯函数:

**① 计算可视窗口**
```
computeTreeWindow(scrollTop, viewportH, rowCount, ROW_H, BUFFER):
  firstVisible = floor(scrollTop / ROW_H)
  startIndex   = max(0, firstVisible - BUFFER)
  rowsInView   = ceil(viewportH / ROW_H)
  endIndex     = min(rowCount, firstVisible + rowsInView + BUFFER)   // slice 上界(不含)
  offsetY      = startIndex * ROW_H
  → { startIndex, endIndex, offsetY }
// visibleRows = displayRows.slice(startIndex, endIndex)
```
- `BUFFER`(上下预渲染行数,建议 6):快滚时避免边缘瞬白。
- 短列表(`rowCount*ROW_H ≤ viewportH`)自然退化:startIndex=0、endIndex=rowCount、offsetY=0,与不虚拟化等价。

**② 滚动到某行(block: 'nearest' 语义,复刻现状 `scrollIntoView`)**
```
scrollTopForIndex(i, curScrollTop, viewportH, ROW_H):
  top = i * ROW_H ; bottom = top + ROW_H
  if top < curScrollTop:                 return top                 // 在视口上方 → 对齐顶
  if bottom > curScrollTop + viewportH:  return bottom - viewportH  // 在视口下方 → 对齐底
  return curScrollTop                                               // 已可见 → 不动
```

**③ 折叠后钳制**:`displayRows` 变短时 `clampScrollTop = min(curScrollTop, max(0, rowCount*ROW_H - viewportH))`,防止停在越界滚动位导致空白。

### 11.4 sticky 覆盖头「当前目录」反查算法
现状是「每个目录行 sticky、后到者覆盖前者」。MVP 用**单个覆盖头**显示「视口顶所属的目录」,反查是 **O(1)**——因为 `FileRow` 已自带 `dirId`([FoldersSection.vue:207/220](../src/components/sidebar/sections/FoldersSection.vue#L207)):
```
resolveCurrentDirId(displayRows, scrollTop, ROW_H):
  topIdx = clamp(floor(scrollTop / ROW_H), 0, rows.length-1)
  row = rows[topIdx]
  return row.kind === 'dir' ? row.node.id : row.dirId
// 再由 folderTree.nodes 查 DirNode → 覆盖头渲染 name / depth 缩进 / mediaCount
```
**关键正确性陷阱(必须测)**:`displayRows` 里目录的**自身文件排在其整个子树之后**([:216-228](../src/components/sidebar/sections/FoldersSection.vue#L216-L228) flush 逻辑)。例如目录 A 含子目录 B 与自身文件 fa1:
```
A(dir) · B(dir) · fb1(B的文件) · fa1(A的文件) · fa2
```
滚到 `fa1` 时,「最近的前一个 dir 行」是 B(错!),但 `fa1.dirId === A`(对)。**故必须用 `FileRow.dirId`,不能用「向上扫描最近 dir 行」**。此用例是 §11.8 测试的必测项。
- 覆盖头 `data-dir-id = currentDir.id`,复用 `onNodeClick` / `onNodeContextMenu` / 拖拽命中,使钉住头的行为与普通目录行一致。
- 边界:`scrollTop=0` 且首行即根目录时,覆盖头与首个可视行重复——MVP 接受(VSCode 亦然);可选精修「当该目录自身 header 完整可见时隐藏覆盖头」,defer。
- 嵌套:MVP 只钉一级(当前所属目录)。多级钉住(父+子叠层)复刻现状观感 → defer 到 T1-b 之后按真机需求定。

### 11.6 响应式与生命周期
- **窗口重算触发源**:①`.tree-viewport` 的 `@scroll`(rAF 节流,复用 `useHVirtualScroll` 的 `ticking`/`pendingUpdate` 模式)②`displayRows` 变化(`watch`,展开/折叠/reload)③视口高变化(`ResizeObserver` on `.tree-viewport`)。
- **currentDir(覆盖头)**:随 scroll + `displayRows` 变化重算 `resolveCurrentDirId`(轻量,可与窗口重算同批)。
- **状态**:`startIndex` / `offsetY` / `visibleRows`(浅量,普通 `ref` 即可,可视行仅几十)/ `currentDirId`。
- **建议封装** `useTreeVirtualScroll(viewportRef, rowsGetter, ROW_H)` composable:内聚 scroll/rAF/ResizeObserver/窗口态,返回 `{ visibleRows, offsetY, spacerHeight, currentDirId, scrollToIndex }`,让 FoldersSection 保持精简。**不复用 `useVirtualScroll`**(理由见 §4.2:异步 fetch-by-Y + 座标压缩不适配)。

### 11.7 accordion 布局改动(方案 A 的落地机制)
让 Folders 本体成为独立滚动窗格,两种实现,T1-a 择一:
- **A-flex(首选)**:`.sidebar__scroll-area` 改 `display:flex; flex-direction:column`;非 Folders section `flex:0 0 auto`(自然高);Folders 的 `.acc-body`(树)`flex:1 1 auto; min-height:0`,内部 `.tree-viewport` `overflow-y:auto`。**风险**:[AccordionSection.vue:80](../src/components/sidebar/AccordionSection.vue#L79) 注释警告「非 flex 让 sticky 更稳健」——须**真机验证 flex 列中 section header 的 sticky 堆叠不回归**(现代 Chromium/WebView2 支持 sticky-in-flex,大概率 OK)。
- **A-js-height(回退)**:保持块级流,给 `.tree-viewport` 用 `ResizeObserver` 算高度 = 侧栏高 − 其他 section 占高,JS 驱动 `max-height`。避开 flex-sticky 交互,但较笨重。
- **决策点**:T1-a 先试 A-flex,sticky 堆叠若真机回归再切 A-js-height。**此子决策留给施工期真机,不预先定死**(承接「开发期不冻结契约」)。
