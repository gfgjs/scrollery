## 4. 真机三问题:定性与解决方案

### 4.1 问题 1:隐藏项显示与「目录选中」混淆 —— 真 bug

**根因** = R-01(样式判等恒真),R-06(隐藏项无视觉区分)加剧。用户截图中「.」开头目录呈现的选中样底色 + 内环 + 半透明,就是 `active`+`drag-over`+`drag-source` 三类同时常挂的样子——不是「隐藏项的专属样式设计得不好」,而是**根本没有隐藏项样式**,看到的全是误挂的实体轴状态样式。

**方案**(小改动,一批可完成):
1. R-01 修复:5 处判等前置非空(必做,几行)。
2. R-06 修复:`hidden` 透传 + 淡化样式。建议**文字 opacity(约 0.55)+ 可选 EyeOff 小图标**,不用背景填充——背景填充语义已被「选中/拖拽」占用,正交才不会再混淆。
3. 回归钉子:spec 造 FS-only 节点断言三类 class 不出现(现有轴契约测试只测动作面)。

### 4.2 问题 2:隐藏目录下 .md 等不能应用内打开 —— 设计有意行为,非失效

**机制链**(核验完好):`walker.rs` 整棵剪掉隐藏目录 → 该 `.md` 从未入库、无 `mediaId` → `isOpenableInApp` false(`folderTree.helpers.ts:39-43`,要求 `id` 与 `mediaType` 双非空)→ 单击只选中、双击走 `reveal_tree_entry`(系统文件管理器显示)。设计件 §4.4 明文:「隐藏目录内的已注册文件 `registered=true` 但无 `mediaId` → 走 reveal 而非应用内查看器。这是三态设计的必然推论,不是缺陷」,背后是 D-001 安全裁决(不调系统默认应用打开,防根内可执行文件;应用内查看器全链靠 mediaId 取数)。

**但用户感知为坏体验是合理的**——「registered=true 的 .md」与「隐藏目录」组合下,应用明知这是自己认识的格式却把用户抛到文件管理器,且单击的「选中」无任何可见反馈(仅键盘 focus 环)。方案分层:

### 4.3 问题 3:树内项不能拖拽 —— 一半从未实现,一半误伤

三段答案:

1. **文件行:从未实现**(「忘了提需求」,不是失效)。`0c54d03` 引入文件行起就只有目录行有 `@pointerdown` 拖拽;树内拖拽的语义一直是**移动/复制物理目录**(`performTreeDrop` → move/copy directory IPC)。媒体文件的移动/复制走的是**画廊卡片拖到树目录**那条既有链路(`ui.mediaDragHoverDirId`)。若需要「从树内文件行发起拖拽」,那是新需求,建议单独提(需定义:拖到哪里?目录=移动文件;画廊=无意义;涉及未入库文件时还叠加问题 2 的身份缺失)。
2. **默认「已注册格式」模式:目录拖拽链核验完好**。入口守卫(`hasEntityIdentity` + 非根)、`nodesById` 实体索引、`canDropOnId` 环检测、`performTreeDrop` 全走 DB id;后端 `get_directory_children`/`get_directory_tree` 均下发 `parent_id`。P1-b 只换了结构轴,实体轴未动。**若真机在默认模式下也拖不动目录,属另一回归,代码审查未见成因**——手测步骤:默认模式展开两层,按住子目录行拖 4px 以上(有 DRAG_THRESHOLD),应出 ghost 标签;Ctrl=复制。
3. **FS 两种模式:被 R-07 误伤**。adapter 对所有 FS 条目 `parentId: null`,拖拽入口第一关即返回 → 连库内目录也不可拖,超出设计 §4.1 只禁 FS-only 的边界。修法二选一(需裁决):
   - **a. 恢复**(推荐):后端 `TreeEntry` 对 DB-backed 目录附带父目录实体 id(`parentDirectoryId`,`skip_serializing_if` 与 directoryId 同姿态),adapter 透传 → FS 模式库内目录恢复拖拽,FS-only 仍被 `hasEntityIdentity` 挡住。后端一处 JOIN/查找 + 前端一行。
   - **b. declare**:裁「FS 模式统一不支持拖拽」为有意行为,设计 §4.1 补记 + 拖拽起手 toast 提示,零代码风险。

## 6. 教训候选(已登记三件套 findings F-020~F-023)

- **F-020** 类型谓词守得住动作面,守不住判等:`number|null === number|null` 类型合法,编译器枚举必改点对「语义要求非空」的比较零信号;同款哑弹修了一处(FolderTreeSelectorDialog)不等于修了全库。
- **F-021** 根治「手工枚举抄漏」的那次提交,自己在另一处手工枚举里抄漏了同一个字段——修枚举点时先全库清点同形枚举点,且无 spec 的接线层是缺口最可能藏身处。
- **F-022** 双数据源下「共享节点沿用旧轴字段」是静默语义漂移:根行跨模式同源(DB),FS 模式下其 DB 轴字段(hasChildren/mediaCount)语义失效但类型合法。模式分发要覆盖**字段语义**,不只取数路径。
- **F-023** 删「恒不触发的死守卫」前,先问引入它的竞态会不会被本批变更复活——loadId 守卫被删的同一批提交(模式 watch 整树重载)恰恰重新制造了它要挡的竞态。
