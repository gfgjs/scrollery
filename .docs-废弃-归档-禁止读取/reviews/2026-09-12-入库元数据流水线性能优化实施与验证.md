# 入库元数据流水线：首批优化实施与验证

本轮承接[性能调查](2026-09-12-文件夹入库元数据流水线性能调查.md)，落实确定的提交与刷新放大、图片批内等待和资源峰值问题。本文区分已落地行为、局部验证与仍需真实库测量的部分。没有扫描、修改用户真实媒体库；微基准使用临时生成的媒体文件。

## 1. 已落地的后端行为

### 快扫收尾短事务

目录媒体计数不再逐条自动提交。缺失检测结束后，目录计数、扫描根完成状态、完整基线标记在同一个短事务内提交，计数更新复用缓存语句。

缺失检测仍使用自己的事务，其临时 seen 表生命周期保持原样。目录计数或根状态写入失败会回滚整个收尾事务，保留未完整扫描标记，后续 quick 不会错误使用完整基线。

新增故障注入覆盖计数写失败、根状态写失败和解除故障后的恢复。参数仍绑定，未引入嵌套事务。

### 图片批内有界重叠

数据库仍每批选择、校验并写回最多1000项；批内按64项读取头部，然后交给解析池。下一块头读可以与当前块解析重叠。两个既有线程池整段复用，每个DB批次只增加一个短生命周期生产线程。

```mermaid
flowchart LR
  A[选择1000项及源快照] --> B[读下一块64项]
  B --> C[容量1的交接队列]
  C --> D[解析当前块并释放头载荷]
  D --> E[按原输入顺序收集结果]
  E --> F[源版本校验与批事务写回]
  F --> G[发布当前代次事件]
```

| 预算/语义 | 原流程 | 本轮 |
|---|---|---|
| 同时保留的头载荷 | 每根最多1000项 | 每根最多192项，生产/排队/消费各一块 |
| 头缓冲理论上限 | 约250MiB | 48MiB，不含解析器额外分配 |
| DB选批/提交粒度 | 1000项 | 1000项 |
| 项目与视图顺序 | 原keyset/临时队列 | 保留 |
| 新鲜度校验 | source revision和generation | 保留 |
| 解析失败 | 写入minimal元数据行 | 保留 |

取消在块边界检查，整批未写回结果丢弃。同步文件I/O需要自行返回才能结束生产线程；这不是硬中断机制。队列载荷使用生命周期守卫，取消及任一侧panic均归还资源计数并结束交接，相关测试包含生产侧阻塞的情况。

EXIF、XMP、JPEG方向、占位尺寸以及整文件回退沿用同一项解析函数。新旧两种批形态使用真实JPEG/PNG、缺失文件和坏文件夹具逐项对照结果。

## 2. 前端刷新合并

统计取数在同一失效代次内最多一个请求执行、一个尾随请求待执行。并发调用共用排空过程；执行期间新到的刷新请求会等待下一张快照，而不是在旧快照返回时提前完成。失败会使这批调用一起拒绝并释放槽位，下次调用可以重试。

跨扫描根共用2秒进度刷新门限，第一条进度立即请求。有效的快扫完成、富化完成、停止和错误会强制请求；这些请求仍经过统计合并。扫描回调捕获统计失败并记录日志。

清库开始与成功提交后分别作废旧统计请求，覆盖清库等待期间其它入口新发请求的情况；store销毁时也作废。跨失效代次允许旧、新请求短暂重叠，但旧响应不能回写新状态。清库屏障和扫描runId防线保持原有语义。

画廊富化事件从首事件起设置2秒刷新窗口，窗口内后续事件不延后定时器。到期请求一次布局刷新并释放窗口，避免连续富化使尾沿防抖长期不触发。这里约束的是定时器等待，不保证主线程拥塞时实际2秒内完成布局。

画廊保留rootId=0哨兵和已有离屏deferred入口，作用域销毁会清理定时器。没有新增完成事件的抢先刷新分支；末批最多等待当前窗口自然到期，避免引入stop/清库迟到完成事件的额外判定。

## 3. 分段观测

- 快扫：按root、generation、run关联遍历、遍历序前500项尺寸、批DB（含等待及单批最大值）、可疑变更确认、收尾耗时和计数；遍历序不等于视图序。
- 图片富化：选批、管线墙钟、DB等待估计值、事务持有、事件发布；另记录头读、解析、消费等待、生产背压、在途块峰值和EXIF路径分布。
- GET_STATS：debug计时覆盖排队及数据库读取，供核对统计查询占用。

头读和解析会重叠，服务时间不能相加作为墙钟。DB等待是外围耗时减事务持有的估计值，包含闸门与少量调度开销。当前资源峰值为单根口径，多根同时富化会叠加；尚未限制进程总预算。

### 暖缓存局部对照

环境为本机Windows、debug构建。32个临时JPEG/PNG文件均含EXIF方向，重复组成1000个逻辑项目；先预热，后测3轮，两组交替执行顺序，使用相同资源统计包装。它测的是图片批内头读与解析，不包含遍历、数据库写回、视频音频和前端布局。

| 指标 | 整批先读后解析 | 有界重叠 |
|---|---:|---:|
| 三轮耗时ms | 35.04 / 36.30 / 35.07 | 27.39 / 28.79 / 28.20 |
| 中位数ms | 35.07 | 28.20 |
| 在途头载荷观测峰值 | 1000 | 181 |

本次局部耗时下降约19.6%，观测峰值下降81.9%；理论新上限为192项。三轮debug暖缓存小样本不能外推真实导入提速比例。复现入口为`microbench_bulk_vs_bounded_pipeline_warm_cache`这个默认忽略的Rust测试；测试源码与实现一起入库。

## 5. 后续测量与边界

1. 真实库首次导入、稳定重扫及多根并发，记录各阶段墙钟、GET_STATS/compute_layout次数、峰值内存与句柄；分别测本地盘和网络挂载，冷热缓存分开。
2. 快扫遍历与批写仍然串行；快扫结束后才进入富化，图片完成后才处理后续媒体阶段。依据分段日志判断是否值得进一步跨阶段重叠。
3. Live Photo仍按全根候选对账。目录事务成本已消除，但增量配对必须覆盖旧关系撤销等正确性后再改。
4. 多根全局资源预算、特殊格式慢项及TIFF超时后的后台工作仍未解决。48MiB是单根头缓冲上限，不是进程内存上限。
5. 自动quick策略、seen回填与可疑变更哈希保持现状；显式quick仍可复用持久基线，自动模式重启后首次仍传full。
