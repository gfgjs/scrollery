## 1. 总结

结论是**有条件通过**,不是按原表直接批准施工:

- U-P3 的 worker/outcome/validate/trait 拆分与 T-D-012 方案 a 可按原推荐采纳。
- U-P1-a 注册清单下沉可采纳;U-P1-b 必须从「把五个捕获块逐个函数化」改为「`bootstrap::setup` 先完整接管 setup 生命周期,再在 owner 模块内拆私有块」。
- U-P2 的层次纠偏方向正确,但原目标 `download/model_assets.rs` 会让通用下载层依赖 Tauri `Channel`,与现有下载引擎边界冲突;应改为 `ipc/model_download.rs` 承载共享 IPC 编排,`download/mod.rs` 继续只管传输机制。
- U-P4 只批准 QoS 下沉;流水线去重不得新建一笔模糊债,必须复用 M 线现有测试盲区与 C1/C2,先补 characterization 再谈行为重构。
- 「豁免档不再复查」改为「本轮豁免 + 触发式重审」,避免把带 commit 的快照误写成永久裁决。

## 2. 审查发现(按优先级)

### [P1] U-P2 把 IPC 传输 DTO 放入通用 download 层,会制造新的反向依赖

原方案拟把 `DownloadProgress`、`download_assets`、文件名安全校验迁入 `download/model_assets.rs`。但当前 `download_assets` 的签名直接接收 `tauri::ipc::Channel<DownloadProgress>`,而 [`download/mod.rs`](../../src-tauri/src/download/mod.rs) 的模块契约明确规定:通用层只收敛 HTTPS/Range/镜像/校验等机制,AI/face 的多资产清单与进度聚合留给调用方。把现代码原样放进 `download/` 会让底层基础设施依赖 Tauri IPC,与 U-P2 想修的「核心层反向 import IPC」同类。

修正:

- `download/mod.rs` 不动,继续保持 transport-agnostic。
- 新建 `ipc/model_download.rs`,容纳 `DownloadProgress`、`download_assets`、`is_safe_model_file_name` 与其测试;`ai_commands`、`face_commands` 作为同层兄弟消费者直接引用。
- P 线 A15 指出的 `.part` metadata/remove/rename 同步 IO 仍是独立行为债;纯搬迁 commit 后再单独用 `tokio::fs` 或 `spawn_blocking` 修,不得夹进结构搬迁。

### [P1] U-P1-b 的拆法与行数目标不相容,并会把 setup 生命周期变成参数袋

`lib.rs` 当前 1,062 行;注册清单约 232 行,setup 闭包约 585 行。原方案只点名 ORT、logging、自愈、tray、tasks 五块,即使全搬走,DB/迁移/配置读取/asset scope/AppState/Coordinator 等 setup 主链仍留在 `lib.rs`,`≤300` 软目标不可达。逐块把捕获的局部量变成参数还会扩散启动顺序契约,审查面反而变差。

修正:

1. U-P1-a 先独立搬注册清单。
2. 重新测量 churn 与体量;若继续 P1-b,先把 setup 闭包整体迁为 `bootstrap::setup(app)`,让一个 owner 保有 DB→config→logging→self-heal→AppState→Coordinator→tasks→tray 的顺序。
3. 再在 `bootstrap/` 内把 logging/ORT/maintenance/tasks/tray 拆为私有子模块;不把共享局部量暴露回 `lib.rs`。
4. `fatal_startup_error` 随 setup owner 迁移。现有 `PICASA_SMOKE_TEST` 启动钩子作为自动化门,托盘/退出 WAL 行为仍需真机 smoke。

本地锁定依赖源码(Tauri 2.11.4 + tauri-macros 2.6.3)核对确认 U-P1-a 本身可行:`Builder::invoke_handler` 接受 `Fn(Invoke<R>) -> bool + Send + Sync + 'static`,`generate_handler!` 展开为同形 `move` 闭包。因此无需宏退路作为默认实现,只保留为编译 spike 失败时的后备。

### [P2] `ai/profile_config.rs` 原归属范围过宽

真正造成层次倒挂的是被 `ai/*` 或兄弟 IPC 消费的共享 helper。`arch_for_image_file`、`variant_fixed_batch` 目前只被 `ai_commands.rs` 自己消费;把它们一并推入核心层不是层次修复,只是为了缩短文件而扩大 API 面。

修正:目标模块改名 `ai/runtime_config.rs`,只迁 `models_dir`、`warn_legacy_ai_backend`、`persist_provider_echo`、`active_profile*`、`active_face_profile*`、`variant_installed`;两个命令私有 helper 原地保留。施工后以 `rg 'ipc::ai_commands::' src-tauri/src/ai` 归零作为依赖方向门。

### [P2] 「豁免档不再复查」把快照写成了永久事实

U 方案自己已经采用带 commit 的数字快照与开工重验纪律,永久豁免与此冲突。supervisor/worker_client 等文件未来仍可能新增第二状态机、跨层消费者或缺陷簇。

修正:豁免仅对 `13a3192` 本轮有效;出现「新增不相关 bounded context / 新增跨层消费 / 生产代码较快照增长 25% 以上 / 后续审查发现同文件缺陷簇」任一条件时重新测绘。

### [P2] U-P4 必须接上 M/N 既有测试与性能债,不能另记一笔泛化 TODO

M 线已把 `thumbnail_commands.rs` 列为后端第一测试盲区,并登记 C1(token 清理)与 C2(滚动期反复建线程池);N 线已真机裁掉旧 Rayon 分支。U-P4 的两条大函数是「视口批请求」与「全量生成」两种语义,不是已被 N 线删除的 A/B 双引擎。未来去重前必须先锁定两入口的重建、取消、token 与结果顺序行为。

修正:本批只搬 QoS,同时给 `thumb_cpu_budget_for(logical)` 增纯函数边界测试;去重仍归 M 线测试盲区/C1/C2,不在 U 线重复登记或施工。

### [P2] 原优先级把高风险 P1-b 放得过早

注册清单下沉是低风险高收益,但 setup 生命周期搬迁明显高于 P2/P3 的定向层次修复。修正后的顺序为:

1. U-P1-a 注册清单;
2. U-P2 层次纠偏;
3. U-P3 worker 接缝;
4. U-P4 QoS;
5. 重新测量后可选 U-P1-b bootstrap。

## 3. T-D-012 复核

**通过方案 a**:search.rs 仍在 T-P1 迁移,先用 `super::push_in_predicate`;T-P4 把 owner 迁进 `layout.rs` 时改为 `super::layout::push_in_predicate`。

依据:

- Rust 子模块可访问父模块私有项,故 P1 过渡引用成立。
- P4 后 helper 标为 `pub(in crate::db::queries)`,search 兄弟模块可定向访问。
- 改点只有一处路径,不改变 SQL/参数顺序/测试归属;比把整个 search 域延后四阶段的扰动小。
- T-D-003 已允许纯搬迁 commit 中出现必要的局部可见性与路径修改,但 P4 commit 说明须点名这一行。
