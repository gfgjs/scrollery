# 开源前最终检查与收费取舍

## 1. 决策摘要

**审查结论：当前不宜直接进行下一次公开同步。** 主程序开源范围已经明确，但推送前检查、内部过滤与第三方资源归属仍有未完成项。源码公开、安装包发行、正式收费服务必须分别验收。

当前收费组合为 **4 个已有授权门控的功能 + 1 项官方稳定发行收费计划**。仓内未发现已经接通的完整收款闭环，也没有证据证明这些项目已实际收款。本次“收费项目”指代码门控与公开产品计划，不是订单或收入审计。

建议供用户选择：官方稳定版一次购买包含现有功能，暂不拆 PSD/OCR/编辑小额加购；增强待模型可交付后再决定是否包含。此项只是建议，未修改现行 4 个门控。

## 2. 开源边界：保留什么

现行 `LICENSE`、`README.zh-CN.md:18`、`CONTRIBUTING.md:7` 与 `copy.bara.sky:3` 一致：前端、Rust 主机、现有随附 worker、授权客户端及验签实现作为第一方源码统一 MPL-2.0。

- 保留产品源码、现有 worker、插件协议、授权逻辑、签发工具源码、公钥及 key ID；**当前没有需因“收费身份”而从源码投影中删除的第一方组件**。
- 保留原锁文件、构建与产品测试脚本、公开 README/贡献说明/许可证、第三方 notices 和来源材料。
- 保留品牌声明；源码许可与官方名称、图标使用规则分别见 `TRADEMARK.md`。品牌不是需要保密的材料。
- 未来独立商业实现、支付与订单服务可另行安排私有仓；当前无需为占位规划预建多仓。真实秘密和用户数据也不应因此存入私有 Git。

MPL 允许使用和自行构建，并对所覆盖文件的分发规定源码义务；独立新文件可以有不同许可。因此本地授权门控不能成为公开算法的独占保护，官方签名、更新与支持可以作为销售价值。参见 [Mozilla MPL FAQ，Q5、Q8–Q11](https://www.mozilla.org/en-US/MPL/2.0/FAQ/)。

## 6. 收费闭环尚缺什么

- **价格与售卖坐标：**3 个 catalog 商店链接均为 example.invalid，编辑无 URL；未见正式价格表与 Steam DLC / MS Store 商品 ID。价格可由外部商店维护，不强制要求在客户端加价格字段。
- **直销：**已有离线签发、验签、keyring 激活能力；未证明生产支付、订单、退款与交付闭环。默认 keyset 明示占位公钥；正式发行需核实际注入的信任根。
- **渠道：**`channel_stubs.rs:22` 起 MS Store / Steam provider 恒未授权，不能当作已接通平台购买。
- **更新：**`tauri.direct-release.conf.json:7` 仍为 updates.scrollery.invalid；配置扫描通过只说明结构满足约束，不说明服务可用。
- **付费载荷：**客户端授权检查和包签名不是服务端下载鉴权。当前安装流程不能证明购买后才能从服务器取得包；若未来分发专有载荷，服务端权限需单独落实。

官方安装包可以通过商店/下载交付收费，**不必因此新增应用启动付费门**。若决定“一次购买包含全部”，需先定义一个订单如何授予现有 4 项权益，或取消这些独立门控；本轮不代用户作此决定。

## 8. 需要用户决定的三件事

1. **收费单位：**官方整包一次购买，还是免费基础包 + 功能加购？建议先选整包一次购买，减少四套商品与售后的维护成本。
2. **现有功能：**PSD、OCR、编辑是否都包含在整包中？建议包含；增强先不承诺可售。当前本地源码均保持 MPL-2.0，收费取舍不改变源码过滤边界。
3. **免费发行持续多久：**只在预览期间免费，还是长期保留免费官方安装包？决定后再统一 README 与 release workflow；自行构建的源码权利继续保留。

这些建议不涉及定价金额，也不替用户承诺终身升级、无限支持或未来商业组件免费。
