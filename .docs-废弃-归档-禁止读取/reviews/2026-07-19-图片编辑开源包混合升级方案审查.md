# 图片编辑开源包混合升级方案审查

## 结论

审查对象：[图片编辑开源包混合升级方案](../designs/2026-07-19-图片编辑开源包混合升级方案.md)，基线提交 `8a5ab68fc03477d74d32170db78f8bf1af7057bd`。

总体方向成立：保留「前端参数与预览、Rust 全分辨率处理」架构，以专用裁剪组件和 Rust 图像算子升级局部能力，比引入一体化编辑器更符合现有 Vue 3/Tauri 契约。但当前稿存在 **4 项 P1、2 项 P2**，不建议在修订前批准施工。主要阻断点不是 UI，而是调色两端的工作色彩空间与位深未统一、WebView 与 Rust 合计内存未纳入门禁，以及 `imageproc` 默认 features 会扩大依赖面。

## 审查范围与方法

- 对照当前未提交的 v1 实现：`src/components/media/EditOverlay.vue`、`src/composables/useImageEditor.ts`、`src-tauri/src/editing/{geometry,memory_budget,io}.rs`、`src-tauri/src/ipc/edit_commands.rs`。
- 对照依赖与交付门禁：`src-tauri/Cargo.toml`、`package.json`、`src-tauri/tauri.conf.json`、`.github/workflows/ci.yml`。
- 复核上游官方资料：`imageproc 0.27` API/Cargo features、`image 0.25.10` decoder/encoder 契约、Vue Advanced Cropper 官方文档与 npm 元数据、W3C Filter Effects Level 1、Canvas 色彩空间与跨源读回规则。
- 本轮只审查方案，不评价尚未施工的代码质量，也未修改设计稿或产品代码。

## Findings

### P1

#### F-01：调色两端没有统一工作色彩空间与位深

位置：设计稿 `§4.3`（第 96–107 行）；当前后端 `src-tauri/src/editing/io.rs:44-70`。

设计稿把 `v` 定义为归一化的 sRGB 编码值，并认为 TS/Rust 使用同一公式与 RGB8 黄金向量即可保证预览等于导出。但当前后端只从 decoder 取出原始 ICC blob，`DynamicImage::from_decoder` 后没有显式 ICC 色彩转换，编码时又把原 ICC 原样写回。前端 Canvas 默认工作空间为 sRGB、默认通道为 8-bit；因此带 Adobe RGB/Display P3 等非 sRGB ICC 的图片，前端和 Rust 可能在不同数值空间上执行相同公式。

同时，256 项 LUT 只完整表达 8-bit 通道。v1 输入包含 PNG/TIFF，二者可以是 16-bit；若 E3 将其转成 RGB8，会发生未声明的位深降级，若不转换则 256 项 LUT 契约不成立。现有 RGB8 fixture 无法发现以上问题。

修订要求：

1. 钉死唯一工作空间与位深。推荐由 Rust 把编辑预览和真处理都规范化到 8-bit sRGB，并在输出端写入/声明 sRGB；若要保留 16-bit 或源 ICC，则必须引入真正的颜色管理路径，不能只保留 ICC blob。
2. 明确无调色操作时是否继续保持 v1 的原位深/ICC 行为，避免新字段为零也触发量化。
3. 增加带 Adobe RGB/Display P3 ICC 的 JPEG、16-bit PNG/TIFF golden，断言预览采样值、导出像素和输出 profile 一致。

#### F-02：降采样 Canvas 没有消除 WebView 原图解码峰值

位置：设计稿 `§4.1`、`§4.3`、`§5`（第 73–85、103–105、112–124 行）；当前 `src/components/media/EditOverlay.vue:8-15`。

「Canvas 长边不超过 2048」只限制 Canvas backing store，不会阻止作为输入的 `<img>` 或 cropper 先在 WebView 解码整张 50–100MP 原图。当前 overlay 直接把 `convertFileSrc` 结果交给 `<img>`；Vue Advanced Cropper 的 `canvas` prop 默认又是 `true`，若不显式关闭，还可能创建额外结果 Canvas。

D-008 探针使用 Windows `GetProcessMemoryInfo` 测 Rust 基准进程，只覆盖后端 decode/rotate/crop/encode，没有覆盖编辑覆层常驻的 WebView 解码缓冲。保存时 overlay 仍打开，Rust 的 fine rotate expand 缓冲会与 WebView 原图和调色 Canvas 同时存在。因此单按 expand 后尺寸复算后端预算，仍可能让整应用越过设备内存上限。

此外，调色需要 `getImageData()`；`convertFileSrc` 资产 URL 在各平台的 origin/CORS 行为必须实测，否则 Canvas 可能因 tainted 状态拒绝读回。当前验证矩阵只有施工完成后的四平台目检，没有把这项架构可行性列为准入 spike。

修订要求：

1. 使用 Rust/现有缩略图链生成带正确 orientation、色彩空间和固定上限的编辑预览，不让 cropper/Canvas 直接吃全尺寸源图。
2. 明确 Vue Advanced Cropper 使用 `:canvas="false"`，只消费坐标；调色 Canvas 使用受限预览资源。
3. 在 E1/E3 开工前增加四平台 `drawImage → getImageData` asset URL spike。
4. D-008 改测实际 Tauri 应用场景的总进程树或系统合计峰值，覆盖「覆层常驻 + 45° fine rotate + 三滑杆 + encode」。

#### F-03：`imageproc` 默认 features 会反向打开 `image/default`

位置：设计稿 D-103 与依赖清单（第 32、63、153 行）；当前 `src-tauri/Cargo.toml:95`。

项目当前对 `image` 使用 `default-features = false`，只打开 JPEG/PNG/WebP/BMP/GIF/TIFF。`imageproc 0.27` 的默认 features 包括 `rayon`、`text`、`fft` 和 `image/default`；Cargo feature 合并后，简单写 `imageproc = "0.27"` 会反向打开 `image` 的默认格式族，并引入当前 E2/E3 不需要的 Rayon、字体与 FFT 依赖。该结果与文中「零额外成本」及现有精简格式面不符，也会增加移动端编译、包体和供应链面。

修订要求：

- 契约直接写明 `imageproc = { version = "0.27", default-features = false }`；只有未来确需文字标注时再单独裁决 `text` feature。
- 记录 `imageproc 0.27` 的 MSRV 1.87，并在准入项加入 `cargo tree -e features`、四目标交叉编译和 release 包体差值。
- 将「纯 Rust、零 FFI」与「零额外成本」分开表述：前者有依据，后者不成立。

#### F-04：拉直端点契约互相冲突

位置：设计稿 `§4.2` 与验证矩阵（第 89、92、113、116 行）。

UI 把滑杆定义为闭区间 `[-45°, +45°]`，IPC 却定义为开区间 `(-45.0, 45.0)`；后文测试与最坏基准又明确使用 `45°`。用户把滑杆拖到端点时会生成 UI 合法、后端以 `edit_invalid_ops` 拒绝的载荷，同时文档要求的 45° 测试无法按公开契约执行。

修订要求：统一为闭区间 `[-45.0, 45.0]`，后端有限值/范围校验与前端 min/max 共用同一常量语义，并覆盖 `-45、0、+45、越界、NaN、∞`。

### P2

#### F-05：CSS Filter 的色彩空间论据错误

位置：设计稿 `§1.3` 第 40 行。

W3C Filter Effects Level 1 明确规定 CSS filter functions 在 sRGB 中运行，`color-interpolation-filters` 对 filter functions 不生效；该属性的 linearRGB 初始值用于 SVG filter primitives。因而「Safari sRGB、Chromium linearRGB」不能作为这里禁用 CSS `filter: brightness()/contrast()/saturate()` 的依据。

禁用 CSS filter 的结论仍然可以保留，因为第 39 行已经给出 CSS 与 `imageops` 现成函数数学不等价的充分理由。应删除本条浏览器分歧论据，或明确它只涉及 SVG `filter: url(...)`/filter primitives，避免把两套规范混为一谈。

#### F-06：选型证据未持久化，首选包缺维护状态门

位置：设计稿 `§1.2`、`§1.3`、`§4.1`（第 30、44、79–85 行）。

文稿把版本、周下载量、CVE、gzip、issue 年龄及移动端先例等决定性材料仅留在会话调研记录，没有保存 URL、访问日期、版本或 commit。时间敏感数字已经会自然漂移；例如 Vue Advanced Cropper 官方 npm 当前显示最新版本约两年未发布、周下载约 20 万，而文稿记录约 24.9 万。包稳定不等于不可用，但方案一面以停更淘汰其他候选，一面没有给首选包设置维护状态准入门，标准不一致。

修订要求：

- 增加来源表：结论、官方 URL、访问日期、版本/tag/commit、置信度和待 spike 项。
- E1 spike 增加最后发布/提交时间、未决高风险 issue、依赖审计、锁定版本、默认 Canvas 行为和替换成本。
- 若维护风险超过阈值，应把活跃的 Cropper.js v2 与自研拖拽层列为同级比较，而不是仅在类型问题单点失败后才允许评估。

## 建议修订顺序

1. 先裁 F-01：工作色彩空间、ICC 与位深策略决定 E3 是否成立，也决定预览资源如何生成。
2. 以同一预览资源设计解决 F-02，并把跨源 Canvas 与整应用 RSS 变成 E1/E3 的前置 spike。
3. 固化 `imageproc` 最小 features 与 MSRV/四目标门禁（F-03）。
4. 修正拉直端点契约（F-04）和 CSS Filter 论据（F-05）。
5. 补齐可复核来源与 E1 维护准入门（F-06），再由用户裁决 U-1 至 U-6。

完成以上修订后，可维持原方案的 E1/E2/E3 范围与「前端参数、Rust 真处理」总架构，无需重新回到一体化编辑器选型。
