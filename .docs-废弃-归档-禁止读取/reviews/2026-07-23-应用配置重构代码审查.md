# 应用配置重构代码审查

## 结论

“外置 `config.toml` + watcher 热应用 + 设置页双向同步”的总方向成立，TOML 保注释写回、父目录监听、语法错误保留旧配置、设置/状态分源等主干也已落地；但当前实现仍有 **4 项 P1、2 项 P2**。其中并发协调、数值约束、缓存目录热切换会直接造成配置丢写、流水线停摆/异常分配或缩略图路径分裂，因此不建议按原三件套“阶段 6 complete、无未解错误”的结论直接收口。

优先阻断项：

1. `ConfigManager` 的互斥只覆盖单进程单实例，项目明确允许双实例；固定 `.tmp` 和整文件读改写会跨进程碰撞/丢键。
2. schema 只有基本类型，没有范围/集合约束；`derive_batch_size = 0` 可让派生流水线立即空跑，极大值可触发异常分配。
3. `thumb_cache_dir` 热切换没有同步现存前端消费者，且空串默认值在热路径被解析成相对空目录。
4. 外部编辑 `ai_hq_cache_enabled` 不会执行设置页同款的派生重启，UI 显示已开启但不会 backfill。

## Findings

### P1

#### F-01：整文件写协调边界不完整，双实例可碰撞/丢键，watcher 与 IPC 也可回写旧快照

`src-tauri/src/config/mod.rs:146`：🔴 `write_lock` 只属于一个 `ConfigManager`，不能协调另一个进程或 watcher 的 `replace_values`。把所有配置写入纳入同一跨进程锁与版本化提交路径。

当前 `set_and_persist` 在进程内持 `std::sync::Mutex` 完成“读整份文件 → 改一键 → 写整份文件”，`file.rs:376` 又固定使用同一个 `config.toml.tmp`。但仓库在 `thumbnail/generator.rs:73` 明确记录“应用无 single-instance 守卫，双实例可共开同库”。因此两个实例同时改不同键时会有两种失败：共写同一个临时文件发生 rename/内容碰撞；即使临时名改成唯一，两边都基于旧文档读改写，后落盘者仍会覆盖先写实例的键。

单进程内也有第二条竞态：watcher 在 `lib.rs:1065-1068` 以先前加载的快照直接 `replace_values`，不进入 `write_lock`。若外部保存事件已读出快照 E，随后设置页写出 E+U 并记录自写指纹，旧 watcher task 再把内存替换回 E；接下来的 E+U 文件事件会被自写指纹吞掉，最终磁盘有 U、内存却没有 U。

修复要求：

1. 若继续允许双实例，在 `<config>.lock` 上使用 OS 级排他锁，锁内重新读取、校验、改写；临时文件名至少含 PID + 单调序号/随机量。
2. watcher 重载经 `ConfigManager` 的统一提交 API 完成；提交前核对读取指纹/版本仍是当前磁盘版本，禁止旧快照覆盖新写。
3. 增加两个确定性测试：两个独立 manager/进程同时写不同键后两键都在；barrier 控制“watcher 已读 E → IPC 写 E+U → watcher 提交 E”的乱序场景。

#### F-02：schema 只验“非负整数”，合法 TOML 仍可停掉流水线或触发异常分配

`src-tauri/src/config/file.rs:125`、`src-tauri/src/ipc/config_commands.rs:225`：🔴 `SettingKind::UInt` 只拒绝负数/非数字，没有表达各键的最小值、最大值和离散档位。把约束放回 `SettingDef`，文件、IPC、迁移共用同一校验/规范化函数。

直接后果已可由控制流证明：

- `derive_batch_size = 0` 会在 `derive/pipeline.rs:318` 被接受，随后查询使用 `LIMIT 0`，生产者把“还有待处理项”当成空批并退出；派生功能静默停摆。
- 极大 `derive_batch_size` 会直达 `derive/pipeline.rs:644` 的 `Vec::with_capacity(batch_size as usize)`，可 panic 或尝试不可接受的内存分配。
- `video_keyframe_count = 0` 在后端 MF 路径被 `max(1)` 规范为 1 帧，前端 `useHoverPreview.ts:117` 却因 `0` 为 falsy 回退 10 列，同一配置产生 1 帧条带/10 列切片。
- `thumb_webp_quality = 200` 会保留为 `ConfigManager`/前端值 200，而热副作用在 `config_commands.rs:359-360` 夹成 100；持久值、UI 值、运行值三源分裂。
- `sprite_cell_height`、缓存容量、debounce 等同样没有上界；其中 sprite 尺寸会参与位图分配，不能只靠“高级用户会填对”兜底。

修复要求：为 `SettingDef` 增加声明式约束（整数区间、离散整数集合、字符串形状/自定义 validator），由 TOML load、IPC set、DB migration 和默认值测试共用；消费点不再各自静默 clamp/fallback。至少覆盖 0、边界、边界外、`u32/u8/i64` 溢出与巨值分配前拒绝。

#### F-03：`thumb_cache_dir` 热切换同时破坏默认路径解析与前端 URL 单源

`src-tauri/src/ipc/config_commands.rs:400`：🔴 热路径直接把原始字符串转 `PathBuf`，没有复用启动期“空串 → `<app_data_dir>/cache`”解析，也没有让已挂载前端消费者切换目录。集中解析/canonicalize，并把目录做成响应式全局单源。

后端启动期在 `lib.rs:378,405-407` 明确把空串规范成默认缓存目录；外部编辑从自定义值恢复注释态时，watcher 取得的生效值却是 `""`，`apply_setting_effects` 会把 `ThumbConfig.cache_dir` 改成空 `PathBuf`，后续目录 join 退化为进程当前目录下的相对路径。该分支还在 async command/task 内持 `thumb_config` 写锁执行 `create_dir_all` 与 asset scope 变更，违反阻塞 IO 应离开执行器线程的项目约束；路径也没有 canonicalize。

前端同样分裂：`utils/thumbCacheDir.ts:13` 整场缓存目录；设置页只有文件选择流程会在 `SettingsView.vue:848` 调 `setThumbCacheDir`，外部 `config-file-changed` 处理器没有这一步。即便设置页直改，已挂载/KeepAlive 的 `MediaGrid`、`ContentViewer` 等各自持有的 local ref 也不会随模块缓存更新；`MediaGrid` 只在 mounted 或 `layoutDirty` 时重取。结果是后端开始往新目录写，而现存缩略图 URL 继续拼旧目录，直到一次偶然重挂/重算。

修复要求：

1. 抽 `resolve_cache_dir(app_data_dir, raw)`，启动和热路径共用；空串回默认，用户路径 canonicalize/边界校验，目录创建放入 `spawn_blocking`。
2. 将缓存根目录改为响应式模块/store 单源，所有 URL 消费方直接读它；UI 写和外部事件都从 `GET_THUMB_CACHE_DIR` 刷新同一源，不能只改 getter 的内部缓存。
3. 覆盖“自定义 A → 自定义 B”“自定义 → 注释态默认”“MediaGrid 已 KeepAlive”三条热切换测试，并核对旧 asset scope 是否可撤销。

#### F-04：外部编辑漏掉 `ai_hq_cache_enabled` 的必要派生重启

`src/composables/useConfigFile.ts:73`：🔴 `DERIVATION_RESTART_KEYS` 没有 `ai_hq_cache_enabled`，外部保存只改 store/`ThumbConfig`，不会执行设置页 setter 的 `restartDerivation()`。加入该键，最好把跨入口副作用收敛到后端单源。

设置页路径在 `configStore.ts:220-223` 明确“保存后重启派生流水线”；派生后端又在 `derive/pipeline.rs:184-198` 仅在每轮启动时快照 `ai_hq_cache_enabled`，决定是否 backfill/领取 `ai_thumb`。因此通过 `config.toml` 从 false 改 true 时，UI 会刷新成开启，后端 `thumb_config.ai_hq_cache` 也会变化，但已结束/正在运行的派生轮次不会建立 AI 缓存任务；从 true 改 false 时，当前轮次也不会按设置页语义重启并排除该 kind。

最小修复是把该键加入派生重放集合并补事件测试；更稳妥的修复是让 watcher 与 IPC 都调用同一个后端“持久化后副作用计划”，前端只刷新展示，避免今后每新增键同时维护 Rust 分支、store setter 和 TS 白名单。

### P2

#### F-05：后一次纯热编辑会清掉前一次仍待重启的提示

`src/composables/useConfigFile.ts:110`：🟡 `restartRequiredKeys` 每次都被当前事件的 `restart_required` 覆盖。先改 `log_dir`，再改 `language`，第二个空数组会让未应用的 `log_dir` 提示消失。

`watcher::diff_changed_keys` 返回的是“本次编辑发生变化且非 hot 的键”，不是“当前文件相对本进程启动快照仍待重启的全部键”。前端却把它当成完整待办集合。简单取 union 会在用户把冷键改回启动值时留下假阳性；正确做法是由后端保留 startup-applied snapshot，每次事件发送“当前配置 vs startup snapshot”的完整 pending restart 集合，前端再整体替换。

#### F-06：首次迁移吞掉 DB 读取错误后仍创建文件，后续永不重试

`src-tauri/src/config/migrate.rs:28-33`：🟡 `query_row(...).ok()` 把 `QueryReturnedNoRows` 之外的锁、IO、schema/类型错误也当作“该键不存在”，随后仍在第 47 行写出配置文件；下次启动因 `path.exists()` 直接 no-op，非默认旧设置永久留在已不再读取的 DB 里。

同一函数的 Bool 归一化也把任何非 `1/true/TRUE/True` 文本都变成 `false`；与 UInt/Float 的“脏值跳过”契约不一致，损坏值会被伪装成用户明确关闭。

修复要求：只把 `rusqlite::Error::QueryReturnedNoRows` 映射为 `None`，其余错误向上返回且不得创建 `config.toml`，让下次启动可重试；Bool 只接受明确的 `0/1/true/false` 变体，其余返回 `None` 并记录键级警告。补一次失败不落盘/二次可重试与非法 Bool 不写 false 的测试。

- 设置键/状态键路由清单有互斥与键唯一性测试；原任务列出的内部设置读取点已基本改走 `ConfigManager`。
