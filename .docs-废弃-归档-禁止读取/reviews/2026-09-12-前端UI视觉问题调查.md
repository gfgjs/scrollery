# 前端 UI 视觉问题调查与优化建议

调查基线：2026-09-12，源码 HEAD `8cba3d97`。V09补修取色链路后，用户新截图仍有白色条带，现按用户最新要求移除所有画廊分组标题的底板、阴影和分隔线；原先保留浅底与细线的建议已被取代。其余问题仍为调查建议。

## 结论

当前已经具备六主题、材质 token、基础 UI 组件、响应式工具栏和虚拟画廊。主要问题集中在：**默认配置与验证场景不一致、缩略图信息缺少统一排布、文字放大后的局部布局失效、控件尺寸与状态反馈仍有分叉**。

建议先修可确认的遮挡与可读性问题，再统一局部视觉规则。已有主题体系足以承接优化，无需再建一套主题或组件框架。

用户提供3840×2088截图：63,685项、64px缩略图、按目录分组/按时间排序、浅色绿色界面。它补充了此前浏览器少量fixture未覆盖的「目录分组＋极密图」场景。**用户明确：每个目录独占一行符合预期；留白不属于问题，不修改分组/换行行为，不建议切换无缝分组。**

### V09 · P1 · 分组标题条带干扰【改为无底板、无阴影、无分隔线】

整行深色分隔条在浅色画廊中反复出现，路径深绿且难以辨认。它应优先于一般的圆角、留白微调：这是可读性故障，并非图片本身的暗色内容。

修复前定位的可复现链条：

- 浏览器回读主题底色可得 `oklch(0.977804 0.005983 none)`；主会话先前Fresh Light的computed背景已实际读到相同值。
- `src/utils/color.ts:63` 的OKLCH正则仅接受数值色相，无法解析合法的 `none`。
- `src/components/media/mediaGridCanvas.palette.ts:103` 调用 `resolveTokenColor` 后再转RGB，失败则兜底为 `{r:34,g:34,b:34}`，即近黑色 `#222`。首轮误以为调用该函数就一定经过探针：实际 `src/utils/cssColor.ts` 仅对包含 `var(` 的输入求值，自定义属性中的变量已展开但仍保留 `color-mix`/`calc` 时会被直接返回，RGB解析依然失败。这是用户首轮反馈后确认的上游遗漏。
- `src/components/media/mediaGridCanvas.painters.ts:399` 在folder/duplicateGroup时绘制sticky底条，`:407` 用该RGB加0.94透明度铺满一行；文字则从 `palette.textPrimary` 读取，仍是浅色主题的深绿。
- DOM 分隔条直接由CSS绘制背景（`MediaGrid.styles.css:173`），不经过此RGB解析，因此两条渲染路径产生视觉分叉。

修复前直接执行解析器复现：上述背景输入返回null，palette同款兜底得到34/34/34；文字 `oklch(0.447351 0.0248427 169.151)` 成功返回71/89/82。这个「黑底＋深绿字」结果与截图一致。截图机器的安装包版本及WebView2输出未直接读取，不能把这次本地复现写成原生应用端到端修复验证。

优化方案：先补上述真实颜色串的失败表征，再按CSS缺失分量语义修复共享解析器，并验证DOM/Canvas分组底色一致。`none` 色相转换时按0deg处理，应保留已有chroma，不能简单把a/b都清零导致去色；依据 [CSS Color 4 §4.4](https://www.w3.org/TR/css-color-4/#missing)。

最新目标观感（用户2026-09-12新截图裁定）：所有画廊分组标题直接融入画廊背景，不绘制独立底色、阴影或分隔线，只保留文字、图标及统计信息。目录独占一行和既有行内sticky行为保持。原先「浅底＋细线和轻层次」建议不再执行。

验收包含64px目录分组、六主题、主题浓度变化、DOM/Canvas路径和sticky位置；标题行不出现独立明暗条带、阴影和横线，正文信息仍清晰。界面由用户直接测试，不修改目录布局。

最新实施：DOM/Canvas两路均已移除标题底板、阴影和横线，清理无用途的sticky装饰类及标题专用色板字段；共享颜色修复保留，原调色板回归改验仍在使用的画廊底色。颜色测试19项和媒体组件测试286项通过，类型检查及定向ESLint通过；界面待用户验收。

2026-09-12首轮修复记录（用户验收未通过）：`src/utils/color.ts` 支持缺失色相 `none` 按0deg转换并保留彩度，该具体颜色输入得到251/246/247。`src/utils/color.spec.ts` 先复现失败（1失败、12通过），修复后13项通过，包含畸形数值拒绝；颜色及关联测试共25项通过，typecheck和lint通过。但这些测试未覆盖上游 `resolveTokenColor → readPalette`，不能证明界面黑条已消失。用户实际测试反馈仍有黑条，需继续修复复杂颜色表达式的求值入口。

截图经过缩小显示；仅凭这张图不判定物理DPI设置错误或所有字号过小。

## 调查范围与证据边界

- 静态审查：全局样式/六主题、基础 UI、标题栏/侧栏/画廊、设置、人物/收藏/插件页、公共弹窗、阅读器与播放器相关样式。
- 浏览器实测：本仓 DEV UI harness，默认 1280×720，以及 Tauri 配置声明的最小逻辑尺寸 800×560；抽查 Minimal Light、Fresh Light、Minimal Dark 的 gallery/settings/viewer 场景。
- 字号实测：设置页通过真实键盘输入由 13 调至 20px，再检查使用引导。浏览器自动 fill 初次未触发预期提交，改用键盘后功能正常，未将此误报为产品缺陷。
- 颜色实测：显式 `text=75&tint=60`，取 computed style 的前景与承重背景计算相对亮度；不是从抗锯齿文字截图吸色。
- 本次没有原生 WebView2、DWM 毛玻璃、真实图库、物理高 DPI 或移动设备验收。浏览器 fixture 无法证明这些场景；其部分 IPC 缺桩日志也不作为产品故障。
- 标记：**实测**为本次界面已见；**代码确认**为当前代码路径可证明；**待实测**为有明确结构依据但尚缺对应数据场景；**设计建议**为可选观感优化。

## 优先修复项

### V01 · P1 · 星级与缩略图信息徽标重叠【实测＋代码确认】

触发：在线图片有评分，同时开启格式/大小/状态信息，且未显示文件名等额外文字行。harness 第一张图片即可复现，1280 与 800 宽均存在。

- `src/components/media/mediaGridCanvas.infoOverlay.ts:90`：无文字行时，徽标占用底部 `h-22…h-6`。
- `src/components/media/mediaGridCanvas.painters.ts:223`：12px 星级占用 `h-16…h-4`，也从左侧 6px 开始。
- `src/components/media/mediaGridCanvas.cellRenderer.ts:192`：只为离线/缺失/待删状态抬升评分，没有考虑信息徽标。
- `src/components/media/MediaThumb.vue:827` 与 `:952`：DOM 路径同样使用独立的左下锚点，具备同构冲突。

影响：星星盖住 ORIG/体积，信息越多越难读。fixture 刻意打开徽标，不应表述成所有新装用户默认可见。

优化：明确左下区域的堆叠顺序，由一份布局计算提供评分、可用性、信息行的占用高度；DOM 与 Canvas 消费同一布局结果。单纯再加一个固定 bottom 值会在下一种组合再次冲突。

验收：评分 0/5 × 在线/离线/缺失 × 无文字/文件名/多行信息，常规与紧凑密度、DOM/Canvas 两路径均不相交；徽标换行或截断策略应一致。

### V02 · P1 · 测试界面与后端默认文字浓度不同【实测＋代码确认】

- `src/themes/strength.ts:23`：前端兜底 `THEME_TEXT_DEFAULT = 100`。
- `src-tauri/src/config/schema.rs:194`：后端默认仍为 `75`；`src-tauri/src/config/mod.rs:128` 的配置读取在未覆盖时返回 schema 默认。
- `src/harness/ipcFixtures.ts:295`：未传 text 时使用 null，落前端兜底；`src/themes/strength.spec.ts:46` 断言的是 100。

实测：未传 text 的设置测试页显示 100，显式 text=75 后显示 75。后端新装默认 75 是代码结论，并非本次原生应用实测；已有用户的持久化配置可能不同。

影响：测试截图看起来更清楚，默认生产配置却更淡；历史注释与部分文档还写着另一组默认值，复查容易失真。

优化：统一后端默认、前端兜底、启动快照、fixture 与测试的语义。先明确是否继续采用 75 的柔和观感；保留 75 时调整文字色阶的实际可读性，不应仅把 harness 改成 75 就宣告修复。本文不替用户改默认偏好。

### V03 · P1 · 默认浅色配色下，小文字偏淡且现有门禁漏检【实测＋代码确认】

Fresh Light，tint=60/text=75，读取实际渲染颜色得到：

| 元素 | 实际字号 | 前景 OKLCH | 背景 OKLCH | 对比度约值 |
|---|---|---|---|---|
| 设置项说明 | 11px | 0.578552 / 0.0286355 / 168.202 | 0.977804 / 0.005983 / none | 3.97:1 |
| 侧栏「个人收藏」 | 14px | 同上 | 0.986501 / 0.00395281 / none | 4.08:1 |
| 侧栏数量 | 13px | 0.668172 / 0.0274304 / 168.971 | 同侧栏背景 | 2.86:1 |

计算采用显示颜色的相对亮度；背景缺失 hue 按绘制阶段 0°处理。低彩度背景的 hue 解释差异不改变以上判断。其他主题的推算没有列作本次实测。

根因有两层：`scripts/check-theme-contrast.mjs:54` 从 color-mix 提取满浓度锚点，没有解析实际 75% 文字；`:93` 部分 secondary 正文组合仅设 3.0 门槛。设置说明在 `src/views/SettingsView.styles.css:390` 使用 secondary + xs；字号初始化在 `src/utils/uiScale.ts:13` 使 13px 基准的 xs 实际为 11px。

建议将普通功能文字与说明以 4.5:1 作为基准验收目标，不能因为 token 名称为 secondary/tertiary 就把它当作大字或装饰。W3C 的普通文本对比度参考为 4.5:1、大字为 3:1；用户主动选择柔和模式应保留可恢复至清晰配色的路径。本报告是可读性调查，不是完整合规认证。[W3C 对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

优化：按文字实际用途校准色阶；默认档与满浓度档都检查最终颜色；保留柔和偏好，不把所有文字一律加黑。默认 11px 的长说明可提高到 12px，并用间距与字重维持层级。

### V04 · P2 · 时间轴顶端年份被裁掉【实测＋代码确认】

### V05 · P2 · 放大字号后，使用引导导航重叠、图标变椭圆【实测＋代码确认】

复现：800×560，设置基础字号 20px，打开「使用引导」。左侧「时间轴与 minimap」换行后挤入上下项，正文上方的圆形背景被压扁。

`src/components/common/UserGuide.vue:176` 的导航子项允许 flex 收缩，只有 32px 最小高度；20px 基准下导航实际字号 19px，双行内容需要更大高度。`:216` 的章节图标处于纵向 flex，宽 60px、高 60px，但高度仍可被压缩。

优化：导航项、章节图标按内容保留尺寸，启用现有容器滚动；单项使用内容高度＋最小触控高度，避免固定行高吞掉多行文字。检查 13/20/24px 与中英文。

反证：本次 13/20px 下对话框高度约 471/477px，标题和页脚均在窗口内。没有证实「最小窗口下整个引导必然超框」，该说法已排除。

### V06 · P2 · 图标按钮和紧凑控件几何不统一【代码确认】

`src/assets/styles/index.css:159` 的裸 `.btn-icon` 使用 6px 内边距＋1px 边框；`src/components/ui/UiIconButton.vue:53` 改为 4px＋无边框。同为 28px 外框，图标可用空间不同。侧栏和状态栏还有更小的局部覆盖。

`src/components/settings/DynamicSettingControl.vue:583` 为紧凑下拉写 26px，但 `src/components/ui/UiSelect.vue:63` 更高特异性的规则采用 28px；数字输入仍为 26px，开关用 scale(0.8) 缩视觉。结果是相同语义的紧凑控件仍有多套尺寸口径。

优化：复用现有 28/32px 尺寸 token，集中按钮内边距、图标尺寸和控件行高；紧凑开关按尺寸布局，避免仅缩视觉而保留大布局盒。先统一高频区域，不开展全仓机械重写。

### V07 · P2 · 键盘焦点反馈偏弱，基础组件覆盖了更强的全局规则【代码确认，待各主题实屏验收】

`src/assets/styles/variables.css:112` 的 control-focus-ring 只用 22% accent；`UiButton.vue:70`、`UiIconButton.vue:75` 都移除 outline 并使用这条阴影。全局 `reset.css:89` 另走 color-focus-ring，导致同页不同控件的键盘反馈强度不一。

优化：统一 focus-visible 的颜色和几何，按最终背景验证，不直接假设另一枚现有 token 已足够。以可辨识的状态指示为目标，参考非文本状态与相邻颜色 3:1 的原则；具体适用范围见 [W3C 非文本对比说明](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)。

### V08 · P1 · 附带发现：已删除收藏夹的恢复按钮可见但无法鼠标点击【代码确认】

这是一项由样式造成的交互缺陷，单列以免被视觉优化掩盖。`src/views/CollectionsView.vue:127` 的恢复按钮被 `:513` 的直接子元素规则命中，最终 pointer-events:none；`:572` 只为删除/编辑/输入恢复 auto。全局按钮样式未覆盖这一结果，hover 也被抑制。

优化：将恢复动作排除于点击穿透规则之外；更清晰的局部方案是只让真正的装饰内容穿透。验收鼠标恢复、悬停反馈及键盘恢复。尚未使用真实已删除收藏数据进行端到端操作。

## 视觉优化方向【设计建议】

1. **让照片主导画廊。** 当前信息浮层峰值黑色 alpha 0.85，仅徽标时 Canvas 也铺约 46px 全宽渐变，220px 图片约有 21% 高度被遮罩影响（`mediaGridCanvas.infoOverlay.ts:81`、`MediaThumb.vue:952`）。优先比较局部徽标底板、按信息量决定渐变范围；保持白字和评分可读。黑色媒体覆层本身是合理的主题独立语义，不应仅因为硬编码就判错，也不建议把所有照片覆层染成主题色。
2. **减少设置页的重复层级和低频参数占屏。** 「外观与布局」在页头、章节、折叠组重复出现；六项玻璃透明度与常用外观选项同级排列（`src/constants/settingsMap.ts:140`）。将材质微调收进一个可展开组，在材质生效时呈现相关项；常用主题、文字、布局优先，解释改成短说明＋按需展开。保留高级调节能力。
3. **统一文字页面的内容宽度与空状态。** 插件页缺少内容最大宽度（`PluginStoreView.vue:605`），宽窗下名称与操作区距离过远；空状态全局与 `UiEmptyState.vue:38` 的标题字阶/颜色不同。复用设置页的内容宽度节奏与统一空状态语义，分别设置页面型和面板型布局。
4. **降低低频工具的持续占位。** 800×560 下侧栏工具卡挤压文件夹区，但这是密度取舍，用户可以折叠；可提供紧凑状态摘要和记忆展开状态。查看器标题、底部工具条、状态栏重复显示文件名，可让一处完整、其他处按情境收起；保留现有本地工具栏及合并/分离选项。
