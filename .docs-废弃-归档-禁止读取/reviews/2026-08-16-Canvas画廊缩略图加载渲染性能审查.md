# Canvas 画廊「缩略图加载 + 渲染」性能审查

> 核实修订版。范围是 `MediaGrid.vue` 在 `galleryRenderMode === 'canvas'` 分支下的缩略图生成、加载与绘制链路。本轮复核了当前代码、测试和 2026-07-17 的既有真机 A/B；没有新增真机采样。因此，本文严格区分“代码事实”“既有实测”和“待测假设”，不把静态推断写成性能结论。
>
> **[2026-08-16 晚追加]** 本报告 §5 的实施顺序已全部施工完毕(阶段 0–5),实测结果与裁决见文末 §9;其中 §5 顺序 6(全选态绘制热点)的前提被实测修正——44–60% jank 基线系测量实例伪影,详见 §9.4/§9.5。

## 1. 证据边界

- **[代码事实]**：可由当前实现或测试直接确认，但不能据此推出耗时占比或 GPU/原生内存峰值。
- **[既有实测]**：来自项目已归档的真机实验，适用于当时记录的场景和版本。
- **[待测假设]**：具备代码依据，但必须在目标 WebView2、分辨率和资源集上 A/B 后才能排序。

本文所称“冷”需进一步分层：

1. **缓存热**：目标位图已在 Canvas LRU 中。
2. **已生成、缓存冷**：缩略图文件已存在，但位图未在 LRU 中，需要 `fetch → Blob → ImageBitmap`。
3. **未生成、库冷**：先走后端生成，结果回填后再进入已生成加载链路。

第 3 类包含第 2 类的后半段，两者不是互相独立的瓶颈线。

## 2. 当前链路的核实结果

### 2.1 滚动与绘制

1. **[代码事实]** bucket 引擎的 `onScroll()` 会更新 `logicalScrollTop`；宿主滚动事件同时还维护滚动态、闸门和目录联动，因此不能概括为“整帧唯一一次响应式写”。
2. **[代码事实]** `currentY` 变化后，Canvas 组件更新方向、取消旧预取计划并调用 `scheduleDraw()`；多个请求由 `requestAnimationFrame` 合并。
3. **[代码事实]** `draw()` 会铺画布背景、二分收窄可视行、提升可见加载优先级、同步选中动画，并逐行逐格绘制；尾部以 1 ms 墙钟预算和最多 16 个新启动推进预取。
4. **[代码事实]** 每个可见格至少绘制底色和边框；有有效位图时再 `drawImage`，状态格还可能使用 `ctx.filter` 或叠加层。当前是全画布重绘，不是 dirty-rect 绘制。

### 2.2 已生成缩略图加载

1. **[代码事实]** `getImage()` 使用 12,000 条目与 512 MiB 的双约束 LRU，并将单个 pipeline 实例的在途加载限制为 64。
2. **[代码事实]** 标准成功路径为 `fetch → blob → createImageBitmap(blob) → createImageBitmap(full, crop[, resize]) → close(full) → commit → scheduleDraw`。
3. **[代码事实]** 第二次 `createImageBitmap` 的输入是已解码的 `ImageBitmap`。它是一次裁剪/格式转换/可选缩放操作，不能仅凭调用次数断言为“第二次源图解码”或“解码线程池任务翻倍”。`resizeQuality: 'high'` 只在实际传入缩放尺寸时生效。
4. **[代码事实]** 第二次转换完成前，完整位图与输出位图会短时重叠；但是否复制底层存储、落在 CPU 还是 GPU、峰值多大，无法由 TypeScript 静态确定。
5. **[代码事实]** `gallery.cacheBytes` 只估算已经提交到 LRU 的输出位图，不包含 Blob、在途完整位图、浏览器原生对象或 GPU 驻留，不能作为提高并发时的完整内存兜底。
6. **[代码事实]** 不支持标准路径时还有 `Image()` 回退；该路径不经过两段 `createImageBitmap`。

### 2.3 未生成缩略图与失败契约

1. **[代码事实]** `useRequestQueue` 以 50 ms 聚合请求，每批最多 24 项，一批完成后再处理下一批。
2. **[代码事实]** 后端不是“单 worker 逐项生成”，而是加载、解码、延后 CPU 和编码等多池流水线，通过 Channel 逐项返回结果。
3. **[代码事实]** 常规加载、解码、延后 CPU 或编码失败会返回 `thumb_status: 2`，并沿现有结果链写回数据库/布局缓存及前端 item；原文“需确认失败是否回写”的判断已经过时。
4. **[代码事实]** 仍有一个更窄的恢复缺口：整批 IPC 失败、30 秒停滞或某项缺失会让前端 Promise 拒绝；`requestThumbOnce` 对同一签名仍保持已请求状态。单纯离开再进入视口不会改变签名，因此不会自动重试。该项首先是正确性与韧性问题，性能影响需另测。

## 3. 已有证据对原优先级的修正

### 3.1 单段 Bitmap 与快速通道不是已证实的首要解法

**[既有实测]** 2026-07-17 的真机 A/B 已试过单段 WebP `createImageBitmap(blob, crop, resize)` 与 8 槽快速通道，冷区没有改善，实验被回滚；最终保留的是 64 在途上限与空闲切片，用于消除任务风暴。该实验不完全等同于“源接近桶高时跳过第二次转换”，但足以否定“少一次调用必然显著降低冷格时延”的确定性表述。

因此，跳过第二次转换仍可作为**内存/转换成本 A/B**，但不能在没有新数据时排为最高收益项。

### 3.2 64 槽是背压边界，不是已证实的瓶颈

**[代码事实]** 64 槽限制了同时进行的 fetch/bitmap 工作，也防止任务风暴。缓存的 512 MiB 预算不覆盖在途内存。

**[待测假设]** 只有当真机记录显示可见项长时间等待空槽、同时帧健康和原生内存仍有余量时，才值得做 64/128 的隔离 A/B。直接提升到 128/256 并不能由当前证据支持，还可能重新引入已被修复的任务堆积。

### 3.3 现有线索优先指向输入像素量

**[既有实测]** 已归档记录把未解决症状限定为“4K 全屏、约 64 px 密集格、480 px 单档缩略图”的冷区。项目待办已经把下一步定为按 `max(item.w, item.h) × DPR` 选择 120/240/480 多档源，并要求同时比较生成吞吐、磁盘占用和冷滚帧时间。

这不证明多档源必然解决问题，但相较于再次先调并发或 Bitmap 调用次数，它有更直接的既有证据支撑。

## 4. 其余热点：事实与假设

### 4.1 绘制、滤镜与选中动画

- **[代码事实]** 全画布背景与全部可见格会在一次 draw 中重绘；每格固定包含底色、边框以及按状态选择的图像/滤镜/叠加层。
- **[待测假设]** `ctx.filter` 可能提高离线或缺失格的绘制成本，但 Chromium 是否走软件回退、占比是否显著，当前没有证据。去掉灰度也会改变视觉语义，不能列为“低风险直改”。
- **[代码事实]** 选中动画持续 250 ms 并连续排帧；实际帧数取决于刷新率，而不是固定 8–15 帧。
- **[待测假设]** dirty rect 复杂度较高，只应在 `gallery.draw` 证明绘制占主导后评估。

### 4.2 热路径分配

- **[代码事实]** `getImage()` 会构造 `sig`/`renderSig` 字符串；`SelectionAnimTracker.sync()` 每次 draw 会为可见项创建 `Map`；滚动位移会取消并重建双 generator 预取计划。
- **[代码事实]** 布局 item 会被原地回填缩略图字段，并非不可变快照。把签名缓存到 item 或改成未定义碰撞策略的数值 hash，存在失效与正确性风险。
- **[代码事实]** `canvasRows` 是 computed 值，只在依赖失效时由 `mountedRows()` 生成新数组，不是“每次读取都平铺”。
- **[待测假设]** 上述分配是否造成可见 GC 抖动必须由 allocation profile 证明；保留旧预取迭代器还会带来过期视口优先级风险，不适合作为顺手改动。

### 4.3 可见项优先级

**[代码事实]** `prioritizeVisibleThumbLoads()` 只在加载闸门延后且在途已满时介入。常态开放闸门下，预取任务可能占用槽位并让新可见项等待；这是一条可测的调度假设，但扩槽不会自动证明或根治它。

## 5. 修订后的实施顺序

| 顺序 | 工作项 | 证据状态 | 完成判据 / 护栏 |
|---|---|---|---|
| 1 | 在目标真机重建三类冷热基线并分段定位 | 必做测量 | 能区分后端生成、asset/bitmap 加载和 draw；同时记录帧健康与原生内存 |
| 2 | 若已生成冷区与输入像素量相关，做 120/240/480 多档源 A/B | 既有实测支持的候选 | 冷格帧积分下降；生成吞吐、磁盘占用和画质不过线 |
| 3 | 为 IPC/停滞/缺失结果补可控重试与测试 | 已确认恢复缺口 | 同一签名可在有界退避后收敛，且不形成请求风暴 |
| 4 | 隔离测试“近桶源跳过第二次 Bitmap 转换” | 待测假设 | 比较 bitmap 时延、冷格帧和原生内存；不得只看调用数 |
| 5 | 仅在槽位等待被证明后做 64/128 并发 A/B | 待测假设 | 冷格改善，同时 draw、长帧和原生内存无显著回退 |
| 6 | 仅在 profile 命中后处理 filter、全量绘制与分配 | 待测假设 | 用对应 span/trace 证明收益，视觉状态需对拍 |

这一路径不要求先做结构性重构；但“当前结构无明显架构缺陷”同样不能由静态审查证明。

## 6. 真机测量设计

建议使用发布构建、目标 Windows WebView2、4K 全屏和约 60–64 px 格尺寸，至少覆盖：

1. LRU 全热的连续滚动。
2. 文件已生成但 LRU 全冷的首次进入。
3. 大量未生成项的冷库首览。
4. offline/missing 高占比资源集。
5. 大范围选中动画期间的滚动。

每个场景分别记录稳定滚动与快速拖动，并明确资源规模、DPR、档位、缓存清理方式和重复次数。现有埋点的解释边界如下：

| 信号 | 类型 | 能回答什么 | 不能回答什么 |
|---|---|---|---|
| `gallery.draw` | span | 单次 Canvas draw 的耗时分布 | draw 之外的生成/加载时延 |
| `gallery.bitmapLoad` | span | 标准 fetch/blob/bitmap 成功链路耗时 | 浏览器内部各阶段占比、原生/GPU 内存 |
| `gallery.imageFallback` | span | `Image()` 回退链路耗时 | 标准 Bitmap 路径成本 |
| `gallery.coldCellFrames` | counter | 冷格跨帧累计暴露量 | 单个冷格的精确完成时刻 |
| `gallery.visibleColdCells` | gauge | 汇总结束时最后一次可见冷格值 | 默认摘要不保留完整时间序列 |
| `gallery.inFlightThumbs` | gauge | 汇总结束时最后一次在途值 | 槽位占满持续时间 |
| `gallery.cacheItems` / `gallery.cacheBytes` | gauge | 已提交 LRU 的最后状态 | Blob、完整位图、浏览器原生/GPU 峰值 |
| `gallery.prefetchedCells` | gauge | 最后一次预取状态 | 预取任务对可见任务的逐时竞争 |

若要判断并发与峰值内存，必须补充操作系统进程内存或浏览器原生/DevTools 记录；现有 gauge 摘要只保留最后值，不应被当作时间序列。既有 headless 用例曾否定“空闲回调必然饥饿”，但真实 WebView2 是否不同仍未验证，不能把环境差异写成既定教训。

## 7. 结论

当前实现可确认的稳健机制包括：rAF 合并、可视行二分收窄、缓存双约束、64 槽背压、可取消的双通道预取，以及旧规格位图续画。它们说明管线已经有明确的防抖与背压设计，但不能推出“剩余瓶颈已集中在双 Bitmap、并发槽和 filter”。

截至本快照，唯一有项目记录支持的未解决性能症状是 4K 全屏密集格下的 480 px 冷区；现有真机反证削弱了“先改单段 Bitmap/快速通道”的优先级，下一轮应先建立分层基线，再优先裁决多档缩略图源。其余项目按测量命中逐项实验，不做无数据的结构性重构。

## 9. 实测结果与裁决(2026-08-16 施工线回写)

施工线:三件套见 [`worklogs/2026-08-16-Canvas缩略图加载渲染性能优化/`](../worklogs/2026-08-16-Canvas缩略图加载渲染性能优化/)(含全部原始数据所在与裁决细节)。环境:本机即目标机(Windows WebView2,DPR 1.5,真实库 65,594 项/99.8% 已生成,grid_row_height=64),tauri dev 构建 + CDP 直驱(裁决均取同窗/重启制交错 A/B,绝对值标注 dev 构建)。

### 9.1 阶段 1:分层基线(§5 顺序 1)
暖区 ≈ 零 jank/120fps;冷区 jank 1.7–59% 且冷格量与掉帧不必然相关(反证样本存在);生成段本库无场景(未生成仅 114 项)。当时测得「全选态滚动 jank 44–60% 为最重场景」——**该结论后被 §9.4 证伪为实例伪影**。

### 9.2 阶段 2:多档缩略图源(§5 顺序 2,已上线)
服务选档(`thumbnail/serve.rs`:最小满足档 + 缺档回退)+ 生成档位×DPR 对齐落地(commit 19cad9b/a510195)。A/B:同区并发装载 P50 37.5→29.75ms(−21%);页内双档微基准:热缓存单件两档均 2–3ms ⇒ **冷装载时延主因是 64 槽并发排队而非输入像素量**;全库磁盘 128 档中位 2.5KB(512 档 24.8KB),存量回填估算 +145MB(+9%)。裁决:选档+对齐保留;**全库存量回填不做**(渐进收敛)。

### 9.3 阶段 3:恢复缺口(§5 顺序 3,已上线)
队列内有界退避重试(`useRequestQueue`:cancelled 不重试;stalled/incomplete 0.5s→1s→2s × 3;cancel 可掐断等待期),commit 80aebb9;23 用例 + 全量 1535 过。

### 9.4 阶段 4c:选中态绘制(§5 顺序 6,**否决回退**)
- E 系列单项开关(降级实例上):mask+ring ≈0.9ms、clip ≈0.7ms、手柄 ≈0——诱导实现「帧级联合 clip + 巨路径单次 fill/stroke」批处理。
- 重启制交错 A/B(每臂全新 app):batched draw span 最快(2.4ms)但 **fps 43/jank 98.9%**;legacy **fps 118–120/jank ≤1.4%**。单实例 2×2 归因:**数百 roundRect 子路径的联合 clip 是灾难级主因**(6.7fps/帧 p50 150ms),巨路径 mask/ring 单独也回退(~19fps)。canvas2d「合并 draw call」在 WebView2 上反直觉地劣化帧光栅化——draw span(JS 提交)与帧健康度是两回事。
- **修正 §5 顺序 6 的前提**:legacy 逐格选中态绘制在健康实例上贴满 vsync;阶段 1 的 44–60% 基线是**实例级渲染降级伪影**(同日同码不同 app 实例在 43/60/118fps 三档间摆动,空闲 rAF 恒 121Hz,成因未明)。代码全部回退,零残留。

### 9.5 阶段 4a/4b(§5 顺序 4/5,**均 no-op/不采纳**)
- 4a(近桶源跳过第二次 Bitmap 转换):阶段 2 已证热缓存单件 2–3ms、瓶颈在排队;维持既有反证门控,不做。
- 4b(64→128 扩槽):冷区 6 区域配对(每 run 全新 app)——coldFrames 被区域差异主导(132↔24,699)无法配对,判据「冷格改善」未证明;无回退信号(draw/内存/fps 两臂无差)。**不采纳,维持 64**。重访前提:同区域同实例内可切换槽位,否则区域+实例双方差不可分。

### 9.6 方法学沉淀(测量效度)
1. **实例方差**:绝对值跨 app 实例不可比;真机 A/B 必须同实例内切换(运行时开关)或每臂重启交错多 rep。
2. **HMR 会清空 Canvas 位图 LRU**:代码切换后必须重跑热身趟,否则「暖区」测成冷区。
3. **draw span ≠ 帧健康**:JS 提交侧变快可能以合成/光栅恶化为代价(9.4 实证)。
4. 附带发现(待立项):app 重载/HMR 重挂载后可进入「0 个项目」死态不自愈(布局 width<100 放弃后无重试);app 窗口保存状态可损坏至屏外(阶段 1 已记录)。
