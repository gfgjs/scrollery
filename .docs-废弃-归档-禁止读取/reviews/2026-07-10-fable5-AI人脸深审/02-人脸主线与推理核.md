## 1. 人脸数据流(现状,亲读核实)

```
face_status=0(独立状态机,与 ai_status 并列;face_enabled/face_auto_analyze 门)
 → Producer(512/批领取→标 Processing;让步阶梯同 CLIP)
 → 派发线程:三级定源(分档缩略图 预测短边≥640 零读盘 → face_thumbs/ 640 WebP 缓存
              (缺则 host WIC 现场预解码,tmp→rename)→ 小原图直派 worker,白名单格式)
   → CPU permit → GPU 令牌 → FaceDetectEmbed(批≤16;YuNet 检测+SFace 128 维嵌入)
   → faces_to_records:bbox/landmarks 按协议回报的实际解码尺寸归一化并 clamp [0,1]
 → Writer 双节奏:16 项小批「先删后插 faces + face_status=Done」(进度平滑、崩溃安全);
   512 项大批增量聚类(cluster_new_faces:最近质心贪心,阈值/质量可 config override)
 → 人物 UI:list_persons(按模型隔离/忽略桶排除/named 优先)→ 人物墙;
   审批五命令(confirm/reassign/unassign/reject/create)同事务重算派生字段;
   recluster_faces(显式):plan_recluster 纯核,pinned/anchored/free + rejections
face_thumbs/ai_thumbs 均纳入缩略图共享 LRU 预算与清理(生命周期闭环,亲证 cache.rs:197-347)
```

## 2. 聚类与一致性发现(F)

### F1 🟠 merge_persons 缺同模型守卫 【子代理报告;守卫不对称性成立】
- 位置:queries.rs:3508-3596。reassign_face_to_person(:3751)与 create_person_from_faces(:3884)都有同模型守卫,唯 merge 没有:src=SFace(128 维)、dst=ArcFace(512 维)时,质心加权累加 `zip` 按短者静默截断产出无意义质心,faces 改派后 dst 簇混入异空间向量。UI 只列当前模型故常规难触发,但 IPC 边界是不可信输入(项目红线),且三命令守卫不对称本身即隐患。
- 建议:事务内先 `SELECT DISTINCT model_name`(dst∪src),非唯一即拒,与 reassign 同款文案。

### F2 🟠 增量聚类快照-写回与人工命令并发:整批聚类结果可静默丢弃 【前提亲证:FK=ON(connection.rs:30)】
- 位置:face_cluster.rs:208-283(读池快照 → 内存决策 → db_writer 短写,读写间无互斥)+ queries.rs:4233-4267(apply_face_clusters)。分析运行期间 merge/reassign/unassign **均无「分析进行中」守卫**(只有 recluster_faces 有,且那个守卫本身是「查 token → spawn_blocking 执行」的非原子 TOCTOU【亲证】)。
- 两个具体病灶:① 快照后用户 merge 删除 person A → `UPDATE persons WHERE id=A` 影响 0 行 → 随后 `UPDATE faces SET person_id=A` **FK 违约 → 整个事务回滚**,warn 一条后本批(≤512 项)聚类结果永久丢失(这些脸落入 F3 的孤儿态);② 不删簇时,用户 reassign 触发的精确重算被随后 flush 的陈旧 roster 值(滑动均值+旧 face_count)整行覆盖(lost update)。
- 建议(组合):apply_face_clusters 检查 `changes()==0` 时把该 update 的脸转挂新占位(防 FK 炸批);人工归属命令在分析运行中拒绝或事后把受影响 item 重新入 cluster_pending;recluster 守卫改原子(占用类 token 标志,start 侧同查)。

### F3 🟠 「孤儿未聚类脸」无自愈 【亲证】
- 位置:face_pipeline.rs:379-435(faces 落库+Done 每 16 项;聚类每 512 项,分离节奏)+ face_cluster.rs:226(get_clusterable_faces 只查**本轮 item_ids**)。
- 成因两个:① 进程硬崩溃(取消路径尾部会 flush,亲证 :419-435;唯 kill/断电丢 cluster_pending);② F2 的 FK 炸批。结果:face_status=Done 而 person_id=NULL 的脸**永不再被增量聚类**,唯一救济是显式 recluster_all——但那会重排全部未确认归属,杀鸡用牛刀。
- 注意修法陷阱:person_id=NULL 还包含「低于 min_quality(有意不聚)」与「用户 unassign 移出」两类,**不能**无脑对账扫描全部 NULL 脸(会对抗用户意图)。建议:faces 表加「已参与聚类」标记(或 pipeline 启动时仅对账 `quality≥min 且无 unassign 痕迹` 的脸,幂等),对齐缩略图线 6ff2841「事件驱动复位+启动兜底」的精神。

### F5 🟡 手动 merge 成果可被下次 recluster 撤销 【子代理报告】
merge 改派的脸不置 is_confirmed → 对 recluster 是 free 脸;且删 src persons 时其 face_rejections(person_id CASCADE)一并蒸发。用户手工合并后跑一次「修碎片」,合并进来的脸可能按最近质心散回新占位簇——恰是 recluster 文档承诺保护的「用户劳动」。建议:merge 对被并入脸置 is_confirmed=1(与 reassign 对齐);或前端确认框明示。

### F6 🟡 recluster 后未触及的 named/ignored 人物 face_count/cover_face_id 陈旧 【双重亲证(主审独立发现+子代理)】
- 位置:queries.rs:4368-4410(rebuild 白板+重放,只回填 updates 内人物)+ face_cluster.rs:436-452。已命名人物若既无 pinned 脸又零吸附 → 不在 updates → 行存活但 face_count 旧值、cover_face_id 指向已解绑(可能已归他人)的脸;[list_persons](../../../src-tauri/src/db/queries.rs#L3393) 直接展示存储的 face_count → 人物墙「张三 · 12 张」点进去 0 张。
- 建议:rebuild 事务末尾对本模型 named/ignored 且未被 updates 覆盖者补对账 UPDATE(face_count=实际引用数,归零者清 cover/centroid,与 recompute_person_aggregates 空槽策略一致)。

### F7 🟠 硬删媒体级联删脸后 persons 派生字段无对账 【子代理报告;CASCADE 亲证(schema.rs:424)】
硬删/移动出库 `DELETE FROM media_items` → faces CASCADE 无声消失,但 persons.face_count/cover_face_id/centroid 均不重算 → 计数虚高、封面悬挂(前端裂头像/占位)、照片删光的人物以旧计数挂墙(空簇清理只在 recluster)。建议:硬删路径删前收集 `DISTINCT person_id`,删后同事务逐个 recompute_person_aggregates;或启动 reconcile 加「face_count 对账」幂等修复(项目已有 reconcile 先例)。

### F9 🟡 Error 项无非破坏性重试通道
face_status=3 只有 restart_face_analysis 能复位,但那会**清空本模型全部 persons/faces、销毁命名与确认**。一批图因临时原因(卷离线/WIC 抽风)标 Error,补跑代价=全部标注劳动。建议:`retry_failed_face_items` 命令(`UPDATE ... SET face_status=0 WHERE face_status=3` 分批)+ 走既有 start,零破坏。CLIP 侧配套见 A11。

### F10 🟡 流水线完成回调无条件 cancel 可误杀新一轮 【子代理报告;结构亲读印证】
face_pipeline.rs:115-123:旧轮被 restart cancel → 新 token 安装新轮启动 → 旧轮 blocking 任务迟退出 → 完成回调 `state.cancel_face_analysis()` take 并 cancel 的是**新一轮 token**。新轮静默中断,is_analyzing=false 而 analysis_active=1 前端自相矛盾;「暂停→立即开始」「连点重启」可复现;自愈靠下次启动。建议:回调持有自己 token 的克隆做 compare-and-clear(仅当槽中是同一枚才 take);CLIP 侧同构一并修。

### F11 🟡 set_active_face_model 切轨与在途 writer 小窗口竞写(face_commands.rs:596-615):cancel 协作式不 join,writer 可在 sync 分批推进已扫过的分片上补写 status=2 → 新轨下无脸却 Done,且 face 侧无 start-sync 自愈(见 X2)兜底。建议 sync 前等待流水线真正退出,或 sync 循环改「连续一轮零改动才收敛」。

### F12 🔵 Error 项若残留上轮成功脸,切轨 sync 会把 3 翻成 2(状态机语义被旁路,行为无害);F13 🔵 「脸+状态一起原子落库」注释与实现不符(同锁下两个事务;崩溃窗口靠先删后插幂等兜住,结果安全——改注释或并事务皆可);F8 🔵 软删项的脸仍留簇内计入 face_count(语义可辩,标注)。

### F14 🔵 download_face_model 在 async 正文 `std::fs::create_dir_all`(face_commands.rs:652);F15 🟡 proofread set/clear key 的 keyring 系统调用直跑 async 正文(proofread_commands.rs:84-99;同文件 get 侧已明注下沉,标准不一,Windows 凭据库可触慢路径)。

### F3'(附注)unassign 不持久:移出不记负样本,下次 recluster 大概率按最近质心吸回(reject 才挡)。前端若把「移出」当终局操作会误导——归功能缺口册 §2.11。

### F4 ✅ 正面确认:rejections 在各归簇路径的地位自洽
全量 recluster 逐脸消费(有测);增量传空集**可证明正确**(新自增 id 不可能有拒绝记录 + face_rejections CASCADE);pinned 优先于 rejection 自洽;手动 merge 不查 rejections=用户显式操作压过负样本(语义成立,但见 F5 的后续矛盾)。

## 4. 推理核发现(K,ai-core;子代理产出,K1 主审亲证)

### K1 🟠 图像批推理不校验输出张量形状:错配模型时静默产出错切向量,全链盲区 【亲证】
- 位置:[clip.rs:426-437](../../../crates/scrollery-ai-core/src/clip.rs#L426):`try_extract_tensor` 的 `_out_shape` 被丢弃,按 `off = i × profile.embed_dim` 手工切行。实际模型输出 768 维而 profile 声明 512 时(手动导入错模型/改名错放,入口=A20 import_ai_model 零校验),切片跨行错位但**每个向量长度恰=profile.embed_dim**。
- 全链盲区(逐环亲证):worker 维度红线(batch.rs:236 `len != profile.embed_dim`)长度恰好匹配 → 失效;SessionReady 的 embed_dim 来自**注册表 profile**(main.rs:224)而非模型自省 → host 侧任何「会话 vs profile」比对恒等、永不触发(裁决:CLIP 路 A6 的 host 侧修法无效);垃圾向量入库标 Done;搜索 ensure_cache 按 blob 长度过滤——长度又恰好合法 → **照常参与打分,结果是噪声**。文本路径 to_vec 整取、人脸路径 total/n 反而能被红线捕获,唯独图像路径漏防。
- 建议(唯一有效修复点在 ai-core):切行前断言 `_out_shape` 末维==embed_dim 且行数==run_rows,不符返 AiError;并在 SessionInit 用 session 元数据自检「输入 [_,3,S,S] 的 S==image_size、输出末维==embed_dim」,把错配在激活时即拒(配套 A20 入口校验、A7 搜索侧最后防线)。

### K2 🟡 CLIP 图像模型文件缺失误触发「GPU 失败」回退,连带人脸降级 CPU
engine.rs:287-339:load_session_pool 对「文件不存在」与「GPU 加载失败」同返 None,回退分支不区分 → 只装了人脸模型的用户,人脸在有 GPU 的机器上被静默降到 CPU,UI provider/gpu_name 失真。建议回退条件补 `image_path.exists()` 三态区分。

### K3 🟡 CPU 路径线程超订:每 session intra_threads=全核 × 池容量 2 × 四池共存(engine.rs:240-284,536-543),最坏 4+ 满核 session 并发,2-4× 超订;文本塔 CPU 池固定 2 只用 1。建议容量×线程≈核数、文本池降 1。

### K4 🟡 人脸 letterbox 全量克隆源 RGBA + ndarray 逐元素索引写(face.rs:92-111/276-302);clip 侧同构热点 T18.5 已改平坦 slice 写,face 侧未跟进。640×640×3≈123 万次带边界检查写/图。建议仿 T18.5 平坦化 + FlatSamples 借用视图免克隆。

### K5 🟡 动态 batch 路径整批冗余复制一次(clip.rs:385-394):`fixed=None` 时循环单轮却仍 `slice().to_owned()`(N=32、224px≈19MB/批);start==0&&end==n 时可 move 零拷贝。

### K6 🟡 vocab 路径非 UTF-8 时静默回退 CWD 相对 "vocab.txt"(clip.rs:581):错误信息完全指错方向。to_str 为 None 直接返 Tokenizer 错误。

### K7 🟡 provider 探测纯编译期 + override 仅识别 "cpu"(provider.rs:74-104、engine.rs:234-238,510-531):CUDA/OpenVINO 枚举与 build 分支永不可达,Linux 有 N 卡只能 CPU;用户传 "cuda"/"directml" 被静默忽略(AiProvider::from_str 存在未接线)。与台账 P1-14「引擎切换」待办互证。建议 override 接 from_str 全量放行(失败自然回退)+ 运行时 EP 可用性探测。

### K8 🟡 preprocess_decoded/encode_image_from_decoded 是**无消费者死代码**且带雷(clip.rs:506-548):无尺寸校验,短边不足时静默中灰填充;doc 硬编码 224 与 336 profile 矛盾。删除或改 Result+校验。

### K9 🟡 CenterCrop/Resize 取整与 torchvision 有 ≤1px 亚像素差(clip.rs:471-479)+CatmullRom≈但≠PIL BICUBIC:检索几乎无感,建议跑一次对拍记录余弦下界(如 ≥0.999)作基线证据,不必改码。

### K-🔵 摘要
输出按 `outputs[0]` 索引取(输入侧有动态名解析,不对称;多输出导出会静默取错)· bytes_to_embedding 非 4 倍长度静默丢尾 · warn_embed_dim 只 warn(依赖调用方终检,建议 doc 注明)· YuNet 后处理 12 次 to_vec 拷贝(~0.5MB/图,借用可并存,理由不成立)· 加载超时 loader 线程泄漏(短命子进程可接受,注明)· l2_normalize 零向量静默 · profile.rs:100 注释残留 · detect_vram_bytes 只枚举 adapter 0(混合显卡取到核显;建议遍历取最大)· face embed_batch 真错误时双倍开销(逐脸回退不分错误类)。

### K-💡(性能/演进,归 04 路线图)
resize 换 fast_image_resize(SIMD,4-8×,需重跑金标对拍)· 嵌入量化预留(f16/int8,profile 加 storage_dtype)· SessionInit 形状自检(即 K1 修法后半)· DML 首查询 warmup(消秒级毛刺)· output_normalized 声明抽检(首条 |‖v‖−1|<0.01)。

### bbox 越界裁决(子代理存疑项,主审裁定)
ai-core 检测框反 letterbox 后不裁剪(face.rs:222-239),贴边脸可负坐标/越界——但 host 落库映射 [faces_to_records](../../../src-tauri/src/ai/face_pipeline.rs#L340) 已把 bbox/landmarks clamp 到 [0,1]【亲证】,DB 与前端画框安全。残留:x 与 w **独立** clamp 有轻微形变(x<0 截到 0 而 w 不缩,右缘外扩);crate 单独消费时无保护。降为 🔵:建议 clamp 改「先裁矩形再归一化」,或 DetectedFace 提供 clamped() 方法。
