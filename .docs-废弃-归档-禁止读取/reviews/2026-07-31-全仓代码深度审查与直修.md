## 1. 结论先行

当前源码的常规质量门已经达到可继续集成的水平：Windows 本地 Rust workspace 的格式、编译、Clippy 和全量测试均通过；前端 lint、严格类型检查、1525 个测试、生产构建和渠道 bundle 扫描均通过；生产 npm 依赖审计为 0 漏洞。本轮确认并直接修复了配置迁移吞错、增强模型占位清单误开放、多处异步旧响应串写、Unix 本地文件 URL 错分流、增强结果落盘/入库错误处理、生产 PostCSS 漏洞以及一批 IPC 原始异常泄漏等无设计分叉问题。

但**当前不能据此判定“正式发布闭包已完成”**。`tauri.conf.json` 的生产构建只准备并打包 `raw-worker`，而运行时还依赖同目录的 `ai-worker`、`enhance-worker` 和 `video-worker`。正式安装器没有这些 sidecar 的构建、声明、内容断言与 fresh-install 冒烟证据。这是本轮唯一 P0，属于发布阻塞项。

其余待裁决项集中在配置事务、布局请求取消/版本仲裁、IPC 错误类型化、增强队列 FIFO 和开发工具链依赖升级。它们不适合在审查中擅自拍板，详见 §4。

## 3. 尚未解决的问题（按严重度）

### P0 · R-001 正式安装包缺少三个运行时 worker

**证据**：

- `src-tauri/tauri.conf.json` 的 `beforeDevCommand` 只额外构建 `ai-worker`，`beforeBuildCommand` 则只执行前端构建和 `build:raw-worker`；
- `bundle.externalBin` 只有 `binaries/raw-worker`；
- AI、增强、视频服务均在运行时查找主程序同目录的对应 worker；
- release workflow 最终调用 Tauri build，但没有为三个 worker 建立 target-aware 构建、复制、签名、bundle 内容断言或安装后冒烟；
- `build-raw-worker.mjs` 在非 Windows 平台直接成功跳过，并按本机 rustc host triple 命名，不能作为交叉目标的通用打包方案。

**影响**：开发机可因 workspace 旧产物或 dev hook 表面可用，但 fresh install 的 AI、增强与扩展视频能力会找不到进程；NOTICE 中“随安装包分发”的描述也缺少真实 bundle 证据。

**结论**：正式发布阻塞。建议采纳 D-001 后一次性闭合构建、打包、签名和安装器验证，不做零散复制脚本补丁。

### P1 · R-002 配置文件只有进程内串行化，没有完整事务与值域契约

**证据**：

- `ConfigManager::write_lock` 只能串行本进程写入；外部编辑器/watcher 与应用写入仍可能在“读旧文档 → 改一键 → 固定 `.tmp` → rename”窗口互相覆盖；
- schema 只表达 `Bool/UInt/Float/Path/Enum` 类型，未表达数值范围。比如 `derive_batch_size = 0` 能通过校验并进入后续批处理参数；质量、容量、帧数等也允许不合理大值；
- `thumb_cache_dir` 的注释要求绝对路径，但通用 `Path` 校验只验证 TOML 字符串类型；启动路径有空串归一，而外部热应用路径没有同等强度的绝对路径、规范化和边界约束；
- watcher 事件的 `restart_required` 是单次 diff，前端会用下一次事件覆盖提示，后续仅热更新的编辑可清掉仍未重启的冷配置提醒。

**影响**：跨进程丢更新、临时文件冲突、零批次停滞/无效配置、相对缓存路径以及重启提示误消失。

**结论**：需要统一事务和 schema 设计，见 D-002、D-007。

### P1 · R-003 布局 30 秒 watchdog 会重新开放并发请求

`mediaStore.computeLayout` 超时后把 `isComputingInternal` 和 UI 标志都清零，但旧 IPC 没有被取消，后端布局计算及 cache 提交仍继续。用户重试后，新旧计算可并行；旧请求晚到时仍能覆盖前端 `layoutSummary`，后端 cache 也没有“仅最新请求可提交”的版本仲裁。

**影响**：大库或锁竞争场景下可能出现布局倒退、行版本不一致、重复高负载计算。只在前端加布尔标志不能可靠修复。

**结论**：需选择后端取消或 request-id/latest-wins 协议，见 D-003。

### P1 · R-004 IPC 错误定向脱敏已落地，但消息型变体仍未形成默认安全契约

本轮已把所有直接 `AppError::System(e.to_string())` 调用改为“固定用户消息 + 私有 source 日志”，并为 `Os` 增加同姿态 helper；WIC、Media Foundation、WebDAV、worker 启动/调度及常见 `JoinError` 路径同步清理，且回归测试锁住 source 不进入序列化结果。

剩余风险在类型架构：`Serialize` 仍会原样返回 `PathResolution/FFmpeg/AudioMetadata/DocumentRender/System/Os/AiTokenizer/Internal/CreateFolder/MoveFile/CopyFile/InvalidMove` 等字符串变体的 message。当前新修调用点是安全文案，但未来任一调用者再次塞入底层 `Display` 就会重新泄漏路径、worker 文本或系统细节。另有部分 worker/域错误仍手工拼装内部信息，需要逐类区分“允许用户看到的业务参数”和“只能写日志的 source”。

**结论**：已消除已批准的直接泄漏面，但还不能宣称全局 fail-closed；见 D-004。

### P2 · R-005 增强队列串行但不是严格 FIFO，且可同时显示多个 Running

每次 enqueue 都独立 `spawn_blocking`；`run_job_blocking` 在获取 worker mutex **之前**就把 job 标成 `Running`。mutex 保证同一时刻只有一个 worker 执行，却不保证等待线程的 FIFO 顺序，也不能保证 UI 只有一个 Running。

**影响**：队列顺序与用户提交顺序可能不一致，状态会过早显示执行中。见 D-005。

### P2 · R-006 全量 npm 审计仍有开发依赖高危告警

生产闭包已清零；全量 `npm audit` 仍报 10 个 high 条目，实际收敛到两个开发工具链根：

- `onnxruntime-node -> adm-zip < 0.6.0`；上游安全修复点为 `adm-zip 0.6.0`，但当前 onnxruntime 依赖范围仍停在 `0.5.x`；
- ESLint / vue-tsc 旧主版本闭包中的 brace/minimatch 系列；当前主版本可接受的补丁已提升，但 npm 建议的完全消除路径涉及 ESLint/vue-tsc 主版本迁移。

这些包不进入生产 bundle，但会在开发/CI 处理仓库输入。自动 `npm audit fix --force` 给出的 onnxruntime 降级或工具链大版本升级都可能引入兼容性回归，因此未擅自执行。见 D-006。

### P3 · R-007 生产入口 bundle 余量偏小，三个动态 import 实际不会拆包

Vite 构建通过预算，但入口为 675.12 kB，距离 708 kB 门槛仅 32.88 kB（约 4.6%）。构建同时提示 `aiStore`、`scanStore`、`faceStore` 既被静态导入又被动态导入，因此动态导入不会形成独立 chunk。

**影响**：不是当前功能错误，但后续少量功能增长即可触碰门禁。见 D-008。
