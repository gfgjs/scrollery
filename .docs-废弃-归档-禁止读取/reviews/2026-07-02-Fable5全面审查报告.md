## §3 产品设计与商业化审查

### 3.1 做对了什么

1. **定位是可防守的**:「本地优先 + 隐私 + 百万级 + 中文语义 + Picasa 文件夹哲学」在 Eagle/digiKam/Immich 之间确实存在一个未被占据的楔子;目标用户分层(Picasa 遗产用户优先)符合迁移成本最低原则。
2. **盈利模型(方案 C)论证充分**:免费四媒体核心 + 三插件买断,技术成本与收费逻辑精确对齐,明确否决「按媒体类型收费」的 crippleware 反模式——这是从竞品翻车史里学来的真教训。
3. **诚实边界罕见地清醒**:Part0 §8.3 与 Part8 RK13 明确承认「防破解只有威慑无阻断」「加密权重对公开权重不构成护城河」「一个泄漏 token 即击穿插件级密钥」,并据此约束营销文案。多数商业方案文档不敢写这个。
4. **命名/商标风险(§10.7)处置专业**:「Picasa」商标活跃、必须改名的裁决 + 清权流程 + Nominative Fair Use 边界,达到了律师函前置水平。⚠️ 但**最终产品名至今未拍板**,而 `tauri.conf.json identifier` 上架后不可改——这是所有上架工作的前置死锁,拖得越久改名成本越高。
5. **§11.4 MVP 切割线**(v0.1 = Windows 直销 + exotic-formats 单插件闭环)是整套文档里最重要的一次自我纠偏,直面「完美规划下的无限期未发布」。

### 3.2 结构性隐忧

1. **DRM 工程与生存要素的比例失衡(最重要的产品级判断)**。Part8 中授权/加密/渠道管线约 20 页,而官网/落地页/转化漏斗/社区(C7/C8)约 1 页。对独立开发者,真正的生存风险是「没人知道这个产品」,不是「有人破解 $9.9 的插件」。RK13 已承认 AES 层对公开权重几乎不买任何东西,AES 也已被 §11.4.3 正确后置——但配套的具名 shm 硬化、DerivedSecret 双门控、跨 4 份文档的加密管线规格仍在消耗规划与维护成本。**建议:把 AES 层从「后置」进一步降级为「私有模型出现时再设计」,把等量精力转投 C7/C8。**
2. **范围仍然对单人产能过大**。即便有 §11.4 切割,在途面仍横跨:百万级滚动结构性修复(T16 方案B ~2 周)+ HEIC 引擎注册 + S4 选区后端迁移 + AI/人脸 worker 化全段 + mac objc2 桥(自述 2–3× Win 工作量)+ 双仓 Copybara 管线 + 上架三渠道。**波次图描述的是依赖,不是产能**;建议每个 Wave 显式标注「单人串行周数」,防止依赖图造成的并行幻觉。
3. **「百万级流畅」这个第一卖点当前无排期兜底**(详见 §9)。产品页写出这句话之前,T16 方案B(或降级话术)必须有里程碑位置。
4. **Steam 渠道的编译变体投入过早**:30% 抽成、自我定位「曝光为主」,却在 Part7 拿到完整的 feature-matrix 车道。在第一笔直销收入发生前,这属于可删减的规划负债。

## §5 架构审查

### 5.1 总体:插件平台的去环设计是全项目最亮眼的架构成果

实测依赖图(无环,本会话据子审查交叉确认):

```
picasa-next-plugin-api        (叶:EntitlementProvider / LicenseStatus / LicenseError)
      ▲         ▲        ▲
exotic-trust  free-stub   │          exotic-protocol(独立叶)
   ▲   ▲          ▲       │               ▲          ▲
   │   │          │       │               │          │
  pro  └── src-tauri ─────┘           src-tauri   psd-worker
```

- `exotic-trust` 收纳验签原语,`src-tauri/exotic/crypto.rs` 降级为纯 re-export 壳;pro 只依赖叶 crate,不依赖 src-tauri——环真正解掉了,且 OSS Cargo.toml 不含 pro path dep 的红线得到遵守。
- worker 进程监督(supervisor/pipeline)是教科书级:Drop/kill_and_reap/shutdown 三路防僵尸、专用 reader 线程防 stdio 死锁、deadline+CANCEL_POLL 超时、崩溃中帧 → strike 重试。
- 安全纵深(install.rs)同样扎实:验签先于解包、zip-slip 四层防御、zip-bomb 上限、fail-closed 时钟、`#[cfg(debug_assertions)]` 把 env 旁路编译期排除出 Release。

### 5.2 发现(按严重度)

**[High] 激活路径绕过「唯一 swap 点」→ ③b 后信任根分裂。**
`default_entitlement_provider()`([exotic/mod.rs:221](../../src-tauri/src/exotic/mod.rs#L221))自我声明为唯一注入点,但 `activate_exotic_plugin` / `deactivate_exotic_plugin` / uninstall 的 `remove_license` 直接 `KeyringLicenseStore::new(VerifyingKeyset::builtin())`([exotic_commands.rs:264-268, 288-292, 663-664](../../src-tauri/src/ipc/exotic_commands.rs#L264))。③b 把 KeyringLicenseStore 迁入 pro(用生产 keyset)后,会出现 **evaluate 走 pro 生产钥、activate 仍走开源占位钥** 的分裂——商业 build 激活静默失败。`activate`/`remove_token` 当初有意不进 trait([plugin-api/lib.rs:82-84](../../crates/picasa-next-plugin-api/lib.rs#L82)),所以这是结构性缺口,**必须在 ③b 动工前解决**(把激活族方法纳入 trait,或提供第二个注入点)。

**[Medium] G1–G6 框架先行于消费者。** AI/人脸 worker 尚不存在,协议/GPU limiter/model-blob 框架已按 P1 排期——todo.md 已自我纠偏为「YAGNI until Part4」,但 Part6 正文仍按 P1 排;属于 §4.2 同一种病的架构版。

**[Medium] worker 资源约束单薄。** `apply_low_priority` 在非 Windows 是 no-op(与注释「始终生效」矛盾,[worker.rs:114-119](../../src-tauri/src/exotic/worker.rs#L114));无 OS 级内存上限(Windows Job Object / setrlimit),失控 worker 仅靠应用层像素/文件体积上限兜底。AI worker(ort + 700MB 模型)接入前应补齐。

**[Low] `install.rs` vs `installer.rs` 命名易混但职责清晰**(原语 vs 编排,非死代码);sha256-hex 格式化三处重复;`is_exotic_running` 一处 `.lock().unwrap()` 与全库 `unwrap_or_else(|e| e.into_inner())` 的毒锁恢复惯例不一致([state.rs:409](../../src-tauri/src/state.rs#L409))。

### 5.3 约定符合性

- **锁纪律 ✅**:`tokio::sync::Mutex` 全库仅 `exotic_install_lock` 一处([state.rs:70](../../src-tauri/src/state.rs#L70)),且属于「必须跨 `.await` 持有以串行化目录变更」的正当场景;`db_writer` 为 std::Mutex 且短持有。未发现 lock-across-await 缺陷。
- **SQL 参数绑定 ✅**:后端子审逐条追踪了 `queries.rs`/`media_commands.rs` 全部 `format!`/`push_str` 进 SQL 的路径——值一律占位符绑定,结构拼接均来自受信 enum/常量匹配(如 `order_dir` 仅能取 "ASC"/"DESC")。LIKE 模式作为参数绑定而非拼串。**未发现注入面**。
- **rusqlite only ✅**;**thiserror + 稳定错误码 ✅**(`error.rs` 有专门测试锁 code 稳定性)——唯 `InstallError` 无 `code()`,install 族错误在 IPC 边界坍缩成 `"install_failed"` 泛码([exotic_commands.rs:512,588,657](../../src-tauri/src/ipc/exotic_commands.rs#L512)),违反本项目自己的 IPC 错误契约,建议补齐。

## §6 后端代码审查(核心发现)

### 6.1 [High] 布局缓存版本号竞争(本会话亲验代码)

[layout/cache.rs:97-127](../../src-tauri/src/layout/cache.rs#L97):`store_layout` 在 **写锁之外** 先 `LAYOUT_VERSION_COUNTER.fetch_add`(:98),之后才 `cache.write()`(:116)。Tauri 并发执行命令,两个并发 `compute_layout`(各自 `spawn_blocking`,[layout_commands.rs:76](../../src-tauri/src/ipc/layout_commands.rs#L76))可发生写序倒置:A 拿到 v5、B 拿到 v6,但 B 先写、A 后写 → 缓存最终存着 **v5 的旧行集**,而前端已握有 v6 → 后续 `get_layout_rows(expected_version=6)` 恒 `None` → 假性 `LayoutNotReady`/重取风暴。**修法很小**:把 fetch_add 挪进写锁临界区(或版本号并入锁内数据)。前端有 fetch-id 竞态守卫兜底,故用户可感概率低,但这是核心数据路径上真实的竞争窗口。

### 6.2 [Medium] 失效契约不完整:软删除后旧布局按原版本继续供货

`soft_delete_items`/`restore_items`([media_commands.rs:426-443](../../src-tauri/src/ipc/media_commands.rs#L426))与扫描新增**均不失效布局缓存、不递增版本**,依赖前端「自觉重算」。收藏与缩略图有专门的 in-place patch(`set_favorite_in_cache`/`apply_thumb_results`),删除却没有对应处理——失效契约是隐式且不完备的。前端恰好有 staged-delete 后重算的习惯掩盖了它,属于「靠调用方好习惯而非契约保证」的脆弱平衡。

### 6.3 [Medium] 绝大多数读命令直接阻塞 async executor

仅 `compute_layout` 与 `get_subtree_scroll_target` 用了 `spawn_blocking`;`get_media_detail`、`search_media`、`get_meta_for_viewport`、`get_directory_tree`、`get_trash`、`get_stats`、`toggle_favorite` 及全部 `batch_*` 都在 tokio worker 上同步跑 rusqlite([media_commands.rs:86,100,130,467-539](../../src-tauri/src/ipc/media_commands.rs#L86) 等)。这直接违反项目 CLAUDE.md「rusqlite 不得阻塞 async executor」约定。大库上 `get_directory_tree`(见 6.5)或 `search_media` 一次可占住 worker 数十 ms,与其他 IPC 争 executor。**建议按「预计 >1ms 的查询一律 spawn_blocking」做一次机械迁移。**

### 6.4 [Medium] 写锁下的长事务

`reset_ai_embeddings` / `sync_ai_status_for_model`([queries.rs:2442-2477](../../src-tauri/src/db/queries.rs#L2442))在 `db_writer` Mutex 内做全表 UPDATE;期间 `toggle_favorite`/`set_rating` 等交互写全部排队。WAL 保证读不受阻,影响限于写延迟,但模型切换恰是用户盯着 UI 等的时刻,值得分批。

### 6.5 [Medium] 目录树查询 O(节点×子树)

[queries.rs:249-291](../../src-tauri/src/db/queries.rs#L249):`get_directory_tree` 每行跑一个相关递归 CTE 计算 `media_count`,外加每行 `has_children` 子查询。深宽目录树(Picasa 遗产用户的典型形态)会慢;可用一次分组聚合替代。`get_app_stats` 的 8 个独立 COUNT(*) 同理可合一(条件聚合)。

### 6.6 其余

- **[Low] `get_view_ids` 双读 TOCTOU**([layout_commands.rs:143-153](../../src-tauri/src/ipc/layout_commands.rs#L143)):仅错误码归类可能失真(ViewStale vs LayoutNotReady),无数据风险。

### 6.7 scanner / thumbnail 流水线(主审亲查)

**[Medium] 缩略图落盘非原子写 + 缓存命中仅查存在性 → 崩溃后半截缩略图永久生效。**
[generator.rs:356,443,527](../../src-tauri/src/thumbnail/generator.rs#L356) 三处均为 `std::fs::write(&disk_path, &webp)` 直写最终路径;而缓存命中判定只做 `full.exists()`(:187)。进程崩溃/断电发生在写中途时,截断的 `.webp` 会留在正式路径上,之后每次都命中「缓存」→ UI 永久裂图,除非用户手动清缓存。**修法一行量级**:写 `*.tmp` 后同卷 `rename`(原子替换),三处同改。

**确认的强项**(与 Part2/Part3 文档回写吻合,抽查属实):
- `panic_guard`(catch_unwind)包裹全部第三方解码/编码路径([generator.rs:41-59](../../src-tauri/src/thumbnail/generator.rs#L41)),配合 workspace 根「必须 unwind、lite profile 不得 abort」的注释纪律,损坏文件只废单项不炸进程。
- 尺寸档位 `snap_to_tier` 带着「4 档未经多设备实测、改档位=全库缓存作废」的诚实告示(:27-29)——这是该文档体系「诚实边界」文化在代码注释层的正向延伸。
- direct-display 路径保留 thumbhash 占位底线(≤500KB 守卫,:225-235),修掉了旧版 strategy=direct 丢占位的缺陷。
- fast_scan 是真流式:一次只持一批、`par_iter` 取尺寸、500 行/事务([fast_scan.rs:297-429](../../src-tauri/src/scanner/fast_scan.rs#L297));enricher 用 `reserved_core_pool` 为前台 `compute_layout` 留核(明确针对「与 2s 自动重排互相饿死」的反馈循环,[enricher.rs:152-155](../../src-tauri/src/scanner/enricher.rs#L152)),批间检查 cancellation,按画廊视图顺序自上而下补全(贴合用户滚动,细节用心)。
- enricher 的 `format!` 拼 SQL 经查全部为常量分支拼装(order 子句 enum 匹配,值走 `?N` 绑定,[enricher.rs:602-621](../../src-tauri/src/scanner/enricher.rs#L602)),无注入面。

**[High] i18n 半途而废,英文用户今天会看到中英混排界面。** locale 文件本身健康(en-US 464 行 / zh-CN 447 行,键位对齐),但 **27 个组件里约 217 处模板硬编码中文**,同一文件内 `t('selection.favorited')` 与硬编码「已取消收藏」并存(MediaGrid.vue:922 vs 940),还有 `t('x') || '中文'` 的临时回退模式。这不是补几个键的事,需要一次系统性清扫 + ESLint 规则(`vue/no-bare-strings-in-template` 类)防回潮。
