# 开源协议迁移全面审计

> 🔴 **2026-09-14 注**：本文针对 Apache-2.0 → MPL-2.0 迁移的许可结论已被 AGPL-3.0-only ＋单独商业授权的决议取代。
> 正文的闭包缺口、门禁与权属证据按其日期保留；第三方许可与历史版本相关结论不受影响。
> 现行规范见 [AGPL-3.0-only 与单独商业授权决策 brief](../decisions/2026-09-14-决策brief-AGPL-3.0-only与单独商业授权.md)。

## 结论

当前不能把迁移判定为“可发布完成”。根目录的 MPL-2.0 正文和若干公开口径已经改对，但发布闭包、权属证明和门禁仍有实质缺口。下面的问题来自当前工作树、实际构建脚本、依赖源码和现有 NSIS 产物；没有把提交说明或已有状态文档当作证据。

## P2 问题

- Rust manifests 的 `license`/`license-file` 均为空；`cargo package` 已给出缺少 license、repository 等元数据的警告。公开 crate 应补机器可读许可，私有 crate 则应明确专有边界，不能统一盲填 MPL。
- 应用按需下载 BtbN 的 `lgpl-shared` FFmpeg，解压时只留下 `bin/`；运行时已纳入 `NOTICE.md` 并标记 LGPL。P1 分发策略已由维护者确认：LibRaw 选择 CDDL-1.0，FFmpeg 保持精确钉定的独立 LGPL-shared 进程运行时；后续仅保留发行渠道变化时的常规复核。
- 一方源码没有 SPDX/MPL 文件头。这不是单独的硬错误：MPL 官方 FAQ 允许在目录级 `LICENSE` 足够清晰时不逐文件放头，但当前项目应为新增文件建立一致策略，避免 Copybara/第三方扫描无法确定覆盖范围。
- `generate-notice.mjs`只声明 Windows MSVC 的三个 Rust root，而 Tauri 配置允许 `all` target；若以后发 macOS/Linux，NOTICE 不能证明对应 target 的闭包。
- `SOURCE.md`仍是未跟踪文件；清洁 checkout 若未纳入它，法律资源映射会缺失。其源码指引还应绑定构建 commit 或等价不可变 revision，而不是只写泛化的 tag/release。
- 活跃状态和待办把迁移、权属闸门、NOTICE/安装包闭包写成已完成，但当前证据只覆盖根文本、部分脚本和一个 NSIS 样本；这些文档不能替代上面的发布门禁。

## 已核实的正面项

1. `LICENSE` 是标准 Mozilla MPL 2.0 正文，包含 Exhibits A/B；没有发现把第三方依赖的原许可证机械替换成 MPL。MPL 正文和[官方 FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/)支持使用相关目录中的许可证文件作为通知方式。
2. `package.json`、`package-lock.json`、README、贡献指南、商标说明和 Tauri 资源映射已出现 MPL 口径。
3. 当前 MSI/NSIS 样本实际包含根法律文件、sidecar/runtime 和完整 `legal/` 树；闭包 verifier 对源文件与归档内容均有门禁。
4. 本轮回归验证通过：前端 140 个测试文件/1574 个测试、TypeScript、Lint、NOTICE freshness、法律材料离线准备、Tauri MSI/NSIS 构建和归档 verifier。

## 建议的阻断顺序

1. 先由权利人/法务确认历史贡献权利链和 Apache→MPL 的授权依据。
2. 以实际安装包和运行时下载路径建立闭包清单，至少覆盖 raw-worker/LibRaw、ORT/DirectML、FFmpeg、vendored 前端和每个发布 target；随产品提供必要的版权声明、许可证全文和源码入口。
3. 让 verifier 检查法律资源源文件、NSIS/MSI 实际条目，并在 release workflow 直接执行 NOTICE freshness、SBOM 生成/校验和闭包断言。
4. 为 Community 与 Private-Pro 选择不同的法律资源/源码指引，再补公开 Rust crate 元数据。

初轮审计仅做报告；后续修复已改动构建、法律资源和发布门禁，不改业务逻辑。

## 复核更新（2026-08-25）

项目维护者确认当前第一方代码全部由其本人创作，没有其他参与者；因此 F-001 的历史重许可权利链阻断已解除。该确认不覆盖第三方依赖、vendored 源码或 `scrollery-pro`，后续 P1/P2 闭包问题仍然有效。

## 实施复核更新（2026-08-25）

- `scripts/generate-notice.mjs` 当前扫描 457 个 Rust、128 个 npm、1 个 vendored 前端和 2 个额外 runtime 组件；NOTICE 明确保留 LibRaw/FFmpeg 的 2 个 strong-copyleft 旗标。
- `npm run vendor:licenses` 只在维护者显式执行时抓取一次；材料已纳入 `third-party/licenses/`，`prepare:legal` 每次构建只做本地 hash 校验和复制，不联网。
- `target/legal` 当前包含 888 份包根许可证文件、7 份固定 SPDX 正文以及 ORT/FFmpeg/LibRaw/foliate-js 材料（共 912 个文件）；26 个没有包根文件的依赖均有 SPDX 映射，unresolved 为 0。
- 新构建的 MSI/NSIS 分别通过载荷与全法律资源归档校验（926/930 个归档条目）；`SOURCE.md` 仍需随最终变更纳入版本控制，FFmpeg 的 LGPL 分发策略仍需人工终审。

## 会话恢复复核（2026-08-25）

维护者确认此前已接受 P1 的运行时分发策略。当前工作树实际复核结果：P1 新增脚本、`third-party/licenses/` 12 份固定材料、`SOURCE.md`、NOTICE 生成接线、Tauri 法律资源映射、CI/release 门禁和现有 MSI/NSIS 产物均存在；法律准备、NOTICE freshness、发货闭包、JS/JSON 语法、前端测试（140 files / 1579 tests）、typecheck、lint 和 diff whitespace 检查均通过。未发现代码或法律材料丢失/损坏。

该确认已恢复到 `docs/decisions/2026-08-25-决策brief-许可证迁移至-MPL-2.0.md` 和 P1 工作记忆。P1 关闭；F-004、公开 Rust 元数据、Community/Private-Pro 法律资源分离、源码指引版本绑定等仍属于 P2/渠道边界工作，不能据此宣称整个迁移任务已收口。
