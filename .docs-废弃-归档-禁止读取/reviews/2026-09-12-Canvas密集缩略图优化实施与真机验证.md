# Canvas 密集缩略图优化实施与真机验证

## 实施范围

用户在同日分析后授权执行，要求减少或集中测试、完成一批及时 commit，并明确直接在本机真实库测试。

| 提交 | 变更 | 行为界限 |
|---|---|---|
| `bf7806cd` | 稀疏档位按图片实际存在的最小满足档选择 | 同批候选检查去重、命中即止、到DB同档截止，无小档时仍回退已有源 |
| `df82ab62` | Canvas行数据窗覆盖共享的1.25屏前向预取范围，余量恰一行 | 两虚拟引擎共用生效判据，DOM既有缓冲不变，模式切换立即重取 |
| `ae2b5171` | 可见真实冷格优先、近前向预取保护、Image回退所有权修复及录制指标 | 维持64并发与512MiB缓存，预取为可见待加载项保留最多16槽，stale升级靠后 |
| `8b103163` | 冷格指标排除DB已判失败的固定占位 | 两臂共同仪器，不改变图片显示行为 |

## 终审核实

- 取消不再按可见格总数决定；可见全热时不取消前向任务，数据签名更新先对账，换源不被旧缓存/失败标记遮住。真机短往返暴露初版保护仅向前的不足，最终补齐后向保护。
- 预取在完成回调与下一draw之间，也受可见待加载需求的预留额度约束；已有不可取消解码仍可能使新冷格等槽，不承诺零等待。
- Image回退由Promise等待onload/onerror真正落定，外层finally不再提前删除任务身份；正常回退成功/失败和失活晚回包均有回归覆盖。
- 首绘指标是Canvas调用draw绘出真图的代理，不能当作显示器实际呈现时间。离屏项及时退出等待表，返回画廊不累计屏外停留。
- 冷格暴露按gauge变化前的旧状态持续时间积分；Canvas draw与录制器rAF先后不固定，不能把新冷格数乘旧帧间隔。失活清零，异步span按录制会话代次归属。
- `gallery.thumbWait`记录候选因槽满被挡到实际启动；分段span只在新版管线存在，不拿缺少该埋点的基线做分段数量比较。
- raw视图只在Canvas组件内部创建，行替换触发computed刷新，就地patch读取同一底层对象并沿用patchTick。父层行数据和命中路径保持代理，避免悬停卡的bare/mirror与元数据响应丢失。

## 真实库与测试边界

使用本机普通Scrollery实例与真实WebView2，没有创建替代数据集，没有重置数据库缩略图状态、清除磁盘缓存或批量重生成全库。

当前主显示器2560×1440，原始DPR=1.5；4K目标通过CDP模拟3840×2160布局。它覆盖密集布局、实际文件加载和位图准备，但不等同物理4K面板的最终合成验收。

初始低密度样本`base-warm-a35.json`只有几十格，已排除出目标基线。准备探针在真实首屏找到1536格；文件夹分组导致全库中段大幅稀疏，故正式比较应固定首部密集区段，不能用全库百分比滚动代表密集场景。

另发现仅改模拟DPR可能留下旧Canvas backing尺寸，正式样本须再次触发resize并确认CSS尺寸、实际bitmap尺寸和DPR一致。

响应抽样共1255次，是准备期样本，不能视为整个库或正式A/B的档位比例。它足以反证“DB路径大，所以实际必然加载大图”：已有64档确实被大量利用。DPR和宽图会提高选档需求，不能假设所有64px格都读64档。

收尾只读SQL复核仍为56381张，128路径4500、无路径1027，其他三档/旧格式数量不变。普通浏览过程中应用的懒生成继续推进了176项；没有手动改库、重置生成状态或全库回填，真实库并非冻结快照。准备期回传的55178实际是有路径图片数，已在本表更正为完整总数并补齐其他/旧格式列。

## 配对协议

首轮候选前端为`ae2b5171`，公共仪器更新到`8b103163`；最终候选为`33f54140`。对照保持同一既有debug后端，通过临时Vite加载覆盖读取`9b9801cd`的五个调度/窗口源文件（pipeline、两虚拟引擎、虚拟引擎交汇层、MediaGrid），其余包括新的Canvas首绘/冷格仪器保持相同。D对照在最终候选额外启用局部raw绘制视图。

因此对照名称是“旧调度/窗口＋共同仪器”，不是纯`9b9801cd`；该比较只归因前端A+B，不能用于计算C1后端选档收益。工作树不checkout/reset，也不将被HMR服务的未提交源码伪称历史基线。

每臂先在远处进行DOM→Canvas重挂，记录旧LRU条目数与新LRU=0，几何调整及刷新率校准也在远处完成；录制开始后才跳首部密集区。单靠reload后曾停首部2.5秒的`ab-baseline-1.json`已污染冷首入，亦排除正式比较。

系统页缓存与浏览器字节缓存不清理，结果只代表这些层未受控的本机重复浏览。正式几何：模拟3840×2160/DPR1，Canvas CSS与backing均3544×2094；folder分组，约64px行高。轨迹0–2000px、2px/ms（约0.96屏/秒）、每次录制4秒，暖轮先走同轨迹3个往返并落定。刷新率校准为144Hz。脚本直接驱动scrollTop，不替代真实wheel链验收。

暖态250ms采样的可见格数：旧基线1603–1870，最终候选1666–1880，均值约1755–1769。冷态基线首轮最初一份采样仅765格，随后进入密集范围；指标只积分已返回的正常行，未单独量化行数据尚未返回时的整片空白。因此不把冷格比例的小差异宣称为冷进入整体改善。

## 真实对比结果

以下范围为各臂两轮结果，不是合并所有帧重新计算的分位数；有限重复只用于本机定向裁决。

| 指标 | 旧调度/窗口＋共同仪器 | 最终候选 |
|---|---:|---:|
| 暖路径冷格时间比例 | 0.94%–1.01% | **0.06%–0.08%** |
| 暖路径每次draw P95 | 25.46–25.93ms | **19.40–19.64ms** |
| 暖路径平均FPS | 29.5–31.8 | **36.8–37.2** |
| 暖路径帧间隔P95 | 36.06–41.60ms | 34.66–34.70ms |
| 冷进入冷格时间比例 | 69.24%–69.84% | 67.24%–68.47% |
| 冷进入平均FPS | 37.3–37.4 | 41.2 / 41.2 |

暖路径占位等待和绘制成本改善方向一致，但仍未贴满144Hz刷新预算。冷进入仍有明显等待，未达到原方案建议的冷格暴露下降50%目标；冷首绘P95波动大（基线868–2983ms、最终993–2954ms），没有证明尾延迟稳定改善。

最终暖轮首入屏miss为27/8，基线为495/519。最终暖轮首绘代理一轮仅5个样本、另一轮无样本，不能拿摘要中的p95=0宣称零延迟。

### 根据实测修正，而非保留初版回退

初版A+B冷格比例为73.39%/75.33%，新增取消372/676次，较旧基线回退。前后近带保护修正后，独立一轮取消降为0，冷格比例72.21%、暖1.36%；此时仍无整体收益，故继续定位绘制热点。最终raw绘制两轮取消均为0。

4.2秒CPU采样确认有响应式读取成本：`isRef2`自耗200.6ms，Vue `get`自耗94.7ms、含子调用410.4ms；原生Canvas `save`/`drawImage`也有显著开销。嵌套inclusive不可相加，不能把某一代理父栈53%的含子调用时间全部当成代理自耗。局部raw视图的取舍由独立前后对照决定，未顺带修改Canvas原生绘制语义。

最终首轮冷测分段均值：候选等槽1076ms、fetch/blob 109ms、源bitmap异步解码76.5ms、裁剪缩放0.02ms。这些都是前端观察到的异步墙钟时间，包含调度及回调等待，不能等同磁盘或解码线程纯执行时间；足以说明当前没有理由为跳过第二次bitmap转换而改动画质/裁剪。

## 后续实验裁决

C2暂不实施：本机已有大量64档且实际正在服务，新增后台补档不能被当作当前问题的必然解法。若后续DPR>1场景确认缺少合适128/256档，再独立量化收益与二次编码画质；必须先设计前台积压时让路，以及换根、清缓存、删除与落盘尾部的竞态。

原分析关于“需要扩展多档保活”的顾虑已更正：现有GC按cache_key判活，删除已枚举五档，不必迁移DB或重做GC。

D保留局部raw绘制，其他原生Canvas/asset供给优化暂不扩做。若继续针对陌生密集区的冷加载，应先分离后端asset处理、异步回调等待与解码供给，不依据上述墙钟分段盲目扩并发；物理4K、低性能设备及真实输入链仍需另外验证。
