# CI 自托管 Runner 运维手册(换机重建指南)

> **快照日期:2026-07-06**(当日全链实装并验证)。本文是**机器侧运维手册**:自托管 runner 的完整重建步骤、踩坑记录、故障诊断。workflow 内部的门禁逻辑坑(pipefail/herestring、YAML 引号、grep 选项顺序等)不在此重复——它们以注释形式长在各 `.yml` 文件内,与代码同步演进,那里才是权威源。
>
> **适用场景**:更换开发设备、重装系统、WSL 重建后,按本文从零恢复 CI 能力;以及日常故障排查。
>
> **2026-07-22 路径更新**:原 `D:\actions-runner` 所在物理盘(Samsung NVMe)硬件故障濒死下线(见运维记录,非本文范畴),`dev-box-win` 已重建于 `C:\workspace\actions-runner`。本文全文路径已同步改写;换机/换盘时路径本就可自定,不影响任何 `.yml`(标签寻址,见 §4)。当前为**进程级运行**(`Start-Process` 拉起,未服务化)——重启/注销即掉,服务化步骤见 §2.3,待执行。

## 1. 拓扑总览与经济账

### 1.1 现役拓扑(2026-07-06 起)

| Runner | 宿主 | 承载 job(私有仓 `gfgjs/scrollery-private`) | 形态 |
|---|---|---|---|
| `dev-box-win` | Windows 本机 `C:\workspace\actions-runner`(2026-07-22 起,原 `D:\actions-runner` 随硬盘故障下线) | `rust`(check/clippy/test/渠道断言/NOTICE 门)、`frontend`、`smoke`(tag/dispatch 时) | ⚠ 当前进程级(待服务化,见 §2.3) |
| `dev-box-wsl` | WSL2 Ubuntu `~/actions-runner` | `rust-linux`(Linux 编译面)、`sync-oss`(Copybara,Docker) | systemd 服务 |
| GitHub 托管 ubuntu | 云 | **仅公开仓** `gfgjs/scrollery` 的 oss-gate / gitleaks / drift-alarm / release | 托管(公开仓分钟免费) |

### 1.2 为什么这么分

- **计费**:私有仓托管 runner 分钟按倍率计费——Linux 1×、**Windows 2×**、macOS 10×;免费档 2000 分钟/月很快被 Windows job 烧穿。**self-hosted 分钟零计费、且不受配额/账单状态限制**(配额耗尽时托管 job 直接不调度,self-hosted 照常跑——2026-07-06 账单欠费期间全靠这个恢复 CI)。
- **安全**:🔴 **自托管 runner 绝不注册到公开仓**——公开仓任何 fork 的 PR 都能在 runner 机器上执行任意代码。公开仓 gate 本就免费用托管 ubuntu,无需也不允许迁。
- **速度**:本机热缓存 + 共享 `~/.cargo` registry,rust job 2m50s / frontend 2m06s(实测 run 28786569249),比托管快且无 toolchain 下载。

## 2. Windows Runner 重建手册

### 2.0 前置条件(即日常开发环境本身)

Git for Windows、rustup/cargo、Node.js、gh CLI(已 `gh auth login`)、MSVC Build Tools、WebView2。runner 以你的账号跑,直接复用这套用户级工具链——**这是自托管快的根源,也是「服务必须以本人账号运行」的原因**。

### 2.1 安装与注册

```powershell
# 取最新版本号并下载解压(路径可换,下文以 C:\workspace\actions-runner 为准——2026-07-22 起;
# 早期文档用过 D:\actions-runner,该盘已因硬件故障下线,勿再沿用)
$ver = gh api repos/actions/runner/releases/latest --jq .tag_name; $v = $ver.TrimStart('v')
New-Item -ItemType Directory -Force C:\workspace\actions-runner | Out-Null
Invoke-WebRequest -Uri "https://github.com/actions/runner/releases/download/$ver/actions-runner-win-x64-$v.zip" -OutFile C:\workspace\actions-runner\runner.zip
Expand-Archive C:\workspace\actions-runner\runner.zip -DestinationPath C:\workspace\actions-runner -Force; Remove-Item C:\workspace\actions-runner\runner.zip

# 注册(token 单命令内直取直用,绝不落盘/回显——30 分钟有效)
cd C:\workspace\actions-runner
.\config.cmd --unattended --url https://github.com/gfgjs/scrollery-private --token (gh api -X POST repos/gfgjs/scrollery-private/actions/runners/registration-token --jq .token) --name dev-box-win --work _work --replace
```

### 2.2 🔴 坑 1:WindowsApps 的 WSL bash stub 劫持 `shell: bash`

**症状**:凡 `shell: bash` 的步骤和 bash 系组合 action(如 `dtolnay/rust-toolchain`)**55ms 退出码 1**,job 秒败;纯 node action 的 job(frontend)却正常——「40 秒神秘失败」即此。
**原因**:runner 按 PATH 解析 bash,解析到 `%LOCALAPPDATA%\Microsoft\WindowsApps\bash.EXE`(WSL 启动 stub);托管镜像把 Git Bash 前置了,自托管机器没有。装了 WSL 发行版后该 stub 能启动 WSL bash——**更隐蔽**:Windows job 会跑进 Linux 环境。
**修法**(注册服务**之前**做,持久):

```powershell
[Environment]::SetEnvironmentVariable('Path', 'C:\Program Files\Git\bin;' + [Environment]::GetEnvironmentVariable('Path','User'), 'User')
```

### 2.3 🔴 坑 2:服务化需要「真密码」

- 服务须以**本人账号**运行(默认 NETWORK SERVICE 看不到 `%USERPROFILE%` 下的 rustup/cargo/node,也没有上面的用户 PATH 修复)。
- `--unattended` 模式**从不交互提问**:`--runasservice` + `--windowslogonaccount` 必须同时给 `--windowslogonpassword`,缺了直接 `Invalid configuration provided for windowslogonpassword` 终止(参数校验先于一切副作用,终止=零状态改变,可直接重试)。
- **PIN/指纹不是密码**(Windows Hello 凭据仅本机交互解锁);账户无密码则服务登录被安全策略拦(空密码禁止服务登录)。二选一:给账户设密码走服务;或不设密码走「登录计划任务」(`Register-ScheduledTask` AtLogOn 跑 `run.cmd`,`-ExecutionTimeLimit ([TimeSpan]::Zero)` 必加——计划任务默认 3 天强杀)。

```powershell
# 服务化(管理员 PowerShell;密码只在本机终端出现)
cd C:\workspace\actions-runner
.\config.cmd remove --token (gh api -X POST repos/gfgjs/scrollery-private/actions/runners/remove-token --jq .token)
.\config.cmd --unattended --url https://github.com/gfgjs/scrollery-private --token (gh api -X POST repos/gfgjs/scrollery-private/actions/runners/registration-token --jq .token) --name dev-box-win --work _work --replace --runasservice --windowslogonaccount "$env:COMPUTERNAME\$env:USERNAME" --windowslogonpassword '你的密码'
Get-Service actions.runner.*   # 应 Running
# 清历史,防密码留在 PSReadLine 文件(Windows PowerShell 5.1 自带 2.0 无敏感过滤)
Clear-History; Set-Content (Get-PSReadLineOption).HistorySavePath ''
```

- ⚠ **改 Windows 密码后必须同步服务凭据**(services.msc → 该服务 → 登录选项卡),否则重启后服务起不来。

### 2.4 坑 3:重配/移除的时序

`config.cmd remove` 在 runner **正在跑 job 时会被服务器拒绝**(`currently running a job and cannot be deleted`)。标准流程:先取消在跑 run(`gh run cancel`)→ 若 runner 进程已被杀导致 run 变孤儿(状态一直 in_progress),用 force-cancel:`gh api -X POST repos/<repo>/actions/runs/<id>/force-cancel`,等 `busy=false` 再 remove。

## 3. WSL Linux Runner 重建手册

### 3.0 前置:装发行版

```powershell
wsl --install -d Ubuntu   # 管理员;可能要求重启;首启设 UNIX 用户(下文以 gf 为例)
```

**信任模型**:Windows 宿主对 WSL 全权——`wsl -d Ubuntu -u root -- <cmd>` 无需任何密码即 root。自动化全程用它,不需要 UNIX 密码。

### 3.1 系统依赖 + Docker(root,一条命令)

```powershell
wsl -d Ubuntu -u root -- bash -c "export DEBIAN_FRONTEND=noninteractive; apt-get update -qq && apt-get install -y -qq libwebkit2gtk-4.1-dev build-essential curl wget file libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev git docker.io && usermod -aG docker gf && systemctl enable --now docker"
```

清单与 `ci.yml` rust-linux job 的托管路径**同源**(Tauri v2 官方 prerequisites);docker.io 供 sync-oss 的 `olivr/copybara` 容器。`usermod -aG docker` 必须在 runner 服务安装**之前**(组成员身份在进程启动时快照)。

### 3.2 Rust 工具链(runner 用户)

```powershell
wsl -d Ubuntu -u gf -- bash -c "curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --default-toolchain stable --profile minimal"
```

`dtolnay/rust-toolchain` action 只调用已存在的 rustup,不会替你装。

### 3.3 Runner 安装、注册、服务化

```powershell
# 下载解压(版本号与 §2.1 同法获取;linux-x64 包)
wsl -d Ubuntu -u gf -- bash -c "mkdir -p ~/actions-runner && cd ~/actions-runner && curl -sL -o r.tar.gz https://github.com/actions/runner/releases/download/v2.335.1/actions-runner-linux-x64-2.335.1.tar.gz && tar xzf r.tar.gz && rm r.tar.gz"
# runner 运行库依赖(libicu 等,官方脚本自动 apt)
wsl -d Ubuntu -u root -- bash -c "cd /home/gf/actions-runner && ./bin/installdependencies.sh"
# 注册(token 同 §2.1 直取直用)
$tok = gh api -X POST repos/gfgjs/scrollery-private/actions/runners/registration-token --jq .token
wsl -d Ubuntu -u gf -- bash -c "cd ~/actions-runner && ./config.sh --unattended --url https://github.com/gfgjs/scrollery-private --token $tok --name dev-box-wsl --work _work --replace"
# systemd 服务化(Linux 侧有 svc.sh;enable 到 multi-user.target,发行版启动即自启)
wsl -d Ubuntu -u root -- bash -c "cd /home/gf/actions-runner && ./svc.sh install gf && ./svc.sh start"
```

### 3.4 🔴 坑 4(最阴):systemd 服务留不住 WSL 虚拟机

**症状**:runner 注册成功、服务 active,几十秒后 GitHub 侧变 offline,job 永远 queued;journal 可见服务被 Stopped + 新 boot 标记。
**原因**:WSL2 的 VM 生命周期跟随「Windows 侧客户端连接」——最后一个 `wsl.exe` 客户端退出后 VM 即整机关停,**发行版内的 systemd 服务不算数、拦不住**。任何一条 `wsl` 命令都会把它唤醒(服务随 boot 自启,于是「一查就活、不查就死」,极具迷惑性)。
**修法**:Windows 侧保持一个常驻客户端连接。

```powershell
# 立即生效(当前会话;重启后失效)
Start-Process wsl -ArgumentList '-d','Ubuntu','--exec','sleep','infinity' -WindowStyle Hidden

# 持久化:登录计划任务(开机登录后自动钉住 VM;runner 服务随发行版 boot 自启)
$action  = New-ScheduledTaskAction -Execute 'wsl.exe' -Argument '-d Ubuntu --exec sleep infinity'
$trigger = New-ScheduledTaskTrigger -AtLogOn -User $env:USERNAME
$settings = New-ScheduledTaskSettingsSet -ExecutionTimeLimit ([TimeSpan]::Zero)
Register-ScheduledTask -TaskName 'WSL-KeepAlive-Ubuntu' -Action $action -Trigger $trigger -Settings $settings
```

⚠ 早期建议的 `--exec true` 版本**无效**(客户端秒退,VM 照关)——必须 `sleep infinity` 这类不退出的客户端。

#### 3.4.1 🔴 坑 4 升级版:AtLogOn keep-alive 一次性触发、不自愈(2026-07-11 复发实证)

**症状(复发)**:上面的 `WSL-KeepAlive-Ubuntu` 任务**在册、Enabled、State=Ready、动作正确**,rust-linux 却在 dev 上**慢性红多日**(连续 5 次 push 全 failure);runner 列表长期 offline,`wsl --list -v` 见 Ubuntu=**Stopped**。
**原因**:`AtLogOn` 触发器**每次登录只触发一次**——它在上次登录时启动的 `sleep infinity` 会话中途死了(任一 `wsl --shutdown` / WSL 更新 / 休眠恢复都会拆掉 VM),AtLogOn **不重触发**,keep-alive 就永久失效直到下次重登。任务 `State=Ready` 一切看着正常、**机制在册却已死**,是坑 4「一查就活、不查就死」的进阶——连查都显示健康,更难发现。
**失败长相**:排队期累积的取消在 runner 偶尔上线接单时立即兑现——`Set up job` ✓ → `Run actions/checkout@v4` **cancelled**(`The operation was canceled`,约 1–2s)→ 余步 skipped。**这不是 cargo 失败**,它伪装成 checkout/代码问题,实为基建离线。
**根治=自愈**(免提权、不依赖重登):`Register-ScheduledTask` 需管理员(无 admin 报 `Access is denied`);改用**用户级启动文件夹**放一个**自愈循环** vbs——阻塞式持有会话,VM 一被拆即自动重建:

```vbs
' %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\boot-wsl-runner.vbs
' 阻塞持有 sleep infinity 钉住 VM;VM 一被拆(shutdown/崩溃/更新/休眠恢复)Run 即返回
' → 15s 退避后自动重建,不等下次登录。撤销:删本文件 + 结束其 wscript.exe 进程。
Dim sh : Set sh = CreateObject("WScript.Shell")
Do
  sh.Run "wsl.exe -d Ubuntu -u root -e sh -c ""exec sleep infinity""", 0, True  ' 0=隐藏 True=阻塞
  WScript.Sleep 15000   ' 退避,防 boot 失败时紧循环
Loop
```

- **为何优于 AtLogOn 任务**:AtLogOn 一次性、会话一死即永久失效;本循环会话一死即自愈。**实测**:`wsl --shutdown` 后不干预,**60s 内** WSL 自动回 Running、runner online。两者并存无害(既有任务需 admin 才能删),留作双保险即可。
- **零提权 + 可逆**:Startup 是当前用户可写面,无需 UAC;删文件 + 结束 wscript 进程即撤销。
- **边界**:仍是**交互登录**触发(适配在用的 dev box)。要 headless 无人登录常驻,须提权建 `AtStartup` 计划任务 + 服务账户凭据。

**诊断三信号(把「基建离线」与「代码失败」一刀切开)**:①`Tauri Linux 系统依赖`步(`if: runner.environment=='github-hosted'`)显示 **skipped** = 已在自托管、非 hosted 额度(ci.yml 早已 `[self-hosted,Linux,X64]`,配置层无可改);②`wsl --list -v` 见 **Stopped** = 整机关停、非 runner 断连;③失败步是 `checkout@v4` **cancelled** 而非某个 `cargo` 步 = 基建取消、非编译/测试。**元教训**:dev CI 常年红本身就是**告警失效**——纯基建取消淹没真回归;宜给 rust-linux 设 `timeout-minutes` + 明确 skip,让离线态快败可辨。

### 3.5 已知无害现象

- WSL interop 默认把整个 Windows PATH 追加进 Linux PATH(journal 的 `.path=` 一长串 `/mnt/c/...`)——Linux 二进制在 `/usr` 系路径先命中,无碍;如需洁癖可 `wsl.conf [interop] appendWindowsPath=false`,但**未实测**对 job 的影响,勿轻动。
- sync-oss 会把 deploy key 写到 runner 用户 `~/.ssh/id_ed25519`(持久盘)。该 key 仅有公开仓写权(方案 A 铁律),单人 dev 机风险可接受;若 WSL 重建,key 不需迁移(每次 job 重新从 secret 装配)。

## 4. Workflow 接线约定(与 runner 配套的 yml 侧规则)

- **标签寻址**:`runs-on: [self-hosted, Windows, X64]` / `[self-hosted, Linux, X64]`。标签是集合匹配,顺序无关;换机器只要标签一致,**yml 零改动**。
- **环境自适应门控**:同一份 yml 兼容托管/自托管双形态,靠 `if: runner.environment == 'github-hosted'` 门控三类步骤:
  1. `Swatinem/rust-cache`——自托管 `_work` 持久目录本身就是缓存,再走 GitHub cache 是纯网络往返,且 restore 会用**陈旧缓存覆盖更新的本地 target**;
  2. `sudo apt-get` 依赖安装步——自托管无免密 sudo,跑了必卡死;依赖在 §3.1 预装;
  3. 未来同类(下载型工具安装步)照此办理。
  **原则:workflow 写成对环境自适应,而不是分叉两份 yml——回迁托管或换机零改动。**
- **回迁路径**:把 `runs-on` 改回 `windows-latest`/`ubuntu-latest` 即回到托管形态,门控步骤自动恢复生效。

## 5. 故障诊断速查表

| 症状 | 原因 | 处置 |
|---|---|---|
| dev CI 慢性红多日 / runner offline,但 keep-alive 任务显示 Enabled+Ready | AtLogOn keep-alive 一次性触发,其 sleep 会话中途死了不自愈(§3.4.1) | 换/加**自愈循环 vbs**(§3.4.1);辨识三信号:系统依赖步 skipped=已自托管、`wsl --list -v` Stopped=整机关停、失败步是 `checkout` cancelled 非 cargo=基建非代码 |
| job 永远 queued,runner 列表 offline | runner 进程/服务没跑;或 WSL VM 已关停(坑 4) | Windows:`Get-Service actions.runner.*`;WSL:任意 `wsl` 命令唤醒 + 检查 keep-alive 任务在不在 |
| job 秒败(<1s 步骤失败,exit 1) | 环境解析层:bash 解析到 WSL stub(坑 1)、命令不在 PATH | 看 `_diag\Worker_*.log` 的 `Which2:`/`Location:` 行——**失败耗时是分诊第一信号:秒级=环境,分钟级=编译/测试** |
| 托管 job 报 `job was not started...payments/spending limit` | 账单/配额(仅托管受影响) | 该 job 若可自托管则迁;否则修 Billing。self-hosted job 不受影响 |
| `config.cmd remove` 被拒 `currently running a job` | 有在跑/孤儿 run 占着 | `gh run cancel`;孤儿用 force-cancel API;等 `busy=false` |
| 杀 runner 进程后 run 卡 in_progress | 孤儿 run,服务器等 runner 应答 | `gh api -X POST .../runs/<id>/force-cancel` |
| job 失败且 **steps 为空**(零步骤),但后继 job 正常 | **会话残影**:VM/进程猝死后服务器端旧 listener 会话未即时失效,job 被派给僵尸会话,超时按 worker-crash 判死(2026-07-06 实证:WSL VM 关停留下的残影吃掉一个 rust-linux,下一 run 自愈) | 单发=自愈,无需处置;**连续**出现才排障(runner 真离线) |
| gh 下载 job 日志网络 EOF | 网络波动 | job 在本机跑的直接读本地 `_diag\Worker_*.log`,比 API 快且全 |
| 服务重启后起不来(Windows) | 改过账户密码没同步服务凭据 | services.msc → 服务 → 登录选项卡更新密码 |
| Windows job 表现出 Linux 行为 | 装 WSL 后 bash stub 能启动了(坑 1 变种) | 确认用户 PATH 中 `Git\bin` 在 `WindowsApps` 之前 |
| 磁盘吃紧 | `_work` 下每仓独立 target(十几 GB/处) | 直接删 `_work` 内容,下次 job 自动重建(等于冷跑一次) |

**PowerShell 5.1 专属坑**(排查时別误判):`gh --jq` 表达式含内嵌双引号+空格会被 5.1 的引号改写拆成多参数(报 `accepts 1 arg(s), received N`)——换用无内嵌双引号的 jq 写法(如 `{name: .name}` 对象形式)。

**跟着 GitHub 走、无需迁移**:workflow yml(标签寻址)、仓库 secrets(`OSS_SYNC_DEPLOY_KEY` 等)、runner 注册表(旧机的注册项在 Settings → Actions → Runners 删除即可)。

## 8. 手动触发 + 实时盯进度(常用命令,2026-07-22 补)

```powershell
# 手动触发 dev 分支一次全量 CI(等价于 GitHub 网页 Run workflow)
gh workflow run CI --repo gfgjs/scrollery-private --ref dev

# 拿到刚触发那次的 run id(可选,上一条命令的输出链接里也有)
gh api repos/gfgjs/scrollery-private/actions/runs --jq '.workflow_runs[0] | {id, head_sha, status}'

# 实时刷新盯到完成(类似 tail -f;<run-id> 换成实际 id)
gh run watch <run-id> --repo gfgjs/scrollery-private
# 不给 id 会从近期 run 列表里交互选一个
gh run watch --repo gfgjs/scrollery-private

# 一次性快照(不常驻刷新,适合快速查一眼)
gh run view <run-id> --repo gfgjs/scrollery-private

# 看某个 job 的实时日志(比 run 级别更细;job-id 从上面 view 输出的 (ID ...) 里拿)
gh run view <run-id> --repo gfgjs/scrollery-private --job=<job-id> --log
```

⚠ **本机网络偶尔抽风**(见运维记录,与硬件病灶无关),`gh run watch`/`gh api` 会不时因 `EOF` 直接退出——这是请求断了,不是任务失败,重跑同一条命令续上即可;判断真实进度更可靠的方式是跳过 GitHub API,直接读 runner 本机日志(§5 诊断表「gh 下载 job 日志网络 EOF」行同源):

```powershell
# 找当前(最新)worker 日志
Get-ChildItem C:\workspace\actions-runner\_diag\Worker_*.log | Sort-Object LastWriteTime -Descending | Select-Object -First 1

# 该 job 属于哪个 workflow 步骤集合(确认对上目标 job)
Select-String -Path <上面那个文件路径> -Pattern 'jobDisplayName' | Select-Object -First 1

# 看最新几行,确认真的在推进(而非卡死)
Get-Content <上面那个文件路径> -Tail 15
```

runner 是否真在干活也可以直接看进程(cargo/rustc/node 存在且 WorkingSet 在涨 = 真在编译,非卡死):

```powershell
Get-Process -Name cargo,rustc,node -ErrorAction SilentlyContinue | Select-Object Id, ProcessName, CPU, @{n='MB';e={[math]::Round($_.WorkingSet64/1MB,1)}}, StartTime
```
