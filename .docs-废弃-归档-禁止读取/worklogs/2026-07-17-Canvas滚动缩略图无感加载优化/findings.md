# 发现与决策:Canvas滚动缩略图无感加载优化

## 需求
- 主页 Canvas 模式稍快速滚动时，可明显看到真实缩略图从上到下替换占位图，需要优先优化 Canvas 路径。
- DOM 模式的一屏额外渲染只在慢速时接近无感；本轮不把 DOM 模式作为主要改造对象。
- 若本地实现与资料不足以确定方案，可联网调研。

## 发现
- `docs/worklogs/` 已有 2026-07-13「主页Canvas性能优化」记录，当前改动前必须先复核其设计边界与已落地内容。
- 当前 Canvas 预取像素范围虽为下方 1.25 屏、上方 0.5 屏，但条目预算固定为 96/48；60px 极密模式下会先被条目数截断，只热约 2–4 行。
- 当前 Canvas 位图 LRU 同时受 2000 条与 512MB 约束；极密高分屏的一屏格数接近或超过 2000 时，条目约束会早于字节约束触发，存在可见屏内部边落地边驱逐的抖动风险。
- `getImage()` 直接在绘制行序中启动请求；快滚闸门放行后，最终可见窗口按顶部到底部入队，现象与用户观察到的“从上到下替换”一致。
- 既有 browser UI harness 固定 18 张、220px 行高，只能证明 Canvas 基本交互，不能覆盖本轮 60px 数千格主场景；本轮增加仅 DEV 且显式 URL 开启的 `items` 密度维度，默认视觉 fixture 不变。
- 密度 harness 首轮若继续复用 960×720 SVG，会使全部条目走 `Image()` 回退并按整图约 2.6MB 记账；4K/5000 项基准实测缓存只能留 194 格、8192 次 fallback，属于夹具失真。密度场景应使用小型 raster 走 `createImageBitmap`，默认视觉场景才保留 SVG。
- 第一版用户真机复验：滚回已加载区域“明显减轻、接近无感”，证明提高极密模式缓存驻留有效；滚到全新区域仅略微改善。
- 第一版同时引入严重回归：极速滚动会先顿一下，再极快追过一段距离；慢速随滚随出，极速则停下才出图。源码对账显示自适应预算在 gate 放行的同一 `draw()` 内同步遍历并创建数千个 `fetch/createImageBitmap` 任务，主线程先被任务创建占住，随后消费积压滚动输入。
- C 版用户复验确认冷区“几乎没改善”，唯一明显变化是替换方向从固定上→下变成随滚动方向。这证明请求优先级只能改变加载动画形态，无法解决冷区吞吐；方向反转不保留。
- 快滚 gate 在 C 版仍是全关：速度超过 60px 模式的 3px/ms 后，`getImage()` 和 idle prefetch 均不启动任何新任务，64ms 无滚动事件后才放行。因此扩大预取窗口对已缓存/慢滚有效，对越过热区的冷区快滚天然无效。
- 现行 WebP 加载管线是 `Blob → 完整 480 ImageBitmap → 裁剪/缩小 ImageBitmap` 两段式。生成器产物尺寸可从 WebP 30B 文件头取得，WebView2 支持直接 `createImageBitmap(blob, crop, resize)`；可避免完整中间位图和第二次 ImageBitmap 创建，未知格式/status=3 保留旧路径兜底。
- D 版用户复验：冷区仍“无改善”，极速滚动“无顿挫”。因此单段 WebP 处理与 8 槽快滚通道对端到端观感无收益，均撤销；64 全局在途上限 + idle 分片对消除顿挫有效，保留。
- 本轮最终边界：Canvas 调度层能显著改善已加载区域的驻留命中，并消除扩大预取后引入的任务风暴；无法让 60px 同屏数千张、480px 源的全新冷区无感。冷区需减少输入字节与解码像素，即按格子长边×DPR 提供 120/240/480 多档源。
- 原图缩略图规格会影响全新区域：Canvas 当前先解码 `thumb_path` 指向的现行源档（用户为 480px），再用 `createImageBitmap` 缩到 64/96/128 等设备像素桶；因此小图可减少磁盘读取、WebP 完整解码与中间位图成本。480→120 的像素面积理论比为 16:1，但真实耗时/文件字节改善必须实测，不能直接按 16 倍宣称。
- 后端与前端常量已有 120/240/480/960 四档，磁盘路径也是按档位分桶；DB `thumb_path` 只记录一个现行档位。要同时保留 480 并让极密 Canvas 读 120，除了生成 120 文件，还需补“按渲染桶选 120、缺失回退 480”的读取契约。
- 不建议新增固定 60px 档：60px 是 CSS 行高，而现有档位约束图片**长边**。例如 16:9 格在 DPR 2 下约需 213px 长边，因此应按 `max(item.w,item.h) × DPR` 选 120/240/480 中满足需求的最小档；固定 120 在高 DPI 宽图上也可能发糊。
