# 发现与决策:Canvas快速拖动防闪烁优化

## 需求
- 快速拖动滚动条时，画廊区在露白与显图之间极速交替，形成强烈闪烁；大行高尤其严重。
- 极速滚轮也会闪烁，但程度很轻。
- 需要优先优化 Canvas 模式，不能重新引入上一轮已消除的极速滚动顿挫。

## 发现
- 上一轮真机结论：扩大缓存使暖区接近无感，64 个全局在途上限与 idle 分片消除了任务风暴顿挫；480px 冷区无法靠调度层变得无感。
- 拖动滚动条比滚轮更容易产生跨越式大位移，若每次滚动都立即以当前可见区清空并重绘，缓存命中率在相邻事件之间可能剧烈变化，从而把冷区空白直接暴露为整块闪烁。
- 默认 bucket 引擎的 `syncDesired()` 会在远跳时先丢弃窗外旧段并发布 rows=null 的新愿望段；`pumpFetch()` 再通过单飞异步 IPC 回填。Canvas 消费 `mountedRows()`，因此 `currentY` 已到新位置而 `rows` 为空或仅部分段就绪是代码允许的正常过渡态。
- `MediaGridCanvas.draw()` 原先在计算 `visibleRowRange()` 前由 `fitCanvas()` 无条件整幅铺底；上述过渡态会提交纯底色/部分空白帧，行回填后下一帧又显图。连续滚动条远跳会重复这组帧，机制与“露白—显图极速交替”一致。
- 仅在滚动中、已有完整帧且新行集尚未闭合覆盖视口时保持 Canvas backing store，可把多次空白交替收敛为稳定旧帧到完整新帧的一次切换；慢滚缓冲命中时覆盖判定为真，仍逐帧更新。
- 覆盖判定逐行允许 16px 正常布局间距，但拒绝缺失段形成的大空洞；在内容尾部只检查 `[currentY, min(currentY+viewH,totalHeight)]`，避免合法尾距误判。
- 第一版仅在本地 DEV harness 以约 140px 行高、单次 12000px 程序化滚动验证落点；未覆盖逻辑滚动条连续拖动，随后已被用户真机否决。
- 第一版用户真机复验：极速滚轮与极速滚动条出现明显顿挫；极速拖动滑块时画廊会变成一片白；中低速拖动仍闪烁。帧保持/冻结方案判定失败并已完整撤销。
- 需求进一步明确：快速拉动时必须持续正常显示缩略图，不能以冻结、白屏、只在停手后出图或安静占位作为降级策略。
- `MediaGrid.onScrollbarJump()` 的现行注释与逻辑明确把拖动链强制关闸，并将“安静的占位场”视为期望体验；该产品假设已被本轮用户裁决推翻，必须同步改正文与代码消费边界。
- Canvas 的快滚全关来自 `getImage()` 直接返回 cached；去掉可见区全关后仍受 64 个全局在途槽约束，而视口外 `runPrefetchSlice()` 继续读取闸门并取消计划，因此不会恢复无界预取。
- `useBucketVirtualScroll` 常态单飞会让已经离开愿望集的旧 IPC 阻塞最新目标段；改为“常态 1，在途全部陈旧时允许最新目标旁路第 2 槽”，可让新视口立即取行且总并发有硬上限。
- 大跨度跳转取消仅限仍在 fetch/读取 Blob 的旧缩略图任务；进入 `createImageBitmap` 后浏览器无取消 API，继续计入 loadingCount，避免账面释放后实际解码无界增长。
- 第二版 DEV harness 以 5000 项覆盖约 64px 密集行与 960px 大行高：逻辑滚动条分别在 19ms/27ms 内跨越到远端冷区，80ms 后截图均为完整真实图源而非白屏；控制台只有既有 i18n HTML 警告，无新增运行错误。该证据能排除稳定白屏回归，但连续拖动时的主观闪烁与真机 IO 吞吐仍以用户实测为准。
- 第二版用户真机复验：闪烁仍存在，仅有少量减轻；说明最新位置供给优化缩短了部分空白窗口，但不能消除 480px 冷区真实 IO 与解码前的底色暴露。
- 亮色主题现行整幅清屏色 `--color-bg-canvas` 接近白色，无 ThumbHash 的格子又回退到近白 `--color-bg-elevated`；连续远跳会在两种高明度底色与彩色缩略图之间切换。第三版将二者收敛到 Canvas 专用低饱和中灰 token，降低切换明度幅度，不冻结、不延迟真实图绘制。

## 阶段 6 发现(2026-07-17 续:稍快速滚动换图波)
- 症状域界定:用户描述的「稍快速滚动可见自上而下换图波」不在开闸慢滚域——headless 基准(1280×900、DPR1、10000 项、bucket 引擎、Canvas 模式、CDP 禁缓存+每请求 40ms 延迟仿真单图 IO)恒速 1.5/5 px/ms 下 coldCellFrames 均为 0,视口外预取完全跟得上。
- **根因实证=闸门关闭期预取整体停取**:200px 行高阈值为 engage 10 / release 5 px/ms(随行高缩放),滚轮连拨的平滑动画峰值帧速可越 engage,谷值又落在滞回带内,闸门整段钉住;此期间旧实现取消全部视口外预取,格子进视口才起载,一个加载时延(仿真下 65-130ms)后逐格弹出=换图波。burst 速度剖面(450ms 周期:150ms 峰 14 px/ms + 300ms 谷 3.15 px/ms)复现:coldCellFrames=4911(约占可见格·帧 35%),而恒速 12 px/ms(整程关闸、真飞掠)高达 14625。
- **修复 A/B(同脚本同参)**:关闸期改为「仅前向预取、后方 0」+分片预算按新启动数计+draw 尾同步小分片后,burst 域 4911 → 510/569/499(三次重复,−89%);载入均时 131.7→94.4ms(供给提前、突发排队减少);帧健康两侧一致(avgFps 120、jank 0)。前向宽度定档实测:1.0 屏余 939、1.25 屏余 ~530,故与开闸态同宽 1.25。
- 开闸域回归对照:恒速 1.5/5 px/ms 修后仍为 0 冷格·帧,无回归。
- **基准适用边界(诚实标注)**:恒速 12 px/ms 域修后 14478(基本不变)——该域需求 ~173 图/s,超过 dev server 每主机 6 连接 × 40ms ≈ 150 req/s 的吞吐钳制,harness 无法评估修复在真飞掠域的效果(真机 asset 协议无该连接数限制);60px 极密域同受钳制且无基线(探针后于症状才存在),不可比。真机验收仍是终裁。
- 会话初的候选假设①「滚动中 rIC 分片饿死」在 headless 被证伪(burst 基线 716 片/9s 照常执行);真机 WebView2 帧忙时是否成立未证,draw 尾同步分片(硬预算 1ms/16 启动)作为保底仍落地,开闸域实测无帧健康代价。假设②「暖头重扫吃光分片预算」在 200px 域非约束项(前向窗仅 ~24 格),按启动数计的修正属理论加固,极密域收益未实证。
- 基建沉淀:harness 新增 `&rowHeight=`/`&bucket=` URL 参数;`window.__scrolleryBench` DEV 桥(生产构建实测 0 引用,tree-shaken);探针新增 coldCellFrames(冷格·帧积分)/visibleColdCells/prefetchLoadsStarted/prefetchSlices;基准脚本(headless Chrome+裸 CDP,含 burst 速度剖面)存 scratchpad,未入仓——是否随仓固化待收口裁决。
- 真机复验裁决(2026-07-17):标准窗口改善较大;4K+全屏+64px 极密域中低速无感,速度较快时加载过程仍明显。用户裁定边际收益不高,**该极速极密域残留列为后期优化**,本轮不再投入——与 harness 预判一致(该域需求吞吐超 dev server 钳制,修复效果本就未获 harness 证据,真机残留说明供给上限在 IO/解码侧,非调度侧)。
- 真机新发现 UI 症状①「占位格糊成连续灰场」:D-003 把整幅清屏色与无 ThumbHash 格面收敛为**同一**中灰后,格缝(GRID_GAP=4px)与格面同色,64px 极密域大片未出图格之间零边界,扩展名文字浮在连续灰场上。根因是 D-003 只考虑了「底色↔真图」切换幅度,漏了「格面↔格缝」需要可辨差。
- 真机新发现 UI 症状②「真图之间区分度下降」:同因——缝色=中灰,与灰调缩略图边缘融合,图与图失去分隔。修复=拆双 token:`--color-bg-canvas-gap`(格缝/清屏,新)比 `--color-bg-canvas-placeholder`(格面)暗一小档(≈6-8% 明度,同色相中性),格界与图间分隔恢复;差值刻意小,远跳冷区「缝↔面/图」切换幅度仍远低于 D-003 前的近白清屏,不回退防闪收益。六主题齐键,契约/对比度门禁绿。
