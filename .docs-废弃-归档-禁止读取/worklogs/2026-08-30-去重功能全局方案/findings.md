# 发现与决策:去重功能全局方案

## 需求
- 从全局视角分析去重功能实现方案，不盲信已有并行会话。
- 项目处于高速迭代，允许推翻任何既有设计和实现，不要求向前兼容。
- 以当前最优设计与实现为裁定原则。

## 发现
- 工作区存在大量与扫描、派生、IPC 和 UI 有关的未提交改动；本轮必须以当前工作树为事实基线，但不得改写无关在途文件。
- 已有 `docs/planning/2026-08-29-资源去重方向分析/` 是另一并行任务且未收口；为避免并发争用，本轮使用独立工作记忆目录。
- 两条参考会话实际是一条主任务及其只读侦察分支，只能视为同一假设链。其“精确字节重复分析 → 重复组审查 → 可撤销清理”方向通过复核，但“现有 hash/删除链足以承载”不成立。
- `content_hash` 对大于 64 MiB 的文件只采样头、中、尾，且新文件不必写入；扫描 mtime 只有秒精度，复制还会继承旧值。它不是删除级精确内容身份。
- `media_items` 是路径/位置项，现有相册、标签、人脸、AI、编辑版本等大面积依赖 `item_id`。首版全仓 content/asset/location 重构扩大风险，却不增加精确去重正确性。
- SQLite 使用单 writer mutex + WAL 读池。文件 hash 必须在锁外进行，只以短批次事务写回；现有 `RunTokenSlot` 可作为代次安全模板。
- 同 root 扫描重启存在旧任务无条件移除新 token、复用同 root seen 表的竞态；这应作为去重施工 P0。
- 软删除只改 `is_deleted`，可恢复但不释放磁盘空间。当前硬删除在系统回收站失败时仍删除数据库行，也没有作为通用 Live Photo 逻辑单元清理，禁止复用。
- Live Photo、硬链接、重复扫描根、离线卷和文件漂移必须在精确身份与清理预检层显式建模。
- UI 应是独立 `/duplicates` 聚合页，使用虚拟列表、恰好一个 keeper、保护标记和显式确认；不能塞入按单项卡片工作的画廊路由层。
