## 复审汇总建议

- **施工顺序仍建议 B → A → C**:先保护不可再生的整理态,再兑现导出,最后进入元数据/内存风险最高的编辑。三案可以独立裁决和回滚。
- 修订后总工程量约 **20.5–27.5 天**(A 5–6.5、B 8.5–11.5、C 7–9.5;均为未实测估算)。初稿 13–15.5 天已被当前代码与缺失安全闭环推翻。
- A/B 共享一个轻量文件任务骨架:AppState 状态快照 + app-wide event + status query + generation 比较清理;不再使用会随发起 WebView 消失的 Channel 作为唯一进度真相。
- A/B 共用一个文件任务 gate,默认不互相抢占或静默取消;状态栏只加右侧轻量任务指示,不挤占查看器左侧文件信息/选择信息优先链。
- B 的 v1 是**完整 catalog DB + documents + manifest**;只排除盘上可再生 cache/models 等。所谓「精简 DB 备份」与 `VACUUM INTO` 全库快照矛盾,降到 P2。
- C 必须先过元数据/色彩与峰值内存两项 P0 spike。V20 显示旋转须在编辑保存时物理烤入新文件,新 item 回到 `view_rotation=0`。
- 三功能仍建议全部进入 free;当前没有通用 per-feature gating 原语,为本批新建一套授权面得不偿失。
- 2026-07-19 二次核对(HEAD=5f92f1d):承重契约全部成立,三案结论与工程量不变;F-025(0bf5ebb)落地后 A/B 所引 RunTokenSlot 已是全仓唯一范式,并补写终态门控姿态精度(文件任务采 thumb/derive 的 finish 返回值姿态,勿仿 ai/face 的 is_cancelled 姿态)。
