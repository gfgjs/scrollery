## 1. 为什么必须换路（方案 A 已见顶）

线性坐标平移（方案 A）把逻辑高度（可达 40M+ px）压进 `SAFE_MAX`（10M）物理 spacer，靠 `ratio=logMax/physMax` 线性映射。真机连续 4 轮暴露：闪烁 → wheel 失灵 → 一格一跳无动画 → 位置不准 + 停后补位闪。

**根因是结构性的，无法在该框架内根治**：
1. **双步补偿**：原生滚动按物理速率移动内容（立即重绘），JS `transform` 再每帧反向补偿差值——两步永远差至少一帧，差值被 `ratio`（2–4×，dev 强制时更大）放大成跳变。
2. **压缩比放大一切**：原生滚轮/惯性按物理 px 走 → 逻辑 `ratio×` 速度，要么飞过取数能力（位置不准、补位闪），要么补偿成离散跳（无动画）。
3. **sticky 头失真**：坐标映射破坏 sticky 参照系（§3.6.3 已记）。

> 结论：这些不是 bug、是线性映射的代价。**方案 B 通过「根本不压缩行级坐标」消除它们。**

## 2. 方案 B 的机制（为什么能根治）

> 🔶 **B1.5 修订(2026-07-04)**:本节「每 bucket(月/文件夹)一个独立 DOM 段」的**段划分方式已被推翻**——真机四根因诊断后改为**等高算术分段**(段边界 = 0, 4000, 8000, … px,与月/文件夹语义无关;get_bucket_rows 半开区间天然支持任意边界)。本节的**核心机制不变且已落地**:段内纯原生滚动、零坐标平移、段懒加载。变更收益:三种分组统一覆盖(含不分组)、段大小恒定(§2.1 第三档「单 bucket 超大」问题构造性消失)、可见段=纯算术不再需要 IntersectionObserver。取数纪律(愿望清单+单飞+视口优先+离窗丢弃)是 B1.5 新增的必要件——B1 真机证明**没有取数纪律的分段引擎比方案 A 更卡**。

废弃「单 spacer + 行级坐标压缩」，改为 **每 bucket（月 / 文件夹）一个独立 DOM 段，段高 = 该 bucket 真实高度（≤ SAFE_MAX）**：

- **段内纯原生**：每段是真实高度的普通绝对定位区，段内滚动/惯性/sticky 头全部走浏览器原生——即你认可的「无平移观感」。**绝大多数实际浏览是段内滚动 → 丝滑、零补偿。**
- **段进出视口懒加载**：IntersectionObserver 监测 bucket 进出视口 → 进则拉该 bucket 的行、出则卸载 DOM。内存 O(可视 bucket 数)，与库大小无关。
- **现成地基**：**T14 已建的 `LayoutSummary.month_buckets`（每月 `count / y / groupId`）就是 bucket 清单**——段的位置、占位高度、密度直接可用，无需新建索引。

### 2.1 容器总高 vs 16.7M 上限（关键分界）

设每 bucket 段绝对定位在其 `y`，容器总高 = Σ 段高 = 逻辑总高。据此分三档：

| 库规模（约） | 逻辑总高 | 方案 B 行为 |
|---|---|---|
| **≤ 40 万项** | ≤ 16.7M px | **容器直接用真实总高、纯原生滚动、零坐标映射** → 行级/段级都不压缩，完美 |
| 40 万 – 数百万 | > 16.7M px | 容器仍超元素上限 → 需保留**一层 bucket 级（非行级）坐标映射**：仅映射段偏移、段内原生。压缩从「行级每帧」降到「段级跨 bucket 跳转时」——粗粒度、低频、误差影响小得多 |
| 单 bucket 超大（单月 5 万+） | 单段 > 16.7M | Immich #28861 同款触顶 → 需对超大 bucket 二次分页（按周 / 按 N 千项再切子段） |

> **重要洞察**：25–40 万项的库**逻辑总高 ≤ 16.7M**，方案 B 下**完全无需任何坐标平移**（当前方案 A 在 10M 就保守进平移了）。这引出一个先行的廉价实验 —— 见 §6。

## 3. 改造范围（耦合面已实测收敛）

坐标平移当前**只被 2 个前端文件消费**（已 grep 实测）：`composables/useVirtualScroll.ts` + `components/media/MediaGrid.vue`。后端 IPC 面：`compute_layout` / `get_layout_rows_by_y` / `get_separator_y_by_group_id` / `get_item_y_by_id` / `get_subtree_scroll_target`。

### 3.1 后端（Rust，中等）
- **新增 `get_bucket_rows(bucket_id 或 (year,month), …)`**：按 bucket 分页取行，替代 / 补充 `get_layout_rows_by_y`。`cache.rs` 已有按 y 区间查询，扩 bucket 维度即可（行已按 y 有序，bucket 边界 = month_buckets 的 y 区间 → 二分定位）。
- **`compute_layout` 不变**：仍算全量行 + summary（含 month_buckets）。bucket 化是**读取侧**切分，不改布局算法。
- **`get_separator_y_by_group_id` / `get_item_y_by_id` 复用**：bucket 跳转 = 定位段 + 段内偏移，现成。
- 工作量：~2–3 天（新 DAO + 命令 + 单测；布局算法零改动）。

### 3.2 前端（TS/Vue，大头）
- **`useVirtualScroll.ts` → 新 `useBucketVirtualScroll.ts`**：核心重写。bucket 清单来自 `month_buckets`；IntersectionObserver 管理段挂载/卸载；段内复用现有「行绝对定位 + 可视窗口」逻辑（可大量复用现有 fetch/buffer/diff 代码）。
- **`MediaGrid.vue`（1754 行）适配**：模板从「单 layer + 行」改为「v-for buckets → 每段 v-for 行」。需迁移 3 处与单 layer 耦合的子系统：
  - **FLIP 动画**（6 处 `layerRef`，971–1048 行）：改为按段或全局重定位。中等复杂。
  - **选区**（橡皮筋 / Ctrl+A，依赖 `flat_ids` / y 坐标）：跨 bucket 的框选需聚合多段坐标。中等复杂。
  - **拖拽幽灵 + 拖入文件夹**：命令式 transform，基本不受影响。低。
- 工作量：~5–8 天（重写 + 三子系统迁移 + 联调）。

### 3.3 既有资产复用
- ✅ **T14 month_buckets** —— bucket 清单 / 段占位高 / 密度，直接用。
- ✅ 段内行渲染、fetch、自适应 buffer、diff 跳过 —— 从现 `useVirtualScroll` 平移过来。
- ✅ `compute_layout` / 布局算法 / 缺失检测 / 扫描 —— **完全不动**。

## 4. 风险与对策

| 风险 | 级别 | 对策 |
|---|---|---|
| 跨 bucket 边界（框选 / 滚动连续性 / 键盘导航跨段） | 中 | 段间用统一逻辑坐标轴对齐；选区在逻辑坐标聚合而非 DOM 坐标 |
| 超大单 bucket（单月 5 万+）仍触顶（#28861） | 中 | 对 > 阈值的 bucket 二次切子段（按周 / 按 N 千项）；T14 已有 count，可判定 |
| 容器总高 > 16.7M（>40 万项）仍需段级映射 | 中 | 段级映射粗粒度、低频，远好于行级；或对超大库才启用，中小库纯原生 |
| MediaGrid 1754 行重构引入回归（FLIP / 选区 / sticky） | 中高 | feature-flag 灰度（见 §5）；分子系统逐个迁移 + 各自验证；保留方案 A 回退 |
| sticky 头在段模型下的实现 | 低 | 段内 sticky 天然可用（方案 B 的卖点之一），反而修复 §3.6.3 遗留 |

## 6. （已否决）提高 SAFE_MAX 的廉价捷径——不适用于市场产品

曾设想：`SAFE_MAX_DEFAULT=10M` 是保守值，真实上限 ~16.7M；若库逻辑总高 ≤ 16.7M（约 ≤ 40 万项），提 `SAFE_MAX` 到 ~16M 即纯原生滚动、不进平移。

**❌ 对本品无效**：这是面向市场的产品，上市后必然遇到 **> 100 万项**（逻辑高度 40M+ px）的用户库——远超任何元素高度上限。「我的/中小库够小」不能作为产品决策依据。故提高 SAFE_MAX 只是把触顶阈值推高一点、治标不治本，**不采纳**。平移模式必须对任意大库都顺滑 → 只有方案 B 这条路。
