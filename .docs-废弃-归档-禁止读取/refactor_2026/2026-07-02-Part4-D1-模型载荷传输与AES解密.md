# Part4 worker 化 · D1:模型载荷传输与 AES 解密(§8.2.1 落定稿)

> 状态:定稿(2026-07-02,无人值守波;worker 化全线启动为当日用户拍板)。
> 上游:Part4 §8.2.1 / §3.7.2 / §3.7.3 / §3.7.3a、Part6 §8(决策2 canonical)。
> 本稿为施工级细化,与正文冲突处以本稿为准(已在 Part4 §8.2 挂指针)。

## 1. 问题与目标

worker 是 `Command::spawn` 出的独立 exec 进程(worker.rs:93-100,三管道、无句柄继承),
要把模型权重交给 worker 构建 ort Session,存在三个约束:

1. **帧上限**:协议单帧 blob ≤ 64 MiB(exotic-protocol frame.rs:33 `MAX_BLOB_LEN`),
   ViT-L 1.7GB 不可能走帧;
2. **AES 边界**:加密权重的解密密钥派生自 license(`enc_seed`,pro crate),worker
   是开源二进制**不得链接 pro** → 解密主体必须是主进程,且明文**不落盘、不经帧**;
3. **句柄失效**:匿名映射的 handle/fd 数值跨 exec 进程无效(§3.7.3 已证),必须用
   OS 级显式传递机制。

## 2. 关键裁决:两级载荷通道(本稿新增的结构性简化)

Part4 §11.4.3 已定 **AES 整体后置变现后**(④)。而 P2 首期 worker 化搬运的
CLIP/YuNet/SFace 权重全是**明文 onnx,本就躺在 models 目录磁盘上**——为它们支付
具名共享内存的复杂度是纯浪费。因此定稿**两级通道,协议一次定型**:

| 级别 | 适用 | 机制 | 何时 |
|---|---|---|---|
| **Level A `ModelHandle::Path`** | 明文权重(P2 首期全部模型) | `SessionInit` 传模型**文件绝对路径**,worker 直接 `Session::builder().commit_from_file(path)` | worker 化首期即用 |
| **Level B `ModelHandle::Named`** | AES 加密权重(④ 变现后) | 主进程解密 → 具名共享内存 → 传 name → worker map 后 `commit_from_memory` | 随首个加密权重插件 |

协议类型**现在就定型**(避免二次破坏性升版):

```rust
// exotic-protocol(新增,serde tag 区分):
#[derive(Serialize, Deserialize)]
#[serde(tag = "kind", content = "value", rename_all = "snake_case")]
pub enum ModelHandle {
    /// 明文权重:models 目录内文件的绝对路径。worker 侧必须校验路径前缀在
    /// 声明的 models 根之下(防宿主被劫持后诱导 worker 读任意文件)。
    Path(String),
    /// 加密权重:具名共享内存对象名(见 §4)。
    Named(String),
    // 保留位:Fd(i32) / Win32Handle(u64) 刻意不进 v1——具名方案跨三平台已闭合,
    // 裸句柄继承复杂且平台分叉,除非实测具名方案有不可接受开销才启用。
}
```

> 裁决记录:①「首期直接传路径」是对 §8.2.1 的补充简化(正文只写了 shm 通道),
> 依据 = AES 后置已是既定裁决,明文模型无保密需求;②Fd/Win32Handle 不进 v1。

## 3. Level A:路径通道(P2 首期施工面)

- `SessionInitBody`(见 D3 §3)携带 `model_handle: ModelHandle` + `model_len: u64` +
  `model_sha256: String`。worker 加载前校验长度与 sha256(复用 utils::hash 同款
  流式 sha256 逻辑,worker 侧独立实现,协议 crate 不引 sha2——worker 各自依赖)。
- worker 校验路径归属:`SessionInitBody.models_root` 声明根目录,`Path` 必须
  canonicalize 后以之为前缀,否则回 `ModelLoadFailed`(见 D3 错误码)。
- 失败语义:文件缺失/校验不符/ort 构建失败 → `Failure{ModelLoadFailed, terminal}`;
  host 收到后按 D3 §5 处置(不重试同一 handle,标记该模型待重下载校验)。

## 4. Level B:具名共享内存通道(④ 启动时施工,本稿先锁设计)

流程(§8.2.1 定稿细化):

1. 主进程(pro 渠道层)`ring::aead` 解密:密文格式 `nonce(12B)||ct||tag(16B)`,
   `key = HKDF(enc_seed, salt=ModelBlob.enc_salt(32B,随 Registry 签名), info=plugin_id||model_id)`
   (CANON-02,Part4 §8.4.4);
2. 创建具名共享内存并写入明文:
   - **Windows**:`CreateFileMappingW(INVALID_HANDLE_VALUE, &sa, PAGE_READWRITE, len, name)`,
     `SECURITY_ATTRIBUTES` 带 DACL:仅当前用户 SID(P1-7 硬化);
   - **Linux**:`shm_open(name, O_CREAT|O_EXCL|O_RDWR, 0600)` + `ftruncate` + `mmap`
     (O_EXCL 防同名抢占,已存在即重生成名);
   - **macOS**:同 `shm_open`(注意 mac 的 name ≤ PSHMNAMLEN≈31 字节 → 名称方案见下);
3. `name = pn-{8B hex(session_id)}-{16B CSPRNG hex}`(P1-7 要求高熵不可猜;
   相对 §3.7.3a 原式收短以适配 mac 31 字节上限——裁决记录:牺牲 plugin_id 可读性
   保跨平台统一,plugin 归属经 SessionInit 上下文可知,不需编码进名称);
4. `SessionInit` 传 `ModelHandle::Named(name)` + len + **明文 sha256**;
5. worker `shm_open(name, O_RDONLY)` / `OpenFileMappingW` → map → 校验 sha256 →
   `commit_from_memory`(ort rc.12 已支持,§8.6 决策2)→ 立即 unmap;
6. 主进程收到 `SessionReady` 后:unmap + `shm_unlink`/`CloseHandle` + 明文缓冲
   `zeroize`。worker 侧 Session 构建后不再持有映射。

生命周期护栏:
- 主进程崩溃遗留的具名对象:Windows 随句柄关闭自动回收;POSIX shm 会残留 →
  启动时清扫 `pn-*` 前缀属主对象(best-effort);
- `SessionInit` 超时(D3)时主进程同样执行 unlink/zeroize——**清理动作挂在 RAII
  guard 上**,任何早退路径不泄漏明文。

## 6. 验收

- Level A:worker 以 Path handle 成功加载 ViT-B/16 与 YuNet/SFace;路径越界/校验
  失败回 ModelLoadFailed 且 host 不崩;
- Level B(④ 时):ViT-L 1.7GB 经具名 shm 加载成功;全程 procmon/strace 证实明文
  不落盘;进程双侧退出后系统无残留具名对象;非属主进程 `shm_open` 被拒(0600/DACL)。

## 7. 开放点

- mac `shm_open` 大小上限与 1.7GB 映射的实测(留 T9.5/T20 原型阶段顺带验证);
- `zeroize` 对被 OS 换页过的明文页无能为力——已知边界,与「本地已授权用户」威胁
  模型一致,不追加 mlock(体量 1.7GB 不宜锁页)。
