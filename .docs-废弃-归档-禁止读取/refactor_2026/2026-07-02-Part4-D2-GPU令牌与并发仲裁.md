# Part4 worker 化 · D2:GPU 令牌与并发仲裁(§8.2.2 落定稿)

> 状态:定稿(2026-07-02);**T11 已按本稿落地(2026-07-03)**:`exotic/limiter.rs` 的 `GpuToken/GpuPermit`(复用 BackgroundHeavyLimiter 骨架的独立类型)+ `AppState.gpu_token` 共享实例 + §4 单测①②(FIFO/RAII 含 panic 路径)③(顺序天条以类型文档+注释锁定);acquire 接线留 T13/T15。上游:Part4 §8.2.2 / §3.6、Part6 G2 接缝。
> 🔴 本稿**修正** §8.2.2 的「跨进程令牌走协议帧」方案——依据实测代码结构,
> 令牌完全留在主进程即可,协议零扩展。已在 Part4 §8.2 挂修正指针(正文回写红线)。

## 1. 现状锚点(实测,2026-07-02)

- **GpuLimiter 在代码中不存在**——只在规划文档里;现有 GPU 协调是
  `state.rs:164` `gpu_analysis_owner` 互斥(GPU_OWNER_AI / GPU_OWNER_FACE,
  CLIP↔face 进程内互斥);
- CPU 侧已有 `BackgroundHeavyLimiter`(FIFO 公平、取消感知,derivation 与 exotic
  共享,预算 `available_parallelism().max(2)`,pipeline.rs:448 acquire);
- **Supervisor 严格串行**:一 Supervisor 同时只有一个在途请求,response 的
  request_id 必须匹配(worker.rs:283-289)——worker **没有**主动向 host 发请求的
  通道语义(现协议方向恒为 host→worker 请求)。

## 2. 为什么帧方案是过度设计(修正依据)

§8.2.2 原案:新帧 `GpuTokenRequest/Granted/Release`,worker 在推理前向 host 要
令牌。但成立条件是「worker 自主决定何时跑 GPU」——而本架构中**批的派发权在
host**(pipeline worker_loop 把 EmbedBatch 发给 worker,worker 被动执行,与现
psd thumbnail 同模型)。既然 host 知道每一批的开始与结束:

- **host 在发 EmbedBatch 前 acquire GPU 令牌,收到 Success/Failure/超时/进程死
  后 release**——令牌生命周期与「在途请求」精确重合,Supervisor 串行模型天然
  保证一 worker 一在途批;
- worker→host 反向请求帧会破坏「响应 request_id 严格匹配」的现有协议状态机,
  为不需要的自由度支付协议复杂度。

结论:**GPU 令牌是主进程侧的调度约束,不是协议问题**。

## 3. 定稿设计

### 3.1 GpuToken(主进程,新小模块 `exotic/gpu_token.rs` 或并入 limiter.rs)

```rust
/// GPU 推理令牌:全局额度 1(集显/单 GPU 语义)。与 BackgroundHeavyLimiter 同款
/// FIFO 公平 + 取消感知;RAII guard,Drop 即释放(批完成/超时/进程死都经 Drop)。
pub struct GpuToken { /* 同 BackgroundHeavyLimiter 骨架,额度固定 1 */ }
```

- **额度 1** 起步(§3.6 原案一致);T22(可选)按 VRAM 档位放行多 permit,不在本稿;
- acquire 点:pipeline worker_loop 在 send 推理批**之前**(与既有
  `deps.limiter.acquire`(CPU permit)同处,先 CPU 后 GPU,两把都拿到才发批;
  顺序固定防死锁);
- release 点:RAII——`TaskOutcome` 返回即 Drop;进程崩溃路径经 kill_and_reap
  返回同样走 Drop。**无泄漏面**。

### 3.2 与 gpu_analysis_owner 的统一(关键接缝)

现 `gpu_analysis_owner` 管「进程内 CLIP↔face 互斥」。worker 化后推理移出主进程,
但 owner 语义仍在(哪条流水线占有 GPU 分析槽)。定稿:

- **owner 互斥保留在命令层**(start/pause 语义,用户可见的「谁在分析」);
- **GpuToken 管物理并发**(哪个 worker 此刻真的在打 GPU);
- 两层不合并:owner 是粗粒度会话语义(分钟级),token 是批粒度(秒级)。
  合并会让「暂停人脸让 CLIP 跑」这类语义纠缠进批调度。

### 3.3 合并 vs 分离(T9.5 拍板)下的形态

| 形态 | GpuToken 的角色 |
|---|---|
| **合并单 ai-worker**(§3.11 倾向) | 一个 worker 池(池宽 1)串行处理 CLIP/face 批 → token 几乎恒空闲即得,退化为保险丝(防未来第二 GPU 消费者);实现不变 |
| 分离 ai-worker + face-worker | 两池各自 acquire 同一 GpuToken → 真跨 worker 仲裁生效;实现同样不变 |

**两形态代码路径完全一致**——这是把令牌放 host 侧的第二收益:T9.5 的拍板不
影响本模块,消除了 §8.2.2 原案「合并则退化简化」的形态分叉。

## 4. 任务映射与验收

- T11(GpuLimiter)→ 本稿 GpuToken:host 侧新模块 + pipeline 双 acquire;
  **协议/worker 零改动**;
