# 发现与决策:资源去重方向分析

## 需求
- 用户希望分析现有代码，判断资源管理器去重功能的设计方向。
- 本轮先看简要报告，暂不进入具体表结构、算法参数、交互流程等详细设计。

## 发现
- 项目为 Windows / macOS / iOS / Android 的高性能资产管理器，需优先关注跨平台路径语义、扫描吞吐与 GPU/派生管线边界。
- 现有工作区包含未提交改动；本轮约束为只读分析，不覆盖或整理这些改动。
- `media_items` 目前以 `(directory_id, file_name)` 表达路径项身份；`content_hash` 可空且有索引，但不代表所有资源都已有可用于去重的完整内容身份（`media_upsert` 新行不写 hash，常规未变更行也不触发 hash）。
- 当前 `content_hash` 链路服务于增量扫描的可疑变更确认：小文件全文 SHA-256，大文件为头/中/尾抽样指纹；现有文档明确保留了大文件抽样可能漏检的边界，因此不能直接把它当作精确去重证明。
- `fast_scan` 是轻量热路径，完整内容哈希刻意不放入常规扫描；但项目已有 blocking、批次、取消、进度/事件等后台任务模式，可作为独立去重分析任务的运行基础。
- 现有画廊 `LayoutItem`/`ViewScope`/选择描述符围绕“一个媒体行一个卡片”建立；去重组是聚合结果，首版不宜硬塞进默认布局契约。更合适的是独立的重复组结果面，最终把选中的成员解析为既有 `media_items.id`，复用选择、回收站和撤销能力。
- `availability` 与 `is_deleted` 是正交状态，且 Live Photo 伴随项通过 `companion_of` 关联；去重结果必须把离线/缺失、回收站和伴随项视为清理前的约束，而不是简单按 hash 删除。
- `cache_key` 是路径/文件名/mtime 派生的缩略图键，`thumbhash` 是视觉占位近似，`content_identifier` 是 Live Photo/HEIC 配对标识；三者都不应直接充当精确重复键。
