## 3. 瓶颈逐项核验

### B1 批内逐文件 SQL —— 成立（机制修正：prepare_cached 已消除编译成本）

**现状证据**：
- 快扫每文件：① 存在性 SELECT（`media_upsert.rs:266-287`，`prepare_cached`）；② upsert——新项 `INSERT`（`:348-368`）/ SourceChanged 走 `apply_source_changed`（`:123`，UPDATE + `DELETE FROM dedup_index` + invalidate_derived）/ SuspectChanged 与 Unchanged **零写**；③ seen 逐条 INSERT（`fast_scan.rs:837` → `mark_missing.rs:92` `SeenWriter::insert`，`prepare_cached` + 单行 execute）。
- enrichment 每项：① 复查 SELECT（`enricher.rs:81-109` `enrichment_source_is_current`，**裸 `query_row`，无缓存**）；② 条件写 2–3 条（`update_media_dimensions`/`upsert_image_meta`/`update_sort_datetime`，走 `db/queries/metadata.rs:59/97/107` 的 `prepare_cached`）。视频段 2 条、音频段 1–2 条。均在批内单事务。
- **无任何多行 VALUES / execute_batch 批量写**（`execute_batch` 仅用于 TEMP 表建/清/删）。

**修正**：快照「全部逐条 prepare+execute」应精确为——热路径语句均经 `prepare_cached` 连接级缓存（`media_upsert.rs:263-264` 注释自证其设计意图），唯 enrichment 复查 SELECT 是裸 `query_row`。因此 **B1 的真实成本 = 逐条 execute 的往返次数**（每文件约 2–3 次语句切换 + 参数绑定 + 行回取），而非 SQL 编译。Unchanged 主导的增量扫描下每文件约 2 次 execute（SELECT + seen INSERT）。

**方向复核**：快照建议仍有效且收益点更聚焦——批量预查存在性（`(directory_id,file_name) IN` 一次取回整批）、seen 改多行 VALUES/execute_batch、复查 SELECT 批量化。注意：Unchanged 零写语义、SuspectChanged 批外定指纹语义、CAS 类守卫列必须原样保留；批量预查返回的行需与批内项对齐。

### B2 walkdir 串行遍历 —— 成立

**现状证据**：`walker.rs:112-127` `WalkDir::new(root).follow_links(false).into_iter().filter_entry(...)`，全文件无 jwalk/rayon/并行分块；流式 `next()` 单项产出（内存 O(batch)，doc `:84-86` 自证）；每步取消检查 `:164-167`；剪枝回调 `:194-200`（跳过剪枝目录直接文件 `:205-211`）。

**影响预判**：目录遍历与文件 stat 完全串行，冷 HDD/网络盘上每次 stat 数毫秒 → 万级库秒级、十万级库分钟级，且此段在快扫批事务之外独占扫描墙钟。热 NVMe 本地盘上 stat 便宜，收益主要来自元数据批量。

**方向复核**：jwalk 是新依赖（提示词1 硬约束：引入需先给成本评估），自研按目录分块需保持四条不变量：流式批处理（内存 O(batch)）、取消响应、quick 剪枝语义（目录级跳过需在分块调度器实现）、批次顺序无关性（现有落库按批无序假设需验证）。建议阶段 2 先实测遍历/落库时间占比再决定是否值得动。

### B3 QuickDirPruner 持锁+逐条 INSERT —— 成立（锁粒度精确化）

**现状证据**：`fast_scan.rs:299-305` `QuickDirPruner` 持 `&Mutex<Connection>`；`should_prune_dir` **每次目录判定取锁一次**（`:316`），`decisions: RefCell<HashMap>` 缓存避免同目录重复取锁（`:309-311,337-339`）；锁内工作 = 目录 id 查询 + mtime 比对（mtime 在锁外已读 `:314`）+ 命中时未删媒体 id 查询（`:287-289`）+ **seen 回填逐条循环**（`:290-292` → `:325` SeenWriter::insert）。

**修正与补充**：锁粒度是「单目录判定」而非整批；但命中目录的 N 条 seen INSERT 是锁内逐条 execute，且该路径**不在批事务内**（直连 autocommit 写 TEMP 表）——与批内 `:837` 的 seen 写入是两条独立路径。大目录（数千媒体）命中剪枝时单次持锁内做数千条 INSERT，与其它根扫描写互斥加剧。

**方向复核**：命中目录的 seen 回填改锁内一次多行 VALUES（或锁外收集、批事务内补写，需保证剪枝判定先于文件遍历的时序语义）。低风险。

### B4 快照逐 id SELECT —— 成立

**现状证据**：`enricher.rs:45-79` `load_enrichment_source_snapshots`——语句 prepare 一次（`:49-52`），`:54-77` 循环逐 id `query_row` 执行 `SELECT ... WHERE id=?1`；图片/视频/音频每批各调用一次（`:587-590/:972-973/:1130-1131`），即每批 500/1000 次单行 SELECT。

**方向复核**：`WHERE id IN (...)` 一次取回整批，改动局部、无语义风险，是标准低风险先行项。

### B5 每批 3 次全局闸门往返 —— 部分成立（成本显著低于快照描述）

**现状证据**（每批结束顺序 bump → send → status）：
- `bump_data_version`（`state.rs:756-758`）= `data_version.fetch_add(1, Release)`，**纯内存原子，不拿 db_writer、不写 DB**；仅经外层 `with_scan_generation_action` 间接取 `scan_lifecycle_gate` 读锁。
- channel send（`fast_scan.rs:948-959`）同走闸门读锁，不写 DB。
- `update_scan_root_status`（`fast_scan.rs:962-973` → `db/queries/scan/roots.rs:199-210`）：**无条件 UPDATE scan_roots 四列，每批真实写 DB，无跳过条件**；经闸门 + db_writer。

**修正**：快照「每次都过闸门锁+db_writer」不成立——每批 4 次闸门读锁（3 事件 + 批事务）、仅 2 次 db_writer（批事务 + status 写）。`RwLock<()>` 读锁与原子加成本可忽略。**B5 的实际成本 ≈ update_scan_root_status 每批一次无条件 UPDATE**。

**重要事实（降低改动的语义风险）**：前端无任何组件直接读 `scan_roots.scan_status/scan_progress` 列——状态栏展示走内存 `progressMap → aggregateProgress → ScanProgressIndicator.vue`；DB 列是持久化冗余（启动恢复/崩溃后状态可能依赖，降频时须保留 completed/cancelled 等终态写入与启动重置逻辑不受影响——阶段 2 需确认启动恢复是否读此列）。

**方向复核**：status 写按批距（如每 10 批）或时间间隔（如 500ms）降频，终态必写；bump/send 不值得动。

### B6 pair_live_photos 全量装载 —— 部分成立（调用时机修正，锁持有确认）

**现状证据**：`live_photo.rs:55-269` `pair_live_photos(conn, root_id)`——候选 SELECT（`:66-96`）无 LIMIT、无时间/路径谓词，仅 `root_id + is_deleted=0 + file_format IN ('jpg','jpeg','heic','heif','mov','mp4')`，整根候选**全 collect 进内存** `Vec<PairingRecord>`；第二段 current_relations 对账查询（`:101-119`）同样全量；配对/对账判定是 Rust 侧 HashMap 分组（`:123-187`），SQL 只管装载与 UPDATE 写回；持 db_writer（调用点 `enricher.rs:854-856` `with_scan_db_write`）+ 短事务。

**修正**：调用时机是**每轮 enrichment 的图片段收尾之后、视频/音频段之前**（`enricher.rs:852-861`，非整个 enrichment 最终收尾）——此处有语义依赖：mp4 配对守门依赖图片段已置位的 `has_embedded_video`。优化不能简单挪到最终收尾或提前。

**影响预判**：百万级库单根数十万候选行 × 两次全量装载 + 全量 HashMap，且全程持全局写锁（阻塞其它根扫描与所有写路径）；每轮 enrichment（可能多次增量触发）都重做。

**方向复核**：谓词裁剪是最直接方向——候选可限制为「文件名 stem 可配对」的行（SQL 层 stem 归一化代价高，可在 SQL 侧先按扩展名+根裁剪、内存分组后只留疑似对）；或按目录分片处理缩短单次持锁窗口。**先实测候选集量级与单次耗时再定**；注意与缩略图/AI 写路径的 db_writer 争用是跨线协议，改动只在缩短持锁窗口，不动单写连接协议。

### B7 fallback 批选无 keyset 谓词 —— 成立

**现状证据**：`enricher.rs:594-601` 触发逻辑（主源空批且未走过 fallback → `image_fallback=true` 续一轮）；fallback SQL `image_batch_sql(keyset=false)` 分支 `:1343-1353` 无 `(sort_datetime,id)` 游标谓词；keyset 分支 `:1325-1341` 才有；keyset 适用判据 `:1307-1309`（folder 轴/filename 组内序不可 keyset 时走队列表 `:569-586`）。EXPLAIN QUERY PLAN 回归测试存在：`keyset_applies_only_to_datetime_axes`（`:1489-1519`，断言走 `idx_media_type_sort` 且无 TEMP B-TREE）——**行号修正：`:1503-1518`，非快照的 :1388+**。

**影响预判**：每轮 enrichment 每根至多一次 fallback 全扫（有标志防重复）；但扫描与 enrichment 并发是常态（fire-and-forget），新插入行序值落在游标之前时每轮都触发全量候选扫。

**方向复核**：fallback 结果集与 keyset 游标做并集去重、或记录已 fallback 覆盖的 min(sort_datetime) 水位。低-中风险，注意不破坏「接住并发插入」的设计意图（`:594-601` 注释）。

### B8 TIFF 超时 detached 线程泄漏 —— 成立

**现状证据**：`metadata.rs:15` `TIFF_DIMENSION_TIMEOUT=5s`；`:25-38` `run_with_timeout` = `thread::spawn` + `rx.recv_timeout(timeout)`，超时后 detached 线程继续跑完（`:20-24` 注释自认「最坏情况泄漏一个线程」并解释为何不用 `thread::scope`——drop 需 join 阻塞调用方）；仅 `tif/tiff` 分支进入守卫（`:96-104`），其它格式直接 `image::image_dimensions` 无守卫。

**影响预判**：仅畸形 TIFF 批量出现时累积线程；正常库影响可忽略。

**方向复核**：信号量/计数上限（同时在飞 TIFF 超时线程 ≤ N）或带上限的专用线程池。低优先级；注意守卫的取消语义（扫描取消后守卫线程无关联取消）。

## 4. 与快照声明不符的差异清单（执行提示词1 前须知的修正）
