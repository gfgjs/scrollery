# 发现与决策:大图加载后重复闪烁排查

## 需求

- 用户报告：大图加载完成、已经显示后仍会再闪一次；先确认旧代码是否已有对应修复。

## 发现

- 已提交历史有三条相关修复：`10df855` 将未知候选限制在离屏 `load + decode()` 成功后才提交可见层；`7a51632` 让跨条目切换立即撤下语义错误的旧帧；`2940600` 删除查看器根入场动画并预取查看器 chunk。三者仍在当前代码中。
- 当前 `useViewerImageSource` 仍用 `new Image()` 完成候选 `load + decode()`，随后只把 URL 写入 `displaySrc`；`ContentViewer` 因 `v-else-if` 移除缩略图/加载 DOM，再新建可见 `<img>`。离屏元素和可见元素不是同一个 DOM 图层，因此大图可能在可见层发生第二次解码、栅格或 GPU 纹理提交。
- 2026-08-18 备份的旧未提交补丁含有精确对应的修复：`useViewerImageSource` 改为 front/back 两个真实 DOM `<img>`，候选在不可见层收到 `load + decode + 两帧 rAF` 后才交叉交接，并在 `transitionend` 后释放旧层。`ContentViewer` 也改为两层绝对叠放，而不是 placeholder 与完整图的 `v-else-if` 替换。
- 该双层实现从未进入 Git 提交，也没有真实 Windows WebView2 验收；它与后来已回退的 gallery-ready/关闭交接状态机共存，不能整体恢复，只能作为独立设计证据。
- 默认 `viewerColorTarget` 为 `srgb`，此时不发色域 IPC。若用户改为 Display P3/DCI-P3/自定义 ICC，`useViewerColorSource` 会在原图已显示后异步取得派生 URL；当前状态机将同条目原图替换为派生图，形成第二个独立的可见换源窗口。
- 当前测试验证 URL、解码与旧响应代次，但不验证真实 DOM 首帧、栅格或 GPU 合成；因此不能证明“已显示后不再闪”。
- 用户已切为 sRGB 直显复测，问题仍在；ICC 原图→派生图换源被排除为本次共同根因。
- `ContentViewer` 的 `ResizeObserver` 对普通图片只更新缩放比例/人脸投影，不会重设 `transform`；只有已有 `viewRotation` 的图片在首个 `@load` 后会恢复旋转。故未旋转图片的通用二次闪动不应归因于缩放动画。
- 最小修复方向是只提取旧补丁中的“真实候选 DOM 层 + 前后两层交接”子集：候选先以 `opacity:0` 挂入 DOM，完成 `load/decode/两帧 rAF` 后才以短交叉淡入替换当前层；旧层仅在 `transitionend` 后释放，fallback 只处理已 ready 的旧层释放。这不延迟打开或关闭操作，不触及路由/画廊状态机，但需为两层资源、迟到事件、错误回退补独立测试。

- 已实施该最小子集：useViewerImageSource 不再创建离屏 Image，改由 front/back 两个真实候选层接收事件；跨条目保持立即撤旧帧，同条目换源在候选 ready 后才作 120ms 图层交接。220ms fallback 只处理交接结束事件丢失，绝不参与资源加载或用户操作等待。
- ContentViewer 的缩放和人脸投影改在新物理图层成为 displaySrc 后的 Vue nextTick 更新，避免候选升层后依赖不会再次发生的可见 img load。
- 新回归测试覆盖真实候选层的 load/decode/两帧握手、跨条目迟到事件、同条目交接、transitionend 丢失、decode 失败、ICC 回退、不可用条目和迟到可见错误。仍不能从 Node 单测证明 WebView2 GPU 合成观感，须真机验收。
- 用户在 sRGB 直显下验收双层实现后仍观察到大图显示后的闪烁，故“离屏图丢弃后重建可见 img”不是充分根因。sRGB 分支本已跳过色域 IPC，并将原始绝对路径转换为 Tauri asset URL 供查看器加载；不存在缩略图或色域派生文件充当大图源。
- 当前仍保留一次应用级呈现切换：新条目先显示缓存缩略图或中性加载态，源文件 img 在透明候选层完成 load/decode/两帧后，再与加载层同批提交为可见。
- 用户已确认下一轮 A/B。sRGB 现改为单一可见 img 直接绑定原始 asset URL，并且禁用 useViewerImageSource 的候选加载；不显示缩略图占位、不做 opacity、decode/rAF 或双层交接。非 sRGB 仍保留双层路径。该对照若仍闪，即可排除应用级图层呈现链。

## 反证与最终结论

- 用户在 sRGB 单图原文件直显 A/B 下复测，反馈“不闪了”。因此本次根因是应用层从缩略图加载态到候选完整图的呈现切换，而不是原文件、ICC 派生、路由或双图层 DOM 是否复用。
- 双层候选实现已完整撤回，不留给未验收的非 sRGB 路径；非 sRGB 回到原有预解码状态机。最终代码只在 sRGB 禁用该状态机并直接呈现原始 asset URL。
- 自动验证在收敛后重跑通过：typecheck、lint、生产 build、全量 135 测试文件和 1544 测试项。
- F-001 与 F-002 被本轮真机反证，不应提升为工程准则；F-003 是本次最终代码与真机验证结论。

## 续项:直显首帧黑屏

- 用户确认 sRGB 直显已消除重复闪烁，但原图尚未首帧呈现时会出现极短黑底。
- 缓存缩略图只在 `thumb_status=1` 时可用，且其尺寸上限为 1024 px；它可以作为原图到达前的低成本临时占位，不能替代原图显示。
- 真机截图反证了“稳定底层”的做法：通用加载预览 CSS 的 `width/height:100%` 把缩略图放大到整个视图区，而小于视图区的原图按自然尺寸居中，缩略图因而在四周长期露出。
- 修正为短生命周期占位：sRGB 原图 `<img>` 始终挂载且不换 source；缩略图按媒体元数据的原始宽高居中，仅在该原图的 `load` 事件尚未完成时显示。以完成的 `id:url` key 判定，旧图的迟到事件不能撤掉新图的占位；原图成功加载后只移除底层缩略图，不做 opacity、decode/rAF 或原图 DOM 交接。
- 用户复测证明上一条“load 后移除占位”仍会恢复已显示后的闪烁。结合 `0f4ed1c` 的真机对照，根因收窄为：原图首帧后哪怕只改变其下方缩略图节点，也足以让 WebView2 再提交一次可见图层。
- 当前修正不在原图 `load` 后改变模板：缓存缩略图若在原图首帧前到达，则按原图显示框静态留在下方；若缓存目录/缩略图到得更晚，则直接放弃本次补位，保留极短黑底。首帧后的完成标记只供 watcher 拒绝迟到缩略图，不参与模板渲染。
